# 레거시 애플리케이션 메뉴 및 기능 포팅 작업지시서

## 0. 문서 목적

- 이 문서는 레거시 LabelManager 네이티브 창의 `파일`, `검색`, `설정` 메뉴를 현 Flutter 프로젝트의 상단 AppBar에 그룹별 아이콘 메뉴로 포팅하기 위한 구현 계약이다.
- 인접한 `도움말` 메뉴는 이번 AppBar 포팅 범위에서 제외하며, 확인된 항목은 후속 범위 참고용으로만 기록한다.
- 현재 동작하는 기능은 기존 owning 화면과 command를 재사용해 연결한다.
- 현 프로젝트에 없는 기능은 레거시 화면, model, DAO와 실제 DB 스키마를 확인한 뒤 공용 차단형 dialog, model, DAO를 구현한다.
- 메뉴 항목만 먼저 만들고 눌렀을 때 `준비 중`, 빈 화면, 임의 안내만 표시하는 상태를 완료로 간주하지 않는다.
- 한 기능을 완료할 때는 메뉴 노출, 권한, 실제 command, 데이터 조회/저장, 오류 전달, 회귀 테스트까지 함께 끝낸다.

## 1. 최우선 구현 원칙

### 1.1 범위와 원인 중심 구현

- 레거시 동작과 현재 프로젝트의 실제 코드 경로를 기준으로 구현한다.
- 과도한 보완, 추측성 fallback, 자동 재시도, 임의 데이터 보정, 레거시에 없는 업무 규칙을 추가하지 않는다.
- 단순 null 방어를 여러 계층에 중복 추가하지 말고, 상태와 command를 소유한 계층에서 원인을 해결한다.
- 메뉴 UI에 업무 로직이나 SQL을 넣지 않는다. 메뉴는 권한/상태 표시와 command 전달만 담당한다.
- 로그 함수에 권한 판단, 저장, 상태 변경, 재시도 같은 비즈니스 로직을 넣지 않는다.
- 이미 탭이나 화면에 있는 기능을 AppBar용으로 다시 구현하지 않는다. owning controller 또는 명시적 command API를 통해 같은 기능을 호출한다.
- 이 포팅으로 추가하는 관리 목록과 조회 결과의 반복 행 테이블은 공용 `FortuneTable<T>`와 `FortuneTableColumn<T>`을 사용한다.
- AppBar 메뉴에서 새로 여는 관리·편집·조회 UI는 `BlockingModelessDialog`와 `BlockingModelessDialogFrame`을 사용한다. 별도 route page, 신규 메인 탭 또는 네이티브 창으로 만들지 않는다.

### 1.2 데이터베이스 절대 제약

- DB schema migration을 구현하거나 실행하지 않는다.
- 테이블 생성, 컬럼 추가/삭제/변경, index 생성/변경, compatibility level 변경을 금지한다.
- 레거시 코드 이름만 보고 테이블명이나 컬럼명을 추정해 SQL을 작성하지 않는다.
- 각 기능 구현 전 다음 순서로 기존 스키마를 확인한다.
  1. 레거시 DAO/model의 SELECT/INSERT/UPDATE/DELETE SQL 확인.
  2. 현 프로젝트의 model/DAO와 doc SQL 확인.
  3. 필요하면 읽기 전용 metadata 조회로 운영 스키마의 기존 테이블/컬럼 확인.
  4. 필요한 기존 스키마가 없으면 기능을 임의 스키마로 대체하지 말고 blocker로 기록한다.
- SQL Server 엔진은 2017이지만 DB `compatibility_level=100`을 SQL 문법 하한선으로 사용한다.
- `OPENJSON`, `JSON_VALUE`, `TRY_CONVERT`, `STRING_SPLIT`과 검증되지 않은 신문법을 사용하지 않는다.
- 구조화된 다중 행 payload가 필요하면 escaped XML과 `CONVERT(XML, ...)`, `.nodes()`, `.value()`, `.query()`, `.exist()`를 사용한다.
- SQL parameter 처리 시 `@@ROWCOUNT`, `@@TRANCOUNT` 같은 SQL Server system variable을 placeholder로 변환하지 않는다.

### 1.3 저장과 transaction 제약

- 읽기 전용 조회에는 불필요한 transaction을 추가하지 않는다.
- 서로 함께 성공해야 하는 다중 DML만 하나의 transaction batch로 묶는다.
- transaction은 다음 범위까지만 책임진다.
  - DML 실행.
  - commit 시도.
  - DML 또는 commit 오류를 원인 보존 상태로 호출자에게 전달.
  - 오류 시 `@@TRANCOUNT > 0`이면 가능한 rollback 수행.
- 여러 statement를 묶는 기본 경로는 기존 `DbClient.transaction(List<DbTransactionStatement>)`을 사용한다. DAO는 DML statement와 parameter, 결과 decoding만 소유하고 공용 driver가 담당하는 `BEGIN TRANSACTION`, `COMMIT TRANSACTION`, 가능한 rollback을 중복 작성하지 않는다.
- commit 오류를 성공으로 바꾸거나, 일부 성공을 정상 처리하거나, 자동 재시도하지 않는다.
- rollback 자체가 실패해도 원래 오류를 숨기지 않는다. 가능한 범위의 rollback을 시도한 뒤 원래 오류를 전달한다.
- 하나의 server-side SQL batch 안에서 rowcount 검증과 여러 DML을 함께 처리해야 할 때만 저장소의 기존 검증된 아래 pattern을 사용한다. 이 batch를 다시 `DbClient.transaction`의 중첩 transaction으로 감싸지 않는다.

```sql
SET XACT_ABORT ON;
SET NOCOUNT ON;
BEGIN TRY
  BEGIN TRANSACTION;

  -- 기존 스키마에 대한 필요한 DML만 수행

  COMMIT TRANSACTION;
  SELECT CAST(1 AS INT) AS RESULT;
END TRY
BEGIN CATCH
  IF @@TRANCOUNT > 0
    ROLLBACK TRANSACTION;
  THROW;
END CATCH
```

- 0건 변경을 성공으로 볼 수 없는 command는 각 DML 직후 `@@ROWCOUNT`를 저장해 명시적으로 검증한다.
- `SQL_NO_DATA(100)` rowcount noise가 가능한 batch는 `SET NOCOUNT ON`과 최종 명시적 `SELECT`를 사용한다.
- commit 전 DML/validation 단계의 확정 실패는 UI draft, 변경 전 snapshot, 임시 선택 상태를 유지하고 같은 저장을 다시 시도할 수 있게 한다.
- `DbCommitOutcomeUnknown`은 저장 실패나 성공으로 단정하지 않는다. 오류를 한 번 전달하고 같은 draft의 저장을 다시 실행하지 못하게 한 뒤 dialog를 닫는다. 사용자가 다시 열어 최신 데이터를 조회하게 하며 별도 읽기 전용 mode나 수동 재조회 command를 추가하지 않는다.
- commit 성공 후 목록/cache reload만 실패하면 저장된 결과를 UI의 committed 상태로 반영해 dirty를 해제하고 같은 draft의 재저장을 막는다. `저장은 완료됐지만 화면 갱신에 실패했습니다.`를 한 번 안내한 뒤 dialog를 닫고, 다시 열 때 최신 데이터를 조회한다. rollback, 자동 retry, 별도 수동 재조회 command를 추가하지 않는다.

### 1.4 model과 DAO 작성 기준

- 현 model/DAO에 같은 책임의 API가 있으면 재사용하거나 최소 확장한다.
- 기능 경계가 다르거나 기존 API를 억지로 확장해야 하면 해당 기능 전용 model/DAO를 작성한다.
- 하나의 거대한 `AppMenuDAO` 또는 모든 관리 기능을 처리하는 generic DAO를 만들지 않는다.
- model은 DB row의 의미와 UI draft를 분리한다.
- DAO는 SQL과 row mapping을 소유하고, dialog는 SQL 문자열을 소유하지 않는다.
- 삭제/순서 변경/복사처럼 여러 row를 저장하는 기능은 payload codec과 DAO transaction을 분리해 테스트한다.
- schema가 확인되지 않은 기능은 model/DAO 이름과 책임까지만 계획하고 SQL을 확정하지 않는다.

## 3. 목표 UI

### 3.1 AppBar 배치

넓은 데스크톱에서는 다음 순서를 사용한다.

```text
[애플리케이션명 + 버전]  [파일/관리] [조회/이력] [설정]  ...  [서버 상태] [로그인/로그아웃]
```

- 각 그룹은 텍스트가 들어간 둥근 버튼이 아니라 익숙한 아이콘 버튼을 사용한다.
- 모든 그룹 아이콘에 명확한 tooltip을 제공한다.
- 권장 아이콘:
  - 파일/관리: `Icons.menu`
  - 조회/이력: `Icons.manage_search`
  - 설정: `Icons.settings_outlined`
  - 좁은 화면 통합 메뉴: `Icons.more_vert`
- `파일/관리`는 비로그인·저권한 상태에서 종료만 남을 수 있으므로 관리자 전용으로 오인되는 아이콘을 사용하지 않는다.
- 팝업 내부에는 전체 한글 명령명을 기본으로 표시한다. command 아이콘은 의미를 즉시 구분하는 데 실제로 도움이 되는 경우에만 선택적으로 사용하고, 모든 항목에 일괄 적용하지 않는다.
- popup 표시명은 현재 앱의 command button처럼 간결한 한글 기본 `label`을 그대로 사용한다. dialog를 연다는 이유만으로 `...`를 붙이거나 별도 metadata를 추가하지 않는다.
- 실제 활성 전역 shortcut이 있는 command는 명령명 문자열에 `(F1)`처럼 합치지 않고 popup 오른쪽의 고정 보조 영역에 `F1`, `F12` 같은 `shortcutLabel`을 표시한다. `품목별 정보 편집`의 `F1`과 `검색출력모드`의 `F12`부터 적용하며, 아직 구현되지 않았거나 현재 화면에서 실행되지 않는 shortcut은 표시하지 않는다. semantics에는 기본 명령명과 shortcut을 함께 제공한다.
- separator는 레거시 메뉴의 command group 경계를 유지한다.
- 위험 command의 확인은 팝업 메뉴가 아니라 해당 화면의 저장/삭제 command 시점에 수행한다.

### 3.2 반응형 기준

- 화면 전체 폭만 하드코딩해 판단하지 말고 AppBar title과 actions에 실제 제공된 폭을 `LayoutBuilder`로 판단한다.
- 그룹 3개, 서버 상태, 로그인/로그아웃이 겹치지 않는 폭에서는 그룹 아이콘을 각각 표시한다.
- 폭이 부족하면 그룹 버튼을 먼저 `more_vert` 하나로 합친다.
- 통합 overflow의 첫 단계에는 현재 표시할 command가 있는 `파일/관리`, `조회/이력`, `설정` 그룹만 표시하고, 그룹을 선택하면 해당 command의 2단계 submenu 또는 panel을 연다. 전체 command를 하나의 긴 평면 목록으로 합치지 않는다.
- 그룹 submenu/panel은 화면의 사용 가능 높이로 clamp하고 필요한 경우 세로 scroll을 제공한다. 키보드 focus 항목이 viewport 밖으로 이동하면 자동으로 reveal한다.
- 서버 상태와 로그인/로그아웃은 항상 오른쪽 끝에 남긴다.
- 메뉴를 합친 뒤에도 폭이 부족하면 title은 `maxLines: 1`, `softWrap: false`, `TextOverflow.ellipsis`로 줄인다. 서버 상태와 현재 로그인/로그아웃 command를 title보다 먼저 숨기거나 줄이지 않는다.
- 좁은 작업 영역에서는 AppBar collapse와 title ellipsis로 주요 command에 접근할 수 있어야 하며 서버 상태와 로그인/로그아웃 command를 숨기지 않는다. native minimum이나 window lifecycle 변경은 이 메뉴 포팅 범위에 포함하지 않는다.
- 버튼 출현/소멸로 AppBar 높이나 body 위치가 바뀌지 않게 한다.
- Tab으로 그룹 아이콘에 focus하고 Enter 또는 Space로 메뉴를 연다. 메뉴 안에서는 위/아래 방향키로 항목을 이동하고 Enter로 실행한다. 통합 overflow에서는 오른쪽/Enter로 그룹에 진입하고 왼쪽/Esc로 한 단계 돌아가며, 첫 단계의 Esc는 메뉴를 닫는다.
- Esc 또는 바깥 클릭으로 메뉴만 닫으면 원래 그룹 아이콘에 focus를 복원한다. command가 top-level dialog를 열면 그룹 focus 복원을 보류하고 dialog의 초기 control로 focus를 넘긴다.
- AppBar menu, modal dialog, `BlockingModelessDialog`, `DbReconnectOverlay`처럼 배경 입력을 막는 surface가 하나라도 보이는 동안 Home의 전역 F1/F2/F3/F5/F12 command를 실행하지 않는다. 여러 차단 surface가 겹치면 마지막 surface가 닫힐 때까지 차단을 유지한다.
- `PreviewFloatingWindow`처럼 배경 작업을 허용하는 non-modal preview는 단축키 차단 surface로 간주하지 않는다. 차단 상태의 구현은 현재 route/overlay 구조에 맞는 가장 작은 방식으로 하며 특정 observer, identity set 또는 lease 자료구조를 필수로 하지 않는다.
- command를 선택하면 AppBar popup을 닫은 뒤 owning command를 정확히 한 번 실행한다. dialog가 열리면 첫 입력으로 focus를 넘기고, 메뉴만 취소하거나 command가 실행되지 않으면 가능한 경우 원래 menu trigger로 focus를 돌린다.
- 넓은 폭과 좁은 대표 폭, 긴 버전 문자열에서 AppBar와 핵심 command 접근성을 focused widget test로 확인한다.

### 3.3 권한 표시 방식

- 레거시 MainFrm의 비활성 표시를 그대로 복제하지 않고 현재 Flutter 앱의 권한 UX를 따른다.
- 현재 로그인 상태나 사용자 등급 policy에서 표시 대상이 아닌 command는 `visible=false`로 메뉴에서 숨긴다. 로그인/로그아웃 또는 사용자 변경 시 policy를 다시 계산한다.
- dirty, busy, 필수 선택 누락처럼 현재 상태를 해결하면 실행할 수 있는 command만 표시한 채 비활성화한다.
- 비활성 popup item은 명령명 아래 또는 오른쪽에 짧은 `disabledReason`을 직접 표시한다. hover에 의존하는 tooltip을 유일한 안내로 사용하지 않는다.
- `disabledReason`은 현재 품목관리 popup처럼 읽을 수 있는 길이로 직접 표시하며 필요한 경우 두 줄까지 허용한다. 실제 공간 때문에 문구를 줄일 때만 tooltip으로 전체 내용을 보조하고, 기본 text semantics로 정보가 전달되지 않는 custom renderer에만 별도 semantics label을 추가한다.
- `legacyInactive`와 `legacyUnreachable` command는 inventory와 숨김 policy만 유지한다. `legacyInactive`는 레거시가 명시적으로 비활성화한 command, `legacyUnreachable`은 메뉴 리소스에서 활성 handler까지 도달하는 경로가 확인되지 않은 command에 사용한다. 별도 활성화 요구나 실제 도달 경로가 확인될 때 기능 범위와 노출 policy를 함께 검토한다.
- 그룹 안에 표시할 command가 하나도 없으면 빈 그룹 아이콘도 숨긴다.
- 로그인/로그아웃 command는 inventory와 controller에 유지하되 `파일/관리` popup에는 렌더링하지 않는다. 현재 상태에 맞는 AppBar 오른쪽 고정 아이콘 하나만 표시한다.
- 종료 command는 AppBar 고정 아이콘으로 중복하지 않고 `파일/관리` popup에 유지한다.
- 비로그인 상태에서는 서버 상태, 로그인과 종료만 사용할 수 있다.
- 일반 사용자 UI의 기존 레거시 정책은 유지한다.
  - 공용라벨관리/자동품목갱신 탭은 숨김.
  - 품목관리 편집 command는 숨김.
  - 조회 가능한 command는 유지.
- `tester01` 테스트 override는 `lib/models/user.dart`의 `User.clientUserTestOverrideId`를 사용하며 메뉴 자체에 별도 예외를 만들지 않는다.

## 4. command 구조

### 4.1 신규 공용 타입

다음 책임을 가진 작은 타입을 추가한다. 파일명은 저장소 구조에 맞춰 조정할 수 있으나 책임은 섞지 않는다.

- `lib/models/app_menu_command.dart`
  - `AppMenuGroup`: file, search, settings.
  - `AppMenuCommandId`: Flutter에서 사용자가 실행하는 owning action별 안정 ID.
  - runtime command 값에는 포팅 추적만을 위한 legacy command ID를 넣지 않는다. 레거시 handler와 ID 대응 관계는 inventory test fixture에 보존한다.
  - command metadata는 기본 `label`, optional icon, optional `shortcutLabel`을 포함한다. shortcut 보조 영역은 이 metadata로 렌더링하며 command별 widget 문자열로 중복하지 않는다.
  - `AppMenuCommandState`: visible, enabled, disabledReason.
  - DB나 BuildContext를 참조하지 않는 순수 값 타입.
- `lib/core/app_menu_policy.dart`
  - 로그인 상태, `UserGrade`, 현재 작업 상태로 command 상태를 계산하는 순수 policy.
  - command 실행은 하지 않는다.
- 전역 단축키 차단 상태
  - 기존 controller 또는 작은 app-scope helper가 차단 surface의 활성 여부를 제공하고 Home의 전역 key handler가 command 분기 전에 확인함.
  - non-modal floating preview는 차단 상태에 포함하지 않음.
- `lib/widgets/app_menu_bar.dart`
  - 넓은/좁은 레이아웃과 popup 표시만 담당.
  - command 상태를 받아 렌더링하고 선택된 command ID를 콜백으로 전달.
- `lib/core/app_menu_controller.dart` 또는 동등한 controller
  - `HomePage` AppBar와 `HomePageManager` command 실행을 연결.
  - controller attach/detach는 기존 controller pattern을 따른다.
  - blocking surface 상태를 전역 handler에 제공한다.
  - AppBar popup을 닫은 뒤 owning command를 한 번 실행한다.
  - 화면별 private method를 복제하지 않는다.

### 4.2 상태 소유권

- `HomePage`가 소유할 command:
  - 로그인, 로그아웃, 종료.
  - 후속 도움말 구현 시 애플리케이션 정보와 외부 링크 실행.
- `HomePageManager`가 소유할 command:
  - 탭 이동.
  - 품목/공용라벨/자동갱신 관련 기능.
  - 라벨출력/저울출력 프린터 설정.
  - 저울 연결 설정.
  - 업무 DB를 사용하는 관리/조회 dialog의 실행과 refresh callback.
  - 기존 메인 탭의 로그아웃/종료 상태 제공. 현재 출력·연결·저장 `writeBusy`, 활성 셀/행 편집 `activeEditing`, 품목·자동갱신·공용라벨 `dirty`를 소유 상태에서 계산하고, dirty 작업의 짧은 표시명과 폐기 callback을 확인창 없이 반환하는 exit snapshot API로 노출한다.
- 신규 AppBar dialog를 여는 owning controller는 해당 dialog의 active와 close 상태, 실제로 존재하는 dirty, write-busy, active editing 상태만 소유한다. dirty이면 짧은 표시명과 폐기 callback을 exit snapshot으로 제공한다. 읽기 전용 dialog에 dirty나 write-busy 상태를 만들지 않는다. 같은 dialog의 open 요청이 처리 중이거나 이미 열려 있으면 중복 entry를 만들지 않는다. 서로 다른 dialog의 실행을 위한 전역 queue나 coordinator는 추가하지 않는다.
- 로그아웃·메뉴 종료·OS 종료의 공용 lifecycle guard는 요청 시점의 활성 dialog owner와 `HomePageManager` exit snapshot만 수집한다. 하나라도 write-busy 또는 active editing이면 dirty 확인창 없이 종료를 차단하고, 그 외에는 모든 dirty 표시명을 한 확인창에 합산한다. 사용자가 폐기를 승인한 경우에만 각 owner의 폐기 callback을 정확히 한 번 실행한다.
- 위 수집은 종료 요청에만 사용하는 작은 `LifecycleManager` 계약이며 dialog open/close, focus, command 실행을 조정하는 범용 coordinator로 확장하지 않는다.
- 기존 `showDialog`/`showGeneralDialog` owning command는 AppBar와 원래 화면의 호출 경로를 그대로 공유한다. 동일 dialog를 coordinator 소유 overlay로 바꾸거나 `BlockingModelessDialog`로 다시 감싸지 않는다.
- 각 dialog가 소유할 command:
  - 자기 화면의 편집 draft, 저장, 취소, 행 선택.
- AppBar는 `HomePageManager` private state를 직접 읽지 않는다. controller가 노출하는 command state snapshot 또는 `ValueListenable`을 사용한다.

### 4.3 편집 중 차단

- 메뉴 선택이 brand, label size, 탭, draft context를 바꾸는 경우 기존 `_block...ContextChange` 경로를 재사용한다.
- 읽기 전용 이력 조회까지 일괄 차단하지 않는다.
- 저장 command busy 중 DB를 다시 갱신하거나 같은 데이터를 수정하는 command만 비활성화한다.
- 로그인 상태/등급/`legacyInactive`/`legacyUnreachable`처럼 현재 policy에서 표시 대상이 아닌 command는 `visible=false`로 처리하고 disabled reason을 만들지 않는다.
- 편집 중, command busy, 필수 context 누락은 서로 다른 disabled reason으로 계산한다.
- disabled reason은 테스트 가능한 순수 policy 결과로 유지하고 popup item 안의 보조 문구로 직접 안내한다. tooltip은 전체 문구 보조에만 사용하고 별도 경고 dialog를 띄우지 않는다.

## 5. 레거시 메뉴 inventory와 포팅 계약

## 5.1 파일/관리 그룹

### 5.1.1 로그인 (`IDM_LOGIN`)

- 레거시: 로그아웃 상태에서만 활성. Flutter에서는 AppBar 오른쪽 고정 로그인 아이콘으로만 표시하고 `파일/관리` popup에는 표시하지 않는다.
- 현행 연결: `HomePage._showStartupDialog()` 또는 DB 연결이 없을 때 `_loginToServerDB()`.
- 새 로그인 화면을 만들지 않는다.
- command inventory와 AppBar 로그인 아이콘은 같은 method를 참조한다.
- 검증:
  - 비로그인 상태에는 AppBar 고정 로그인 아이콘만 표시하고 `파일/관리` popup에는 로그인/로그아웃 command를 렌더링하지 않음.
  - DB 연결 유무에 따른 기존 분기 유지.

### 5.1.2 로그아웃 (`IDM_LOGOUT`)

- 레거시: 로그인 상태에서만 활성. Flutter에서는 AppBar 오른쪽 고정 로그아웃 아이콘으로만 표시하고 `파일/관리` popup에는 표시하지 않는다.
- 현행 연결: `HomePage._onLogout(false)`.
- clean 상태에는 일반 로그아웃 확인창을 새로 추가하지 않고 바로 기존 로그아웃을 진행한다. 확인은 저장하지 않은 작업을 폐기할 때만 표시한다.
- `_doLogout()` 전에 공용 lifecycle guard로 활성 신규 dialog와 `HomePageManager`의 exit snapshot을 함께 확인한다. 라벨 발행, 저울 발행·연결, 품목·자동갱신 저장 같은 `writeBusy`는 로그아웃을 거부하고 해당 owner의 차단 사유를 한 번 안내한다. 품목·자동갱신·저울출력 또는 신규 dialog의 active editing은 자동 확정하거나 폐기하지 않고 먼저 편집 완료 또는 취소를 요구한다.
- 신규 dialog와 품목·자동갱신·공용라벨 중 하나 이상이 dirty면 영향받는 작업명을 한 번의 폐기 확인에 합산한다. 승인 시 각 owner의 폐기 callback을 한 번씩 실행하고, 화면별 확인창을 연속으로 띄우거나 일부 상태만 확인하고 나머지를 우회하지 않는다.
- 검증: 로그인 상태에는 AppBar 고정 로그아웃 아이콘만 표시한다. clean 로그아웃은 추가 확인 없이 진행되고, busy/activeEditing은 차단되며, dirty일 때만 폐기 확인 후 login log 저장과 상태 초기화가 기존 순서로 실행되는지 확인한다.

### 5.1.3 협력업체 관리 (`IDM_COOP_MANAGE`)

- 레거시 기준: `CMainFrame::OnCoopManage` → `CCooperatorManagerDlg`.
- 권한: 6.1의 `systemAdminCommand`.
- 구현 지시:
  - 기존 `Cooperator` model/조회 API를 먼저 확인한다.
  - 목록, 추가, 이름 수정, 삭제를 제공하는 `BlockingModelessDialog` 기반 관리 dialog를 구현한다.
  - 추가·수정은 별도 입력 dialog의 적용/취소 단위로 수행하고, 적용 성공 시 즉시 저장한 뒤 목록을 갱신한다. 목록 전체의 전역 저장/취소 footer는 두지 않는다.
  - 신규 CRUD가 필요하면 `CooperatorDAO`를 최소 확장한다.
  - 삭제 종속성은 레거시 DAO가 검사하는 기존 조건만 적용한다.
- DB gate: `BM_COOPERATOR` 실제 컬럼과 레거시 SQL을 확인하기 전 DML SQL을 작성하지 않는다.
- 저장 후 로그인 세션의 현재 협력업체가 영향을 받으면 필요한 cache만 명시적으로 reload한다.

### 5.1.4 거래처 관리 (`IDM_CUST_MANAGE`)

- 레거시 기준: `OnCustManage` → `CCustManagerDlg`.
- 권한: 6.1의 `adminCommand`.
- 협력업체 선택에 종속된 거래처 목록과 CRUD를 포팅한다.
- command 접근 권한과 selector 변경 권한을 구분한다. 협력업체 selector는 레거시와 같이 `IsSystemAdmin` 또는 `IsAdminConnect`일 때만 활성화하고, 그 외 허용 사용자는 현재 로그인 context의 협력업체를 표시하되 변경하지 못하게 한다.
- 선택 거래처 `Connect`를 포팅한다. 레거시와 같이 원래 관리자 계정을 한 번 보존하고 현재 관리자 종류에 맞는 `IsAdminConnect`/`IsCoopAdminConnect`를 설정한 뒤, 선택 거래처의 사용자·지점·거래처·협력업체 context로 전환하고 기존 관리자 접속 로그를 저장해 메인 화면을 다시 초기화한다.
- `Connect`에 사용할 지점과 사용자 선택은 레거시 `CCustManagerDlg::Connect` 범위를 그대로 따른다. 관리 사용자를 자동 생성하거나 다른 등급으로 대체하는 fallback, 임의 사용자 선택 UI를 추가하지 않는다.
- 기존 `Customer` model을 우선 사용하고 CRUD가 없을 때만 DAO API를 추가한다.
- `BM_CUSTOMER` 실제 schema와 레거시 DAO의 정렬/중복/삭제 조건을 그대로 따른다.
- 협력업체 관리와 하나의 generic CRUD dialog로 합치지 않는다. 공용 table shell 정도만 재사용한다.

### 5.1.5 지점 관리 (`IDM_MARKET_MANAGE`)

- 레거시 기준: `OnMarketManage` → `CMarketManagerDlg`.
- 권한: 6.1의 `managerCommand`.
- 현재 레거시 구현은 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나만 활성이고 `MANAGER_USER`는 제외하므로 이를 visibility policy test로 고정한다.
- command 접근 권한과 selector 변경 권한을 구분한다. 레거시 `CMarketManagerDlg::OnInitDialog`와 같이 `IsCoopAdmin`이면 협력업체 selector를 비활성화하며, 허용된 나머지 상태의 selector 동작도 해당 dialog 구현을 그대로 따른다.
- 기존 `Market` model/조회 API를 확장해 거래처별 지점 CRUD를 구현한다.
- 현재 로그인 지점 삭제/변경처럼 세션을 무효화할 수 있는 동작은 레거시 확인 없이 자동 로그아웃 같은 보완을 추가하지 않는다. 해당 동작이 레거시에 있으면 그대로 포팅한다.

### 5.1.6 사용자 관리 (`IDM_USER_MANAGE`)

- 레거시 기준: `OnUserManage` → `CUserManagerDlg`, `CUserManagerModel`.
- 권한: 지점 관리와 같은 6.1의 `managerCommand`.
- 현재 레거시 구현은 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나만 활성이고 `MANAGER_USER`는 제외하므로 이를 visibility policy test로 고정한다.
- 권한별 selector 활성 범위를 레거시 model에서 그대로 포팅한다.
  - 협력업체 selector: `IsSystemAdmin` 또는 `IsAdminConnect`.
  - 거래처 selector와 전체 표시: `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나.
  - 지점 selector: 위 조건 또는 `IsManager`. 다만 현재 command visibility에서는 `MANAGER_USER`를 숨기므로 도달하지 않는 상태를 별도 예외 UI로 만들지 않는다.
  - 생성·수정 가능한 사용자 등급은 `CLIENT_USER`와 `MANAGER_USER`뿐이며 신규 기본값은 `CLIENT_USER`다. `SYSTEM_ADMIN_USER`와 `COOP_ADMIN_USER` 생성 UI를 추가하지 않는다.
- 선택 사용자의 `Connect`를 포팅한다. 원래 관리자 계정을 한 번 보존하고 레거시 조건대로 `IsAdminConnect`/`IsCoopAdminConnect`를 설정한 뒤, 선택 사용자와 해당 지점·거래처·협력업체 context로 전환하고 기존 관리자 접속 로그를 저장해 메인 화면을 다시 초기화한다.
- 거래처·사용자 `Connect` 외에 일반적인 사용자 전환, 임의 권한 상승 또는 별도 impersonation 이력 UI로 확장하지 않는다.
- 기존 `User`/`UserDAO` 조회와 로그인 mapping을 재사용한다.
- 관리용 row/draft가 로그인 `User.instance`와 다른 책임이면 별도 `ManagedUser` model을 작성한다.
- 비밀번호 저장 형식은 레거시 DB 형식을 확인해 그대로 사용한다. 임의 hash migration을 수행하지 않는다.
- 현재 로그인 사용자의 권한이 변경돼도 자동 반영/강제 로그아웃을 추측으로 추가하지 않는다.

### 5.1.7 관리자 복사 (`IDM_ADMIN_COPY`)

- 레거시 기준: `OnAdminCopy`가 main window observer를 통해 복사 흐름을 시작한다. `AdminCopyDlg`, 관련 observer/model/DAO를 끝까지 추적한 뒤 구현한다.
- 권한: 6.1의 `adminCommand`.
- 레거시 UI와 같이 협력업체를 선택하고 복사 원본과 대상의 거래처·브랜드·라벨 크기를 명시적으로 선택한다. `브랜드 복사`, `품목까지 복사` 옵션도 레거시 동작에 맞게 제공한다.
- 별도 데이터 목록 preview나 일괄 확인 단계를 추가하지 않는다. 대상 라벨 크기에 기존 column 데이터가 있어 덮어쓰기·삭제가 발생하는 경우에만 레거시와 같은 데이터 손실 경고를 표시하고, 그 외에는 `복사` command에서 바로 실행한다.
- 레거시에서 복사하는 테이블만 복사한다. 편의를 위해 신규 테이블을 추가하지 않는다.
- 여러 테이블 복사는 하나의 transaction으로 처리한다.
- 일부 테이블 복사 성공을 전체 성공으로 표시하지 않는다.
- commit 전 DML/validation 단계의 확정 실패는 가능한 rollback 후 오류를 그대로 전달하고 선택 상태를 유지한다. `DbCommitOutcomeUnknown`이면 같은 복사를 다시 실행하지 못하게 하고 오류 안내 후 dialog를 닫는다. 다시 열 때 최신 데이터를 조회하며 별도 읽기 전용 mode를 추가하지 않는다.
- 대량 payload는 compatibility 100 XML projection을 사용한다.

### 5.1.8 종료 (`ID_APP_EXIT`)

- 현행 `PopScope`와 `LifecycleManager.notifyExitRequested()` 경로를 command API로 추출해 재사용한다.
- `SystemNavigator.pop()`을 메뉴에서 직접 중복 호출하지 않는다.
- 메뉴 종료와 OS 창 닫기는 같은 command에서 `활성 owner exit snapshot 수집 → write-busy/active editing 차단 → 전체 dirty 통합 확인과 승인된 폐기 callback 실행 → 열린 overlay 정리 → DB 정리 → 실제 종료` 순서로 처리한다.
- 활성 신규 dialog와 기존 메인 탭 중 하나라도 write-busy이면 종료를 거부한다. active editing은 자동 확정하거나 폐기하지 않고 종료를 중단해 먼저 편집 완료 또는 취소를 요구한다.
- 차단 상태가 없으면 신규 dialog와 품목·자동갱신·공용라벨의 dirty를 한 번의 폐기 확인에 합산한다. 취소하면 어떤 상태도 변경하지 않고, 승인하면 각 dirty owner의 폐기 callback을 정확히 한 번 실행한다.
- 모든 owner가 clean이면 일반 확인창을 추가하지 않는다. 메뉴 종료와 OS 창 닫기는 같은 차단 사유, 통합 폐기 확인, DB 정리 순서를 사용한다.

## 5.2 조회/이력 그룹

### 5.2.1 검색 및 치환 (`IDM_SEARCH_AND_REPLACE`)

- 레거시 `OnSearchAndReplace` → `CSearchAndReplaceDlg`, `CSearchAndReplaceModel` 범위를 포팅한다.
- 권한: 6.1의 `managerCommand`.
- FortuneSheet 내부 검색/치환 기능과 레거시 업무 데이터 검색/치환을 동일 기능으로 간주하지 않는다.
- 검색 종류는 `품명`과 `주원료`만 제공한다. 레거시에서 주석 처리된 `추가 주원료` 검색을 활성화하지 않는다.
- 검색 범위는 현재 거래처의 품목으로 제한하고 선택적으로 브랜드, 브랜드의 label size 순서로 좁힌다. `CItemDetailDAO`의 품명·주원료 부분 일치 조회 범위를 사용한다.
- 결과 column은 브랜드, label size, 품명, 주원료로 제한한다. 선택 품목의 개별 주원료 변경, 선택 행 일괄 치환, 변경된 품목 저장과 기존 품목편집/출력 이동 command를 포팅한다.
- 검색 결과 table에서 대상 행을 선택하고 일괄 치환한 변경값을 같은 table에 반영해 저장 전에 확인할 수 있게 한다. 레거시의 일괄 치환 확인과 최종 저장 확인을 유지하고 별도 preview dialog나 대상 건수 panel을 추가하지 않는다.
- 변경된 행의 저장은 하나의 transaction으로 처리한다.
- 조회는 기존 `CItemDetailDAO`, 저장은 변경된 품목에 대응하는 기존 `CItemDAO` 책임으로 제한한다.
- 전체 DB 문자열을 임의로 검색하거나 범위를 확장하지 않는다.
- 권한은 실제 `OnEnableManager` 구현과 동일하게 적용한다.

### 5.2.2 발행내역 보기 (`IDM_PRINT_LOG`)

- 레거시 기준: `OnPrintLog` → `CPrintLogDlg`, `CPrintLogModel`.
- 권한: 6.1의 `loggedIn`.
- 레거시 `CPrintLogDAO`와 현행 `label_print_persistence.dart`가 함께 사용하는 기존 `BM_RICH_PRINT_LOG`를 조회 source로 고정해 read model과 DAO를 작성한다. `BM_RICH_STATUS`와 `BM_RICH_STATUS_DATA`는 5.2.6 발행 통계 책임으로 유지한다.
- filter는 기간, 권한별 협력업체/거래처 범위와 검색 종류 `품명`·`사용자ID`·`거래처`로 제한한다. 품명은 부분 일치, 사용자 ID와 거래처는 완전 일치를 사용하며 다른 filter를 추가하지 않는다.
- 결과는 레거시의 거래처, 브랜드, label size, 품명, 발행 수량, 사용자 ID·이름·등급, 발행 시각, 프린터, 서식 크기와 margin/push 값을 표시한다.
- 총 누계, 기간 합계와 단일 거래처 결과의 label size별 합계를 포팅한다. 결과 행 상세는 `RICH_COLUMNS`, `RICH_PRINT_CELLS`, `RICH_SAVE_IN_DB_CELLS`의 레거시 저장값/출력값 비교 범위만 표시한다.
- 전체 조회 결과를 read-only `FortuneTable`로 표시하며 pagination UI나 별도 paging API를 추가하지 않는다.
- 조회 전용이므로 transaction을 추가하지 않는다.
- 라벨출력과 저울출력이 같은 persistence와 `BM_RICH_PRINT_LOG`에 출력 경로 구분값 없이 저장되므로 하나의 통합 목록으로 표시한다. 프린터명이나 다른 값으로 출력 경로를 추측해 분류하거나 구분 column을 추가하지 않는다.

### 5.2.3 사용자 접속 이력 보기 (`IDM_LOGIN_LOG`)

- 권한: 6.1의 `loggedIn`.
- `lib/page_login/login_history_page.dart`는 현재 사용처가 없는 demo route/page이며 `Scaffold`, `Card`, `DataTable`, 일반 `showDatePicker`를 사용하므로 직접 재사용하지 않는다.
- 해당 파일의 demo row와 page shell을 제거하고 AppBar owning command가 여는 `BlockingModelessDialogFrame`용 content widget으로 전환한다. 기존 `BM_LOGIN_LOG`를 조회하는 DAO API를 구현하고 결과는 read-only `FortuneTable`로 표시한다.
- `LoginLogDAO`를 조회까지 확장하거나 조회 책임이 다르면 `LoginHistoryDAO`를 작성한다.
- 조회 filter는 레거시 `CLoginLogDlg`와 같이 기간과 권한별 협력업체/거래처 범위만 포팅한다. 지점과 사용자는 filter로 추가하지 않는다.
- 사용자 ID·등급, 로그인 시각·상태·IP, 거래처와 프로그램 버전은 레거시 결과 column으로만 표시한다.
- 별도 route, `Scaffold`, `AppBar`, 장식용 `Card`, `DataTable`을 유지하지 않는다. 날짜 선택은 기존 `showBlockingModelessOverlayDialog` 경로로 현재 차단형 dialog 위에 표시하며, 같은 구성이 둘 이상에서 반복될 때만 공용 date picker helper로 추출한다.
- locale 표시 형식은 현 `DateFormat`을 사용하되 DB 저장 문자열 형식은 변경하지 않는다.

### 5.2.4 데이터내용 이력 조회 (`IDM_CONTENT_SAVE_LOG`)

- 사용자 ID·등급, 품목명, label size, 저장 시각·IP와 신규/수정 상태는 결과 column으로 표시한다. 레거시의 행 상세는 `CONTENT_COLUMNS`와 `CONTENTS`를 표시하며 별도 before/after 비교 field나 UI를 추가하지 않는다.

- 조회 전용 DAO와 row model만 작성하며 원본 업무 데이터를 변경하지 않는다.

### 5.2.5 공용라벨 수정 이력 보기 (`IDM_COMMON_LABEL_LOG`)

### 5.2.6 발행 통계 조회 (`IDM_STATUS_PRINT`)

- 사용자 등급은 결과 field로만 표시하며 filter로 추가하지 않는다. 발행 수량은 각 결과의 `RICH_PRINT_COUNT`를 표시하고, 활성 조회 흐름에서 사용하지 않는 `SelectPrintCountSum` 계열 합계 기능이나 별도 SQL aggregate를 추가하지 않는다.

## 5.3 설정 그룹

### 5.3.1 품목별 정보 편집 (`IDM_EDIT_ITEMINFO`)

- 레거시 기준: `OnEditItemInfo` → `CMainWindowModel::OnSelectEditItemInfo` → `CItemInfoDlg`/`CItemInfoModel`.
- 일반 사용자는 현재 Flutter 권한 UX에 따라 command를 표시하지 않는다.
- 현재 지점과 현재 label size의 품목별 출력 보정값을 일괄 편집하는 전용 `BlockingModelessDialog`를 구현한다. 단순 품목관리 탭 이동으로 대체하거나 품목관리의 상시 column을 늘리지 않는다.
- 반복 행은 `FortuneTable`로 표시하고 품명은 읽기 전용으로 둔다. 편집 대상은 레거시 활성 field인 줄간격 사용 여부·줄간격, 저울 바코드 사용 여부, 기본 발행 수량, 개별 label size 사용 여부·폭·높이, 개별 margin 사용 여부, 좌·우·상 margin과 좌·상 push로 제한한다.
- 줄간격, 개별 label size, margin의 세부 입력은 각 사용 여부가 켜진 행에서만 편집 가능하게 한다. 판매 시작일, 원가, 할인 관련 field처럼 레거시 dialog에서 숨긴 field를 이번 command에 추가하지 않는다.
- 기존 `ItemOfMarket`과 `ItemOfMarketDAO`를 재사용하거나 최소 확장한다. 저장은 현재 목록의 변경값을 레거시 `CItemOfMarketDAO::UpdateBatch`에 대응하는 하나의 batch/transaction으로 반영하고, 성공 후 현재 품목·출력 session이 사용하는 `ItemOfMarket` 목록만 갱신한다.
- dialog가 dirty이면 닫기·로그아웃·종료의 기존 통합 폐기 확인에 포함하고, 저장 중에는 닫기와 중복 저장을 차단한다.

### 5.3.2 영양성분 형식추가 (`IDM_NEW_NUTTYPE`)

- 레거시 기준: `OnInsertNewNutTypeDlg` → `CNuttypeManagerDlg`.
- 권한: 6.1의 `adminCommand`.
- `BM_RICH_NUTTYPE` 형식 목록과 `BM_RICH_NUTCOLUMN` 구성 행의 추가·수정·삭제를 포팅한다. 형식명은 필수이고 구성 행은 1개 이상이어야 한다.
- 구성 행 추가 시 keyword는 레거시처럼 `N01`부터 순서대로 자동 부여하고 사용자가 수정하지 못하게 하며 성분명만 편집한다. 별도 행 정렬 command, 형식명·성분명 중복 검증, 신규 검증 규칙을 추가하지 않는다.
- 기존 형식 수정은 parent 이름을 갱신하고 기존 detail을 삭제한 뒤 현재 구성 행을 다시 저장한다. 형식 삭제는 해당 형식을 사용하는 `BM_RICH_NUTBOX`, `BM_RICH_NUTCOLUMN`, `BM_RICH_NUTTYPE` 순서의 연관 삭제를 하나의 transaction으로 처리한다.
- 관련 기존 테이블과 column이 실제 DB에 있는지 확인한 뒤 전용 model/DAO를 작성한다.
- 현재 label column/barcode 모델에 억지로 포함하지 않는다.
- 신규·수정의 형식 parent와 detail 저장도 하나의 transaction으로 처리한다. `MAX(RICH_NUTTYPE_ID)`로 방금 삽입한 parent를 추측하지 않고 현재 SQL Server 2017과 compatibility level 100에서 지원하는 동일 transaction의 생성 ID 반환을 사용한다.

### 5.3.3 영양성분표 추가 (`IDM_NEW_NUTBOX`)

- 레거시 기준: `OnInsertNewNutboxDlg` → `CNutBoxManagerDlg`.
- 권한: 6.1의 `adminCommand`.
- `BM_RICH_NUTBOX` 목록에 영양성분 형식명과 표 명칭을 표시하고 형식 ID 순서로 조회한다. 선택 행의 `RICH_NUTBOX_DATA` RTF는 목록 옆 읽기 전용 preview로 표시한다.
- 추가·수정 입력은 영양성분 형식, 표 명칭, RTF 내용, 폭만 제공한다. 명칭과 0이 아닌 폭, 형식 선택을 필수로 검증하고 별도 영양성분 schema나 field를 추가하지 않는다.
- 추가·수정은 `RICH_NUTBOX_TYPE`, `RICH_NUTBOX_NAME`, `RICH_NUTBOX_DATA`, `RICH_NUTBOX_WIDTH`만 저장하고 삭제는 선택한 `RICH_NUTBOX_ID` 한 건만 처리한다.
- RTF 편집·읽기 전용 preview는 현 프로젝트의 기존 RTF renderer/helper를 우선 재사용한다. `RICH_NUTBOX_DATA`를 FortuneSheet workbook으로 변환하거나 renderer 재사용을 위해 별도 저장 형식을 추가하지 않는다.
- 형식 관리와 공용 dialog/table shell은 재사용할 수 있으나 영양성분표 row model, DAO와 입력 draft는 형식 관리의 parent/detail 저장 책임과 섞지 않는다.
- 임의의 신규 nutrition schema를 만들지 않는다.

### 5.3.4 고정 항목 관리 (`IDM_FIX_COLUMN_MANAGER` / `IDM_FIX_COLUMN_MANAGE`)

- 레거시 기준: `OnFixColumnManage` → `CFixColumnEditDlg`.
- 권한: 6.1의 `systemAdminCommand`.
- 레거시 메뉴 리소스는 `IDM_FIX_COLUMN_MANAGER(32853)`를 사용하지만 `MainFrm.cpp`의 command/update message map은 `IDM_FIX_COLUMN_MANAGE(32854)`를 사용한다.
- 현재 소스에는 두 ID를 잇는 alias나 다른 활성 진입점이 없어 메뉴에서 handler까지 도달하는 경로가 확인되지 않는다. Flutter inventory에는 하나의 `fixColumnManage` ID와 두 legacy ID의 불일치 사유를 기록하고 `legacyUnreachable`로 분류한다.
- production 메뉴에서는 숨기며 이번 포팅의 dialog/model/DAO 구현·내부 schema 조사·완료 판정 범위에서 제외한다. 두 ID를 별도 메뉴로 만들거나 도달하지 않는 handler를 활성 command로 되살리지 않는다.
- 실제 배포된 레거시 binary에서 도달 경로가 확인되거나 별도 활성화 요구가 생기면 `CFixColumnEditDlg`, `SpecalKeyword`, `TColumnSpecial`과 실제 저장 source를 다시 대조해 별도 범위로 구현한다. schema가 확인되지 않으면 migration 없이 blocker 처리한다.

### 5.3.5 전자저울 관리 (`IDM_SETUP_SCALE`)

- 기존 저울출력의 `showScaleConnectSettingsDialog`, `DbScaleConnectInfoHelper`, `_openScaleConnectSettings()` owning method를 재사용한다.
- `HomePageManager` controller에 공개 command API를 노출하고, 이 API가 기존 private `_openScaleConnectSettings()`에 위임한다. private method를 외부에서 직접 호출할 수 있게 변경하거나 내용을 AppBar controller에 복제하지 않는다.
- 저울 연결 중에는 기존 정책대로 먼저 연결 해제를 요구한다.
- 포트 scan, 연결 retry 같은 추가 보완을 메뉴 포팅 범위에 넣지 않는다.

### 5.3.6 프린터 설정 (`IDM_SETUP_PRINT`)

- 현재 라벨출력과 저울출력에는 서로 다른 session/settings context가 있다.
- 레거시 전역 프린터 설정과 현 화면별 설정의 차이를 확인해 command 동작을 확정한다.
- AppBar `설정` popup에서는 하나의 문맥 의존적인 `프린터 설정` 항목으로 합치지 않고 `라벨출력 프린터 설정`과 `저울출력 프린터 설정`을 명시적인 두 command로 표시한다.
- 두 Flutter command는 각각 안정적인 command ID와 label을 가진다. 두 command와 레거시 `IDM_SETUP_PRINT`의 대응 관계는 포팅 inventory test fixture에 기록한다.
  - `라벨출력 프린터 설정` 공개 command는 기존 private `_openLabelPrintSettings()` owning method에 위임한다.
  - `저울출력 프린터 설정` 공개 command는 기존 private `_openScaleOutputPrinterSettings()` owning method에 위임한다.
- private owning method를 public으로 바꾸거나 설정 dialog 실행 내용을 AppBar controller에 복제하지 않는다.
- 현재 탭에 따라 같은 menu item의 의미나 label을 바꾸지 않고, 다른 탭에서 라벨출력 설정으로 자동 기본화하지 않는다.
- 필요한 label size나 session context가 없으면 해당 command를 비활성화하고 popup에 짧은 `disabledReason`을 표시한다.
- 설정 저장은 기존 `LabelPrintSettingsController`/DAO를 재사용한다.
- 별도 전역 printer schema를 만들지 않는다.

### 5.3.7 거래게시판 (`IDM_TRADE_BOARD`)

- 레거시 메뉴는 `INACTIVE`다.
- inventory와 `legacyInactive` 숨김 policy만 유지하며 이번 포팅의 내부 기능 구현·source 조사 범위에서는 제외한다.
- 별도의 활성화 요구가 생기면 `CTradeBoardViewDlg`와 실제 DB/URL source를 확인해 별도 범위로 구현하며, 임의 게시판 테이블이나 외부 서비스를 만들지 않는다.

### 5.3.8 이더넷 설정 (`IDM_SETUP_ETHENET`)

- 레거시 `OnUpdateSetupEthernet`이 항상 비활성화하므로 inventory에는 유지하되 `legacyInactive`로 분류하고 production 메뉴에서는 숨긴다.
- 이번 포팅의 dialog/model/DAO 구현·내부 source 조사·완료 판정 범위에서는 제외한다.
- 별도의 활성화 요구가 생기면 `OnSetupEthenet`, `CSetupEthenet`의 대상 장치와 저장 source를 다시 확인해 별도 범위로 구현한다. OS 네트워크 어댑터 일반 설정, 관리자 권한 상승, Windows UAC 자동 실행으로 확대하지 않는다.

### 5.3.9 업데이트 메시지 (`IDM_UPDATE_NOTICE`)

- 기존 `NoticeDAO`와 startup notice 흐름을 재사용한다.
- 로그인된 현재 사용자의 `BM_UPDATE_NOTICE` 단일 row를 조회해 해당 공지를 다시 연다. 공지 목록·이력·최신 공지 선택 UI나 신규 table은 추가하지 않는다.
- 사용자 등급에 따른 레거시 전체 동작을 포팅한다.
  - `SYSTEM_ADMIN_USER`: 공지 내용 편집과 전체 협력업체 또는 선택 사용자 대상 지정을 제공한다.
  - `COOP_ADMIN_USER`: 공지 내용 편집과 현재 협력업체 또는 선택 사용자 대상 지정을 제공한다.
  - 그 외 로그인 사용자: 공지를 읽기 전용으로 표시하고 `다시 보지 않기` 상태만 변경한다.
- 기능 권한은 실제 사용자 등급으로 결정하며 `IsAdminConnect`, `IsCoopAdminConnect`, `IsFirstConnectByAdmin`만으로 관리자 편집 기능을 부여하지 않는다.
- startup dialog의 private UI를 복제하지 말고 공용 notice content/component로 추출해 시작 화면과 메뉴 command가 같은 표시·편집 경로를 사용한다.
- 기존 `BM_UPDATE_NOTICE`의 `UN_MSG`, `UN_STATE`, `UN_TIME`, 사용자·협력업체 대상 범위만 사용하고 migration을 추가하지 않는다.
- 업데이트 다운로드/자동 설치를 이번 command에 임의 추가하지 않는다.

### 5.3.10 검색출력모드 (`IDM_SEARCH_PRINT_MODE`)

- 레거시처럼 `F12`와 menu command가 같은 bool mode를 toggle한다. mode가 켜지면 메인 tab을 비활성화하고 기존 검색 button label을 `발행`으로, 꺼지면 `검색`으로 복원한다.
- mode가 꺼진 상태의 검색 button은 기존 검색·치환 흐름을 유지한다. mode가 켜진 상태에서는 현재 label size 안에서 품명 완전 일치 또는 `RICH_SEARCH_PRINT=1`인 column 내용 완전 일치로 조회한다.
- 일치 결과가 여러 건이어도 별도 선택·중복 경고·정렬을 추가하지 않고 레거시처럼 DB가 반환한 첫 행의 품목 1건을 기존 라벨출력 pipeline으로 즉시 발행한다. 발행 요청 후 검색 입력을 비운다.
- 단순 bool toggle이라도 mode state는 AppBar widget이 아니라 HomePageManager/controller가 소유한다.
- popup에서는 command 앞 checkmark로 mode 활성 상태를 표시한다. segmented control은 사용하지 않는다.
- menu item을 선택하면 AppBar popup을 닫은 뒤 controller mode를 한 번 변경한다. 메뉴가 닫힌 상태에서 `F12`로 mode가 바뀌어도 다음 popup open 시 controller의 현재 값을 읽어 checkmark를 표시한다.
- 프린터 설정, 자동 증가, 출력 log 등은 현재 라벨출력 pipeline을 재사용한다. mode 전용 출력 구현이나 레거시와 다른 자동 검색/자동 발행 규칙을 추가하지 않는다.

### 5.3.11 검색출력 설정 (`IDM_SEARCH_PRINT_SETUP`)

- 레거시 `CSearchPrintSetupDlg`와 같이 브랜드, 브랜드의 label size, 해당 label size의 column 목록을 표시한다.
- 설정값은 각 column의 기존 `RICH_SEARCH_PRINT` 선택뿐이다. 개별 선택, 전체 선택, 전체 해제와 적용 command를 제공하고 기존 `CColumnDAO::UpdateBatch`에 대응하는 column 저장 API를 사용한다.
- 별도 검색 문구, 자동 발행 조건, 사용자별 설정이나 신규 설정 table을 추가하지 않는다.
- 기존 schema/config가 없으면 migration으로 대체하지 않는다.
- 설정 저장 commit 실패 시 dialog 입력 상태를 유지하고 오류를 전달한다.

## 5.4 후속 범위 참고: 도움말 그룹

- 다음 항목은 `파일`부터 `설정`까지인 이번 AppBar 포팅과 완료 판정에 포함하지 않는다.
- 후속 구현 요청이 있을 때 레거시 handler와 URL을 다시 확인한 뒤 별도 `도움말` 그룹으로 추가한다.

### 5.4.1 라벨매니저 정보 (`ID_APP_ABOUT`)

- 앱명, `appVersion`, 빌드 정보, 저작권/지원 정보를 표시하는 작은 dialog를 구현한다.
- 실행 환경의 비밀값, DB credential, 전체 connection string은 표시하지 않는다.

### 5.4.2 라벨지·프린터 구매, 원격지원, ITSNG 자료실

- 레거시 handler에서 실제 URL과 실행 방식을 확인한다.

- URL을 추측하거나 검색 결과 URL로 대체하지 않는다.
- 외부 브라우저 열기 실패는 오류를 한 번 전달하고 자동 재시도하지 않는다.
- 원격지원 프로그램을 자동 다운로드/실행하거나 권한 상승시키지 않는다.

## 6. 권한 policy 계약

### 6.1 등급 기반 policy

- `systemAdmin`: `SYSTEM_ADMIN_USER`.
- `admin`: `SYSTEM_ADMIN_USER` 또는 `COOP_ADMIN_USER`.
- `systemAdminCommand`: 레거시 `OnEnableSystemAdmin`과 같이 `IsSystemAdmin` 또는 `IsAdminConnect`를 허용한다. 협력업체 관리에 사용하며 고정 항목 관리는 inventory의 권한 metadata만 유지하되 `legacyUnreachable` 숨김이 우선한다.
- `adminCommand`: 레거시 `OnEnableAdmin`과 같이 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect`, `IsFirstConnectByAdmin` 중 하나를 허용한다. 거래처 관리, 관리자 복사, 영양성분 형식·표에 사용한다.
- `managerCommand`: 레거시 `OnEnableManager`와 같이 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나를 허용한다. 지점 관리, 사용자 관리, 검색 및 치환에 사용하며 `IsFirstConnectByAdmin`과 `MANAGER_USER`를 자동 포함하지 않는다.
- 세 command policy의 세션성 연결 상태는 6.2의 신뢰 가능한 source가 포팅된 경우에만 포함한다. 해당 상태가 없을 때 `systemAdminCommand`의 기본 등급은 `systemAdmin`, `adminCommand`와 `managerCommand`의 기본 등급은 `admin`이며, 임의로 허용 범위를 넓히지 않는다.
- `editable`: 현재 메인 업무 편집 정책인 client 제외 등급. 메뉴별 legacy admin policy와 혼동하지 않는다.
- `loggedIn`: 로그인된 모든 등급.
- `always`: 비로그인에서도 허용되는 종료 등.

### 6.2 세션성 관리자 연결 상태

- 레거시에는 `IsAdminConnect`, `IsCoopAdminConnect`, `IsFirstConnectByAdmin`가 있다.
- 현 프로젝트에 대응 상태와 신뢰 가능한 source가 없으면 `UserGrade`만으로 허용 범위를 넓히지 않는다.
- 거래처·사용자 관리의 `Connect`를 위해 별도 session model에 원래 관리자, `IsAdminConnect`, `IsCoopAdminConnect`, `IsFirstConnectByAdmin`에 대응하는 상태를 둔다. 최초 로그인과 두 `Connect` owning command만 이 상태를 설정하며 로그아웃은 기존 순서에서 초기화한다.
- 중첩 `Connect`에서는 원래 관리자를 덮어쓰지 않고 레거시 `GetConnectOrigin() == nullptr` 조건과 같이 최초 원본을 유지한다. 연결 후 권한 policy는 이 session model의 신뢰 가능한 상태만 사용한다.
- query parameter, 사용자 ID 문자열, UI checkbox만으로 관리자 연결 상태를 위조하지 않는다.

### 6.3 policy 테스트 필수 matrix

command마다 모든 등급 조합을 반복하지 않는다. 공용 policy table test에서 비로그인, 관리자 계열, 일반 사용자, `tester01` override, `legacyInactive`, `legacyUnreachable`의 대표 경계를 고정한다. `systemAdminCommand`, `adminCommand`, `managerCommand`는 `IsFirstConnectByAdmin` 포함 여부와 `MANAGER_USER` 제외를 포함한 서로 다른 경계를 한 번씩 검증하고, command별 test는 해당 command에 별도 권한이나 busy/dirty 조건이 있을 때만 추가한다. admin-connect session은 실제 신뢰 가능한 상태가 구현된 command에만 검증한다.

## 7. 화면 및 DAO 구현 공통 기준

### 7.1 메뉴 dialog 표시 원칙

- AppBar 메뉴에서 새로 여는 관리·편집·조회 화면은 `OverlayEntry`의 root에 `BlockingModelessDialog`를 두고, 실제 창은 `BlockingModelessDialogFrame`으로 구성한다.
- 공용 wrapper는 구조상 modeless overlay이지만 배경의 pointer/touch와 처리되지 않은 key event를 차단한다. dialog가 열린 동안 배경 탭이나 AppBar command를 조작할 수 있게 우회하지 않는다.
- widget tree의 key 차단만으로 `HardwareKeyboard.instance.addHandler` 전역 handler가 차단된다고 가정하지 않는다. 차단 surface가 보이는 동안 F1/F2/F3 탭 이동, F5 새로고침, F12 검색출력 mode를 실행하지 않으며 dialog 내부의 Tab, Enter, Esc와 셀 편집 shortcut은 유지한다.
- `DbReconnectOverlay`처럼 widget tree 안에서 `ModalBarrier`를 렌더링하는 기존 전역 차단 UI도 같은 단축키 차단 결과를 보장한다.
- 기존 품목관리·공용라벨관리·라벨출력·자동품목갱신·저울출력처럼 상시 반복 작업으로 이미 존재하는 메인 탭은 그대로 재사용한다. 다만 레거시 `품목별 정보 편집`은 품목관리 탭과 저장 책임이 다른 출력 보정값 일괄 편집 기능이므로 5.3.1의 전용 차단형 dialog로 구현한다.
- 로그인, 로그아웃, 종료, 즉시 적용되는 검색출력 mode toggle처럼 별도 편집 화면이 없는 command도 억지로 dialog를 만들지 않는다.
- 이미 동작하는 저울·프린터 설정 등의 `showDialog`/`showGeneralDialog` owning dialog는 기존 command를 그대로 호출하고 같은 dialog를 `BlockingModelessDialog`로 한 번 더 감싸거나 coordinator 소유로 이전하지 않는다.
- 신규 관리·편집·조회 기능은 별도 `Navigator` route page, 새 메인 탭 또는 Windows native child window로 구현하지 않는다. 예외가 필요하면 장시간 상시 작업이어야 하며 근거와 영향 범위를 `SESSION_HANDOFF.md`에 기록하고 별도 승인 후 진행한다.
- 신규 AppBar dialog의 owning controller는 동일 dialog를 중복으로 열지 않는다. 차단형 dialog가 열린 동안 AppBar와 전역 command가 차단되므로 서로 다른 dialog 요청을 위한 전역 queue, stack 또는 focus 전환 처리는 추가하지 않는다.
- 작은 기존 설정 dialog는 현재 크기를 유지하되 화면보다 커지지 않도록 clamp한다.
- 신규 관리·조회 dialog는 보편적인 화면 비율을 강제하지 않는다. 입력 수, table column과 command 영역에 맞는 기능별 content 크기를 먼저 정하고, `MediaQuery`에서 가로 48px, 세로 64px 이상의 바깥 여백을 뺀 사용 가능 영역으로 clamp한다.
- 1168x720은 현재 라벨 항목 편집창처럼 넓은 table·편집 영역이 필요한 dialog의 참고 상한으로만 사용한다. 내용이 적은 dialog를 이 크기로 늘리지 않으며 더 넓은 결과 column이 확인된 경우에만 기능별 max width를 확장한다.
- 제목 bar에는 전체 한글 기능명과 닫기 icon을 표시한다.
- 명시적 draft 저장이나 command 영역이 필요한 신규 dialog는 `BlockingModelessDialogFrame.footer`에 화면에 필요한 상태와 `취소`/`저장`, `취소`/`적용`, `닫기` command를 직접 구성한다. 같은 footer 구조가 둘 이상에서 반복될 때만 공용 widget으로 추출한다.
- 즉시 적용형·단순 설정형 dialog와 기존 owning dialog는 현재 동작에 지속적인 footer가 없으면 억지로 추가하지 않는다.
- dialog를 열면 현재 작업의 첫 번째 주요 입력이나 table에 초기 focus를 두고, 비활성 control을 건너뛰며 마우스 없이 주요 입력과 command를 이동할 수 있게 한다. 화면마다 동일한 고정 Tab 영역 순서를 강제하지 않는다.
- Esc는 현재 focus를 가진 child에 실제 취소할 상태가 있을 때만 그 상태를 먼저 취소한다. 활성 셀 편집이나 비어 있지 않은 다중 선택이 Esc를 처리하면 dialog를 닫지 않고, 처리할 상태가 없으면 dialog 닫기 요청으로 이어진다. 일반 단일 행 선택은 별도 취소 단계로 간주하지 않는다.
- 사용자가 해당 dialog만 직접 닫을 때는 clean 상태를 즉시 닫고 그 dialog가 dirty일 때만 폐기 확인을 거친다. 로그아웃·메뉴 종료·OS 종료는 dialog별 확인창을 띄우지 않고 공용 lifecycle guard의 전체 dirty 통합 확인을 사용한다. Enter는 활성 셀 편집 확정에 사용하며 dialog 전체 저장 command를 실행하지 않는다.
- dialog를 닫으면 가능한 경우 이를 연 AppBar control로 focus를 돌린다. 공용 wrapper 확장은 실제로 여러 dialog에서 같은 처리가 중복될 때 수행한다.
- dirty, write-busy 또는 active editing처럼 실제 종료 차단 상태가 있는 신규 dialog owner만 exit snapshot을 `LifecycleManager.notifyExitRequested()` 흐름에 제공한다. dialog별 observer가 각자 종료 확인창을 띄우지 않는다.
- 읽기 전용 dialog는 종료용 dirty/write-busy 상태를 추가하지 않고 닫은 뒤 늦은 조회 결과를 폐기한다. 공용 lifecycle guard는 신규 dialog와 `HomePageManager` snapshot을 함께 평가하고 통합 dirty 확인이 끝난 뒤 열린 overlay를 정리한다. HomePage나 AppBar가 manager의 private 상태를 각각 복제하거나 별도 확인창을 만들지 않는다.
- 저장·삭제 transaction busy 중에는 중복 실행과 닫기를 비활성화한다.
- footer가 없는 즉시 적용형·단순 설정형 dialog는 busy를 시작한 control 가까이에 작업 성격에 맞는 spinner 또는 짧은 상태 문구를 표시하고 관련 입력과 command만 비활성화한다. 장시간 저장처럼 상태 설명이 필요한 경우에만 spinner와 문구를 함께 표시하며, 진행 표시 없이 닫기만 비활성화해 화면이 멈춘 것처럼 보이게 하지 않는다.
- 읽기 전용 조회 busy 중에도 닫기 경로를 유지한다. 실제 조회 취소 API가 있을 때만 `조회 취소` command를 표시한다. 취소할 수 없는 DB Future는 dialog를 닫은 뒤 늦게 도착한 결과만 폐기하며 자동 retry나 복구 저장소를 추가하지 않는다.
- dialog 안에서 확인·경고나 date/time picker를 열 때는 root overlay의 현재 차단창 위에 삽입되는 `showBlockingModelessOverlayDialog` 경로를 사용한다. 같은 picker 구성이 반복될 때만 공용 helper로 추출한다.
- dropdown처럼 별도 overlay surface가 필요한 control은 현재 `_ModelessDropdownField`/`_DialogDropdown` 패턴을 재사용하고 dialog 위 표시와 화면 경계 clamp를 보장한다. 같은 구현이 두 화면 이상에서 중복될 때 공용 control로 추출한다.
- 중첩 확인창이나 picker를 닫으면 가능한 경우 이를 연 control로 focus를 복원한다.
- commit 전 DML/validation 단계의 확정 실패는 dialog와 draft를 유지하고 오류를 한 번 전달한다. `DbCommitOutcomeUnknown`과 commit 성공 후 reload 실패는 1.3의 결과별 계약을 적용해 같은 draft를 재저장하지 못하게 한다.
- commit과 필요한 reload가 모두 성공하면 committed 상태를 반영한 뒤 overlay를 제거하고 controller, listener, focus node를 dispose한다.

### 7.2 FortuneTable 사용 원칙

- 관리 목록, 이력, 통계, 검색 결과처럼 동일한 column 구조의 row가 반복되는 화면은 `FortuneTable<T>`로 구현한다.
- 신규 화면에서 Flutter `DataTable`, `Table`, row별 `ListView` 조합 또는 기능별 자체 table widget으로 대체하지 않는다.
- column은 `FortuneTableColumn<T>`으로 선언하고 공용 header, column resize, 정렬, 선택, checkbox, 편집 callback 중 필요한 기존 API를 재사용한다.
- 관리 화면의 row draft와 저장 상태는 dialog/controller가 소유한다. `FortuneTable` 내부에 DAO 호출이나 업무 저장 로직을 넣지 않는다.
- 조회 화면은 `FortuneTable`을 read-only로 구성한다. 레거시 동작과 데이터 성격상 필요한 filter, 조회 command, 건수 또는 합계는 table 바깥의 owning dialog가 관리한다.
- 필요한 공용 table 기능이 없으면 개별 화면에 wrapper나 중복 구현을 추가하기 전에 `third_party/fortune_sheet/lib/src/fortune_table.dart`의 공용 API로 확장하고 `test/fortune_table_test.dart`에서 검증한다.
- `FortuneSheet`/LabelSheet는 workbook·라벨 시트 편집 또는 read-only 시트 미리보기에만 사용하며, 일반 관리 목록과 조회 결과 table 용도로 사용하지 않는다.
- 단일 상세값, key-value form, 선택 항목이 없는 짧은 안내 목록처럼 반복 column table이 아닌 UI는 `FortuneTable` 적용 대상이 아니다.
- 레거시 동작을 `FortuneTable`로 표현할 수 없는 기술적 blocker가 확인되면 임의 대체 table을 만들지 말고 원인과 필요한 공용 API를 `SESSION_HANDOFF.md`에 기록한 뒤 해결한다.

### 7.3 관리 dialog

- 운영 도구 성격에 맞게 밀도 높은 `FortuneTable` + 기능에 맞는 명확한 command 영역을 사용한다.
- 장식용 카드 중첩, hero, 과도한 animation을 사용하지 않는다.
- 행 단위 CRUD command는 작업 빈도와 현재 owning 화면의 패턴에 따라 테이블 상단 toolbar, 측면 command rail 또는 context menu에 배치한다. 자주 쓰는 핵심 command를 icon button으로 표시하면 tooltip을 제공한다.
- 지원하지 않는 row command는 비활성 button으로 남기지 않고 렌더링하지 않는다. 관리자 복사, 검색출력 설정처럼 row CRUD가 아닌 dialog에 CRUD toolbar/rail을 억지로 추가하지 않는다.
- 현재 품목관리처럼 context menu가 주 command인 작업은 같은 패턴을 사용할 수 있다. toolbar나 command rail을 추가할 때는 context menu와 command 구현을 공유한다.
- 명시적 draft 저장 흐름이 있는 신규 관리 dialog는 `BlockingModelessDialogFrame.footer`에 필요한 상태와 `취소`/`저장` 또는 `취소`/`적용`을 배치한다. 공용 footer widget은 같은 구조가 반복될 때만 추가한다.
- 즉시 적용형·단순 설정형 관리 dialog는 footer 없이 title bar 닫기와 본문 command만 사용할 수 있다.
- 추가/수정은 draft에서 수행하고 저장/취소를 명시한다.
- 삭제는 레거시 확인 문구와 종속성 검사를 따른다.
- 저장 성공 후 해당 목록과 필요한 app cache만 reload한다.
- 각 dialog의 owning controller가 해당 overlay와 open/close command를 관리한다.

### 7.4 조회 dialog

- 조회 결과는 read-only `FortuneTable`로 표시하고, filter, 명시적 조회 button, 건수와 합계는 레거시 동작과 해당 데이터에 필요한 항목만 제공한다. 자동 조회에는 불필요한 조회 button을 추가하지 않고 일반 이력에는 의미 없는 합계를 만들지 않는다.
- 최초 자동 조회 여부와 기본 기간은 레거시를 따른다.
- 조회 중 중복 요청만 막고 일반적인 자동 retry는 추가하지 않는다.
- 조회 중에도 닫기 command를 사용할 수 있어야 하며 닫힌 dialog에 늦은 결과를 적용하지 않는다. 실제 취소 가능한 조회에만 별도 `조회 취소` command를 제공한다.
- 빈 결과는 정상 상태로 표시하고 오류와 구분한다.
- export가 레거시에 있거나 명시 요구가 있을 때만 추가한다.

### 7.5 오류 처리

- DAO 오류를 빈 목록이나 `false`로 바꾸지 않는다.
- DB 오류는 원인 문자열을 보존해 command 계층으로 전달한다.
- 차단형 overlay가 열린 동안 실패는 dialog 내부 inline 상태 또는 `showBlockingModelessOverlayDialog`로 한 번 알리고 draft를 유지한다. 뒤쪽 `ScaffoldMessenger` snackbar를 오류 전달 경로로 사용하지 않는다.
- snackbar는 차단형 overlay가 제거된 뒤 표시하는 비차단 성공 알림 또는 overlay 밖의 기존 화면 알림에만 사용한다. 사용자 확인이나 action이 필요한 오류를 snackbar로 표시하지 않는다.
- 같은 오류를 DAO, controller, UI에서 각각 중복 로그로 남기지 않는다.
- 권한 부족은 DB command 실행 전 policy에서 차단한다.

## 8. 구현 단계

### Phase 0. inventory와 command contract 고정

1. 파일/검색/설정의 Flutter owning action마다 `AppMenuCommandId`, group, label, optional icon, optional `shortcutLabel`, permission, `legacyInactive`, `legacyUnreachable`을 순수 table로 작성한다.
2. 모든 command의 레거시 handler, legacy command ID 대응 관계와 현 구현 상태는 포팅 대조용 test fixture로 고정한다. 하나의 legacy ID에서 분리된 여러 Flutter command는 서로 다른 안정 ID를 갖는다.
3. 권한 matrix unit test를 먼저 작성한다.
4. 아직 기능이 없는 command도 ID를 예약하되 실제 menu에는 기능 완료 시점에만 연결한다.

완료 기준:
- 파일/검색/설정 command 누락 없음.
- 권한별 visible/enabled 상태와 `legacyInactive`/`legacyUnreachable` 숨김이 테스트로 고정됨.

### Phase 1. AppBar shell과 기존 기능 연결

1. AppBar 그룹 아이콘과 좁은 화면의 2단계 overflow를 구현한다. 기존 desktop window 초기화 동작은 변경하지 않는다.
2. login/logout/exit를 기존 HomePage command에 연결한다.
3. 저울 설정, 라벨출력/저울출력 프린터 설정을 HomePageManager controller로 연결한다.
4. update notice 공용 dialog를 추출해 메뉴에서 연결한다.
5. AppBar menu·modal dialog·modeless overlay·`DbReconnectOverlay`가 보이는 동안 전역 F1/F2/F3/F5/F12를 차단하고 non-modal `PreviewFloatingWindow`만 보일 때는 기존 단축키를 유지한다.
6. 신규 관리·조회 dialog의 owning controller에 `BlockingModelessDialog` open/close, 동일 dialog 중복 방지, 초기 focus와 중첩 modal/picker pattern을 적용한다. 편집 또는 저장이 있는 dialog에만 실제 dirty, write-busy, active editing 상태를 추가한다.
7. AppBar popup을 닫은 뒤 owning command를 한 번 실행하고, dialog를 열면 내부로 focus를 넘긴다.
8. `HomePageManager`와 신규 dialog owner가 실제 busy, active editing, dirty 표시명·폐기 callback을 exit snapshot으로 제공하고, 공용 lifecycle guard가 차단 상태를 먼저 평가한 뒤 모든 dirty를 한 번 확인하고 overlay를 정리하도록 연결한다.
9. 명시적 draft 저장·command 영역은 기존 frame footer slot에 구성하고, 행 CRUD command는 작업 빈도와 현재 owning 화면에 맞는 toolbar, rail 또는 context menu에 배치한다.

완료 기준:
- 기존 화면 버튼과 AppBar 메뉴가 같은 owning command를 호출함.
- 편집 차단을 우회하지 않음.
- 신규 관리·조회 command가 별도 route page, 새 메인 탭 또는 native child window를 만들지 않음.
- AppBar popup을 닫은 뒤 owning command가 한 번만 실행됨.
- 재연결 차단 UI가 표시되는 동안 전역 F-key와 배경 focus 이동이 차단됨.
- floating preview `OverlayRoute`만 표시된 상태에서는 기존 Home 전역 F-key가 오차단되지 않음.
- 넓은 폭과 좁은 대표 폭에서 AppBar와 현재 핵심 탭의 주요 command에 접근할 수 있음.
- clean 로그아웃/종료에는 일반 확인창이 없고, 신규 dialog와 기존 메인 탭의 busy/activeEditing은 먼저 차단되며 모든 dirty는 한 번의 통합 확인으로 처리됨.
- wide/narrow widget test 통과.

### Phase 2. 읽기 전용 이력/통계

1. 로그인 이력 demo를 실제 `BM_LOGIN_LOG` 조회로 교체한다.
2. 발행내역 조회를 현 persistence schema 기준으로 구현한다.
3. 발행 통계를 구현한다.
4. 데이터내용 이력 schema를 확인해 구현한다.
5. 공용라벨 이력은 inventory의 legacyInactive 숨김 상태만 유지하고 활성화 요구 전에는 구현하지 않는다.

완료 기준:
- 조회 기능에 DML이 없음.
- 레거시 filter/column/권한 테스트 통과.
- 큰 결과에서도 UI overflow/중복 조회 없음.

### Phase 3. 계층형 관리 기능

다음 순서로 구현한다.

1. 협력업체 관리.
2. 거래처 관리.
3. 지점 관리.
4. 사용자 관리.
5. 관리자 복사.

순서 이유:
- 하위 selector와 foreign key 의미가 상위 entity에 의존한다.
- 각 단계에서 실제 schema와 레거시 DAO를 확인할 수 있다.

완료 기준:
- CRUD 및 selector 권한이 레거시와 일치.
- 거래처·사용자 `Connect`가 원래 관리자와 연결 상태를 보존하고 업무 context 전환·관리자 접속 로그를 레거시 범위로 수행함.
- 다중 DML transaction commit/rollback 테스트 통과.
- 현재 app cache가 필요한 범위만 갱신됨.

### Phase 4. 설정 데이터 관리

1. 품목별 정보 편집.
2. 영양성분 형식.
3. 영양성분표.
4. 검색출력 설정과 mode.
5. 검색 및 치환.

완료 기준:
- schema 미확인 기능을 임의 구현하지 않음.
- mode/settings/data 저장 책임이 분리됨.
- 검색/치환 결과 table의 변경값 확인, 레거시 확인 흐름과 transaction 검증 통과.

### Phase 5. 숨김 command 최종 검증

1. 거래게시판, 공용라벨 이력, 이더넷 설정을 inventory에 유지한다.
2. 고정 항목 관리를 `legacyUnreachable`과 두 legacy ID의 불일치 사유와 함께 inventory에 유지한다.
3. `legacyInactive`와 `legacyUnreachable` command는 production 메뉴에서 숨김 상태를 유지한다.

완료 기준:
- `legacyInactive`와 `legacyUnreachable` command가 production 메뉴에 노출되지 않음.

## 9. 테스트 지시

### 9.1 순수 unit test

### 9.3 integration test

- AppBar 메뉴 → 기존 핵심 탭 또는 owning 설정 dialog 연결, 신규 관리·조회 command → 차단형 overlay dialog 표시.

- 실제 server integration은 기본 test 실행에서 제외하고 명시적 opt-in 설정이 있을 때만 실행한다. 조회 DAO는 데이터 변경 없는 read-only 경로만 검증한다.
- CRUD integration은 대상이 비운영 테스트 DB임이 명시적으로 식별되고, 전용 ID 범위·초기 상태·정리 절차가 준비된 경우에만 실행한다. 이 조건 중 하나라도 없거나 운영 DB 여부를 판별할 수 없으면 실행하지 않는다.
- 테스트를 위해 운영 DB row·권한을 수정하거나 테스트 table을 생성하지 않는다. 실제 server integration의 대상과 실행 명령은 `SESSION_HANDOFF.md`에 기록한다.
- commit·rollback 실패 simulation은 fake driver 기반 unit test에서 수행한다. 실제 server integration은 정상 transaction 경로만 검증한다.

### 9.4 회귀 검증

기능별 focused test와 함께 실제로 재사용하거나 수정한 owner의 기존 suite만 실행한다. AppBar shell 변경은 `app_menu_bar`와 사용자 policy test를, `FortuneTable` 공용 API 변경은 `fortune_table_test.dart`를, 기존 출력·설정 command 연결 변경은 해당 session/widget test를 회귀 범위로 선택한다. 변경하지 않은 전체 suite를 일률적인 완료 조건으로 두지 않는다.

## 10. 명령별 완료 체크리스트

각 command는 아래 항목 중 해당 command의 성격과 실제 구현 범위에 적용되는 항목을 충족해야 완료다. 비해당 항목을 충족하기 위해 별도 UI, DB 접근 또는 transaction을 추가하지 않는다.

- [ ] 레거시 handler/dialog/model/DAO 확인.
- [ ] DB를 사용하는 command는 실제 기존 DB schema 확인.
- [ ] command ID/label/group과 optional icon/`shortcutLabel` 등록.
- [ ] 해당 command의 권한·로그인·`legacyInactive`·`legacyUnreachable` 또는 busy/dirty 조건 확인.
- [ ] 기존 기능이면 owning command 재사용.
- [ ] 미구현 기능이면 필요한 model/DAO와 `BlockingModelessDialog` 기반 화면 구현.
- [ ] 기존 핵심 탭 이동 외에 별도 route page, 신규 메인 탭, native child window를 추가하지 않음.
- [ ] 신규 dialog를 여는 command는 주요 입력, Esc, 오류와 종료 흐름이 공용 계약을 따르고, 편집·저장이 있는 경우에만 실제 dirty/write-busy/active editing 상태를 처리함.
- [ ] 관리 목록 또는 조회 결과에 반복 행 table이 있는 command는 공용 `FortuneTable`을 사용함.
- [ ] 행 CRUD command는 작업 빈도와 현재 owning 화면에 맞는 toolbar/rail/context menu를 사용하고 비CRUD dialog에는 불필요한 CRUD command가 없음.
- [ ] 조회 command는 데이터 성격에 필요한 조회 UI와 오류 흐름을 구현함.
- [ ] 명시적 draft 저장 흐름이 있는 command만 저장/취소 UI를 구현함.
- [ ] 쓰기 transaction이 있는 command는 statement·parameter·결과 decoding을 검증하고, UI는 확정 실패·`DbCommitOutcomeUnknown`·commit 후 reload 실패를 1.3 계약대로 구분함.
- [ ] DB를 사용하는 command는 DB migration을 사용하지 않음.
- [ ] focused test 통과.
- [ ] 변경한 owner의 관련 회귀 test 통과.
- [ ] `SESSION_HANDOFF.md`에 구현/검증/commit 기록.

## 11. 금지 사항

- 동작하지 않는 메뉴를 활성 상태로 먼저 노출하지 않는다.
- 좁은 화면 overflow에 모든 command를 하나의 긴 평면 목록으로 표시하지 않는다.
- 미구현 command를 snackbar `준비 중`으로 완료 처리하지 않는다.
- 레거시 INACTIVE command를 임의 활성화하지 않는다.
- 레거시 메뉴에서 handler 도달 경로가 확인되지 않은 command를 임의 활성화하지 않는다.
- schema가 없다는 이유로 앱 시작 시 table/column을 자동 생성하지 않는다.
- DB migration script를 추가하거나 실행하지 않는다.
- generic catch에서 DB 오류를 성공/빈 결과로 바꾸지 않는다.
- commit 실패를 무시하거나 자동 retry하지 않는다.
- rollback이 가능하지 않은 상태에서 억지 rollback command를 반복하지 않는다.
- 관리 기능을 하나의 거대한 dialog/model/DAO에 합치지 않는다.
- HomePage와 HomePageManager에 같은 업무 command를 중복 구현하지 않는다.
- 메뉴 widget에서 직접 SQL을 실행하지 않는다.
- shortcut을 command label 문자열에 직접 합치거나, 차단 surface가 보이는 동안 화면 전역 `HardwareKeyboard` command를 실행하지 않는다.
- AppBar popup을 닫기 전에 dialog·탭 이동·toggle·종료 command를 시작하거나 command를 중복 실행하지 않는다.
- 좁은 폭을 지원하려고 서버 상태·로그인 command를 숨기지 않는다.
- 비활성 popup item의 실행 불가 사유를 hover tooltip으로만 제공하지 않는다.
- 지원하지 않는 CRUD command를 비활성 toolbar/rail button으로 표시하지 않는다.
- 같은 footer 구조가 반복되기 전에 새 공용 footer widget을 선행 추가하지 않는다.
- 즉시 적용형·단순 설정형 또는 기존 owning dialog에 footer를 억지로 추가하지 않는다.
- footer 없는 dialog에서 진행 표시 없이 닫기와 입력만 비활성화하지 않는다.
- 신규 관리·편집·조회 command를 별도 route page, 신규 메인 탭 또는 Windows native child window로 구현하지 않는다.
- `BlockingModelessDialog` 안에서 일반 `showDialog`, `showDatePicker`, `showTimePicker`로 중첩 modal을 열지 않는다.
- 같은 신규 AppBar dialog의 `OverlayEntry`를 중복으로 쌓지 않는다.
- 신규 dialog에 실제 dirty, write-busy 또는 active editing이 있는데 이를 확인하지 않고 메뉴 종료나 OS 창 닫기를 진행하지 않는다. 읽기 전용 dialog에 종료 차단 상태를 임의로 추가하지 않는다.
- HomePage나 AppBar가 `HomePageManager`의 기존 출력·연결·저장 busy, activeEditing, dirty private 상태를 각각 복제해 판정하거나 clean 로그아웃에 일반 확인창을 추가하지 않는다.
- 차단형 overlay가 열린 동안 뒤쪽 `ScaffoldMessenger` snackbar로 오류나 사용자 action을 요구하지 않는다.
- 관리·조회용 반복 행 table을 `DataTable`, `Table`, row별 `ListView` 또는 기능별 자체 table widget으로 새로 구현하지 않는다.
- 테스트를 위해 운영 사용자 권한이나 운영 DB row를 수정하지 않는다.
- 비운영 DB 식별, 전용 ID 범위와 정리 절차 없이 실제 server CRUD integration을 실행하지 않는다.
- 사용자 소유 변경 `lib/core/app.dart`를 이 작업에 포함하지 않는다.
- release build, installer, 원격 push는 명시 요청 없이 수행하지 않는다.

## 12. 최종 완료 상태

전체 포팅 완료 시 다음 상태여야 한다.

- AppBar에는 폭에 따라 그룹 아이콘 3개 또는 overflow 메뉴 1개가 표시된다.
- 기존 desktop window 초기화 동작을 변경하지 않고 넓은 폭과 좁은 대표 폭에서 AppBar와 핵심 탭의 주요 command에 접근할 수 있다.
- 통합 overflow는 3개 그룹의 2단계 구조와 화면 높이 clamp·scroll·키보드 reveal을 제공한다.
- AppBar title은 메뉴 collapse 후에도 공간이 부족하면 한 줄 ellipsis되고 서버 상태와 현재 로그인/로그아웃 command는 유지된다.
- AppBar menu는 키보드만으로 열기·이동·실행·닫기가 가능하다. 메뉴만 취소하면 원래 trigger에 focus가 복원되고 top-level dialog를 실행하면 dialog 내부로 focus가 인계된다.
- AppBar menu는 간결한 한글 기본 label을 표시하고 실제 활성 shortcut을 오른쪽 보조 영역과 semantics에 표시한다.
- AppBar menu와 차단형 dialog가 보이는 동안 전역 F1/F2/F3/F5/F12의 배경 command 실행을 막고 마지막 차단 surface가 닫힌 뒤 복원한다. non-modal floating preview만으로는 차단하지 않는다.
- AppBar menu command는 popup이 닫힌 뒤 정확히 한 번 실행되며 새 dialog를 열면 첫 주요 입력으로 focus를 넘긴다.
- 서버 상태와 로그인/로그아웃 영역은 기존 위치와 동작을 유지한다.
- 파일/검색/설정의 모든 레거시 command가 inventory와 권한 policy에 존재한다.
- 현재 동작 기능은 중복 구현 없이 같은 command로 연결된다.
- 미구현 기능은 실제 `BlockingModelessDialog` 기반 화면, model/DAO, DB 계약과 테스트를 갖는다.
- 기존 핵심 탭 이동과 기존 owning 설정 dialog를 제외한 신규 관리·편집·조회 화면은 공용 차단형 overlay dialog로 일관되게 열린다.
- 신규 AppBar dialog는 owning controller가 동일 dialog 중복 실행과 close를 관리하고, 실제 편집·저장 상태가 있을 때만 exit snapshot을 제공한다. 종료 요청의 dirty 요약·폐기 callback 수집 외에 서로 다른 dialog를 위한 전역 coordinator는 추가하지 않는다.
- 로그아웃·메뉴 종료·OS 창 닫기는 신규 dialog와 기존 메인 탭의 exit snapshot을 함께 평가한다. 읽기 전용 dialog는 닫고 늦은 결과를 폐기하며, write-busy와 activeEditing은 dirty 확인 전에 종료를 막고 모든 dirty 상태는 한 번의 통합 확인으로 처리한다. clean 상태에는 일반 확인창을 추가하지 않는다.
- 차단형 dialog의 모든 중첩 modal/picker는 현재 dialog 위에 표시되고, form-only dialog도 첫 활성 입력에 초기 focus가 설정된다.
- 모든 관리 목록과 조회 결과의 반복 행 table은 공용 `FortuneTable`을 사용한다.
- 명시적 draft 저장 흐름이 있는 신규 관리 dialog는 기존 frame footer slot에 필요한 command를 구성하고, 즉시 적용형·단순 설정형과 기존 owning dialog는 필요한 command 영역만 유지한다. 행 CRUD command는 작업 빈도와 owning 화면에 맞는 toolbar, rail 또는 context menu를 사용한다.
- footer 없는 busy 상태는 실행 control 가까이에 표시되고, 차단형 overlay 오류는 inline 또는 공용 overlay dialog로 전달된다.
- `legacyInactive`와 `legacyUnreachable` command는 inventory에 사유와 함께 유지하되 production 메뉴에서는 숨기며 활성화 요구나 실제 도달 경로 확인 전에는 내부 구현을 완료 조건으로 삼지 않는다.
- DB schema는 변경되지 않는다.
- 저장 오류는 호출자에게 전달되고 가능한 transaction만 rollback된다. `DbCommitOutcomeUnknown`과 commit 후 reload 실패는 같은 draft를 재저장하지 않도록 안내 후 dialog를 닫고, 다시 열 때 최신 데이터를 조회한다.
- 과도한 fallback, retry, 자동 보정 없이 레거시 업무 동작과 현 UI 구조가 일관되게 결합된다.
