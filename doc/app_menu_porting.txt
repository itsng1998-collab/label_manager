# 레거시 애플리케이션 메뉴 및 기능 포팅 작업지시서

## 0. 문서 목적

- 이 문서는 레거시 LabelManager 네이티브 창의 `파일`, `검색`, `설정` 메뉴를 현 Flutter 프로젝트의 상단 AppBar에 그룹별 아이콘 메뉴로 포팅하기 위한 구현 계약이다.
- 인접한 `도움말` 메뉴는 이번 AppBar 포팅 범위에서 제외하며, 확인된 항목은 후속 범위 참고용으로만 기록한다.
- 현재 동작하는 기능은 기존 owning 화면과 command를 재사용해 연결한다.
- 현 프로젝트에 없는 기능은 레거시 화면, model, DAO와 실제 DB 스키마를 확인한 뒤 공용 차단형 dialog, model, DAO를 구현한다.
- 메뉴 항목만 먼저 만들고 눌렀을 때 `준비 중`, 빈 화면, 임의 안내만 표시하는 상태를 완료로 간주하지 않는다.
- 한 기능을 완료할 때는 메뉴 노출, 권한, 실제 command, 데이터 조회/저장, 오류 전달, 회귀 테스트까지 함께 끝낸다.

## 1. 최우선 구현 원칙

### 1.1 범위와 원인 중심 구현

- 레거시 동작과 현재 프로젝트의 실제 코드 경로를 기준으로 구현한다.
- 과도한 보완, 추측성 fallback, 자동 재시도, 임의 데이터 보정, 레거시에 없는 업무 규칙을 추가하지 않는다.
- 단순 null 방어를 여러 계층에 중복 추가하지 말고, 상태와 command를 소유한 계층에서 원인을 해결한다.
- 메뉴 UI에 업무 로직이나 SQL을 넣지 않는다. 메뉴는 권한/상태 표시와 command 전달만 담당한다.
- 로그 함수에 권한 판단, 저장, 상태 변경, 재시도 같은 비즈니스 로직을 넣지 않는다.
- 이미 탭이나 화면에 있는 기능을 AppBar용으로 다시 구현하지 않는다. owning controller 또는 명시적 command API를 통해 같은 기능을 호출한다.
- 이 포팅으로 추가하는 관리 목록과 조회 결과의 반복 행 테이블은 공용 `FortuneTable<T>`와 `FortuneTableColumn<T>`을 사용한다.
- AppBar 메뉴에서 새로 여는 관리·편집·조회 UI는 `BlockingModelessDialog`와 `BlockingModelessDialogFrame`을 사용한다. 별도 route page, 신규 메인 탭 또는 네이티브 창으로 만들지 않는다.

### 1.2 데이터베이스 절대 제약

- DB schema migration을 구현하거나 실행하지 않는다.
- 테이블 생성, 컬럼 추가/삭제/변경, index 생성/변경, compatibility level 변경을 금지한다.
- 레거시 코드 이름만 보고 테이블명이나 컬럼명을 추정해 SQL을 작성하지 않는다.
- 각 기능 구현 전 다음 순서로 기존 스키마를 확인한다.
  1. 레거시 DAO/model의 SELECT/INSERT/UPDATE/DELETE SQL 확인.
  2. 현 프로젝트의 model/DAO와 doc SQL 확인.
  3. 필요하면 읽기 전용 metadata 조회로 운영 스키마의 기존 테이블/컬럼 확인.
  4. 필요한 기존 스키마가 없으면 기능을 임의 스키마로 대체하지 말고 blocker로 기록한다.
- SQL Server 엔진은 2017이지만 DB `compatibility_level=100`을 SQL 문법 하한선으로 사용한다.
- `OPENJSON`, `JSON_VALUE`, `TRY_CONVERT`, `STRING_SPLIT`과 검증되지 않은 신문법을 사용하지 않는다.
- 구조화된 다중 행 payload가 필요하면 escaped XML과 `CONVERT(XML, ...)`, `.nodes()`, `.value()`, `.query()`, `.exist()`를 사용한다.
- SQL parameter 처리 시 `@@ROWCOUNT`, `@@TRANCOUNT` 같은 SQL Server system variable을 placeholder로 변환하지 않는다.

### 1.3 저장과 transaction 제약

- 읽기 전용 조회에는 불필요한 transaction을 추가하지 않는다.
- 서로 함께 성공해야 하는 다중 DML만 하나의 transaction batch로 묶는다.
- transaction은 다음 범위까지만 책임진다.
  - DML 실행.
  - commit 시도.
  - DML 또는 commit 오류를 원인 보존 상태로 호출자에게 전달.
  - 오류 시 `@@TRANCOUNT > 0`이면 가능한 rollback 수행.
- commit 오류를 성공으로 바꾸거나, 일부 성공을 정상 처리하거나, 자동 재시도하지 않는다.
- rollback 자체가 실패해도 원래 오류를 숨기지 않는다. 가능한 범위의 rollback을 시도한 뒤 원래 오류를 전달한다.
- 권장 SQL batch 형태는 저장소의 기존 검증된 pattern을 따른다.

```sql
SET XACT_ABORT ON;
SET NOCOUNT ON;
BEGIN TRY
  BEGIN TRANSACTION;

  -- 기존 스키마에 대한 필요한 DML만 수행

  COMMIT TRANSACTION;
  SELECT CAST(1 AS INT) AS RESULT;
END TRY
BEGIN CATCH
  IF @@TRANCOUNT > 0
    ROLLBACK TRANSACTION;
  THROW;
END CATCH
```

- 0건 변경을 성공으로 볼 수 없는 command는 각 DML 직후 `@@ROWCOUNT`를 저장해 명시적으로 검증한다.
- `SQL_NO_DATA(100)` rowcount noise가 가능한 batch는 `SET NOCOUNT ON`과 최종 명시적 `SELECT`를 사용한다.
- 저장 성공이 확인되기 전에는 UI draft, 변경 전 snapshot, 임시 선택 상태를 폐기하지 않는다.

### 1.4 model과 DAO 작성 기준

- 현 model/DAO에 같은 책임의 API가 있으면 재사용하거나 최소 확장한다.
- 기능 경계가 다르거나 기존 API를 억지로 확장해야 하면 해당 기능 전용 model/DAO를 작성한다.
- 하나의 거대한 `AppMenuDAO` 또는 모든 관리 기능을 처리하는 generic DAO를 만들지 않는다.
- model은 DB row의 의미와 UI draft를 분리한다.
- DAO는 SQL과 row mapping을 소유하고, dialog는 SQL 문자열을 소유하지 않는다.
- 삭제/순서 변경/복사처럼 여러 row를 저장하는 기능은 payload codec과 DAO transaction을 분리해 테스트한다.
- schema가 확인되지 않은 기능은 model/DAO 이름과 책임까지만 계획하고 SQL을 확정하지 않는다.

## 3. 목표 UI

### 3.1 AppBar 배치

넓은 데스크톱에서는 다음 순서를 사용한다.

```text
[애플리케이션명 + 버전]  [파일/관리] [조회/이력] [설정]  ...  [서버 상태] [로그인/로그아웃]
```

- 각 그룹은 텍스트가 들어간 둥근 버튼이 아니라 익숙한 아이콘 버튼을 사용한다.
- 모든 그룹 아이콘에 명확한 tooltip을 제공한다.
- 권장 아이콘:
  - 파일/관리: `Icons.menu`
  - 조회/이력: `Icons.manage_search`
  - 설정: `Icons.settings_outlined`
  - 좁은 화면 통합 메뉴: `Icons.more_vert`
- `파일/관리`는 비로그인·저권한 상태에서 종료만 남을 수 있으므로 관리자 전용으로 오인되는 아이콘을 사용하지 않는다.
- 팝업 내부에는 아이콘과 전체 한글 명령명을 함께 표시한다.
- 실행 전에 추가 사용자 입력·선택이 필요한 command의 popup 표시명에는 `...`를 붙인다. 관리·설정 form과 filter 입력 후 조회하는 command는 대상이고, 단순 공지·안내 dialog, 즉시 실행, toggle, 기존 탭 이동, 종료는 대상이 아니다. 안정 ID, 기본 `label`, dialog title에는 `...`를 포함하지 않고 popup renderer가 `requiresFurtherInput` metadata로 표시명만 구성한다.
- 실제 활성 전역 shortcut이 있는 command는 명령명 문자열에 `(F1)`처럼 합치지 않고 popup 오른쪽의 고정 보조 영역에 `F1`, `F12` 같은 `shortcutLabel`을 표시한다. `품목별 정보 편집`의 `F1`과 `검색출력모드`의 `F12`부터 적용하며, 아직 구현되지 않았거나 현재 화면에서 실행되지 않는 shortcut은 표시하지 않는다. semantics에는 기본 명령명과 shortcut을 함께 제공한다.
- separator는 레거시 메뉴의 command group 경계를 유지한다.
- 위험 command의 확인은 팝업 메뉴가 아니라 해당 화면의 저장/삭제 command 시점에 수행한다.

### 3.2 반응형 기준

- 화면 전체 폭만 하드코딩해 판단하지 말고 AppBar title과 actions에 실제 제공된 폭을 `LayoutBuilder`로 판단한다.
- 그룹 3개, 서버 상태, 로그인/로그아웃이 겹치지 않는 폭에서는 그룹 아이콘을 각각 표시한다.
- 폭이 부족하면 그룹 버튼을 먼저 `more_vert` 하나로 합친다.
- 통합 overflow의 첫 단계에는 현재 표시할 command가 있는 `파일/관리`, `조회/이력`, `설정` 그룹만 표시하고, 그룹을 선택하면 해당 command의 2단계 submenu 또는 panel을 연다. 전체 command를 하나의 긴 평면 목록으로 합치지 않는다.
- 그룹 submenu/panel은 화면의 사용 가능 높이로 clamp하고 필요한 경우 세로 scroll을 제공한다. 키보드 focus 항목이 viewport 밖으로 이동하면 자동으로 reveal한다.
- 서버 상태와 로그인/로그아웃은 항상 오른쪽 끝에 남긴다.
- 메뉴를 합친 뒤에도 폭이 부족하면 title은 `maxLines: 1`, `softWrap: false`, `TextOverflow.ellipsis`로 줄인다. 서버 상태와 현재 로그인/로그아웃 command를 title보다 먼저 숨기거나 줄이지 않는다.
- Windows의 권장 content minimum은 `Size(960, 640)` logical px로 유지한다. 대상 display의 사용 가능 크기는 `visibleSize ?? size`로 정하고, native minimum은 이 logical size를 넘지 않도록 각 축을 clamp한 `effectiveMinimum`을 계산한다.
- `lib/core/bootstrap.dart`는 display 조회 후 `WindowOptions.minimumSize`에 `effectiveMinimum`을 전달해 최초 표시 전에 적용한다. 초기 적용 직후 같은 값을 `windowManager.setMinimumSize()`로 중복 호출하지 않는다. 초기 bounds도 대상 display의 `visibleSize ?? size`를 넘지 않는다.
- `lib/core/desktop_window_policy.dart` 또는 동등한 순수 helper가 권장 content minimum, `effectiveMinimum`, 초기 bounds clamp를 계산한다. 이 helper는 `window_manager`나 `screen_retriever`를 직접 호출하지 않고 `bootstrap.dart`가 조회한 logical `Size`만 받는다.
- desktop window lifecycle owner는 창이 다른 display로 이동하거나 display 구성이 바뀌는 event를 한 곳에서 처리한다. 같은 순수 policy로 `effectiveMinimum`을 다시 계산하고 이전 적용값과 다를 때만 `windowManager.setMinimumSize(effectiveMinimum)`을 호출한다. minimum이 같더라도 현재 bounds가 새 작업 영역을 벗어나면 별도로 clamp하며, 이미 작업 영역 안이면 불필요하게 이동시키지 않는다. 초기 표시 뒤의 `setMinimumSize()`는 이 runtime display 변경 경로에서만 허용한다.
- 960x640보다 작은 작업 영역에서는 AppBar collapse/title ellipsis와 핵심 탭의 pane 축소·scroll fallback으로 주요 command에 접근할 수 있어야 하며 서버 상태와 로그인/로그아웃 command를 숨기지 않는다.
- 버튼 출현/소멸로 AppBar 높이나 body 위치가 바뀌지 않게 한다.
- Tab으로 그룹 아이콘에 focus하고 Enter 또는 Space로 메뉴를 연다. 메뉴 안에서는 위/아래 방향키로 항목을 이동하고 Enter로 실행한다. 통합 overflow에서는 오른쪽/Enter로 그룹에 진입하고 왼쪽/Esc로 한 단계 돌아가며, 첫 단계의 Esc는 메뉴를 닫는다.
- Esc 또는 바깥 클릭으로 메뉴만 닫으면 원래 그룹 아이콘에 focus를 복원한다. command가 top-level dialog를 열면 그룹 focus 복원을 보류하고 dialog의 초기 control로 focus를 넘긴다.
- `showDialog`, `showGeneralDialog`, route 기반 popup처럼 root `Navigator`에 blocking `ModalRoute`를 추가하는 surface는 호출부마다 lease를 붙이지 않는다. app-scope `NavigatorObserver`가 baseline Home route 위에 활성인 blocking route를 identity set으로 중앙 집계하고 push/pop/remove/replace에서 정확히 갱신한다. `didPop` 즉시 count를 줄이지 않고 reverse transition과 overlay 제거가 완료된 뒤 해당 route identity를 제거해 닫힘 animation 중 단축키가 먼저 복원되지 않게 한다.
- 현재 `PreviewFloatingWindow`의 `_PreviewFloatingRoute`처럼 장시간 유지되는 non-modal `OverlayRoute`는 blocking route count에 포함하지 않는다. `ModalRoute.of(context)?.isCurrent`만으로 차단 여부를 계산하면 floating preview가 표시된 동안 Home 전역 단축키를 계속 오차단하므로 금지한다.
- AppBar menu, `BlockingModelessDialog`, `DbReconnectOverlay`처럼 Navigator blocking route를 추가하지 않고 배경 입력을 막는 surface는 구현 방식이 `OverlayEntry`인지 widget tree인지와 관계없이 공용 non-route blocking lease를 획득한다. lease는 활성 surface 수를 추적하는 참조 계수형 token으로 구현하고 정상 종료·오류 경로에서 정확히 한 번 release한다.
- `blocksGlobalShortcuts`는 `blockingNavigatorRouteCount > 0 || nonRouteBlockingLeaseCount > 0`으로 계산한다. 중첩 surface 하나가 닫혀도 다른 blocking route나 non-route surface가 남아 있으면 차단을 유지하고, 두 count가 모두 0이 된 뒤에만 단축키를 복원한다. 각 전역 handler는 command 분기 전에 이 상태를 확인하고 F1/F2/F3/F5/F12를 소비한다.
- `DbReconnectOverlay`는 재연결 UI가 실제 표시되는 동안 lease를 하나만 유지하고 숨김·복구·취소로 화면이 제거되면 해제한다. 표시 시 취소 button 같은 최초 활성 control로 focus를 옮기고, 닫힐 때 이전 focus가 아직 유효하면 복원하되 그 사이 열린 상위 modal/dialog의 focus를 빼앗지 않는다.
- command item을 선택하면 안정 ID와 trigger focus를 먼저 snapshot한 뒤 1단계/2단계 AppBar popup을 모두 제거하고 menu lease 해제와 renderer의 close 완료 신호를 기다린 다음 owning command를 한 번 호출한다. close 완료 신호는 관련 `OverlayEntry` 제거와 menu focus cleanup이 끝난 뒤 완료하며 고정 delay나 임의 1-frame 대기로 대체하지 않는다. popup widget의 `onTap` 안에서 dialog·탭 이동·toggle·종료 command를 즉시 실행하지 않는다.
- command가 top-level surface를 열면 trigger focus 복원을 보류하고 새 surface의 초기 control로 넘긴다. command가 차단·실패·취소되어 새 surface나 탭 전환이 발생하지 않은 경우에만 살아 있는 원래 trigger 또는 현재 AppBar의 첫 활성 menu control로 focus를 복원한다.
- 권장 960x640과 이보다 작은 대표 display `visibleSize`, 100%, 125%, 150% Windows display scale, 긴 버전 문자열에서 AppBar와 body의 접근성·overflow를 widget test와 Windows integration/screenshot으로 나눠 확인한다.

### 3.3 권한 표시 방식

- 레거시 MainFrm의 비활성 표시를 그대로 복제하지 않고 현재 Flutter 앱의 권한 UX를 따른다.
- 현재 로그인 상태나 사용자 등급 policy에서 표시 대상이 아닌 command는 `visible=false`로 메뉴에서 숨긴다. 로그인/로그아웃 또는 사용자 변경 시 policy를 다시 계산한다.
- dirty, busy, 필수 선택 누락처럼 현재 상태를 해결하면 실행할 수 있는 command만 표시한 채 비활성화한다.
- 비활성 popup item은 명령명 아래 또는 오른쪽에 짧은 `disabledReason`을 직접 표시한다. hover에 의존하는 tooltip을 유일한 안내로 사용하지 않는다.
- `disabledReason`은 popup의 정해진 폭에서 한 줄 ellipsis하고 전체 내용은 tooltip과 semantics label로 보조한다.
- `legacyInactive` command는 inventory와 내부 기능을 유지하되 production 메뉴에서는 숨긴다. 별도 활성화 요구가 있을 때 policy 상수 한 곳에서만 노출을 변경한다.
- 그룹 안에 표시할 command가 하나도 없으면 빈 그룹 아이콘도 숨긴다.
- 로그인/로그아웃 command는 inventory와 controller에 유지하되 `파일/관리` popup에는 렌더링하지 않는다. 현재 상태에 맞는 AppBar 오른쪽 고정 아이콘 하나만 표시한다.
- 종료 command는 AppBar 고정 아이콘으로 중복하지 않고 `파일/관리` popup에 유지한다.
- 비로그인 상태에서는 서버 상태, 로그인과 종료만 사용할 수 있다.
- 일반 사용자 UI의 기존 레거시 정책은 유지한다.
  - 공용라벨관리/자동품목갱신 탭은 숨김.
  - 품목관리 편집 command는 숨김.
  - 조회 가능한 command는 유지.
- `tester01` 테스트 override는 `lib/models/user.dart`의 `User.clientUserTestOverrideId`를 사용하며 메뉴 자체에 별도 예외를 만들지 않는다.

## 4. command 구조

### 4.1 신규 공용 타입

다음 책임을 가진 작은 타입을 추가한다. 파일명은 저장소 구조에 맞춰 조정할 수 있으나 책임은 섞지 않는다.

- `lib/models/app_menu_command.dart`
  - `AppMenuGroup`: file, search, settings.
  - `AppMenuCommandId`: Flutter에서 사용자가 실행하는 owning action별 안정 ID.
  - legacy command ID는 별도 provenance field로 보존한다. 현재 프로젝트에서 이미 분리된 설정 context를 명시적인 command로 노출하는 경우에만 여러 Flutter command가 하나의 legacy command ID를 공유할 수 있다.
  - command metadata는 기본 `label`, icon, optional `shortcutLabel`, 실행 전에 추가 사용자 입력·선택이 필요한지를 나타내는 `requiresFurtherInput`을 포함한다. popup의 `...`와 shortcut 보조 영역은 이 metadata로 렌더링하며 command별 widget 문자열로 중복하지 않는다.
  - `AppMenuCommandState`: visible, enabled, disabledReason.
  - DB나 BuildContext를 참조하지 않는 순수 값 타입.
- `lib/core/app_menu_policy.dart`
  - 로그인 상태, `UserGrade`, 현재 작업 상태로 command 상태를 계산하는 순수 policy.
  - command 실행은 하지 않는다.
- `lib/core/global_shortcut_gate.dart` 또는 동등한 app-scope service
  - baseline Home route 위의 blocking `ModalRoute` identity set과 AppBar menu, `BlockingModelessDialog`, `DbReconnectOverlay` 등 non-route blocking surface가 공유하는 참조 계수형 lease/count를 소유.
  - 메뉴 controller나 특정 Home widget의 lifecycle에 종속되지 않으며 로그인 전 재연결 UI에서도 사용할 수 있음.
  - root `NavigatorObserver`를 제공해 route push/pop/remove/replace와 실제 닫힘 완료를 반영하고 `blocksGlobalShortcuts`를 계산함. baseline Home `PageRoute`와 non-modal `OverlayRoute`는 blocking count에서 제외함.
  - pop 요청과 reverse transition 사이에는 route를 활성 set에 유지하고 `TransitionRoute.completed` 또는 동등한 overlay 제거 완료 신호 뒤에 제거함. 강제 remove/replace와 dispose에서도 stale identity를 남기거나 새 route를 잘못 제거하지 않음.
- `lib/core/desktop_window_policy.dart`
  - 권장 content minimum 960x640과 target `visibleSize ?? size`로 native `effectiveMinimum`과 초기 bounds를 계산하는 순수 policy.
  - display 조회, `WindowOptions`, window 이동 event 같은 plugin 책임은 소유하지 않는다.
- `lib/widgets/app_menu_bar.dart`
  - 넓은/좁은 레이아웃과 popup 표시만 담당.
  - command 상태를 받아 렌더링하고 선택된 command ID를 콜백으로 전달.
- `lib/widgets/app_dialog_command_footer.dart` 또는 동등한 공용 footer
  - 왼쪽 상태/진행 영역과 오른쪽 command 영역의 높이, padding, 버튼 간격을 통일.
  - 명시적 draft 저장 흐름이 있는 신규 관리 dialog는 `취소`/`저장` 또는 기능에 맞는 `취소`/`적용`, 신규 조회 dialog는 `조회 취소`/`닫기` 등 전달된 command만 렌더링.
  - 즉시 적용형·단순 설정형 dialog와 기존 owning dialog는 지속적인 footer command 영역이 필요하지 않으면 footer를 렌더링하지 않는다.
- `lib/core/app_menu_controller.dart` 또는 동등한 controller
  - `HomePage` AppBar와 `HomePageManager` command 실행을 연결.
  - controller attach/detach는 기존 controller pattern을 따른다.
  - 공용 shortcut gate의 `blocksGlobalShortcuts`를 전역 handler에 제공한다. route set과 non-route lease 소유권을 메뉴 controller 안에 가두지 않는다.
  - AppBar popup close 완료와 owning command 실행을 직렬화하는 dispatcher를 제공한다. popup renderer나 item callback이 command를 직접 실행하지 않는다.
  - 화면별 private method를 복제하지 않는다.
- `lib/core/app_menu_dialog_coordinator.dart` 또는 동등한 coordinator
  - 신규 AppBar top-level blocking overlay의 active command ID, `OverlayEntry`, dirty/busy, trigger focus를 한 곳에서 소유.
  - 중첩 확인창·picker를 제외하고 top-level blocking overlay를 앱 전체에서 하나만 허용.
  - dialog 닫기, AppBar command 재진입, OS 종료 요청의 순서를 직렬화하고 overlay queue나 stack을 만들지 않음.

### 4.2 상태 소유권

- `HomePage`가 소유할 command:
  - 로그인, 로그아웃, 종료.
  - 후속 도움말 구현 시 애플리케이션 정보와 외부 링크 실행.
- `HomePageManager`가 소유할 command:
  - 탭 이동.
  - 품목/공용라벨/자동갱신 관련 기능.
  - 라벨출력/저울출력 프린터 설정.
  - 저울 연결 설정.
  - 업무 DB를 사용하는 관리/조회 dialog의 실행과 refresh callback.
  - 기존 메인 탭의 로그아웃/종료 guard. 현재 출력·연결·저장 `writeBusy`, 활성 셀/행 편집 `activeEditing`, 품목·자동갱신·공용라벨 `dirty`를 소유 상태에서 계산하고 HomePage가 호출할 단일 비동기 command API로 노출한다.
- top-level dialog coordinator가 소유할 상태:
  - 현재 열린 신규 AppBar blocking dialog와 originating command/group focus.
  - dialog dirty/busy와 close/exit 요청.
  - 자신이 여는 top-level/nested `OverlayEntry`의 non-route blocking lease. `Navigator` modal은 app-scope observer의 blocking route set으로 감지한다.
  - dialog가 없을 때는 상태를 남기지 않는다.
- 기존 `showDialog`/`showGeneralDialog` owning command는 AppBar와 원래 화면의 호출 경로를 그대로 공유하며 별도 lease를 소유하지 않는다. 동일 dialog를 coordinator 소유 overlay로 바꾸거나 `BlockingModelessDialog`로 다시 감싸지 않는다.
- 각 dialog가 소유할 command:
  - 자기 화면의 편집 draft, 저장, 취소, 행 선택.
- AppBar는 `HomePageManager` private state를 직접 읽지 않는다. controller가 노출하는 command state snapshot 또는 `ValueListenable`을 사용한다.

### 4.3 편집 중 차단

- 메뉴 선택이 brand, label size, 탭, draft context를 바꾸는 경우 기존 `_block...ContextChange` 경로를 재사용한다.
- 읽기 전용 이력 조회까지 일괄 차단하지 않는다.
- 저장 command busy 중 DB를 다시 갱신하거나 같은 데이터를 수정하는 command만 비활성화한다.
- 로그인 상태/등급/`legacyInactive`처럼 현재 policy에서 표시 대상이 아닌 command는 `visible=false`로 처리하고 disabled reason을 만들지 않는다.
- 편집 중, command busy, 필수 context 누락은 서로 다른 disabled reason으로 계산한다.
- disabled reason은 테스트 가능한 순수 policy 결과로 유지하고 popup item 안의 보조 문구로 직접 안내한다. tooltip은 전체 문구 보조에만 사용하고 별도 경고 dialog를 띄우지 않는다.

## 5. 레거시 메뉴 inventory와 포팅 계약

## 5.1 파일/관리 그룹

### 5.1.1 로그인 (`IDM_LOGIN`)

- 레거시: 로그아웃 상태에서만 활성. Flutter에서는 AppBar 오른쪽 고정 로그인 아이콘으로만 표시하고 `파일/관리` popup에는 표시하지 않는다.
- 현행 연결: `HomePage._showStartupDialog()` 또는 DB 연결이 없을 때 `_loginToServerDB()`.
- 새 로그인 화면을 만들지 않는다.
- command inventory와 AppBar 로그인 아이콘은 같은 method를 참조한다.
- 검증:
  - 비로그인 상태에는 AppBar 고정 로그인 아이콘만 표시하고 `파일/관리` popup에는 로그인/로그아웃 command를 렌더링하지 않음.
  - DB 연결 유무에 따른 기존 분기 유지.

### 5.1.2 로그아웃 (`IDM_LOGOUT`)

- 레거시: 로그인 상태에서만 활성. Flutter에서는 AppBar 오른쪽 고정 로그아웃 아이콘으로만 표시하고 `파일/관리` popup에는 표시하지 않는다.
- 현행 연결: `HomePage._onLogout(false)`.
- clean 상태에는 일반 로그아웃 확인창을 새로 추가하지 않고 바로 기존 로그아웃을 진행한다. 확인은 저장하지 않은 작업을 폐기할 때만 표시한다.
- `_doLogout()` 전에 `HomePageManager`의 기존 메인 탭 guard를 호출한다. 라벨 발행, 저울 발행·연결, 품목·자동갱신 저장 같은 `writeBusy`는 로그아웃을 거부하고 기존 owner의 차단 사유를 한 번 안내한다. 품목·자동갱신·저울출력의 활성 편집기는 자동 확정하거나 폐기하지 않고 먼저 편집 완료 또는 취소를 요구한다.
- 품목·자동갱신·공용라벨 중 하나 이상이 dirty면 영향받는 작업을 한 번의 폐기 확인에 합산한다. 화면별 확인창을 연속으로 띄우거나 품목 상태만 확인하고 나머지를 우회하지 않는다.
- 검증: 로그인 상태에는 AppBar 고정 로그아웃 아이콘만 표시한다. clean 로그아웃은 추가 확인 없이 진행되고, busy/activeEditing은 차단되며, dirty일 때만 폐기 확인 후 login log 저장과 상태 초기화가 기존 순서로 실행되는지 확인한다.

### 5.1.3 협력업체 관리 (`IDM_COOP_MANAGE`)

- 레거시 기준: `CMainFrame::OnCoopManage` → `CCooperatorManagerDlg`.
- 권한: system admin 또는 레거시 admin-connect 상태.
- 현행 구현:
  - 기존 `Cooperator` model/조회 API를 먼저 확인한다.
  - 목록, 추가, 이름 수정, 삭제, 저장/취소를 제공하는 `BlockingModelessDialog` 기반 관리 dialog를 구현한다.
  - 신규 CRUD가 필요하면 `CooperatorDAO`를 최소 확장한다.
  - 삭제 종속성은 레거시 DAO가 검사하는 기존 조건만 적용한다.
- DB gate: `BM_COOPERATOR` 실제 컬럼과 레거시 SQL을 확인하기 전 DML SQL을 작성하지 않는다.
- 저장 후 로그인 세션의 현재 협력업체가 영향을 받으면 필요한 cache만 명시적으로 reload한다.

### 5.1.4 거래처 관리 (`IDM_CUST_MANAGE`)

- 레거시 기준: `OnCustManage` → `CCustManagerDlg`.
- 권한: system admin, cooperator admin 또는 확인된 admin-connect 상태.
- 협력업체 선택에 종속된 거래처 목록과 CRUD를 포팅한다.
- 기존 `Customer` model을 우선 사용하고 CRUD가 없을 때만 DAO API를 추가한다.
- `BM_CUSTOMER` 실제 schema와 레거시 DAO의 정렬/중복/삭제 조건을 그대로 따른다.
- 협력업체 관리와 하나의 generic CRUD dialog로 합치지 않는다. 공용 table shell 정도만 재사용한다.

### 5.1.5 지점 관리 (`IDM_MARKET_MANAGE`)

- 레거시 기준: `OnMarketManage` → `CMarketManagerDlg`.
- 최종 활성 조건은 주석이 아니라 `OnEnableManager`의 실제 구현을 따른다.
- 현재 레거시 구현은 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나만 활성이고 `MANAGER_USER`는 제외하므로 이를 visibility policy test로 고정한다.
- 기존 `Market` model/조회 API를 확장해 거래처별 지점 CRUD를 구현한다.
- 현재 로그인 지점 삭제/변경처럼 세션을 무효화할 수 있는 동작은 레거시 확인 없이 자동 로그아웃 같은 보완을 추가하지 않는다. 해당 동작이 레거시에 있으면 그대로 포팅한다.

### 5.1.6 사용자 관리 (`IDM_USER_MANAGE`)

- 레거시 기준: `OnUserManage` → `CUserManagerDlg`, `CUserManagerModel`.
- command 노출 조건은 지점 관리와 같은 실제 `OnEnableManager` 구현을 따른다.
- 현재 레거시 구현은 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나만 활성이고 `MANAGER_USER`는 제외하므로 이를 visibility policy test로 고정한다.
- 권한별 selector 활성 범위를 레거시 model에서 그대로 포팅한다.
  - 협력업체 selector.
  - 거래처 selector와 전체 표시.
  - 지점 selector.
  - 생성 가능한 사용자 등급.
- 기존 `User`/`UserDAO` 조회와 로그인 mapping을 재사용한다.
- 관리용 row/draft가 로그인 `User.instance`와 다른 책임이면 별도 `ManagedUser` model을 작성한다.
- 비밀번호 저장 형식은 레거시 DB 형식을 확인해 그대로 사용한다. 임의 hash migration을 수행하지 않는다.
- 현재 로그인 사용자의 권한이 변경돼도 자동 반영/강제 로그아웃을 추측으로 추가하지 않는다.

### 5.1.7 관리자 복사 (`IDM_ADMIN_COPY`)

- 레거시 기준: `OnAdminCopy`가 main window observer를 통해 복사 흐름을 시작한다. `AdminCopyDlg`, 관련 observer/model/DAO를 끝까지 추적한 뒤 구현한다.
- 원본 관리자와 대상 범위를 명시적으로 선택하고, 복사 대상 데이터 목록을 확인 화면에 표시한다.
- 레거시에서 복사하는 테이블만 복사한다. 편의를 위해 신규 테이블을 추가하지 않는다.
- 여러 테이블 복사는 하나의 transaction으로 처리한다.
- 일부 테이블 복사 성공을 전체 성공으로 표시하지 않는다.
- commit 실패 시 가능한 rollback 후 오류를 그대로 전달하고 선택 상태를 유지한다.
- 대량 payload는 compatibility 100 XML projection을 사용한다.

### 5.1.8 종료 (`ID_APP_EXIT`)

- 현행 `PopScope`와 `LifecycleManager.notifyExitRequested()` 경로를 command API로 추출해 재사용한다.
- `SystemNavigator.pop()`을 메뉴에서 직접 중복 호출하지 않는다.
- 메뉴 종료와 OS 창 닫기는 같은 command에서 `top-level dialog coordinator → HomePageManager 기존 메인 탭 guard → DB 정리 → 실제 종료` 순서로 처리한다.
- 활성 dialog가 write busy면 종료를 거부하고, activeEditing은 먼저 편집 완료 또는 취소를 요구하며, dirty면 현재 overlay 위에서 폐기 확인을 한 번 표시한다. clean dialog는 닫은 뒤 기존 메인 탭 guard로 진행한다.
- 기존 메인 탭의 라벨 발행, 저울 발행·연결, 품목·자동갱신 저장이 busy면 종료를 거부한다. 활성 편집기는 자동 확정하거나 폐기하지 않고 종료를 중단하며, 품목·자동갱신·공용라벨 dirty는 한 번의 폐기 확인에 합산한다.
- dialog와 기존 탭을 모두 통과한 clean 종료에는 일반 확인창을 추가하지 않는다. 메뉴 종료와 OS 창 닫기는 같은 차단 사유, 폐기 확인, DB 정리 순서를 사용하고 단계별 중복 확인창을 띄우지 않는다.

## 5.2 조회/이력 그룹

### 5.2.1 검색 및 치환 (`IDM_SEARCH_AND_REPLACE`)

- 레거시 `OnSearchAndReplace`와 observer/model을 추적해 검색 대상 테이블, column, 치환 범위, 권한을 먼저 확정한다.
- FortuneSheet 내부 검색/치환 기능과 레거시 업무 데이터 검색/치환을 동일 기능으로 간주하지 않는다.
- 업무 데이터 치환이라면 preview, 대상 건수, 적용 확인, transaction 저장 순서를 제공한다.
- 레거시가 수정하는 기존 테이블만 대상으로 한다.
- 전체 DB 문자열을 임의로 검색하거나 범위를 확장하지 않는다.
- 권한은 실제 `OnEnableManager` 구현과 동일하게 적용한다.

### 5.2.2 발행내역 보기 (`IDM_PRINT_LOG`)

- 레거시 기준: `OnPrintLog` → `CPrintLogDlg`, `CPrintLogModel`.
- 현행 `label_print_persistence.dart`의 실제 저장 schema/필드를 기준으로 read model과 DAO를 작성한다.
- 기간, 사용자, 거래처/지점, 품목 등 레거시 filter와 column을 확인해 포팅한다.
- 대형 read-only `BlockingModelessDialog`는 pagination 또는 레거시와 동등한 조회 범위를 사용한다. 근거 없는 무제한 전체 조회를 추가하지 않는다.
- 조회 전용이므로 transaction을 추가하지 않는다.
- 라벨출력/저울출력 양쪽에서 생성된 이력을 현재 저장 schema 기준으로 구분 또는 통합한다.

### 5.2.3 사용자 접속 이력 보기 (`IDM_LOGIN_LOG`)

- `lib/page_login/login_history_page.dart`는 현재 demo row를 생성하므로 완료된 기능으로 간주하지 않는다.
- demo 생성 코드를 제거하고 기존 `BM_LOGIN_LOG`를 조회하는 DAO API를 구현한다.
- `LoginLogDAO`를 조회까지 확장하거나 조회 책임이 다르면 `LoginHistoryDAO`를 작성한다.
- 레거시 `CLoginLogDlg`의 기간, 협력업체/거래처/지점/사용자 filter와 권한별 selector 범위를 포팅한다.
- `LoginHistoryPage`의 demo UI를 재사용할 수 있더라도 AppBar에서는 별도 route로 push하지 않는다. 실제 조회 content를 대형 read-only `BlockingModelessDialog` 안에 배치한다.
- 현재 `LoginHistoryPage`의 일반 `showDatePicker` 호출을 그대로 재사용하지 않는다. 차단형 overlay 위에 표시되는 공용 date picker helper로 교체하고 선택·취소 후 원래 기간 filter로 focus를 복원한다.
- locale 표시 형식은 현 `DateFormat`을 사용하되 DB 저장 문자열 형식은 변경하지 않는다.

### 5.2.4 데이터내용 이력 조회 (`IDM_CONTENT_SAVE_LOG`)

- 레거시 기준: `OnContentSaveLog` → `CContentSaveLogDlg`와 model/DAO.
- 조회하는 로그 테이블과 before/after field를 레거시 SQL로 확인한다.
- 품목, label size, column, 사용자, 변경 시각 filter와 표시 column을 레거시 기준으로 포팅한다.
- 현재 프로젝트의 저장 로그 table이 없거나 기존 schema가 다르면 migration으로 해결하지 않는다. blocker로 기록한다.
- 조회 전용 DAO와 row model만 작성하며 원본 업무 데이터를 변경하지 않는다.

### 5.2.5 공용라벨 수정 이력 보기 (`IDM_COMMON_LABEL_LOG`)

- 레거시 메뉴는 `INACTIVE`다.
- 내부 조회 기능은 `CCommonLabelLog`와 `BM_RICH_LABELSIZE_FORM_LOG` 계열의 실제 schema를 기준으로 구현한다.
- before/after workbook payload를 raw text로만 보여주지 말고 현재 LabelSheet read-only preview로 비교할 수 있게 한다.
- 비교/미리보기는 원본 payload를 수정하지 않는다.
- production 메뉴에서는 `legacyInactive` policy로 숨긴다.
- 별도의 명시 요구로 활성화할 때 command policy 상수 한 곳만 변경하도록 한다.
- 기능 미완성을 숨김 사유로 사용하지 않는다. 내부 기능과 테스트를 완료한 뒤 legacyInactive 정책 때문에 숨겨야 한다.

### 5.2.6 발행 통계 조회 (`IDM_STATUS_PRINT`)

- 레거시 기준: `OnStatusPrint` → `CStatusPrintDlg`, `CStatusPrintModel`.
- 현행 `BM_RICH_STATUS`, `BM_RICH_STATUS_DATA` 저장 계약은 `label_print_persistence.dart`에서 확인한다.
- 레거시의 기간, 사용자 등급, 품목/라벨, 발행 수량 집계 기준을 그대로 포팅한다.
- SQL aggregate가 compatibility 100에서 동작하는지 DAO test로 고정한다.
- 통계 조회는 저장 이력 생성과 분리하며 조회 시 원본 데이터를 갱신하지 않는다.

## 5.3 설정 그룹

### 5.3.1 품목별 정보 편집 (`IDM_EDIT_ITEMINFO`)

- 신규 화면을 만들지 않고 품목관리 탭으로 이동한다.
- 일반 사용자는 현재 Flutter 권한 UX에 따라 command를 표시하지 않는다.
- 현재 편집 중 context가 있으면 기존 탭 변경 차단 흐름을 사용한다.
- 탭 이동 후 현재 brand/label size의 품목 목록과 선택을 유지한다.

### 5.3.2 영양성분 형식추가 (`IDM_NEW_NUTTYPE`)

- 레거시 기준: `OnInsertNewNutTypeDlg` → `CNuttypeManagerDlg`.
- 형식 목록, 추가/수정/삭제, 정렬, 중복 검증을 레거시 dialog/model/DAO에서 확인한다.
- 관련 기존 테이블과 column이 실제 DB에 있는지 확인한 뒤 model/DAO를 작성한다.
- 현재 label column/barcode 모델에 억지로 포함하지 않는다.
- 저장은 형식 parent와 detail이 함께 성공해야 하면 하나의 transaction으로 처리한다.

### 5.3.3 영양성분표 추가 (`IDM_NEW_NUTBOX`)

- 레거시 기준: `OnInsertNewNutboxDlg` → `CNutBoxManagerDlg`.
- 영양성분 형식과 표 instance의 관계를 레거시 model에서 확인한다.
- 형식 관리와 공용 shell은 재사용할 수 있으나 DAO와 draft 책임은 구분한다.
- 레거시가 제공하는 preview가 있으면 현재 LabelSheet/FortuneSheet read-only renderer를 우선 사용한다.
- 임의의 신규 nutrition schema를 만들지 않는다.

### 5.3.4 고정 항목 관리 (`IDM_FIX_COLUMN_MANAGER` / `IDM_FIX_COLUMN_MANAGE`)

- 레거시 기준: `OnFixColumnManage` → `CFixColumnEditDlg`.
- 레거시 메뉴 리소스는 `IDM_FIX_COLUMN_MANAGER(32853)`를 사용하지만 `MainFrm.cpp`의 command/update message map은 `IDM_FIX_COLUMN_MANAGE(32854)`를 사용한다.
- 포팅 전 실제 legacy build의 도달 경로를 확인하고 Flutter inventory에서는 하나의 `fixColumnManage` ID로 정규화한다. 두 ID를 별도 메뉴로 만들지 않는다.
- `SpecalKeyword`, `TColumnSpecial`, 날짜/주원료 같은 현 고정 항목 모델과 레거시 저장 source를 먼저 대조한다.
- 현재 코드 상수만 변경하는 UI로 만들지 않는다. 레거시가 DB에 저장하는 항목만 CRUD 대상으로 한다.
- 시스템 관리자 전용 command로 유지한다.
- schema가 확인되지 않으면 migration 없이 blocker 처리한다.

### 5.3.5 전자저울 관리 (`IDM_SETUP_SCALE`)

- 기존 저울출력의 `showScaleConnectSettingsDialog`, `DbScaleConnectInfoHelper`, `_openScaleConnectSettings()`를 재사용한다.
- AppBar command가 private method를 복제하지 않도록 `HomePageManager` controller에 command를 노출한다.
- 저울 연결 중에는 기존 정책대로 먼저 연결 해제를 요구한다.
- 포트 scan, 연결 retry 같은 추가 보완을 메뉴 포팅 범위에 넣지 않는다.

### 5.3.6 프린터 설정 (`IDM_SETUP_PRINT`)

- 현재 라벨출력과 저울출력에는 서로 다른 session/settings context가 있다.
- 레거시 전역 프린터 설정과 현 화면별 설정의 차이를 확인해 command 동작을 확정한다.
- AppBar `설정` popup에서는 하나의 문맥 의존적인 `프린터 설정` 항목으로 합치지 않고 `라벨출력 프린터 설정`과 `저울출력 프린터 설정`을 명시적인 두 command로 표시한다.
- 두 Flutter command는 레거시 `IDM_SETUP_PRINT`의 포팅 provenance를 공유하되 각각 안정적인 command ID와 label을 가진다.
  - `라벨출력 프린터 설정`은 `_openLabelPrintSettings()`를 호출한다.
  - `저울출력 프린터 설정`은 `_openScaleOutputPrinterSettings()`를 호출한다.
- 현재 탭에 따라 같은 menu item의 의미나 label을 바꾸지 않고, 다른 탭에서 라벨출력 설정으로 자동 기본화하지 않는다.
- 필요한 label size나 session context가 없으면 해당 command를 비활성화하고 popup에 짧은 `disabledReason`을 표시한다.
- 설정 저장은 기존 `LabelPrintSettingsController`/DAO를 재사용한다.
- 별도 전역 printer schema를 만들지 않는다.

### 5.3.7 거래게시판 (`IDM_TRADE_BOARD`)

- 레거시 메뉴는 `INACTIVE`다.
- `CTradeBoardViewDlg`와 데이터 source가 실제로 동작하는지 끝까지 확인한다.
- 기존 DB/URL source가 확인되면 `BlockingModelessDialog` 기반 내부 화면과 model/DAO를 구현한다.
- source가 존재하지 않으면 임의 게시판 테이블이나 외부 서비스를 만들지 않고 blocker로 기록한다.
- 내부 기능이 구현돼도 production 메뉴에서는 legacyInactive로 숨긴다.

### 5.3.8 이더넷 설정 (`IDM_SETUP_ETHENET`)

- 레거시 `OnSetupEthenet`, `CSetupEthenet`, update handler를 기준으로 대상 장치, 저장 위치, 입력값을 확인한다.
- OS 네트워크 어댑터 일반 설정 화면으로 확대 해석하지 않는다.
- 레거시가 라벨 프린터/저울 장치 endpoint를 저장하는 기능이면 그 범위만 dialog/model/DAO로 포팅한다.
- DB 저장이 아니라 로컬 config라면 현 프로젝트의 검증된 로컬 설정 저장 방식을 사용한다.
- 관리자 권한 상승이나 Windows UAC 실행을 앱에서 자동 시도하지 않는다.

### 5.3.9 업데이트 메시지 (`IDM_UPDATE_NOTICE`)

- 기존 `NoticeDAO`와 startup notice 흐름을 재사용한다.
- 메뉴 command는 현재 사용자에게 해당하는 공지 목록 또는 최신 공지를 다시 열어야 한다.
- startup dialog의 private UI를 복제하지 말고 공용 notice dialog/component로 추출한다.
- 읽음 상태를 저장하는 레거시 동작이 확인될 때만 기존 table에 저장한다.
- 업데이트 다운로드/자동 설치를 이번 command에 임의 추가하지 않는다.

### 5.3.10 검색출력모드 (`IDM_SEARCH_PRINT_MODE`)

- 레거시 observer 흐름에서 mode가 영향을 주는 검색 필드, 출력 대상, 키보드 단축키 `F12`를 확인한다.
- 단순 bool toggle이라도 mode state는 AppBar widget이 아니라 HomePageManager/controller가 소유한다.
- popup에서는 command 앞 checkmark로 mode 활성 상태를 표시한다. segmented control은 사용하지 않는다.
- menu item을 선택하면 command ID를 확정하고 AppBar popup과 menu lease가 완전히 닫힌 뒤 controller mode를 변경한다. 메뉴가 닫힌 상태에서 `F12`로 mode가 바뀌어도 다음 popup open 시 controller의 현재 값을 읽어 checkmark를 표시한다.
- 현재 라벨출력 command와 중복되는 부분은 출력 pipeline을 재사용한다.
- 레거시와 다른 자동 검색/자동 발행 규칙을 추가하지 않는다.

### 5.3.11 검색출력 설정 (`IDM_SEARCH_PRINT_SETUP`)

- 레거시 `CSearchPrintSetupDlg`의 입력값, 저장 source, 기본값을 확인한다.
- 검색출력 mode가 사용할 최소 설정만 dialog로 포팅한다.
- 기존 schema/config가 없으면 migration으로 대체하지 않는다.
- 설정 저장 commit 실패 시 dialog 입력 상태를 유지하고 오류를 전달한다.

## 5.4 후속 범위 참고: 도움말 그룹

- 다음 항목은 `파일`부터 `설정`까지인 이번 AppBar 포팅과 완료 판정에 포함하지 않는다.
- 후속 구현 요청이 있을 때 레거시 handler와 URL을 다시 확인한 뒤 별도 `도움말` 그룹으로 추가한다.

### 5.4.1 라벨매니저 정보 (`ID_APP_ABOUT`)

- 앱명, `appVersion`, 빌드 정보, 저작권/지원 정보를 표시하는 작은 dialog를 구현한다.
- 실행 환경의 비밀값, DB credential, 전체 connection string은 표시하지 않는다.

### 5.4.2 라벨지·프린터 구매, 원격지원, ITSNG 자료실

- 레거시 handler에서 실제 URL과 실행 방식을 확인한다.
- 확인된 URL만 `url_launcher` 같은 검증된 방식으로 연다.
- URL을 추측하거나 검색 결과 URL로 대체하지 않는다.
- 외부 브라우저 열기 실패는 오류를 한 번 전달하고 자동 재시도하지 않는다.
- 원격지원 프로그램을 자동 다운로드/실행하거나 권한 상승시키지 않는다.

## 6. 권한 policy 계약

### 6.1 등급 기반 policy

- `systemAdmin`: `SYSTEM_ADMIN_USER`.
- `admin`: `SYSTEM_ADMIN_USER` 또는 `COOP_ADMIN_USER`.
- `managerCommand`: 레거시에서는 `IsSystemAdmin`, `IsCoopAdmin`, `IsAdminConnect`, `IsCoopAdminConnect` 중 하나를 허용한다. Flutter에서는 신뢰 가능한 세션성 관리자 연결 상태가 포팅된 경우에만 뒤의 두 조건을 포함하고, 기본 `UserGrade` 기준은 `SYSTEM_ADMIN_USER` 또는 `COOP_ADMIN_USER`이며 `MANAGER_USER`를 자동 포함하지 않는다.
- `editable`: 현재 메인 업무 편집 정책인 client 제외 등급. 메뉴별 legacy admin policy와 혼동하지 않는다.
- `loggedIn`: 로그인된 모든 등급.
- `always`: 비로그인에서도 허용되는 종료 등.

### 6.2 세션성 관리자 연결 상태

- 레거시에는 `IsAdminConnect`, `IsCoopAdminConnect`, `IsFirstConnectByAdmin`가 있다.
- 현 프로젝트에 대응 상태와 신뢰 가능한 source가 없으면 `UserGrade`만으로 허용 범위를 넓히지 않는다.
- 해당 연결 mode 포팅이 필요하면 별도 session model을 작성하고 로그인 흐름에서만 설정한다.
- query parameter, 사용자 ID 문자열, UI checkbox만으로 관리자 연결 상태를 위조하지 않는다.

### 6.3 policy 테스트 필수 matrix

각 command는 최소 다음 사용자에 대한 enabled 상태를 table test로 고정한다.

- 비로그인.
- system admin.
- cooperator admin.
- manager.
- client.
- `tester01` override client.
- 필요한 경우 admin-connect session.
- command busy/편집 dirty 상태.
- legacyInactive 상태.

## 7. 화면 및 DAO 구현 공통 기준

### 7.1 메뉴 dialog 표시 원칙

- AppBar 메뉴에서 새로 여는 관리·편집·조회 화면은 `OverlayEntry`의 root에 `BlockingModelessDialog`를 두고, 실제 창은 `BlockingModelessDialogFrame`으로 구성한다.
- 공용 wrapper는 구조상 modeless overlay이지만 배경의 pointer/touch와 처리되지 않은 key event를 차단한다. dialog가 열린 동안 배경 탭이나 AppBar command를 조작할 수 있게 우회하지 않는다.
- widget tree의 key 차단만으로 `HardwareKeyboard.instance.addHandler` 전역 handler가 차단된다고 가정하지 않는다. blocking Navigator route 또는 non-route blocking lease가 하나라도 활성화된 동안 `blocksGlobalShortcuts`를 먼저 확인해 F1/F2/F3 탭 이동, F5 새로고침, F12 검색출력 mode를 실행하지 않고 해당 전역 key를 소비한다. dialog 내부의 Tab, Enter, Esc와 셀 편집 shortcut은 이 gate 대상에 포함하지 않는다.
- `DbReconnectOverlay`처럼 widget tree 안에서 `ModalBarrier`를 렌더링하는 기존 전역 차단 UI도 non-route blocking lease에 참여시킨다. pointer barrier만으로 전역 `HardwareKeyboard` handler나 뒤쪽 focus가 차단된다고 가정하지 않는다.
- 기존 품목관리·공용라벨관리·라벨출력·자동품목갱신·저울출력처럼 상시 반복 작업으로 이미 존재하는 메인 탭은 그대로 재사용한다. `품목별 정보 편집`처럼 기존 탭으로 이동하는 command에는 dialog를 중복 생성하지 않는다.
- 로그인, 로그아웃, 종료, 즉시 적용되는 검색출력 mode toggle처럼 별도 편집 화면이 없는 command도 억지로 dialog를 만들지 않는다.
- 이미 동작하는 저울·프린터 설정 등의 `showDialog`/`showGeneralDialog` owning dialog는 기존 command를 그대로 호출한다. app-scope observer가 해당 blocking `ModalRoute`를 중앙 집계하므로 호출부에 lease를 추가하지 않고, 같은 dialog를 `BlockingModelessDialog`로 한 번 더 감싸거나 coordinator 소유로 이전하지 않는다.
- 신규 관리·편집·조회 기능은 별도 `Navigator` route page, 새 메인 탭 또는 Windows native child window로 구현하지 않는다. 예외가 필요하면 장시간 상시 작업이어야 하며 근거와 영향 범위를 `SESSION_HANDOFF.md`에 기록하고 별도 승인 후 진행한다.
- 중첩 확인창·picker를 제외한 신규 AppBar top-level blocking overlay는 command 종류와 관계없이 앱 전체에서 하나만 존재해야 한다. 같은 command나 다른 command가 다시 요청되면 새 entry를 쌓거나 queue하지 않고 기존 dialog에 focus한다.
- 작은 기존 설정 dialog는 현재 크기를 유지하되 화면보다 커지지 않도록 clamp한다.
- 신규 관리·조회 dialog는 보편적인 화면 비율을 강제하지 않는다. `MediaQuery`에서 가로 48px, 세로 64px 이상의 바깥 여백을 뺀 사용 가능 영역과 기능별 content max size 중 작은 값을 사용한다.
- 관리·조회 dialog의 기본 content max size는 현재 라벨 항목 편집창과 같은 1168x720을 기준으로 한다. 더 넓은 결과 column이 실제로 필요할 때만 기능별 max width를 늘리고 100%, 125%, 150% display scale에서 검증한다.
- 제목 bar에는 전체 한글 기능명과 닫기 icon을 표시한다.
- 명시적 draft 저장이나 조회 command 영역이 필요한 신규 dialog는 공용 `AppDialogCommandFooter` 또는 동등한 widget을 사용한다. 왼쪽에는 상태·선택 건수·진행 표시, 오른쪽에는 `취소`/`저장`, `취소`/`적용` 또는 조회 기능에 맞는 command를 두고 footer를 사용하는 dialog끼리 높이, 위치, 간격을 바꾸지 않는다.
- 즉시 적용형·단순 설정형 dialog와 기존 owning dialog는 현재 동작에 지속적인 footer가 없으면 억지로 추가하지 않는다.
- dialog를 열면 첫 번째 활성 filter → 첫 번째 활성 form input → `FortuneTable` → 첫 번째 활성 본문 command 순으로 존재하는 최초 대상을 찾아 초기 focus를 둔다. 공용 wrapper의 자체 focus node에만 focus를 남기지 않는다.
- Tab 순서는 filter → form input → table → 본문 command → command footer 순서로 구성하되 존재하는 영역만 포함하고 비활성 control은 건너뛴다. form-only dialog도 마우스 없이 첫 입력부터 footer 또는 닫기까지 이동할 수 있어야 한다.
- Esc 우선순위는 `활성 셀 편집 취소 → FortuneTable 다중 선택 해제 → dialog 닫기 요청`이다. 셀 편집이나 다중 선택이 Esc를 처리한 경우 dialog를 닫지 않는다. 일반 단일 행 선택은 별도 취소 단계로 간주하지 않고 Esc가 바로 dialog 닫기 요청으로 이어진다.
- dialog 닫기 요청 시 clean 상태는 즉시 닫고 dirty 상태만 폐기 확인을 거친다. Enter는 활성 셀 편집 확정에 사용하며 dialog 전체 저장 command를 실행하지 않는다.
- 초기 focus, Esc/닫기, focus 반환을 dialog마다 복제하지 않는다. 필요한 `initialFocusNode` 또는 callback/intent가 공용 wrapper에 없으면 `blocking_modeless_dialog.dart`의 공용 API와 test를 먼저 확장한다.
- top-level dialog가 닫히면 coordinator가 originating AppBar 그룹 또는 overflow icon으로 focus를 복원한다. responsive collapse나 권한 변경으로 trigger가 사라졌으면 현재 AppBar의 첫 활성 menu control을 fallback으로 사용한다.
- 신규 dialog의 dirty/busy 상태는 coordinator를 통해 `LifecycleManager.notifyExitRequested()` 흐름에 참여한다. dialog별 observer가 각자 종료 확인창을 띄우지 않는다.
- coordinator가 신규 dialog 종료 가능 여부를 승인한 뒤에는 `HomePageManager`의 단일 기존 메인 탭 guard를 호출한다. HomePage나 AppBar가 manager의 private busy/editing/dirty 값을 각각 읽거나 별도 확인창을 만들지 않는다.
- 저장·삭제 transaction busy 중에는 중복 실행과 닫기를 비활성화한다.
- footer가 없는 즉시 적용형·단순 설정형 dialog는 busy를 시작한 control 가까이에 spinner와 필요한 짧은 상태 문구를 표시하고 관련 입력과 command만 비활성화한다. 진행 표시 없이 닫기만 비활성화해 화면이 멈춘 것처럼 보이게 하지 않는다.
- 읽기 전용 조회 busy 중에는 `조회 취소` 또는 닫기 경로를 유지한다. DB Future 자체를 취소할 수 없으면 overlay를 닫은 뒤 늦게 도착한 결과가 폐기된 dialog나 새 조회 상태에 반영되지 않게 한다. 자동 retry나 복구 저장소는 추가하지 않는다.
- dialog 안에서 확인·경고뿐 아니라 date/time picker 등 중첩 `Navigator` modal을 열 때 일반 `showDialog`, `showDatePicker`, `showTimePicker`를 직접 호출하지 않는다. root overlay의 현재 차단창 위에 삽입되는 `showBlockingModelessOverlayDialog` 또는 이를 기반으로 한 공용 picker helper를 사용한다.
- dropdown처럼 별도 overlay surface가 필요한 control은 현재 프로젝트의 private `_ModelessDropdownField`/`_DialogDropdown` 구현을 참고하되, 신규 화면을 만들기 전에 root overlay 위 표시와 dialog 경계 clamp를 담당하는 공용 overlay-safe control로 추출한다. 화면별 `OverlayEntry` 구현을 복제하지 않는다.
- 중첩 확인창이나 picker를 닫으면 이를 연 원래 control 또는 table cell로 focus를 복원한다.
- 저장 또는 commit 실패 시 dialog와 draft를 유지하고 오류를 한 번 전달한다. 성공 시 필요한 cache를 갱신한 뒤 overlay를 제거하고 controller, listener, focus node를 dispose한다.

### 7.2 FortuneTable 사용 원칙

- 관리 목록, 이력, 통계, 검색 결과처럼 동일한 column 구조의 row가 반복되는 화면은 `FortuneTable<T>`로 구현한다.
- 신규 화면에서 Flutter `DataTable`, `Table`, row별 `ListView` 조합 또는 기능별 자체 table widget으로 대체하지 않는다.
- column은 `FortuneTableColumn<T>`으로 선언하고 공용 header, column resize, 정렬, 선택, checkbox, 편집 callback 중 필요한 기존 API를 재사용한다.
- 관리 화면의 row draft와 저장 상태는 dialog/controller가 소유한다. `FortuneTable` 내부에 DAO 호출이나 업무 저장 로직을 넣지 않는다.
- 조회 화면은 `FortuneTable`을 read-only로 구성하고 filter, 조회 command, 합계/건수는 table 바깥의 owning dialog가 관리한다.
- 필요한 공용 table 기능이 없으면 개별 화면에 wrapper나 중복 구현을 추가하기 전에 `third_party/fortune_sheet/lib/src/fortune_table.dart`의 공용 API로 확장하고 `test/fortune_table_test.dart`에서 검증한다.
- `FortuneSheet`/LabelSheet는 workbook·라벨 시트 편집 또는 read-only 시트 미리보기에만 사용하며, 일반 관리 목록과 조회 결과 table 용도로 사용하지 않는다.
- 단일 상세값, key-value form, 선택 항목이 없는 짧은 안내 목록처럼 반복 column table이 아닌 UI는 `FortuneTable` 적용 대상이 아니다.
- 레거시 동작을 `FortuneTable`로 표현할 수 없는 기술적 blocker가 확인되면 임의 대체 table을 만들지 말고 원인과 필요한 공용 API를 `SESSION_HANDOFF.md`에 기록한 뒤 해결한다.

### 7.3 관리 dialog

- 운영 도구 성격에 맞게 밀도 높은 `FortuneTable` + 기능에 맞는 명확한 command 영역을 사용한다.
- 장식용 카드 중첩, hero, 과도한 animation을 사용하지 않는다.
- 행 단위 CRUD를 지원하는 관리 dialog는 그 기능이 실제 지원하는 추가·수정·삭제 command만 테이블 상단 toolbar 또는 측면 command rail에 항상 보이는 icon button으로 제공하고 tooltip을 표시한다.
- 지원하지 않는 row command는 비활성 button으로 남기지 않고 렌더링하지 않는다. 관리자 복사, 이더넷 설정, 검색출력 설정처럼 row CRUD가 아닌 dialog에 CRUD toolbar/rail을 억지로 추가하지 않는다.
- 행 CRUD dialog에서 우클릭 context menu를 제공할 수 있지만 visible command와 동일한 기능의 보조 경로여야 한다. 지원되는 row command를 우클릭 메뉴에서만 제공하지 않는다.
- 명시적 draft 저장 흐름이 있는 신규 관리 dialog는 공용 footer를 사용하고 row command를 넣지 않는다. 왼쪽 상태/진행과 오른쪽 `취소`/`저장` 또는 `취소`/`적용`을 배치한다.
- 즉시 적용형·단순 설정형 관리 dialog는 footer 없이 title bar 닫기와 본문 command만 사용할 수 있다.
- 추가/수정은 draft에서 수행하고 저장/취소를 명시한다.
- 삭제는 레거시 확인 문구와 종속성 검사를 따른다.
- 저장 성공 후 해당 목록과 필요한 app cache만 reload한다.
- dialog별 overlay 소유권과 open/close command를 한 controller에서 관리한다.

### 7.4 조회 dialog

- filter, 조회 button, read-only `FortuneTable`, 건수/합계 영역을 제공한다.
- 최초 자동 조회 여부와 기본 기간은 레거시를 따른다.
- 조회 중 중복 요청만 막고 일반적인 자동 retry는 추가하지 않는다.
- 조회 중에도 `조회 취소` 또는 닫기 command를 사용할 수 있어야 하며 닫힌 dialog에 늦은 결과를 적용하지 않는다.
- 빈 결과는 정상 상태로 표시하고 오류와 구분한다.
- export가 레거시에 있거나 명시 요구가 있을 때만 추가한다.

### 7.5 오류 처리

- DAO 오류를 빈 목록이나 `false`로 바꾸지 않는다.
- DB 오류는 원인 문자열을 보존해 command 계층으로 전달한다.
- 차단형 overlay가 열린 동안 실패는 dialog 내부 inline 상태 또는 `showBlockingModelessOverlayDialog`로 한 번 알리고 draft를 유지한다. 뒤쪽 `ScaffoldMessenger` snackbar를 오류 전달 경로로 사용하지 않는다.
- snackbar는 차단형 overlay가 제거된 뒤 표시하는 비차단 성공 알림 또는 overlay 밖의 기존 화면 알림에만 사용한다. 사용자 확인이나 action이 필요한 오류를 snackbar로 표시하지 않는다.
- 같은 오류를 DAO, controller, UI에서 각각 중복 로그로 남기지 않는다.
- 권한 부족은 DB command 실행 전 policy에서 차단한다.

## 8. 구현 단계

### Phase 0. inventory와 command contract 고정

1. 파일/검색/설정의 Flutter owning action마다 `AppMenuCommandId`, group, label, icon, optional `shortcutLabel`, `requiresFurtherInput`, legacy command ID provenance, permission, legacyInactive를 순수 table로 작성한다. 하나의 legacy ID를 공유하는 명시적 context 분리 command는 같은 provenance와 서로 다른 안정 ID를 갖는다.
2. 모든 command의 레거시 handler와 현 구현 상태를 test fixture로 고정한다.
3. 권한 matrix unit test를 먼저 작성한다.
4. 아직 기능이 없는 command도 ID를 예약하되 실제 menu에는 기능 완료 시점에만 연결한다.

완료 기준:
- 파일/검색/설정 command 누락 없음.
- 권한별 visible/enabled 상태와 legacyInactive 숨김이 테스트로 고정됨.

### Phase 1. AppBar shell과 기존 기능 연결

1. AppBar 그룹 아이콘과 좁은 화면의 2단계 overflow를 구현한다. desktop 초기화에는 권장 content minimum 960x640과 대상 display의 logical `visibleSize`로 `effectiveMinimum`을 계산하는 순수 window policy를 두고 `WindowOptions.minimumSize`에 적용한다.
2. login/logout/exit를 기존 HomePage command에 연결한다.
3. 품목관리 탭 이동을 연결한다.

- [ ] `PreviewFloatingWindow`의 non-modal `OverlayRoute`는 shortcut gate에서 제외되고 그 위의 실제 modal/popup만 차단함.
- [ ] AppBar menu 선택은 command ID/trigger snapshot → 전체 popup close → menu lease release/renderer close 완료 → owning command 1회 실행 순서를 따르고 결과에 맞게 focus를 인계 또는 복원함.
- [ ] `DbReconnectOverlay` 등 widget-tree blocking surface도 shortcut gate lease, 최초 focus, 조건부 이전 focus 복원에 참여함.
- [ ] `requiresFurtherInput` command의 popup 표시명에만 `...`를 사용하고 단순 공지·안내 dialog에는 사용하지 않으며, 실제 활성 shortcut만 명령명과 분리된 오른쪽 보조 영역과 semantics에 표시함.
- [ ] 권장 content minimum 960x640, target `visibleSize`로 clamp한 native `effectiveMinimum`, 초기 bounds, display 이동과 100%/125%/150% 배율에서 AppBar·핵심 탭 주요 command 접근성이 검증됨.
- [ ] 초기 native minimum은 `WindowOptions.minimumSize`로 한 번 적용되고 display 변경 시 계산값이 달라진 경우에만 runtime `setMinimumSize`가 적용되며 bounds는 새 작업 영역 밖일 때만 clamp됨.
- [ ] 통합 overflow는 3개 그룹의 2단계 구조이며 높이 clamp·scroll·focus reveal·단계별 Esc가 검증됨.
- [ ] `파일/관리`는 종료만 남는 상태에서도 관리자 전용으로 오인되지 않는 중립 아이콘을 사용함.
- [ ] 라벨출력/저울출력 프린터 설정은 명시적인 별도 command이며 현재 탭에 따라 같은 항목의 의미를 바꾸지 않음.
- [ ] 편집/busy 차단 정책 확인.
- [ ] 기존 기능이면 owning command 재사용.
- [ ] 미구현 기능이면 필요한 model/DAO와 `BlockingModelessDialog` 기반 화면 구현.

- [ ] top-level blocking overlay는 전역 coordinator가 하나만 소유하고 서로 다른 command 요청도 stack/queue하지 않음.
- [ ] top-level dialog dirty/busy가 메뉴 종료와 OS 창 닫기의 `LifecycleManager` 흐름에 참여하고 확인창을 중복 표시하지 않음.
- [ ] 기존 메인 탭의 출력·연결·저장 busy와 activeEditing은 로그아웃/종료를 차단하고, 품목·자동갱신·공용라벨 dirty는 한 번의 폐기 확인에 합산되며 clean 상태에는 일반 확인창이 없음.

## 11. 금지 사항

- 동작하지 않는 메뉴를 활성 상태로 먼저 노출하지 않는다.
- 좁은 화면 overflow에 모든 command를 하나의 긴 평면 목록으로 표시하지 않는다.
- 미구현 command를 snackbar `준비 중`으로 완료 처리하지 않는다.
- 레거시 INACTIVE command를 임의 활성화하지 않는다.
- schema가 없다는 이유로 앱 시작 시 table/column을 자동 생성하지 않는다.
- DB migration script를 추가하거나 실행하지 않는다.
- generic catch에서 DB 오류를 성공/빈 결과로 바꾸지 않는다.
- commit 실패를 무시하거나 자동 retry하지 않는다.
- rollback이 가능하지 않은 상태에서 억지 rollback command를 반복하지 않는다.
- 관리 기능을 하나의 거대한 dialog/model/DAO에 합치지 않는다.
- HomePage와 HomePageManager에 같은 업무 command를 중복 구현하지 않는다.
- 메뉴 widget에서 직접 SQL을 실행하지 않는다.
- popup 표시명의 `...`나 shortcut을 command별 문자열에 직접 합치거나, `blocksGlobalShortcuts` 확인 없이 화면 전역 `HardwareKeyboard` handler를 추가하지 않는다.
- `Navigator` modal 호출부마다 shortcut lease를 수동 추가하지 않는다. route 상태가 바뀌지 않는 AppBar menu·`OverlayEntry`·widget-tree blocking surface에만 non-route blocking lease를 사용하고, 중첩 surface가 남아 있는데 하나의 종료만으로 차단을 해제하지 않는다.
- AppBar popup item의 `onTap`에서 owning command를 직접 실행하거나 popup/menu lease가 남은 상태에서 dialog·탭 이동·toggle·종료를 시작하지 않는다.
- native minimum을 target display의 logical `visibleSize ?? size`보다 크게 설정하지 않는다. 초기 표시 직후 같은 minimum을 중복 적용하거나 display 변경 없이 `setMinimumSize()`로 덮어쓰지 않는다. runtime 호출은 target display 변경으로 계산값이 달라진 경우에만 허용한다. 작은 display를 지원하려고 서버 상태·로그인 command를 숨기지 않는다.
- 비활성 popup item의 실행 불가 사유를 hover tooltip으로만 제공하지 않는다.
- 행 CRUD dialog의 지원 command를 우클릭 context menu에서만 제공하지 않는다.
- 지원하지 않는 CRUD command를 비활성 toolbar/rail button으로 표시하지 않는다.
- footer가 필요한 신규 dialog마다 footer 높이, padding, 정렬, 버튼 간격을 개별 구현하지 않는다.
- 즉시 적용형·단순 설정형 또는 기존 owning dialog에 공용 footer를 억지로 추가하지 않는다.
- footer 없는 dialog에서 진행 표시 없이 닫기와 입력만 비활성화하지 않는다.
- 신규 관리·편집·조회 command를 별도 route page, 신규 메인 탭 또는 Windows native child window로 구현하지 않는다.
- `BlockingModelessDialog` 안에서 일반 `showDialog`, `showDatePicker`, `showTimePicker`로 중첩 modal을 열지 않는다.
- 신규 AppBar top-level blocking overlay를 command별로 따로 쌓거나 queue하지 않는다.
- 신규 dialog dirty/busy를 확인하지 않고 메뉴 종료나 OS 창 닫기를 진행하지 않는다.
- HomePage나 AppBar가 `HomePageManager`의 기존 출력·연결·저장 busy, activeEditing, dirty private 상태를 각각 복제해 판정하거나 clean 로그아웃에 일반 확인창을 추가하지 않는다.
- 차단형 overlay가 열린 동안 뒤쪽 `ScaffoldMessenger` snackbar로 오류나 사용자 action을 요구하지 않는다.
- 관리·조회용 반복 행 table을 `DataTable`, `Table`, row별 `ListView` 또는 기능별 자체 table widget으로 새로 구현하지 않는다.
- 테스트를 위해 운영 사용자 권한이나 운영 DB row를 수정하지 않는다.
- 사용자 소유 변경 `lib/core/app.dart`를 이 작업에 포함하지 않는다.
- release build, installer, 원격 push는 명시 요청 없이 수행하지 않는다.

## 12. 최종 완료 상태

전체 포팅 완료 시 다음 상태여야 한다.

- AppBar에는 폭에 따라 그룹 아이콘 3개 또는 overflow 메뉴 1개가 표시된다.
- Windows 창은 권장 content minimum 960x640과 target display의 logical `visibleSize`를 기준으로 native `effectiveMinimum`을 정하고, 작은 고배율 display에서도 AppBar와 핵심 탭의 주요 command에 접근할 수 있다.
- 초기 native minimum은 표시 전에 한 번 적용한다. runtime에는 target display 변경으로 `effectiveMinimum`이 달라진 경우에만 새 minimum을 적용하고, bounds는 minimum 변화와 무관하게 새 작업 영역 밖일 때만 보정한다.
- 통합 overflow는 3개 그룹의 2단계 구조와 화면 높이 clamp·scroll·키보드 reveal을 제공한다.
- AppBar title은 메뉴 collapse 후에도 공간이 부족하면 한 줄 ellipsis되고 서버 상태와 현재 로그인/로그아웃 command는 유지된다.
- AppBar menu는 키보드만으로 열기·이동·실행·닫기가 가능하다. 메뉴만 취소하면 원래 trigger에 focus가 복원되고 top-level dialog를 실행하면 dialog 내부로 focus가 인계된다.
- AppBar menu는 추가 입력·선택이 필요한 `requiresFurtherInput` command의 popup 표시명에만 `...`를 사용하고 실제 활성 shortcut을 오른쪽 보조 영역과 semantics에 표시한다.
- app-scope observer에 blocking `ModalRoute`가 있거나 AppBar menu·신규 `OverlayEntry`·`DbReconnectOverlay` 같은 non-route blocking surface의 참조 계수 lease가 활성인 동안 `HardwareKeyboard` 전역 F1/F2/F3/F5/F12의 뒤쪽 command 실행을 막고 마지막 차단 surface의 정상·오류 종료 후에만 복원한다. 지속형 floating preview `OverlayRoute`는 차단하지 않는다.
- AppBar menu command는 전체 popup과 menu lease가 닫힌 뒤 정확히 한 번 실행되며, 새 surface를 열면 그 안으로 focus를 인계하고 열지 못하면 유효한 AppBar trigger로 복원한다.
- 서버 상태와 로그인/로그아웃 영역은 기존 위치와 동작을 유지한다.
- 파일/검색/설정의 모든 레거시 command가 inventory와 권한 policy에 존재한다.
- 현재 동작 기능은 중복 구현 없이 같은 command로 연결된다.
- 미구현 기능은 실제 `BlockingModelessDialog` 기반 화면, model/DAO, DB 계약과 테스트를 갖는다.
- 기존 핵심 탭 이동과 기존 owning 설정 dialog를 제외한 신규 관리·편집·조회 화면은 공용 차단형 overlay dialog로 일관되게 열린다.
- 신규 AppBar top-level blocking overlay는 전역 coordinator가 하나만 소유하고 dirty/busy·종료 요청·AppBar focus 복원을 함께 관리한다.
- 로그아웃·메뉴 종료·OS 창 닫기는 신규 dialog coordinator와 기존 메인 탭 guard를 순서대로 거친다. 기존 출력·연결·저장 busy와 activeEditing은 종료를 막고, 여러 dirty 상태는 한 번만 확인하며, clean 상태에는 일반 확인창을 추가하지 않는다.
- 차단형 dialog의 모든 중첩 modal/picker는 현재 dialog 위에 표시되고, form-only dialog도 첫 활성 입력에 초기 focus가 설정된다.
- 모든 관리 목록과 조회 결과의 반복 행 table은 공용 `FortuneTable`을 사용한다.
- 명시적 draft 저장 흐름이 있는 신규 관리 dialog는 공용 command footer를 사용하고, 즉시 적용형·단순 설정형과 기존 owning dialog는 필요한 command 영역만 유지한다. 행 CRUD dialog만 실제 지원 command의 visible toolbar/rail을 사용한다.
- footer 없는 busy 상태는 실행 control 가까이에 표시되고, 차단형 overlay 오류는 inline 또는 공용 overlay dialog로 전달된다.
- legacyInactive 기능은 내부 구현 완료 후 production 메뉴에서 숨김 상태를 유지한다.
- DB schema는 변경되지 않는다.
- 저장 오류는 호출자에게 전달되고 가능한 transaction만 rollback된다.
- 과도한 fallback, retry, 자동 보정 없이 레거시 업무 동작과 현 UI 구조가 일관되게 결합된다.
