작성일: 2026-07-12
최종 정리: 2026-07-14

0. 최우선 범위 제한

이 절은 자동 검토, 구현, 테스트 작성과 문서 해석에 적용하는 최우선 규칙이다. 아래 절을 넓게 해석할 수 있거나 다른 요구와 충돌하면 이 절을 우선한다.

- 이 문서는 구현할 요구사항을 확정한 작업지시서다. 문서에 없는 위험을 가정해 요구사항을 추가하거나 기존 요구를 더 엄격하게 만들지 않는다.
- 검토는 현재 문서가 요구한 UI/CRUD를 구현할 수 없는 명백한 모순, 현재 코드 또는 지원 DB와 직접 충돌하는 내용, 잘못된 테이블·컬럼·레거시 의미만 확인한다.
- 새 하위 시스템, 범용 framework, capability 상태기계, trigger fingerprint·metadata 인증, DDL 경합 방어, 전역/table-wide lock, connection generation cache, journal·checksum, exact-set 검증 체계, 범용 commit reconciliation·자동 복구 상태, 품목 저장·삭제 재설계를 추가하지 않는다.
- DB 처리는 현재 프로젝트의 transaction 안에서 parameterized CRUD를 실행한다. 커밋 전 오류는 예외를 전달하고 가능한 경우 rollback하며 working copy를 유지한다. 이 다이얼로그의 커밋 결과 불명확 또는 커밋 후 재조회 실패는 중복 저장을 막기 위해 안내 후 닫는다.
- 레거시 프로그램이 현재 사용하는 DB schema를 그대로 사용한다. 이 기능을 위해 table, column, index, constraint, view, trigger 또는 stored procedure를 생성·변경·삭제하거나 data migration을 실행하지 않는다.
- 기존 설치 DB 사이의 선택 column/table 차이는 필요한 object의 존재 여부를 읽기 전용으로 확인한 뒤, 이미 존재하는 object만 참조하는 미리 작성된 SQL 중 하나를 선택해 처리한다. 없는 column을 같은 SQL text의 조건문 안에서 참조하지 않는다.
- 테스트는 이 문서의 사용자 흐름, validation, CRUD 성공, 중간 오류 rollback만 검증한다. 가상 schema 변경, DDL 동시 실행, 미지원 DB 조합이나 장애 복구 상태를 위한 테스트를 추가하지 않는다.
- 더 강한 보완이 필요해 보여도 현재 구현이나 완료를 막지 않는다. 사용자가 별도로 승인하기 전에는 이 문서의 요구사항으로 취급하지 않는다.
- 확인된 문제가 없으면 추가 개선안을 만들지 말고 `현재 작업 범위에서 구현을 막는 문제 없음`으로 검토를 끝낸다.

1. 목적

공용라벨관리의 `사용 항목 > 항목 편집`에서 현재 라벨 크기에 사용할 항목을 추가, 수정, 삭제, 정렬하고 DB에 저장할 수 있는 `라벨 항목 편집` 다이얼로그를 구현한다.

기능과 데이터 의미는 레거시 `CColumnEditDlg`, `CColumnEditModel`, `CColumnSetupMainDlg`, `CUserColumnEditDlg`, `CCommonLabelModel::SaveColumns`, `CColumnDAO`를 기준으로 한다. UI는 현 프로젝트의 라벨 설정 다이얼로그와 공용 테이블 pattern을 따른다.

핵심 원칙은 다음과 같다.

- 현재 라벨 크기의 사용 항목과 고객별 사용자 항목 사전은 서로 다른 편집 단위다.
- 다이얼로그의 테이블은 `SwipeActionTable` 계열 공용 위젯을 재사용한다.
- 사용 항목 상세 속성은 별도 모달이 아니라 왼쪽 속성 패널에서 편집한다.
- 속성 편집, 순서 변경, 사용자 항목 설정은 상호 배타적으로 관리한다.
- 사용 항목과 사용자 항목 사전은 각각 독립 working copy로 편집하고 다이얼로그 하단 저장 전에는 DB를 변경하지 않는다.
- 하단 저장은 사용 항목의 신규, 수정, 삭제, 순서, 보조 테이블 및 사용자 항목 사전 변경 statement를 하나의 SQL Server transaction으로 반영한다.
- transaction의 시작, commit과 rollback은 기존 `DbClient.transaction()` 경로가 소유한다. DAO SQL에서 transaction을 중첩하지 않는다.
- 신규 컬럼 ID는 레거시의 마지막 행 재조회 대신 같은 저장 batch의 `OUTPUT INSERTED`로 매핑한다.
- 저장 command가 지정한 변경만 적용하며 unrelated 행이나 속성을 전체 working copy 값으로 덮어쓰지 않는다.
- 레거시 source, 실행 파일, 설정과 공유 DB trigger/schema는 수정하지 않는다.
- 저장 결과는 레거시가 읽는 기존 `BM_RICH_*`, `BM_GS1_*`, `BM_UPDATE_*` table과 column 의미로만 기록한다. 앱 전용 row, 별도 mapping table 또는 레거시가 해석하지 못하는 식별값을 DB에 남기지 않는다.
- 항목 편집은 바코드·QR·GS1·이미지의 데이터 의미와 생성 규칙을 소유하고, 라벨 에디터의 객체는 연결할 항목과 위치·크기·회전 같은 시각 표현을 소유한다. 같은 설정을 두 화면에서 독립적으로 중복 저장하지 않는다.
- DB 저장과 후속 재조회가 성공한 경우에만 화면과 cache를 교체한다. 커밋 전 오류는 가능한 rollback 뒤 working copy를 유지하고, 커밋 후 복구 오류는 저장 여부를 안내한 뒤 재저장을 차단한다.

2. 현재 프로젝트 기준점

2.1 UI

- `lib/page_home/common_label_manage.dart`의 사용 항목 `항목 편집` callback은 아직 비어 있다.
- 현재 사용 항목 표는 `TColumn.datas`를 읽는다.
- 기존 공용라벨 표 layout은 유지하고 새 편집 다이얼로그 내부 테이블만 `SwipeActionTable` 계열로 구현한다.
- 라벨 설정 다이얼로그의 `BlockingModelessDialog`, `BlockingModelessDialogFrame`, reorder rail과 footer pattern을 재사용한다.
- 공용라벨 시트 또는 품목 draft에 미저장 변경이 있으면 기존 상태를 잃지 않도록 항목 편집기 진입과 저장을 차단한다. 필요한 dirty/busy boolean만 기존 상위 callback 경계로 전달하며 workbook queue나 저장 체계는 재설계하지 않는다.
- 현 라벨 에디터의 바코드·이미지 객체는 각각 `barcodeObjectId`와 `imageObjectId`로 항목 keyword에 연결되고 객체 자체가 geometry를 저장한다. 바코드 형식의 기본값은 `ItemCodeDataResolver`가 항목 type과 `TColumn.barcodeType`에서 계산하며, 기존 `preserveTemplateBarcodeFormat` metadata는 라벨별 형식 고정에 사용한다.
- 현재 바코드 후보를 keyword의 `barcode`/`qrcode` 포함 여부로 추정하고 이미지 후보에 모든 keyword를 넣는 helper는 항목 type 기준으로 교체한다.

2.2 모델과 DAO

- `lib/models/column.dart`의 `TColumn`은 레거시 컬럼 속성 대부분을 보유한다.
- `TColumnDAO.selectByLabelSizeId()`는 main, 누락검사, GS1 info와 GS1 contain 관계를 조회한다.
- 현재 `TColumnDAO`에는 항목 편집용 insert/update/delete transaction API가 없다.
- 고정 항목 분류·후보와 고객별 사용자 항목 모델/DAO가 없다면 기존 model pattern으로 추가한다.
- DB 조회 모델을 직접 mutate하지 않고 편집 전용 draft와 working copy를 사용한다.

4. 다이얼로그 공통 구조

4.1 표시

- `BlockingModelessDialog(child: BlockingModelessDialogFrame(...))`를 사용한다.
- 제목은 `라벨 항목 편집`이다.
- 화면 크기에 맞는 최대 크기와 세 영역이 유지되는 최소 크기를 둔다.
- 확인·경고·실패 알림은 공용 blocking overlay dialog를 사용한다.
- 다이얼로그가 열린 동안 바깥 공용라벨 화면 입력을 차단한다.

4.2 배치

왼쪽부터 다음 순서로 배치한다.

1. 사용 항목 속성 패널
2. 사용 항목 테이블
3. 중앙 command rail
4. 고정/사용자 후보 영역

후보 영역 상단에는 `고정 항목`/`사용자 항목` 전환 control을 둔다. 고정 항목이면 분류 dropdown을, 사용자 항목이면 고객별 사용자 항목 표를 표시한다.

command rail에는 휴지통과 왼쪽 화살표 icon button을 세로로 두고 tooltip을 제공한다.

4.3 메인 footer

- 오른쪽에 `취소`, `저장` 버튼을 둔다.
- `저장`은 working copy가 원본과 다르고 validation을 통과했을 때만 활성화한다.
- 미저장 변경이 있는 `취소`, 닫기 icon과 Esc는 폐기 확인을 거친다.
- 전용 mode 또는 DB command 실행 중에는 메인 footer를 비활성화한다.

5. 편집 상태

5.1 mode

- `normal`: 선택, 속성 편집, 후보 추가·삭제, 메인 저장
- `reorder`: 사용 항목 순서 변경 전용
- `userItemEdit`: 고객별 사용자 항목 사전 편집 전용

단일 enum을 source of truth로 사용한다. DB 조회·저장 중에는 busy 상태로 중복 command와 닫기를 막는다.

5.2 working copy

최소한 다음 상태를 둔다.

- `originalColumns`: dialog open 시점 immutable snapshot
- `workingColumns`: 화면에서 편집하는 목록
- `deletedColumnIds`: 기존 DB 행 중 삭제한 ID
- `selectedColumnKey`: 안정적인 행 identity
- `propertyBaseline`, `propertyDraft`, `propertyDirty`
- `pendingInitialApplyColumnKeys`: 신규 특수 타입 중 최초 적용 전 행
- 사용자 항목 mode의 별도 original/working/deleted/selected 상태
- reorder mode 진입 시점 순서 snapshot

기존 행 identity는 `columnId`, 신규 행은 dialog session에서 생성한 `draftColumnKey`를 사용한다. 선택, drag/drop, reorder와 삭제 후 선택 복원에 list index를 identity로 사용하지 않는다.

`initialApplyRequiredTypeCodes`는 레거시와 같이 바코드, 이미지, QR, GS1 AI, GS1 바코드다. 이 타입의 신규 행은 기본값 그대로라도 최초 `적용`을 완료해야 메인 저장할 수 있다.

dirty는 다음 의미만 구분한다.

- `propertyDirty`: 속성 panel에서 아직 적용하지 않은 변경
- `workingDirty`: 적용된 속성, 추가, 삭제 또는 순서 변경
- `userItemDirty`: 사용자 항목 mode의 변경
- `orderDirty`: reorder mode 진입 snapshot 대비 변경

속성 `적용`과 reorder mode `저장`은 working copy만 변경한다. DB 저장은 메인 footer `저장`에서만 실행한다.

6. 사용 항목 테이블

- `SwipeActionTable<LabelColumnDraft>` 또는 동등한 공용 wrapper를 사용한다.
- 신규 상태, 키워드, 항목명, 종류, 제목, 표시 여부를 표시한다.
- 좌상단 교차 영역에 순서 변경 icon을 둔다.
- QR/사용자 정의/barcode text link/GS1 관계가 참조하는 행은 상태 icon과 tooltip으로 표시한다.
- 참조 계산은 행 표시, keyword 변경 경고와 삭제 경고가 공유하는 하나의 순수 함수를 사용한다.
- 행 click은 해당 행을 선택하고 속성 패널을 갱신한다.

`propertyDirty` 또는 최초 적용 전 신규 행이 있는 상태에서 선택 변경, 후보 추가, 삭제, mode 전환, 메인 저장·취소와 닫기를 요청하면 공용 pending edit guard를 먼저 실행한다. 사용자가 취소하지 않으면 원래 요청을 실행하지 않는다.

삭제는 다음과 같이 처리한다.

- 기존 행은 `deletedColumnIds`에 기록하고 working copy에서 제거한다.
- 신규 행은 working copy에서만 제거한다.
- 참조 중인 행은 영향 경고 후 확인한 경우에만 삭제한다.
- GS1 포함 목록에서도 삭제 행 identity를 제거한다.
- button 삭제와 휴지통 drop은 같은 handler를 사용한다.
- drag payload에는 source 종류와 안정 key를 넣는다.

7. 속성 패널

7.1 공통 동작

- 선택 행이 없으면 빈 상태를 표시하고 입력을 비활성화한다.
- 패널 하단에 `취소`, `적용`을 둔다.
- `취소`는 property draft를 baseline으로 복원한다.
- `적용`은 validation을 통과하고 `propertyDirty`이거나 최초 적용이 필요할 때 활성화한다.
- 최초 적용 전 특수 타입 신규 행에서 취소하면 해당 신규 행 자체를 제거한다.
- 신규 draft는 하나의 factory에서 레거시 기본값으로 만든다.

신규 기본값에는 최소한 체크디지트 사용=true, 바코드 번호 표시=true, 표시=false, QR 하단 문자열 표시=false, QR 정렬=left, QR font size=10, QR scale=100, GS1 AI=`01`, format option=-1, line check/size/rotate=0과 나머지 빈 문자열·0·false를 명시한다.

7.2 공통 속성과 validation

- 키워드
- 항목명
- 항목 종류
- 제목
- 표시 여부
- 누락 키워드 검사 사용 여부

규칙은 다음과 같다.

- 키워드와 항목명은 필수다.
- 신규 또는 keyword 변경 행이 최종 목록에 대소문자 무시 중복을 만들 수 없다.
- `ITEMNAME`, `ELEMENT`, `SWEIGHT`, `SPRICE`는 일반 사용 항목의 예약 keyword다.
- 기존 DB에 이미 존재하는 untouched 중복·예약 keyword 행은 무관한 수정·삭제·정렬을 막거나 자동 정리하지 않는다.
- 키워드, 항목명, 제목은 CP949 round-trip과 각각 100바이트, 50바이트, 20바이트 한계를 검사한다.
- 종류는 `TColumnType.datas`의 값만 허용한다.
- keyword 변경 대상이 다른 항목에서 참조 중이면 영향 경고를 표시한다.
- 기본↔QR 전환은 레거시처럼 QR 생성 방식과 사용자 정의 data/text를 초기화한다.
- GS1 AI가 다른 타입으로 바뀌면 GS1 바코드 contain 관계에서 제거한다.
- 나머지 공통·타입별 값은 레거시처럼 보존한다.

7.3 타입별 속성

현재 `TColumn` field와 DB column을 기준으로 다음 속성을 제공한다.

- 기본/문자: 일반 또는 사용자 정의 data, 자동 증가, 검색 출력, 사용자 정의 text
- 제조일자/유통기한/시간: 날짜·시간 타입, 자동 증가, 날짜 범위
- 바코드: 종류, 폭, 높이, 체크디지트, 번호 표시, text link, 타임바코드, 자동 증가, 사용자 정의 text, 비율 조절, line check/size, 회전
- 이미지: 폭, 높이
- QR/2D: 종류, 생성 방식, 사용자 정의 data와 하단 text, pixel size, scale, 하단 text 표시, 정렬, font/size, 자동 증가
- GS1 AI: AI code, format option, GS1 code 표시
- GS1 바코드: 종류, 폭, 높이, 포함할 GS1 AI 목록

항목 속성과 라벨 객체 속성은 다음처럼 구분한다.

- 바코드 종류, QR 생성 방식·data/text, GS1 AI와 contain 관계, 체크디지트와 번호 표시 여부는 항목 속성이다.
- 레거시 1D 바코드의 `비율 조절` checkbox와 수치는 별도 DB column이 아니라 각각 `RICH_SHOW_QRCODE_TEXT`와 `RICH_QRTEXT_FONTSIZE`를 재사용한다. 현 `TColumn.checkMode`와 `barFontSize`는 이 두 영속값에서 파생되는 편집 상태이며 별도 저장 field나 schema를 추가하지 않는다.
- 품목별 이미지 파일명은 레거시와 같이 이미지 타입 column content이며 품목관리에서 선택한다.
- 항목의 바코드/이미지 폭·높이는 레거시 DB 호환값으로 유지한다. 현 라벨 시트에 배치된 객체의 최종 위치·크기·회전은 라벨 객체 geometry를 사용한다.

레거시 validation과 경고를 유지한다.

- 바코드/이미지/GS1 바코드의 폭 또는 높이 0은 경고한다.
- QR pixel size 또는 scale 0은 경고한다.
- GS1 AI code는 필수다.
- 체크디지트 또는 타임바코드 변경 영향을 경고한다.
- 사용자 정의 QR data가 비었거나 나트륨 구성이 완성되지 않으면 적용하지 않는다.
- 자유 입력 문자열은 레거시 운영 DB의 기존 column 길이와 CP949 round-trip을 검사한다. 확인한 길이는 코드 상수와 테스트에 반영하되 DB column을 늘리거나 type/collation을 변경하지 않는다.
- 수치는 정수 parsing, DB 타입 범위, 정의된 enum과 레거시 필수 조건만 검사한다. 임의의 UX 범위를 추가하지 않는다.

공통 입력과 타입별 editor widget을 분리한다. editor widget은 draft 변경 callback만 반환하고 DB를 직접 호출하지 않는다.

7.4 라벨 에디터의 바코드·이미지 연결

항목 편집 구현과 함께 기존 라벨 에디터의 바코드·이미지 삽입/수정 다이얼로그를 다음 규칙으로 보정한다. 기존 FortuneSheet 객체와 저장 metadata를 재사용하고 workbook format, DB schema 또는 출력 engine을 새로 만들지 않는다.

공통 규칙은 다음과 같다.

- 기술적인 `ID` label은 `연결 항목`으로 바꾸고 dropdown에는 `항목명 (#KEYWORD) · 형식`을 표시한다. 내부 저장값은 기존 `barcodeObjectId`/`imageObjectId` keyword를 유지한다.
- `연결 안 함`을 선택한 고정 객체는 `barcodeObjectId`/`imageObjectId` extra field를 저장하지 않고 기존 Fortune 객체 `id` 자동 생성 규칙만 사용한다. 편집 재로드 시 연결 extra field 없음 또는 빈 값은 고정, 비어 있지 않고 현재 후보와 일치하면 연결, 비어 있지 않지만 후보에 없으면 연결 끊김으로 판정한다.
- 연결 끊김 객체는 저장된 keyword를 유지하고 임의 항목으로 바꾸지 않는다. 항목 keyword 변경 시 workbook 객체 ID를 자동 변경하는 기능은 추가하지 않는다.

바코드 다이얼로그는 다음과 같이 동작한다.

- 연결 후보는 keyword 문자열이 아니라 `TYPE_BARCODE`, `TYPE_QR_CODE`, `TYPE_GS1_BARCODE`인 사용 항목만 포함한다. `TYPE_GS1_AI`는 GS1 바코드의 source이므로 직접 바코드 객체 후보에 넣지 않는다.
- 연결형 바코드는 선택 항목의 type, `barcodeType`, QR 생성 규칙과 GS1 관계에서 값과 기본 형식을 가져온다. 값은 직접 편집하지 않고 현재 preview 품목의 결과 또는 `품목 데이터로 출력 시 생성` 상태를 표시한다.
- 연결형의 형식은 기본적으로 읽기 전용이다. 기존 `preserveTemplateBarcodeFormat`을 사용하는 `이 라벨에서 형식 고정` checkbox를 선택한 경우에만 형식 dropdown을 활성화하고, 이 설정은 DB 항목 속성을 변경하지 않는다.
- 연결형 1D 바코드의 번호 표시는 항목의 `showBarcodeNum`을 사용하며 다이얼로그에서는 현재 값을 읽기 전용으로 표시한다. Fortune 객체의 기존 `barcodeShowText`는 연결형의 독립 설정으로 사용하지 않고 품목별 materialize 시 항목 값으로 갱신한다.
- 고정 바코드는 연결 항목 없이 형식, 고정 값과 1D 번호 표시를 직접 입력한다.
- 가로·세로·회전은 연결 여부와 무관하게 라벨 객체 속성으로 편집한다. 1D 표시 글꼴은 DB 항목 속성이 아니므로 라벨 객체가 소유하고 연결형에서도 편집할 수 있다. 막대 높이와 적용 가능한 표시 control은 1D 형식에서만 표시하며 QR/Data Matrix 같은 2D 형식은 module scale 등 적용 가능한 control만 표시한다.
- 연결형 preview용 임시 값은 품목 column content로 저장하지 않는다. 실제 품목 미리보기와 출력용 workbook 전처리는 기존 `ItemCodeDataResolver` 결과와 `labelSheetBarcodeRenderer`를 사용해 `barcodeText`, 기본 형식과 객체 `src`를 함께 다시 생성한다. 출력 engine은 materialize된 기존 FortuneImage를 그대로 출력한다.
- `이 라벨에서 형식 고정`은 편집 시 기존 `preserveTemplateBarcodeFormat` 값을 읽고 저장 시 보존한다. 이 값이 true일 때만 template format을 resolver에 전달하며 GS1 바코드도 같은 규칙을 사용한다.

이미지 다이얼로그는 다음과 같이 동작한다.

- `품목 이미지`와 `고정 이미지`를 segmented control로 구분한다.
- 품목 이미지의 연결 후보는 `TYPE_IMAGE`인 사용 항목만 포함한다. 파일 선택은 표시하지 않고 현재 preview 품목의 BMP 또는 `품목 데이터로 출력 시 지정` placeholder를 보여준다.
- 고정 이미지는 항목에 연결하지 않고 파일을 직접 선택한다. 삽입뿐 아니라 수정에서도 파일 교체를 제공한다.
- 가로·세로·비율 잠금·회전은 두 종류 모두 라벨 객체 속성으로 편집한다.
- 고정 이미지 수정에서 새 파일을 선택하면 `src`, 원본 크기와 파일 표시값을 갱신하고 선택하지 않으면 기존 `src`를 유지한다.
- 품목 이미지 column content가 비었거나 `C:\ITS\LabelManager\bmp files`에서 해당 BMP를 찾지 못하면 라벨 편집 화면에는 명확한 placeholder를 표시하되, 품목 미리보기와 실제 출력용 workbook 전처리에서는 `TYPE_IMAGE` 연결 객체를 `sheet.images`에서 제외한다. 연결 extra field가 없는 고정 이미지는 제외하지 않는다.

8. 고정 항목 후보

- 분류는 `BM_RICH_FIX_COL_TYPE`에서 레거시와 같은 DB 반환 순서로 조회한다.
- 후보는 `BM_RICH_FIX_COLUMN`에서 선택한 분류 ID로 조회한다.
- 후보 표에는 keyword, 항목명과 종류를 표시한다.
- 분류 변경 시 후보 선택을 해제한다.
- 선택 없음, 중복 keyword 또는 예약 keyword 후보는 추가를 비활성화하고 이유를 표시한다.
- 화살표와 drag/drop 추가는 같은 handler와 신규 draft factory를 사용한다.
- 같은 drag gesture로 중복 추가하지 않도록 in-flight guard를 둔다.

9. 사용자 항목 후보와 설정

9.1 후보

- 현재 로그인 customer ID의 `BM_RICH_CUST_COLUMN`을 조회한다.
- keyword, 항목명과 종류를 표시한다.
- 화살표 또는 drag/drop으로 현재 라벨 크기의 신규 사용 항목 draft를 만든다.
- 사용자 항목 사전 행과 사용 항목은 이후 자동 동기화하지 않는다.
- 예약 keyword는 사전에는 표시·저장할 수 있지만 일반 사용 항목으로 추가하지 못한다.

9.2 설정 mode

- 사용자 항목 표의 편집 icon으로 `userItemEdit` mode에 진입한다.
- 진입 시 별도 original과 working copy를 만든다.
- 사용자 항목 영역 외 control과 메인 footer를 비활성화한다.
- 표 아래에 `사용자 항목 설정`, `취소`, `적용` footer를 둔다.
- 추가 icon은 마지막에 신규 빈 행을 만들고 첫 입력 cell에 focus한다.
- keyword와 항목명은 inline 입력, 종류는 DB `BM_RICH_COLUMN_TYPE` 순서의 dropdown이다.
- keyword는 대문자로 정규화하고 ASCII 영문·숫자만 허용하며 최대 100자다.
- 항목명은 필수이며 CP949 50바이트 이하다.
- 신규 또는 keyword 변경 행이 사전 안에 새 중복을 만들 수 없다.
- 기존 untouched 중복은 무관한 name/type 수정과 삭제를 막지 않는다.
- 기존 행 삭제는 delete ID로 기록하고 신규 행 삭제는 working copy에서만 제거한다.
- 사전 행 삭제는 이미 복사된 사용 항목을 삭제하지 않음을 확인 문구에 표시한다.
- 적용은 검증 후 신규/수정/삭제를 다이얼로그의 사용자 항목 working copy에 반영하고 normal mode로 돌아간다.
- 다이얼로그 하단 취소는 적용된 변경이 있으면 폐기 확인 후 두 working copy를 버리고, 하단 저장은 두 변경 command를 하나의 transaction으로 처리한다.
- 최종 저장 실패 시 다이얼로그와 두 working copy를 유지한다.

10. 사용 항목 순서 변경

- 좌상단 순서 변경 icon으로 `reorder` mode에 진입한다.
- 진입 전 pending property edit guard를 처리하고 현재 순서를 snapshot으로 보관한다.
- 행 drag와 오른쪽 위/아래 rail을 제공한다.
- drag와 button은 같은 reorder 함수를 사용한다.
- 이동 후 선택은 안정 key를 유지한다.
- `취소`는 snapshot 순서로 복원한다.
- `저장`은 순서를 1부터 연속 값으로 정규화해 working copy에만 적용한다.
- 실제 DB 저장은 메인 footer `저장`에서 실행한다.
- 공용 `SwipeActionTable`에 필요한 API가 없으면 안정 row key, typed drag payload와 header action만 최소 확장한다. 기존 index callback 의미와 기본 동작은 유지한다.

11. 메인 저장

11.1 저장 전 검증

- 미적용 property와 최초 적용 전 신규 특수 행이 없어야 한다.
- 모든 행의 keyword와 항목명이 유효해야 한다.
- 신규/keyword 변경 행의 중복과 예약 keyword를 검사한다.
- 문자열의 CP949 round-trip과 DB byte 한계를 검사한다.
- 타입별 필수값, enum과 수치 parsing을 검사한다.
- GS1 contain 대상이 현재 working copy에 존재하고 GS1 AI 타입인지 검사한다.
- 삭제, 신규와 수정 identity가 중복되지 않아야 한다.
- 기존 column의 labelSizeId가 현재 편집 대상과 같아야 한다.
- 최종 order를 1부터 연속 값으로 만든다.

해당 라벨 크기에 기존 품목이 있으면 신규 content 생성, 컬럼 삭제와 속성 변경 영향을 설명하는 최종 확인을 표시한다. 삭제 또는 keyword 변경은 라벨 내용이나 출력 참조에 영향을 줄 수 있다는 일반 경고를 포함한다. workbook 참조 분석 API는 추가하지 않는다.

11.2 저장 결과

- dialog는 DAO와 cache를 따로 조작하지 않고 상위 save callback 하나를 호출한다.
- callback은 사용 항목과 사용자 항목 statement의 통합 transaction과 현재 label size 재조회를 순서대로 실행한다.
- 성공하면 기존 label size 재조회 경계로 `TColumn.datas`와 관련 화면/cache를 갱신하고 dialog를 닫는다.
- DB transaction 전/중 오류는 사용자에게 알리고 working copy를 유지한다. 커밋 완료 후 결과 해석·재조회 실패 또는 커밋 결과 불명확은 별도 안내 후 dialog를 닫아 재저장을 막는다.
- 활성 transaction은 가능한 경우 rollback하며 실패를 성공으로 처리하거나 자동 재시도하지 않는다.

12. DB 모델과 DAO

12.1 모델

- `LabelColumnDraft`: `TColumn` 저장 속성, 기존 columnId 또는 신규 draft key, order와 신규 여부
- `LabelColumnEditSession`: original/working/deleted/selection/property 상태
- `FixedColumnType`, `FixedColumnCandidate`
- `CustomerColumnCandidate`, `CustomerColumnDraft`, `CustomerColumnEditSession`
- `CustomerColumnSaveCommand`: customerId, 편집 시작 시점 원본 snapshot, 신규, 수정, 삭제
- `LabelColumnSaveCommand`: labelSizeId, 편집 시작 시점 원본 snapshot, 신규 draft, 변경된 기존 행, delete ID, 최종 order와 GS1 관계
- `LabelColumnSaveResult`: 신규 draft key와 실제 column ID mapping

DTO는 immutable하게 만들고 widget 상태나 전역 목록을 직접 참조하지 않는다. UI 임시 상태를 `TColumn`에 추가하지 않는다.

12.2 조회

- 현재 사용 항목은 기존 `TColumnDAO.selectByLabelSizeId()`를 사용·확장한다.
- 고정 분류는 `BM_RICH_FIX_COL_TYPE`, 고정 후보는 `BM_RICH_FIX_COLUMN`에서 조회한다.
- 사용자 항목은 현재 customer ID 조건으로 `BM_RICH_CUST_COLUMN`에서 조회한다.
- 고정 항목과 사용자 항목 후보는 독립적으로 조회하며 한쪽 실패가 다른 쪽의 정상 조회·편집을 차단하지 않는다.
- 종류는 `TColumnType.datas`를 사용하고 미초기화면 먼저 조회한다.
- 문자열은 현 DAO의 CP949→NVARCHAR 변환 규칙을 사용하되 저장 대상 값이 잘리지 않게 조회한다.
- `BM_RICH_COL_CONTENT.RICH_EDITABLE`이 있는 DB는 실제 값을 조회하고, 없는 DB는 SQL에서 해당 식별자를 참조하지 않은 채 결과 alias만 `0 AS RICH_EDITABLE`로 반환한다. 두 경우 모두 `TColumnContent`의 row shape는 유지한다.

12.3 사용자 항목 저장

- insert/update/delete를 parameterized statement로 만들고 사용 항목 statement와 같은 `DbClient.transaction()`에서 실행한다.
- transaction 안에서 현재 고객 항목의 행 집합과 저장 command의 원본 snapshot을 먼저 비교하고, 편집 시작 후 추가·수정·삭제가 있으면 충돌 오류로 중단한다. snapshot 조회에는 `UPDLOCK, HOLDLOCK`을 적용해 검사 후 실제 DML까지 같은 customer key range를 보호한다.
- update/delete는 customerId와 custColumnId를 함께 조건으로 사용한다.
- 필수 update/delete affected row가 1이 아니면 오류를 발생시킨다.
- 신규/keyword 변경 행이 같은 customer 사전에 새 중복을 만드는지 저장 전에 검사한다.
- SQL 문자열 보간을 사용하지 않는다.
- 적용 후 사용자 항목 후보는 메모리 working copy를 사용하고, 최종 저장 성공 후 다음 dialog 진입에서 재조회한다.
- 커밋 전 오류는 호출자에게 전달하고 가능한 rollback 뒤 mode와 working copy를 유지한다.

12.4 사용 항목 저장

신규 ID와 보조 테이블 처리를 위해 `returnsRows=true`인 하나의 parameterized SQL batch를 `DbClient.transaction()`으로 실행한다. batch의 마지막 결과만 신규 draft key와 실제 ID mapping으로 반환한다.

처리 순서는 다음과 같다.

1. 현 DB driver가 scalar parameter만 지원하므로 save command를 JSON 문자열 parameter로 전달하고 기존 품목 저장과 같이 `OPENJSON`으로 table variable에 투영한다.
2. 현재 labelSizeId의 main 저장 속성, 누락검사와 GS1 info/contain 값을 원본 snapshot과 비교해 편집 시작 후 동시 변경을 거부하고, update/delete 대상 `BM_RICH_COLUMN`의 소유권을 확인한다. main/check/GS1 info/contain 조회에는 `UPDLOCK, HOLDLOCK`을 사용해 존재하지 않는 보조 행의 key range까지 실제 DML 완료 전까지 보호한다. 레거시 nullable 값은 기존 `TColumnDAO`와 같은 0·빈 문자열·GS1 기본값으로 정규화한다.
3. 신규 `BM_RICH_COLUMN`을 한 행씩 insert하고 `OUTPUT INSERTED.RICH_COLUMN_ID`를 draft key와 함께 내부 mapping table에 기록한다.
4. 신규 column의 `BM_RICH_CHECK_COLUMNS`는 keyword, name과 draft의 최종 `useMissingKeywordCheck` 값을 사용해 생성한다. 기존 DB의 `BM_RICH_COLUMN`에 `RICH_USE_MISSING_KEYWORD_CHECK`가 있으면 같은 최종값을 main row에도 기록하고, 없으면 해당 식별자를 INSERT SQL에 포함하지 않는다. 해당 label size의 `BM_RICH_COL_MIN`에 `ELEMENT` 기준행이 없으면 레거시와 같이 column ID 0 의미, keyword `ELEMENT`, name `주원료`, order 0, `RICH_MIN_CHECK=0`으로 한 번 생성한다. 신규 column의 min 행도 `RICH_MIN_CHECK=0`으로 생성한다.
5. 신규 column마다 현재 label size의 기존 `BM_RICH_ITEM`에 없는 `BM_RICH_COL_CONTENT` 조합을 빈 data로 생성한다. `RICH_EDITABLE`이 있는 DB용 INSERT는 0을 함께 기록하고, 없는 DB용 INSERT는 해당 column 이름을 SQL text에 포함하지 않는다. trigger가 먼저 생성한 행은 `NOT EXISTS` 조건으로 중복하지 않는다.
6. 기존 DB에 `BM_UPDATE_ITEM`과 `BM_UPDATE_COL_CONTENT`가 모두 있으면 레거시와 같이 신규 column의 빈 update content를 생성한다. 둘 중 하나가 없으면 이 단계만 생략하며 table을 생성하거나 migration을 요구하지 않는다. 존재/부재별로 미리 작성된 SQL을 사용한다.
7. 기존 `BM_RICH_COLUMN`은 실제 변경된 속성만 update한다.
8. keyword, name 또는 누락검사 값이 바뀐 기존 column은 `BM_RICH_CHECK_COLUMNS`의 대응 값을 갱신한다. `BM_RICH_COLUMN.RICH_USE_MISSING_KEYWORD_CHECK`가 있는 DB에서는 누락검사 변경 시 main row도 같은 값으로 갱신하고, 없는 DB용 UPDATE SQL은 해당 column을 참조하지 않는다.
9. `BM_RICH_COL_MIN` 기존 column 행은 keyword/name/order가 바뀐 경우만 갱신하고 `RICH_MIN_CHECK`는 보존한다. label size별 `ELEMENT` 기준행은 유지한다.
10. GS1 AI는 `BM_GS1_COLUMN_INFO`를 insert/update/delete하고 GS1 바코드 contain 관계는 최종 working copy와 일치하도록 해당 main column 관계만 교체한다.
11. 삭제 column은 `BM_RICH_COL_CONTENT`, check, min, GS1 info와 contain 양쪽 참조를 정리한다. 기존 DB에 update content 또는 `BM_RICH_STATUS_DATA`가 있으면 레거시와 같이 해당 행 정리와 삭제일 `GETDATE()` 갱신을 수행하고, 없으면 그 단계만 생략한 뒤 `BM_RICH_COLUMN`을 삭제한다. 없는 table/column을 참조하거나 생성하지 않으며 선택 종속행과 status 이력 0건은 정상으로 허용한다.
12. 잔존 column의 `RICH_COLUMN_ORDER`를 최종 목록의 1부터 연속 값으로 반영한다.
13. 소유권이 있는 main update/delete와 개수가 정해지는 필수 DML의 affected row를 확인한다. 불일치하면 오류를 발생시킨다.
14. 신규 draft key mapping의 누락·중복을 확인하고 mapping 결과를 반환한다.

레거시 trigger가 order를 변경할 수 있으므로 최종 order는 DAO가 명시적으로 다시 적용한다. 신규 ID를 `SelectLastNRecord()` 또는 마지막 N개 행 조회로 추정하지 않는다.

저장 시작 전 필요한 기존 object의 존재 여부는 `OBJECT_ID`와 `COL_LENGTH` 같은 read-only metadata 조회로 한 번 확인한다. 결과는 SQL variant 선택에만 사용한다. 지원에 필요한 core `BM_RICH_COLUMN` 또는 레거시 column 속성이 없으면 migration을 시도하지 않고 오류를 알리며 저장하지 않는다. schema 확인 SQL과 저장 SQL 어디에도 `CREATE`, `ALTER`, `DROP`, trigger enable/disable 또는 기존 data 보정 DML을 넣지 않는다.

커밋 전 오류는 예외를 전달하고 기존 driver transaction 경로가 가능한 rollback을 수행하며 working copy를 유지한다. 신규 ID mapping 개수는 SQL transaction 안에서 검증한다. 커밋 후 결과 해석·재조회 실패와 `DbCommitOutcomeUnknown`은 별도 상태로 전달하고, dialog는 재저장을 막기 위해 안내 후 닫는다.

13. 오류와 재진입

- dialog open, 조회와 저장 command의 중복 실행을 막는다.
- busy 중 닫기, mode 전환, drag/drop과 행 선택을 막는다.
- DB 연결·SQL·validation·affected row 오류는 진행 표시를 닫고 사용자에게 알린다.
- 커밋 전 저장 실패는 dialog와 working copy를 유지하고 cache를 교체하지 않는다. 커밋 결과 불명확 또는 커밋 후 화면 갱신 실패는 중복 저장 방지 안내 후 dialog를 닫는다.
- 저장 성공 후 widget이 dispose됐으면 setState하지 않는다.
- 로그에는 operation, labelSizeId, customerId, 변경 개수와 성공/실패만 기록하고 실제 payload는 기록하지 않는다.
- 로그를 저장 분기나 결과 판정에 사용하지 않는다.

14. 권한과 진입 조건

- 선택된 label size가 없거나 편집 권한이 없으면 진입할 수 없다.
- 품목 draft 또는 공용라벨 시트가 dirty이면 먼저 저장하거나 취소하도록 안내한다.
- 관련 상위 command가 busy이면 진입과 저장을 차단한다.
- dialog를 열 때 labelSizeId와 customerId를 immutable input으로 전달한다.
- dialog open 뒤 상위 상태가 바뀔 수 있으므로 저장 직전에 권한, 대상 ID, dirty와 busy를 다시 확인한다.

17. 완료 조건

- 선택한 label size의 `라벨 항목 편집` dialog를 열 수 있다.
- 사용 항목과 후보 테이블, 속성 panel, 추가·삭제·정렬과 사용자 항목 설정이 문서대로 동작한다.
- 바코드와 이미지 항목의 데이터 의미·생성 규칙은 항목 편집에서 저장되고 라벨 에디터 객체는 연결 대상과 geometry를 저장한다.
- 1D 바코드 비율 조절은 레거시 DB의 `RICH_SHOW_QRCODE_TEXT`/`RICH_QRTEXT_FONTSIZE`에 저장하며 별도 schema나 저장 field를 추가하지 않는다.
- 라벨 에디터의 바코드 후보는 세 barcode type, 이미지 후보는 `TYPE_IMAGE`만 사용하며 기술 ID 대신 항목명·keyword·형식을 표시한다.
- 연결 extra field 없음/일치/불일치로 고정형·연결형·연결 끊김을 구분하고 새 workbook metadata를 추가하지 않는다.
- 연결 바코드는 항목 설정을 기본 형식과 1D 번호 표시로 사용하고 명시적인 라벨별 형식 고정만 객체 형식을 유지한다. 고정 바코드는 값·형식·1D 번호 표시를 라벨 에디터에서 직접 설정하며 표시 글꼴은 라벨 객체가 소유한다.
- 품목 이미지와 고정 이미지를 구분하고, 연결 이미지의 품목 값·BMP가 없을 때 template 이미지를 실제 출력에 사용하지 않는다. 고정 이미지는 수정 시 파일을 교체할 수 있다.
- 신규 특수 타입은 최초 적용 전 저장할 수 없고 일반 변경은 pending guard를 거친다.
- 사용자 항목 사전과 실제 사용 항목은 각각 독립 working copy로 편집되고 다이얼로그 하단 취소/저장에서 함께 폐기하거나 확정된다.
- 최종 저장은 하나의 parameterized transaction에서 사용자 항목 사전 변경과 사용 항목 main, order, check/min/content 및 GS1 관계를 함께 반영한다.
- 신규 column ID는 `OUTPUT INSERTED`로 draft key에 정확히 매핑된다.
- 신규 column은 JSON parameter에서 투영되며 draft의 최종 누락검사 값, 없는 경우의 레거시 `ELEMENT` 기준행과 기존 item의 빈 content를 저장하고 삭제 column은 직접 소유한 종속 데이터를 정리한다.
- `RICH_EDITABLE`, update content와 status object가 없는 기존 DB에서도 migration 없이 해당 단계만 생략하거나 기존 column용 SQL로 저장한다.
- 커밋 전 저장 오류는 예외로 전달되고 가능한 rollback 뒤 working copy와 기존 cache가 유지된다. 커밋 후 오류는 중복 저장을 막기 위해 안내 후 dialog를 닫는다.
- 저장 성공 후 전체 column 재조회 결과가 공용라벨, 품목관리와 preview에 반영된다.
- 레거시 source, 실행 환경과 공유 DB schema/trigger는 변경하지 않으며 설치 SQL·DDL·data migration을 실행하지 않는다. 저장 결과는 레거시 프로그램이 기존 table/column 의미로 다시 조회할 수 있다.
- 관련 model/widget/DAO/integration test와 정적 분석이 통과한다.
