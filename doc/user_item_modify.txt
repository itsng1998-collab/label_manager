공용라벨관리 라벨 항목 편집기 구현 작업지시서
작성일: 2026-07-12

1. 목적

공용라벨관리의 `사용 항목 > 항목 편집`에서 현재 라벨 크기에 사용할 항목을 추가, 수정, 삭제, 정렬하고 DB에 저장할 수 있는 `라벨 항목 편집` 다이얼로그를 구현한다.

기능과 데이터 의미는 레거시 `CColumnEditDlg`, `CColumnEditModel`, `CColumnSetupMainDlg`, `CUserColumnEditDlg`, `CCommonLabelModel::SaveColumns`, `CColumnDAO`를 기준으로 한다. UI는 레거시 화면을 그대로 복제하지 않고 현 프로젝트의 라벨 설정 다이얼로그와 공용 테이블 패턴에 맞춘다.

핵심 원칙은 다음과 같다.

- 현재 라벨 크기의 실제 사용 항목과 고객별 사용자 항목 사전을 서로 다른 편집 단위로 관리한다.
- 다이얼로그의 두 테이블은 라벨 설정에서 사용하는 `SwipeActionTable` 계열 공용 위젯을 재사용한다.
- 사용 항목의 상세 속성은 별도 모달을 열지 않고 왼쪽 속성 패널에서 편집한다.
- 속성 편집, 순서 변경, 사용자 항목 설정은 동시에 열리지 않는 상호 배타 상태로 관리한다.
- 사용 항목 DB 저장은 신규, 수정, 삭제, 순서, 보조 테이블 및 기존 품목의 빈 컬럼 콘텐츠를 하나의 SQL Server 트랜잭션으로 반영한다.
- 사용 항목(label-column) DB transaction commit 전에는 working copy를 확정하지 않는다. commit 성공 후에는 같은 저장 command를 다시 실행할 수 없는 `committedReloadPending` 상태로 전환하고 root `LabelSizeReloadCoordinator`가 현재 라벨 크기의 candidate `LabelSizeSession`에 기존 `expectedOldGeneration`보다 큰 단조 증가 `newGeneration`을 발급해 강제 재로드한다. `HomePageManager`는 candidate generation의 render/typed failure ACK만 반환한다. 같은 generation이어야 하는 범위는 candidate 내부 data/resources/context뿐이며 기존 session generation을 재사용하지 않는다. reload가 실패해도 DB 저장 실패로 취급하거나 저장 command를 재시도하지 않고, 부분 cache를 노출하지 않은 채 reload만 다시 실행한다. 고객별 사용자 항목 사전 저장은 label-size session을 교체하지 않는 별도 post-commit 경로를 사용한다.
- DB transaction public API는 `compatibilityTransaction()`과 `strictTransaction(StrictDbOperation)` 또는 동등한 두 typed 경계로 분리한다. 기존 `transaction()`은 migration 동안 compatibility alias로만 유지하고 신규 strict 호출에서 금지한다. 두 경계는 메서드명뿐 아니라 `compatibilityTransactionV1 | strictTransactionV1` wire action, request/statement DTO, decoder, response와 typed error를 공유하지 않는다. compatibility decoder는 `StrictDbOperation`을 역직렬화할 수 없고 strict dispatcher는 기존 단일 요청 자율 commit `executeDriverTransaction()`을 호출할 수 없다. label/customer 저장은 strict API만 사용하며 versioned result contract가 marker/schema/cardinality뿐 아니라 count와 신규 ID mapping의 결정적 구조·command 일치까지 검증한 뒤에만 commit한다. strict API가 정상 반환한 순간 이 pre-commit 검증과 DB commit은 완료된 것으로 취급한다. 그 이후 isolate 응답/wire decode처럼 commit 전에 검출할 수 없었던 payload 손상이 발견되면 일반 저장 실패가 아니라 `DbCommittedResultInvalid(committedKnown: true)`로 분류하고 동일 command 재실행을 금지한다. 기존 writer의 lock-only migration은 compatibility API를 사용하며 strict ACK/recovery 완료로 간주하지 않는다.
- commit 응답이 유실된 `DbCommitOutcomeUnknown`은 재조회만으로 해당 operation의 실제 commit 여부를 단정하지 않는다. 기존 DB identity를 포함하는 `concurrencyFingerprint`와 신규 identity에 독립적인 `desiredObservationProjection`을 분리해 `desiredStateObserved`, `originalStateObserved`, `indeterminate` 3상태로 reconciliation하고, 정확한 operation 귀속이나 자동 멱등 재시도가 필요하면 별도 operation ID ledger 또는 저장 stored procedure를 선행한다.

2. 현재 프로젝트 기준점

2.1 현재 UI

- 공용라벨관리 오른쪽 `사용 항목` 영역의 `항목 편집` 버튼은 `lib/page_home/common_label_manage.dart`에 있으나 callback은 비어 있다.
- 현재 공용라벨의 사용 항목 목록은 `TColumn.datas`를 읽어 표시한다.
- 현재 목록용 `_CommonLabelTable`은 `FortuneTable` 기반이다. 기존 공용라벨 화면의 읽기 전용 목록은 그대로 유지하고, 새 편집 다이얼로그 안의 두 테이블만 라벨 설정과 같은 `SwipeActionTable` 계열로 구현한다.
- 현재 `_CommonLabelTable`의 `필수등록` 체크박스는 `TColumnBase.useMissingKeywordCheck`만 직접 변경하고 DB에 저장하지 않는다. 새 편집기 구현 시 이 체크박스를 읽기 전용 표시로 바꾸고 `필수등록` 변경과 DB 저장은 라벨 항목 편집기의 속성 패널만 소유한다. 별도 즉시 저장 UX를 유지해야 한다면 같은 원자적 DAO와 세션 재로드를 연결하는 별도 작업으로 분리한다.
- 라벨 설정 다이얼로그는 `BlockingModelessDialog`, `BlockingModelessDialogFrame`, `EditableSwipeNameTable`, `rowReorderEnabled`, 우측 위/아래 이동 rail, 전용 footer를 사용한다.

2.2 현재 모델/DAO

- `lib/models/column.dart`의 `TColumn`은 레거시 컬럼 속성 대부분을 이미 보유하고 있다.
- `TColumnDAO.selectByLabelSizeId()`는 `BM_RICH_COLUMN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `VIEW_BM_GS1_CONTAIN_COLUMN`을 조회한다.
- 현재 `TColumnDAO`에는 라벨 항목 편집용 insert/update/delete transaction API가 없다.
- 고정 항목 분류, 고정 항목, 고객별 사용자 항목에 대응하는 현 프로젝트 모델/DAO가 없다면 새로 추가해야 한다.
- `TColumn`과 `TColumnBase`는 대부분 불변 필드지만 편집용 `copyWith`와 안정적인 draft identity가 없다. DB 조회 모델을 직접 mutate하지 말고 편집 전용 draft를 사용한다.

3. 구현 범위

3.1 포함 범위

- 공용라벨관리 `사용 항목 > 항목 편집` 진입 연결
- `라벨 항목 편집` blocking modeless 다이얼로그
- 사용 항목 속성 패널과 사용 항목 테이블
- 고정 항목/사용자 항목 전환 및 후보 테이블
- 후보 항목 추가 버튼과 drag/drop 추가
- 사용 항목 삭제 버튼과 drag/drop 삭제
- 사용 항목 순서 변경 모드
- 고객별 사용자 항목 설정 모드
- 속성별 입력 UI와 검증
- 사용 항목 및 사용자 항목 모델/DAO/transaction
- 컬럼/품목/content를 쓰는 현 프로젝트의 모든 writer와 라벨 크기 삭제가 공유하는 label-size 단위 DB lock protocol
- Windows ODBC, macOS DB-Lib와 Android/iOS native adapter의 marker 기반 다중 결과셋 collector와 명시적 Unicode parameter type
- Web과 Linux를 제외한 Windows/macOS/Android/iOS의 플랫폼별 DB execution boundary와 cancel/session-discard capability gate
- 저장 후 root `LabelSizeReloadCoordinator` 소유 label-size 세션 전체 강제 재로드와 `HomePageManager` render ACK
- widget/model/DAO/transaction 회귀 테스트

3.2 제외 범위

- 공용라벨 시트 workbook 자체의 셀/서식 저장 포맷 변경
- 품목관리의 기존 품목 값 편집 기능 변경. 단, 컬럼 구조 저장과의 동시 쓰기를 막기 위해 `ItemManagerSaveDAO`, 품목 순서 저장, element sheet update/migration과 라벨 크기 삭제가 같은 label-size DB lock protocol에 참여하고 필요한 context를 전달받는 최소 변경은 포함한다.
- 레거시 SpreadSheet OCX UI 복제
- 레거시의 비어 있는 `InsertColumnsToLogDB()`를 근거 없이 새 로그 테이블로 구현하는 작업
- DB 스키마를 임의 변경하는 작업. 스키마 변경이 필요하면 별도 SQL과 배포 절차를 먼저 합의한다.

4. 다이얼로그 공통 구조

4.1 표시 방식

- 기존 Label Manager 모달리스 규칙에 따라 `BlockingModelessDialog(child: BlockingModelessDialogFrame(...))`를 사용한다.
- 다이얼로그 `OverlayEntry`와 중복 open guard는 브랜드/라벨 설정과 같이 `HomePageManager`가 소유한다. `CommonLabelManage`는 open callback만 호출하고 overlay lifecycle이나 전역 cache를 직접 소유하지 않는다.
- `LabelColumnEditCoordinator`는 overlay widget보다 긴 lifecycle로 edit session, immutable save command, in-flight transaction Future, commit outcome, reconciliation/reload와 overlay attach 상태를 소유한다. dialog widget은 coordinator state를 표시하고 사용자 event를 전달하는 view로 제한한다. 앱 루트 수명의 `LabelColumnSaveRecoveryRegistry`는 UI detach 시 coordinator와 durable operation record를 인수하고 success/unknown/committed-invalid 후속 처리와 reload 필요 상태를 보존한다. `HomePageManager`가 dispose되어도 coordinator는 DB 결과와 동일 command 금지 상태를 registry에 넘긴 뒤에만 dispose한다. 같은 앱 프로세스에서 coordinator 또는 registry가 original/desired projection을 메모리에 보유한 동안에만 commit 결과 미확정 reconciliation을 허용한다. 프로세스 재시작 후 durable evidence를 평가해 `commitCompletedDurable` 이상은 resource별 reload 성공 후 사용자 확인 없이 tombstone하고, `commitOutcomeUnknown`, 손상 또는 알 수 없는 artifact처럼 결과를 확정할 수 없는 상태만 resource를 차단한 채 강제 DB reload와 명시적 사용자 수용으로 해제한다. 앱 시작/DB reconnect 어느 경로에서도 save command를 자동 재실행하지 않는다.
- 다이얼로그 제목은 `라벨 항목 편집`으로 한다.
- 가용 너비가 960 logical px 이상이면 속성 패널, 두 테이블, 중앙 command rail, footer가 겹치지 않는 4영역 가로 배치를 사용한다. dialog 기본 크기는 화면 너비의 85~90%, 화면 높이의 80~90%로 하되 viewport 안에 제한한다.
- 가용 너비가 960 logical px 미만인 Android/iOS 및 축소 window에서는 사용자 결정에 따라 전체 가로 스크롤이나 진입 차단 대신 적응형 탭/단계 UI를 사용한다. `속성`, `사용 항목`, `후보` 세 view를 명시적으로 전환하고 추가/삭제 command와 현재 전용 모드 footer는 화면 하단 safe area 위에 고정한다. pending property dirty guard, 선택 stable key와 drag 대체 버튼은 view 전환에도 유지한다. drag/drop은 pointer가 있는 환경의 보조 UX이며 touch 환경에서 모든 기능을 아이콘/명령 버튼으로 수행할 수 있어야 한다.
- layout gate viewport는 desktop `1280×720`, desktop compact `960×600`, mobile portrait `360×640`, mobile landscape `640×360` logical px와 text scale `1.0`, `1.3`, `2.0`을 고정한다. safe area/keyboard가 있는 모바일에서는 현재 입력과 footer가 가려지지 않도록 해당 view 내부 세로 스크롤과 inset을 적용하며 960 미만에서 4영역을 억지로 축소하지 않는다.
- 확인, 경고, 실패 알림은 다이얼로그보다 위에 나타나는 공용 blocking overlay dialog API를 사용한다.
- 다이얼로그가 열린 동안 공용라벨의 시트, 브랜드/라벨 선택, 탭 전환 등 바깥 화면 입력을 차단한다.

4.2 기본 배치

왼쪽부터 다음 순서로 배치한다.

1. 사용 항목 속성 패널
2. 사용 항목 테이블
3. 중앙 command rail
4. 후보 영역

후보 영역 상단에는 `고정 항목`/`사용자 항목` segmented control 또는 radio를 둔다. 고정 항목일 때는 고정 항목 분류 dropdown을 표시하고, 사용자 항목일 때는 고객별 사용자 항목 테이블을 표시한다.

중앙 command rail에는 다음 아이콘 버튼을 세로로 둔다.

- 휴지통: 위쪽에 독립적으로 배치하고 아래 추가 버튼과 시각적 간격을 둔다.
- 왼쪽 화살표: 선택한 고정/사용자 후보를 사용 항목으로 추가한다.

아이콘은 현 프로젝트의 Material/Lucide 정책에 맞는 익숙한 아이콘을 사용하고 tooltip을 제공한다. 텍스트가 있는 둥근 사각형으로 아이콘 기능을 대신하지 않는다.

4.3 메인 footer

- 다이얼로그 하단 오른쪽에 `취소`, `저장` 버튼을 둔다.
- `저장`은 `workingDirty=true`, `propertyDirty=false`, 모든 working row의 `initialApplyState != requiredPending`, busy=false일 때만 활성화한다. 속성 변경 또는 최초 적용 필수 행이 아직 `적용`되지 않은 동안에는 비활성화하고 `먼저 속성 변경을 적용하거나 취소해 주세요.` 안내를 제공한다.
- `취소`는 다이얼로그 전체의 미저장 변경을 버리고 닫는 기능이다.
- 미저장 변경이 있으면 `변경 내용을 취소하고 닫으시겠습니까?`를 질의한다. 확인한 경우에만 원본 snapshot으로 복원하고 닫는다.
- 창 닫기 아이콘과 Esc도 메인 `취소`와 같은 guard를 거친다.
- 현재 `BlockingModelessDialog`는 wrapper가 primary focus일 때만 key를 소비하고 Esc 취소 callback이 없으며 `OverlayEntry`는 Navigator route가 아니어서 시스템 back/pop을 소유하지 못한다. 공용 `BlockingOverlayStack`이 root overlay별 단조 token, push/pop과 최상단 여부를 소유하고 blocking dialog/confirmation을 모두 등록한다. 공용 위젯은 optional `Future<void> Function(BlockedCloseSource source) onCloseRequest` callback을 받아 descendant에서 bubble된 최초 Esc `KeyDownEvent`, frame 제목 표시줄 닫기, Android/iOS system back과 desktop app window-close request를 같은 top-token 비동기 close command로 중재한다. 앱이 소유한 route pop은 전역 임의 `Navigator.pop()`을 가로챌 수 있다고 가정하지 않고 중앙 `requestGuardedPop()` API를 통해 `appOwnedNavigatorPop` source로만 요청한다. blocking stack이 비어 있지 않은 app-owned call site에서 direct `Navigator.pop()` 사용은 구조 lint로 거부한다. repeat/up, 하위 token event와 callback Future 중 추가 close 요청은 소비만 하며 root `PopScope`/app exit lifecycle로 전달하지 않는다. TextField/dropdown 등 child가 focus를 가진 상태에서도 Esc를 바깥 shortcut으로 전달하지 않는다. confirmation이 top이면 confirmation만 source별 dismiss 정책을 결정하고 하위 editor guard를 호출하지 않는다. callback 기본값은 기존 위젯 동작을 유지하되 앱 root의 back/window-close dispatcher는 blocking stack이 비어 있을 때만 기존 exit lifecycle을 실행한다. confirmation dismiss와 dialog dispose는 owner token이 일치할 때 정확히 한 번 pop하고 stale pop은 무시하지 말고 typed lifecycle 오류로 테스트한다.
- `reorder` 또는 `userItemEdit` 모드에서 창 닫기/Esc를 누르면 메인 취소를 바로 실행하지 않는다. 먼저 현재 전용 모드의 취소 guard를 실행해 `normal`로 돌아가며, 사용자가 다시 닫기를 요청했을 때만 메인 close guard를 실행한다. DB busy, canonical `commitOutcomeUnknown`, `committedResultInvalid`, `committedReloadPending`에서는 Esc와 제목 표시줄 닫기를 소비만 하고 상태를 변경하지 않는다.
- commit 후 reload 실패 상태는 `committedReloadFailed`로 분리한다. 이 상태에서도 Esc와 제목 표시줄 닫기는 소비하고, read-only 오류 화면의 명시적 `화면 닫기` 버튼만 overlay를 닫을 수 있다. 이 버튼은 상위 `force-reload-required`를 해제하지 않으며 저장 command도 실행하지 않는다.
- `normal` 이외의 전용 모드 또는 DB command 실행 중에는 메인 footer의 `취소`와 `저장`을 비활성화한다.

5. 편집 상태 모델

5.1 상호 배타 모드

다이얼로그 상태는 최소한 다음 enum으로 관리한다.

- `normal`: 사용 항목 선택, 속성 편집, 후보 추가/삭제, 메인 저장 가능
- `reorder`: 사용 항목 순서 변경 전용
- `userItemEdit`: 고객별 사용자 항목 사전 편집 전용

`reorder`와 `userItemEdit`는 동시에 true가 될 수 없다. 여러 boolean 조합으로 유효하지 않은 상태가 생기지 않도록 단일 mode를 source of truth로 사용한다.

DB 조회/저장 중에는 coordinator의 별도 busy state로 중복 command, 다중 route, 중복 저장을 막는다. coordinator와 `RecoveryTransitionTableV1`은 같은 canonical post-commit state ID를 사용한다. label-column과 customer-column의 commit 결과 미확정 canonical state는 모두 resourceKind로 구분되는 `commitOutcomeUnknown` 하나이며 label-column은 추가로 `committedResultInvalid`, `committedReloadPending`, `committedReloadFailed`를, customer-column은 `customerCommittedResultInvalid`, `customerDictionaryReloadPending`, `customerDictionaryReloadFailed`를 폐쇄 열거한다. UI 문구/진행 표시가 필요한 경우 `commitOutcomeUnknown → commitOutcomeReconciling` 또는 customer 전용 표시명으로 투영할 수 있지만 이 이름은 enum/stateSet/transition ID가 아니며 checked-in descriptor의 전단사 display mapping으로만 생성한다. resource별 reload 상태를 서로 합치거나 post-commit 상태를 `normal`/busy boolean 조합이나 dialog-local State만으로 표현하지 않는다.

5.2 사용 항목 working copy

다이얼로그를 열 때 DB 조회 결과로 다음 상태를 만든다.

- `originalColumns`: 다이얼로그를 연 시점의 immutable snapshot
- `workingColumns`: 화면에서 추가/수정/삭제/정렬되는 목록
- `deletedColumnIds`: DB에 존재했던 행 중 working copy에서 삭제된 ID
- `selectedColumnKey`: index가 아닌 안정적인 행 identity
- `propertyBaseline`: 현재 선택 행에서 속성 패널을 연 시점의 값
- `propertyDraft`: 속성 패널 입력값
- `propertyDirty`: baseline과 draft의 실제 내용 비교 결과
- 각 `LabelColumnDraft.initialApplyState`: `notRequired | requiredPending | completed`. `requiredPending`은 `propertyDirty`와 독립적인 저장·선택 이탈·모드 전환 차단 상태다.

기존 행 identity는 `columnId`, 신규 행 identity는 dialog session에서 생성한 `draftColumnKey`를 사용한다. 선택, drag/drop, reorder, 삭제 후 선택 복원은 list index를 identity로 사용하지 않는다.

5.3 dirty 구분

- `propertyDirty`: 속성 패널의 아직 적용하지 않은 변경
- `workingDirty`: 적용된 속성 변경, 항목 추가/삭제, 순서 변경으로 working copy가 original snapshot과 달라진 상태
- `userItemDirty`: 사용자 항목 설정 모드 안의 별도 working copy가 해당 모드 진입 snapshot과 달라진 상태
- `orderDirty`: 순서 변경 모드 진입 snapshot과 현재 순서가 다른 상태

속성 패널의 `적용`은 `propertyDraft`를 `workingColumns`에 반영하여 `workingDirty`를 만들지만 DB에는 쓰지 않는다. 사용 항목 DB transaction은 메인 `저장`에서만 실행한다. 순서 변경 모드의 `저장`은 순서를 working copy에 적용하는 의미이며 DB에 쓰지 않는다.

6. 사용 항목 테이블

6.1 테이블 구성

- `SwipeActionTable<LabelColumnDraft>` 또는 이를 일반화한 공용 wrapper를 사용한다.
- 컬럼은 레거시와 동일한 의미를 유지한다.
  - 신규 상태
  - 키워드
  - 항목명
  - 종류
  - 제목
  - 표시 여부
- 행 번호 영역과 컬럼 헤더의 좌상단 교차 영역에는 순서 변경 아이콘을 둔다.
- 현재 active QR data/하단 text, barcode link와 natrium token에서 참조 중인 행은 `ReferenceTokenParserV1` 결과와 현재 session 전 품목 `LegacyOutputDependencyTraceV1`의 합집합으로 표시한다. 이는 data 일부만 검사하던 레거시 `IsQRCodeUseThis()` 누락과 parser/output 의미 차이를 실제 출력 참조 전체로 보완한 `intentionalDivergence=true` 정책이다. GS1 포함 관계에서 참조 중인 행은 신규 UX로 별도 상태 표시를 제공한다. QR/token 참조와 GS1 ID 관계를 하나의 `referenced` boolean으로 합치지 않고 서로 다른 아이콘/tooltip과 command guard를 사용한다. 색만으로 의미를 전달하지 않는다.
- 신규 행은 `신규` 상태를 표시한다.
- 행 클릭은 해당 행을 선택하고 속성 패널을 갱신한다. 더블클릭으로 별도 속성 다이얼로그를 열지 않는다.

6.2 선택과 속성 dirty guard

`propertyDirty=true` 또는 현재 선택 행의 `initialApplyState=requiredPending`인 상태에서 다음 이벤트를 요청하면 공용 guard를 먼저 실행한다.

- 다른 사용 항목 행 선택
- 고정/사용자 후보 선택 또는 추가
- 사용 항목 삭제
- 사용 항목 순서 변경 모드 진입
- 고정/사용자 후보 모드 전환
- 사용자 항목 설정 모드 진입
- 메인 취소, 창 닫기

guard는 폐쇄된 두 분기를 가진다. `requiredPending`이면 `이 항목은 최초 속성 적용이 필요합니다. 적용하지 않고 항목 추가를 취소하시겠습니까?`를 질의하고, 사용자가 확인한 경우에만 해당 pending 신규 행을 working copy와 selection/property state에서 원자 제거한다. 원래 요청이 바로 그 pending 행의 삭제이면 행 제거가 요청을 이미 완료한 것이므로 continuation을 실행하지 않는다. 다른 행 선택, 후보 추가, 모드 진입, 닫기처럼 행 제거 뒤 별도 목적이 남은 요청만 원래 이벤트를 정확히 한 번 이어서 실행한다. 확인하지 않으면 현재 행과 입력 focus를 유지하고 이벤트를 실행하지 않는다. 그 외 `propertyDirty`이면 기존 `적용하지 않은 속성 변경을 취소하시겠습니까?`를 질의하고, `변경 취소` 확인 시 property draft를 baseline으로 되돌린 뒤 원래 이벤트를 정확히 한 번 이어서 실행한다. 두 조건이 동시에 true이면 `requiredPending` 분기를 우선해 행 제거 또는 현재 선택 유지 중 하나로 종료하며 draft 복원만으로 원래 이벤트를 허용하지 않는다.

guard callback 안에서 이벤트별 로직을 복제하지 말고 `Future<PendingPropertyResolution> resolvePendingPropertyEdit(PendingPropertyRequest request)` 같은 공용 경계를 둔다. request는 최소 목적 command kind, nullable target stable key, capture한 edit-session revision과 pending key를 가지며 결과는 `proceedUnchanged | proceedAfterDraftReset | proceedAfterPendingRowRemoved | requestConsumedByPendingRowRemoval | stay | superseded`를 폐쇄 열거한다. resolver는 session별 single-flight latch를 소유해 확인 Future 중 버튼/drop/programmatic 재호출을 새 dialog로 열지 않는다. 확인 완료 뒤 같은 serializer에서 captured revision/pending key를 CAS 검증하고 달라진 stale request는 `superseded`로 종료해 상태 변경과 continuation을 실행하지 않는다. route가 닫히기 전에 다음 command가 실행되지 않도록 원자 상태 변경 완료 뒤 호출자는 `proceed*` 결과에서만 원래 이벤트를 한 번 실행하고 `requestConsumedByPendingRowRemoval`은 성공 완료로 반환하되 continuation을 실행하지 않는다. target key가 현재 pending key인 삭제만 consumed 결과가 될 수 있고 다른 key 또는 목적 command를 consumed로 오분류하면 typed state error다.

6.3 항목 삭제

- 사용 항목 선택이 없으면 중앙 휴지통 버튼을 비활성화한다.
- 휴지통 버튼을 누르면 선택 행을 working copy에서 삭제한다.
- DB 기존 행은 `deletedColumnIds`에 추가하고 신규 행은 working copy에서만 제거한다.
- QR/기본 사용자 정의 문자열에서 참조 중인 행은 삭제하지 못한다. 사용자가 참조하는 QR/기본 항목의 token을 먼저 제거하거나 다른 항목으로 바꿔 적용하도록 안내한다. GS1 관계에서 참조 중인 행은 제거될 관계를 명시한 영향 확인 후에만 삭제한다.
- 삭제 시 GS1 바코드 draft의 포함 항목 목록에서도 해당 기존 ID 또는 신규 draft key를 제거한다.
- 삭제 후 가능한 경우 다음 행, 마지막 행 삭제였으면 이전 행을 선택한다. 행이 없으면 선택과 속성 패널을 비운다.

사용 항목 행을 drag하여 휴지통 drop target에 올릴 수 있어야 한다.

- drag payload에는 안정적인 행 key와 source 종류를 넣고 index만 전달하지 않는다.
- drag hover 중 휴지통을 강조한다.
- 허용된 행을 drop하면 참조 경고/확인을 먼저 처리한다.
- 삭제가 확정된 경우에만 휴지통이 항목을 받아들이는 짧은 scale/fade 애니메이션을 실행하고 행을 제거한다.
- 확인을 취소하거나 유효하지 않은 payload이면 애니메이션과 삭제를 실행하지 않는다.
- 아이콘 버튼 삭제와 drag/drop 삭제는 같은 command handler를 사용한다.

7. 사용 항목 속성 패널

7.1 공통 동작

- 선택 행이 없으면 빈 상태를 표시하고 모든 입력을 비활성화한다.
- 행 선택 시 해당 타입에 맞는 속성 UI를 구성한다.
- 패널 하단에는 항상 `취소`, `적용` 버튼을 둔다.
- `적용`은 현재 입력이 유효하고 `propertyDirty=true` 또는 현재 행의 `initialApplyState=requiredPending`일 때 활성화한다. 최초 적용 필수 행은 값을 바꾸지 않았어도 적용할 수 있어야 한다.
- `취소`는 현재 행이 `requiredPending`이 아니면 property draft를 baseline으로 복원하고 DB 또는 working copy의 적용 완료 값을 바꾸지 않는다. `requiredPending`이면 공용 pending 제거 확인을 실행해 사용자가 확인한 경우에만 신규 행과 selection/property state를 원자 제거하고, 거부하면 현재 draft와 focus를 유지한다. 이 버튼 command 결과도 `draftReset | pendingRowRemoved | stayed`의 폐쇄 결과로 처리하며 pending 행에서 baseline 복원만 수행해 행을 남기는 경로는 허용하지 않는다.
- `적용` 성공 후 현재 값이 새 baseline이 되고 `propertyDirty=false`가 된다. `requiredPending` 행이면 같은 command에서 `initialApplyState=completed`로 전환한다.
- 신규 특수 타입 행은 사용 항목 테이블에 pending 신규 행으로 표시하고 즉시 선택한다. `requiresInitialPropertyApply` 폐쇄 집합은 레거시와 같은 바코드/이미지/QR/GS1 AI/GS1 바코드(type code `3 | 4 | 9 | 11 | 12`)이며, 해당 행은 `initialApplyState=requiredPending`으로 생성한다. 첫 속성 적용 전 `취소`하면 레거시 상세 설정 dialog 취소와 동일하게 신규 행 자체를 제거한다. `requiredPending`인 동안 다른 행 선택, 후보 추가, reorder/userItemEdit 진입과 메인 저장을 공용 `resolvePendingPropertyEdit()` guard가 차단하고 `적용` 또는 행 제거 중 하나를 완료하도록 한다. 제조일자/유통기한을 포함한 나머지 지원 타입은 `initialApplyState=notRequired`로 기본값을 즉시 추가한다.
- 일반 타입처럼 별도 설정 없이 추가 가능한 항목은 레거시 기본값으로 즉시 working copy에 추가한다.

7.2 공통 속성

최소한 다음 속성을 제공한다.

- 키워드
- 항목명
- 항목 종류
- 제목
- 표시 여부
- 누락 키워드 검사 사용 여부

검증 규칙은 다음과 같다.

- 키워드와 항목명은 필수다.
- 키워드는 현재 사용 항목 안에서 중복될 수 없다.
- 제목은 실제 DB `RICH_TITLE VARCHAR(20)` 제약에 맞춰 CP949 인코딩 기준 최대 20바이트로 제한한다. UI에는 `한글은 최대 10자, 영문·숫자는 최대 20자이며 혼합 입력은 20바이트 이내`라고 안내하고 혼합 문자열도 실제 CP949 byte length로 검증한다.
- 제목뿐 아니라 키워드, 항목명, 사용자 정의 QR 데이터/텍스트, 나트륨 문자열, 폰트명, 사용자 정의 바코드 텍스트, 날짜 범위와 사용자 항목 사전 문자열도 실제 대상 DB 컬럼의 `max_length`, nullable, CP949 collation에 맞춰 저장 전에 검증한다. CP949로 표현할 수 없는 문자는 `?`로 대체하지 않고 해당 필드 validation error로 거부한다.
- 종류 dropdown은 현재 DB의 `BM_RICH_COLUMN_TYPE` 조회 행과 지원 code 0~12의 교집합만 제공하고 `TYPE_END_OF_CULUMN(13)` sentinel은 표시·추가·저장하지 않는다. 기존 행이 사용하는 0~12 code의 reference row가 누락되거나 이름/필수 metadata가 malformed이면 타입을 합성하지 않고 schema capability 오류로 편집기 진입을 차단한다. 기존 행이 사용하지 않는 지원 code가 DB에 없으면 신규 선택 목록에서만 제외하고 진단에 기록한다. DB에서 0~12 밖의 알 수 없는 raw type code를 조회하면 fallback 타입으로 바꾸지 않고 원본 code를 보존한 채 해당 행 편집과 전체 저장을 차단한다.
- 키워드 변경 대상이 QR/기본 사용자 정의 문자열에서 참조 중이면 적용하지 않는다. 참조 token을 먼저 제거/교체하도록 안내한다. GS1 포함 관계는 기존 column ID 또는 신규 draft key로 연결되므로 키워드만 변경할 때 관계를 제거하거나 영향 경고를 표시하지 않는다. GS1 AI의 타입 변경·삭제 또는 GS1 barcode 포함 목록 변경처럼 endpoint 자체가 사라지는 경우에만 제거될 ID 관계를 명시한 영향 확인을 수행한다.
- 종류 변경 시 기존 타입 전용 값이 초기화될 수 있음을 확인한다.
- GS1 AI를 다른 타입으로 바꿀 때 GS1 바코드 포함 관계에서 제거되는 영향을 확인한다.

7.3 타입별 속성

레거시 `CColumnSetupMainDlg`와 각 하위 설정 화면에 있는 속성을 누락 없이 제공한다. 현재 `TColumn` 필드와 DB 컬럼을 source of truth로 사용한다.

단, `TColumn`에는 DB 저장값과 화면 런타임 상태가 함께 있으므로 클래스의 모든 필드를 저장 대상으로 간주하지 않는다. 12.1의 persisted field allow-list에 포함된 값만 속성 draft와 dirty 비교, SQL 저장에 사용한다.

- 기본/문자: 일반 텍스트 또는 사용자 정의 데이터, 자동 증가 사용/자리수/범위/저장/0 제거/업데이트. 기본 타입 UI에는 `RICH_USER_DEFINE_QRDATA`만 노출하고 `RICH_USER_DEFINE_QRTEXT` 입력은 제공하지 않는다. 사용자가 data를 실제 변경해 적용하면 `CColumnSetupBasic::OnEnChangeEditUserDefineData()`의 명시적 편집 효과와 같이 text를 `''`로 초기화한다. editor hydration/진입과 data가 변경되지 않은 다른 속성 저장에서는 기존 raw text를 보존한다. 레거시 MFC의 `SetWindowText`/`ENM_CHANGE` 순서로 진입만 해도 handler가 발생할 수 있는 부작용은 재현하지 않는 `intentionalDivergence=true` 정책이다. 레거시 별도 `SearchPrintSetupDlg`가 소유하는 검색 출력은 이번 속성 UI에서 표시·수정하지 않는다.
- 제조일자/유통기한: 레거시 `CColumnSetupDate`에 대응하는 날짜 editor, 자동 증가 속성, 날짜 범위 사용 및 전/후 범위
- 제조시각/유통시각: 사용자 결정에 따라 레거시 `CColumnSetupMainDlg` fallback과 같은 기본 editor를 사용한다. 날짜 editor나 별도 시각 형식 필드를 추가하지 않는다.
- 바코드: 바코드 종류, 폭, 높이, 체크디지트, 번호 표시, 텍스트 연동, 타임바코드 타입, 자동 증가 속성, 사용자 정의 바코드 텍스트, line check/size, 회전
- 이미지: 폭, 높이
- QR/2D 코드: 2D 종류, 생성 방식(일반/사용자 정의/나트륨), 사용자 정의 데이터와 하단 문자열, pixel size, scale, 하단 문자열 표시, 정렬, 폰트/크기, 자동 증가 속성
- GS1 AI: AI 코드, format option, GS1 코드 표시 여부
- GS1 바코드: 종류, 폭, 높이, 포함할 GS1 AI 항목 목록
- 고정(`TYPE_FIX`), 영양성분(`TYPE_NUT`), 매수(`TYPE_PRINTCOUNT`) 및 그 밖의 0~12 타입은 레거시 `ColumnSetupMainDlg`의 fallback과 같이 기본 editor를 사용하되 타입별 기본값과 변경 초기화 규칙을 매핑표에 명시한다.

레거시 검증과 경고도 유지한다.

- 바코드/이미지/GS1 바코드의 폭 또는 높이가 0이면 출력되지 않을 수 있음을 경고한다.
- QR pixel size 또는 scale 직접 입력값이 0이면 출력되지 않을 수 있음을 경고하고 사용자가 명시적으로 확인한 경우 적용을 허용한다. 0은 validation error가 아니며 신규 후보의 pixel size 0도 첫 속성 적용 전 보존한다.
- GS1 AI 코드는 필수다.
- 체크디지트 또는 타임바코드 변경이 기존 품목 바코드 값에 영향을 주면 경고한다.
- 사용자 정의 QR 데이터가 비어 있거나 나트륨 구성에 초기화되지 않은 값이 있으면 적용하지 않는다.
- 레거시 수치 범위를 최소 계약으로 유지한다. QRCode pixel size `1~20`과 QR scale `10~100`은 spinner/권장 입력 범위이며 직접 입력 `0`은 위 경고 확인 후 저장 가능한 별도 레거시 값이다. 그 밖의 범위 밖 값은 validation error다. QR 하단 문자열 font size는 3~50, barcode text font size 의미를 사용하는 입력은 1~100이다. 폭/높이, 자동 증가, line size, 날짜 범위 등 나머지 숫자는 실제 DB 타입과 레거시 control range를 매핑표에서 확정하며 범위 미확정 상태로 editor를 구현하지 않는다. `RICH_BARCODE_LINE_SIZE`는 레거시 header의 `int` 선언과 implementation의 `BOOL` 반환 불일치를 범위 근거로 사용하지 않고 운영 스키마/데이터 분포 fixture로 정수 보존 또는 0/1 규격화를 먼저 확정한다.

속성 패널은 하나의 거대한 build 함수로 만들지 않는다. 공통 입력과 타입별 editor widget을 분리하되, 각 editor는 `LabelColumnPropertyDraft`를 입력받아 변경 callback만 반환하고 DB를 직접 호출하지 않는다.

8. 고정 항목 후보

8.1 조회와 표시

- `고정 항목` 선택 시 고정 항목 분류 dropdown을 활성화한다.
- 분류는 레거시 `BM_RICH_FIX_COL_TYPE`의 ID와 이름을 조회한다. 배포 스키마에 별도 순서 컬럼이 없으므로 `RICH_FIX_COL_TYPE_ID ASC`를 결정적 표시 순서로 사용한다. 향후 별도 사용자 정렬이 필요하면 이번 기능과 분리된 DB 스키마 변경으로 처리한다.
- 선택 분류의 후보는 `BM_RICH_FIX_COLUMN`에서 `RICH_FIX_COLUMN_ID`, 키워드, 항목명, 종류를 조회하고 stable identity와 표시값을 분리한다. 배포 capability에서 레거시 primary key `RICH_FIX_COLUMN_ID`가 확인되어야 편집기 진입을 허용하고 `RICH_FIX_COLUMN_ID ASC`로 정렬한다. ID가 없는 스키마에서 정규화 문자열이나 row index를 임시 identity로 만들지 말고 명시적 호환/migration 계약을 먼저 추가한다.
- 분류를 바꾸면 후보 선택을 해제하고 해당 분류 목록을 다시 표시한다.

8.2 사용 항목으로 추가

- 고정 항목 행 선택이 없거나 같은 키워드가 이미 사용 중이면 왼쪽 화살표를 비활성화한다.
- 행 선택 후 왼쪽 화살표를 누르면 후보 추가 전용 persisted-field 기본값 fixture로 신규 사용 항목 draft를 만든다. 생성자 이름이나 Dart model fallback을 기본값 source of truth로 사용하지 않는다. fixture는 실제 레거시 후보 추가 경로인 `CColumn(int labelSizeId, const CColumnBase&, int order)`를 기준으로 최소 `barcodeType=0`, `lineSize=0`, `GS1 AI='01'`, `QR scale=100`, `QR text font size=10`, visible/check digit/show barcode number와 각 persisted scalar를 타입별로 고정한다. 다른 레거시 생성자의 `lineSize=1` 같은 값은 후보 추가 기본값으로 사용하지 않는다.
- 고정 항목 행을 drag하여 사용 항목 테이블에 drop해도 같은 add command를 실행한다.
- 버튼과 drag/drop은 중복 검사, 초기값 생성, 특수 타입 pending 속성 편집, 선택 이동까지 동일한 handler를 사용한다.
- 같은 drag gesture가 중복 callback으로 전달되어 두 행이 추가되지 않도록 command generation 또는 in-flight guard를 둔다.

9. 사용자 항목 후보와 사용자 항목 설정

9.1 일반 후보 상태

- `사용자 항목` 선택 시 현재 로그인 고객 ID의 `BM_RICH_CUST_COLUMN`을 조회한다.
- 키워드, 항목명, 종류를 표시한다.
- 후보는 `RICH_CUST_COLUMN_ID ASC`로 결정적으로 정렬하고 재조회 뒤에도 stable ID로 선택을 복원한다.
- 선택 행을 왼쪽 화살표 또는 사용 항목 테이블 drop으로 추가한다.
- 추가 시 고객별 사전 row를 직접 연결하지 않고 레거시처럼 현재 라벨 크기의 신규 `TColumn` draft로 복사한다. 이후 사용자 항목 사전을 수정해도 이미 추가된 사용 항목은 자동 변경하지 않는다.
- 사용자 항목 테이블의 좌상단 헤더 교차 영역에는 `항목 편집` 아이콘과 tooltip을 둔다.

9.2 사용자 항목 설정 모드 진입

- `항목 편집` 아이콘을 누르면 `userItemEdit` 모드로 전환한다.
- 진입 전 pending property edit을 공용 guard로 해소한다.
- 모드 진입 시 고객별 사용자 항목 원본 snapshot과 별도 working copy를 만든다.
- 사용자 항목 영역 이외의 속성 패널, 사용 항목 테이블, 고정/사용자 전환, 분류 dropdown, 왼쪽 화살표, 메인 footer를 비활성화한다.
- 사용자 항목 테이블 좌상단의 편집 아이콘은 숨기고 `항목 추가` 아이콘으로 교체한다.
- 테이블 아래에는 라벨 설정 순서 변경 footer와 같은 형식으로 왼쪽 제목 `사용자 항목 설정`, 오른쪽 `취소`, `저장`을 둔다.

9.3 사용자 항목 inline 편집

- `항목 추가` 아이콘을 누르면 마지막에 신규 빈 행을 추가하고 첫 입력 셀에 focus한다.
- 사용자 항목 working row는 기존 행의 `custColumnId` 또는 dialog session에서 생성한 `DraftMappingKeyV1 draftCustomerColumnKey` 중 정확히 하나를 stable identity로 가진다. 선택, focus, inline edit, 삭제와 drag payload는 row index나 레거시 공통 `NEW_COLUMN` sentinel을 사용하지 않고 이 identity를 사용한다.
- 키워드와 항목명은 직접 입력한다.
- `CustomerColumnGrandfatherPolicyV1`은 `normalEditable | keywordFrozenOtherFieldsEditable | fullyReadOnlyDeleteOnly`의 폐쇄 집합이다. hydration/focus는 어떤 policy에서도 keyword를 정규화하지 않고 DB raw를 그대로 표시한다. 레거시 즉시 대문자화는 `normalEditable` 행의 사용자 keyword 입력 event에만 적용한다.
- 신규 행과 정상 기존 행은 `normalEditable`이며 사용자가 실제로 키워드를 수정하면 `[A-Z0-9]+`만 허용하고 예약 token과 충돌하는 `ITEMNAME`은 거부한다. 한글, 공백, 기호가 들어오면 저장하지 않고 해당 셀에 오류를 표시한다. 레거시 `IsAlphabet()` 범위 때문에 이미 저장된 `_`, `[`, `\\`, `]`, `^`, `` ` `` 등을 포함한 비준수 키워드와 기존 `ITEMNAME`은 `keywordFrozenOtherFieldsEditable`로 분류해 keyword raw를 보존하고 keyword 변경·복사·V1 컬럼 참조 선택을 차단하되 항목명과 지원 type 변경 및 삭제는 허용한다. 0~12 밖의 미지원 raw type 행은 `fullyReadOnlyDeleteOnly`로 분류한다. 비준수/예약어 충돌/미지원 기존 행이 존재한다는 이유만으로 다른 정상 행의 저장과 해당 행 삭제를 차단하지 않으며 자동 정규화하지 않는다.
- 종류 컬럼의 모든 셀을 dropdown으로 바꾼다.
- 종류 목록은 DB `BM_RICH_COLUMN_TYPE`을 `RICH_COLUMN_TYPE_ORDER`, `RICH_COLUMN_TYPE_CODE` 순서로 조회하되 공통 `editableColumnTypes` 정책으로 신규/수정 가능한 type code 0~12만 제공한다. `TYPE_END_OF_CULUMN(13)` sentinel과 미지원 raw type을 신규 dropdown에 제공하거나 새 값으로 저장하지 않으며 임의의 축약 목록을 별도로 하드코딩하지 않는다. 다만 운영 DB에 이미 존재하는 0~12 외 사용자 항목은 raw type code/DB 표시명을 보존한 read-only 행으로 표시하고 삭제만 허용한다. 해당 행의 키워드·항목명·종류 수정, 사용 항목으로 복사와 신규 생성은 차단한다. 실제 배포 `BM_RICH_COLUMN_TYPE` fixture에서 각 외부 type의 `legacyVisible`, `newReadOnly`, `deleteAllowed`, `copyBlocked`, `intentionalDivergence`를 고정한다.
- 신규/수정 행의 키워드와 항목명은 필수이며 고객별 사용자 항목 목록 안에서 키워드 중복을 허용하지 않는다. read-only 비준수 기존 행도 원본 keyword 그대로 중복 비교 집합에 포함하되, 삭제 command에는 신규 validation을 요구하지 않는다.
- 셀 값이 바뀔 때마다 원본 snapshot과 content 비교로 `userItemDirty`를 계산한다.

9.4 사용자 항목 삭제

- `userItemEdit` 모드에서는 중앙 휴지통의 대상이 사용자 항목 테이블로 전환된다.
- 선택 행이 없으면 휴지통을 비활성화한다.
- 기존 행 삭제는 delete ID에 기록하고 신규 행은 working copy에서만 제거한다.
- 사용자 항목 행을 휴지통에 drop하면 사용 항목 삭제와 같은 hover 및 수용 애니메이션 후 삭제한다.
- 사용자 항목 사전 삭제는 이미 현재 사용 항목으로 복사된 컬럼을 삭제하지 않는다. 이 동작을 확인 dialog 문구에서 명확히 알린다.

9.5 사용자 항목 설정 저장/취소

- `저장`은 `userItemDirty=true`, 모든 `normalEditable` 및 허용 필드가 변경된 `keywordFrozenOtherFieldsEditable` 행의 validation 성공, grandfather policy별 금지 필드 raw 보존 검증 성공, busy=false일 때만 활성화한다. 기존 비준수/예약어 충돌 keyword나 미지원 raw type 자체는 validation error가 아니다. `fullyReadOnlyDeleteOnly`는 삭제 외 변경을, `keywordFrozenOtherFieldsEditable`은 keyword 변경·복사를 거부한다. 삭제 command에는 신규 값 validation을 적용하지 않는다.
- 클릭하면 `사용자 항목 설정 변경을 저장하시겠습니까?`를 질의한다.
- 확인 시 신규/수정/삭제를 하나의 DB transaction으로 저장한다.
- 저장 command는 진입 시 customer-scoped 원본 목록의 정규화 original fingerprint와 working copy의 desired fingerprint를 필수로 가진다. transaction에서 같은 customer 범위를 공통 customer-column DB lock과 `UPDLOCK, HOLDLOCK`으로 다시 읽고 fingerprint가 다르면 어떤 CRUD도 실행하지 않은 채 conflict로 rollback한다.
- commit과 result decode가 정상 성공하면 `customerDictionaryReloadPending`으로 전환해 동일 command 재실행과 편집을 차단하고 DB에서 사용자 항목 후보 전체를 다시 조회한다. 저장 직전 선택이 기존 행이면 같은 `custColumnId`, 신규 행이면 검증된 `draftCustomerColumnKey → custColumnId` mapping으로 선택 복원 ID를 계산한다. 재조회 결과에 해당 ID가 정확히 한 번 있을 때만 선택을 복원하고 삭제됐거나 없으면 선택을 `null`로 해제한다. 재조회 성공 후에만 새 customer-column baseline을 만들고 `normal` 모드로 돌아간다. committed-invalid/reload-only 경로에서는 mapping을 working state나 선택 복원에 사용하지 않고 전체 재조회 후 선택을 해제한다. 이 저장은 이미 사용 항목으로 복사된 label-column이나 현재 `LabelSizeSession`을 변경하지 않으므로 label-size session reload를 실행하지 않는다. 후보 재조회가 실패하면 read-only 복구 화면에서 후보 재조회만 다시 시도하며 customer-column save를 재실행하지 않는다.
- 일반적인 commit 전 실패는 모드를 유지하고 working copy를 보존해 같은 command 재시도를 허용한다. `DbConcurrencyConflict`는 이 범위에서 제외한다. conflict이면 working copy를 별도 비교 입력으로 보존하되 동일 command와 자동 rebase를 금지하고, 최신 customer-column snapshot을 재조회한 뒤 사용자가 변경을 수동 재적용·재확인해 새 fingerprint와 operation ID를 가진 command를 생성해야만 다시 저장할 수 있다. `DbCommitOutcomeUnknown`은 11.2의 공용 desired/original/indeterminate 판정 알고리즘에 customer-column 전용 adapter를 주입해 수행하고 동일 command 자동 재실행을 금지한다. 이 adapter는 customer application lock resource, cust-column raw snapshot/projection, `(customerId, keyword)` natural-key resolver를 소유하며 label-size lock이나 label-column projection을 재사용하지 않는다.
- `취소`는 변경이 있으면 `사용자 항목 설정 변경을 취소하시겠습니까?`를 질의하고, 확인 시 snapshot으로 되돌린 뒤 `normal`로 돌아간다.
- 모드 종료 시 좌상단 `항목 추가` 아이콘을 다시 `항목 편집` 아이콘으로 바꾼다.

10. 사용 항목 순서 변경

10.1 진입과 UI

- 사용 항목 테이블 좌상단의 순서 변경 아이콘을 누르면 `reorder` 모드로 전환한다.
- 진입 전에 pending property edit을 공용 guard로 해소한다.
- 사용 항목 목록의 현재 stable key 순서를 `ReorderSession(snapshotKeys, draftKeys, selectedKey)`로 보관한다. 진입 시 두 key 목록은 같고 이 mode-local session이 확인 전 임시 순서의 유일한 source of truth다.
- 사용 항목 테이블의 컬럼 구성과 행 내용은 그대로 유지한다.
- 테이블 오른쪽에 라벨 설정과 같은 폭/간격/버튼 크기의 위/아래 이동 rail을 표시한다.
- `rowReorderEnabled=true`로 전환하여 행 또는 행 번호 drag reorder를 지원한다.
- 선택 행 기준으로 위/아래 버튼 활성 상태를 계산한다.
- 속성 패널을 포함한 사용 항목 테이블 이외의 위젯은 비활성화한다.
- 속성 패널은 값을 표시해도 입력과 `취소`/`적용`은 비활성화한다.
- 메인 footer `취소`/`저장`도 비활성화한다.
- 사용 항목 테이블 아래에는 왼쪽 제목 `순서 변경`, 오른쪽 `취소`, `저장`을 둔다.

10.2 이동 규칙

- drag와 위/아래 버튼은 같은 reorder function을 사용하고 `ReorderSession.draftKeys`만 변경한다. 확인 전 `workingColumns`의 목록 순서와 persisted order는 바꾸지 않는다.
- 인접 이동과 비인접 이동의 insert index 계산은 현재 `SwipeActionTable` 라벨 설정 테스트 계약을 따른다.
- 이동 후 선택은 이동한 행의 안정 key를 유지한다.
- `orderDirty`는 `ReorderSession.snapshotKeys`와 `draftKeys`의 stable-key sequence 비교 결과다. 한 행뿐이거나 실제 순서가 바뀌지 않으면 false다.

10.3 저장과 취소

- `취소`는 `ReorderSession`만 폐기하고 `normal` 모드로 돌아간다. `workingColumns`, 진입 전 `workingDirty`와 적용된 속성/추가/삭제 상태는 변경하지 않는다.
- `저장`은 `orderDirty=true`일 때만 활성화한다.
- 클릭하면 `변경한 사용 항목 순서를 적용하시겠습니까?`를 질의한다.
- 확인 시 `draftKeys`가 현재 `workingColumns` stable key 집합과 정확히 일치하는지 검증하고, 그 key 순서를 `workingColumns`에 원자 투영해 각 행의 order를 1부터 연속 값으로 다시 부여한다. 원래 순서와 달라진 경우에만 content 비교로 `workingDirty`를 갱신하고 `ReorderSession`을 폐기한 뒤 `normal` 모드로 돌아간다. key 누락·중복·추가는 typed conflict이며 DB transaction을 실행하지 않는다.
- 확인을 취소하면 `reorder` 모드와 현재 임시 순서를 유지한다.
- 최종 DB 저장은 메인 footer의 `저장`에서 신규/수정/삭제/순서를 하나의 transaction으로 처리한다. 따라서 순서 변경 적용 후에도 메인 `취소`로 다이얼로그 전체 변경을 버릴 수 있다.

11. 메인 저장

11.1 저장 전 검증

- `propertyDirty=true`이거나 `initialApplyState=requiredPending`인 행이 하나라도 있으면 메인 저장을 실행하지 않고 사용자가 속성 `적용` 또는 pending 행 제거를 먼저 완료하도록 안내한다.
- 모든 행의 키워드와 항목명 필수
- 전체 키워드 중복 금지
- order를 1부터 연속 값으로 정규화
- 타입별 필수 속성과 범위 검증
- GS1 포함 대상이 현재 working copy에 존재하는지 검증
- 삭제 대상과 신규/수정 대상의 identity 중복 금지
- 현재 labelSizeId와 모든 기존 column의 labelSizeId 일치 확인

해당 라벨 크기에 `BM_RICH_ITEM`이 하나라도 있으면 레거시와 같이 기존 편집 데이터 영향을 최종 확인 내용에 포함한다. 문구는 실제 transaction이 신규 컬럼 콘텐츠 생성, 컬럼 삭제 및 타입 속성 변경을 수행한다는 사실을 명확히 설명한다. 이 확인을 workbook 참조 영향 확인과 별도 순차 dialog로 만들지 않는다.

삭제 또는 키워드 변경이 있으면 dialog open context와 같은 generation의 현재 `LabelSizeSession`이 소유한 revisioned in-memory workbook draft를 참조 영향 검사의 source of truth로 사용한다. DB에 마지막 저장된 workbook, 마지막 비원자적 `onChange` 값이나 별도 static cache로 대체하지 않는다. FortuneSheet controller 공용 API가 `Future<CommitAndPinResult> commitPendingEditAndPinSnapshot()` 또는 동등 API를 직접 소유한다. controller는 모든 cell/formula/object mutation의 실제 적용점에서 단조 `controllerMutationVersion`을 동기 증가시키고, pending editor/IME commit, 최종 version, immutable workbook 복사와 mutation pin 획득을 같은 mutation queue 경계에서 원자 완료한다. `CommitAndPinResult.pinned`에서만 snapshot pin을 반환하며 edit validation 또는 `beforeUpdateCell` 거부는 명시적 reject 결과로 저장을 중단한다. detach는 controller가 아니라 `LabelWorkbookDraftPort`의 attachment epoch 검증이 `WorkbookDraftDetached`로 판정한다. pin이 살아 있는 동안 새 workbook mutation 적용은 대기시키지 않고 `WorkbookSnapshotPinned` typed reject하며, callback은 같은 controller mutation version을 전달하는 관측용 알림일 뿐 snapshot 포함 여부나 저장 권한의 근거가 아니다. `unfocusSheet() → 다음 frame → getAllSheets()` 조합과 callback 증가 횟수 추정은 완료 증거로 사용할 수 없다. session resources의 attachable `LabelWorkbookDraftPort`는 `LabelSheetWorkbench` constructor에 주입하고 `attach(controller, generation, context, ownerToken)`, `detach(ownerToken)`, `flushPendingEditAndSnapshot()`과 `validateSnapshotLeaseAndFreezeCommand(lease)`의 상태 전이를 하나의 serializer로 직렬화하되 controller Future await 중에는 serializer를 점유하지 않는다. port는 성공한 attach와 detach/dispose마다 단조 증가 `attachmentEpoch`을 발급하고, attach owner token과 epoch가 모두 일치하는 callback만 revisioned 관측 draft에 반영한다. flush는 첫 짧은 임계구역에서 owner token/attachment epoch/generation/context와 고유 `flushAttemptId`를 capture·등록하고 serializer를 해제한 뒤 controller의 snapshot pin Future를 await한다. detach는 이 await 중에도 serializer를 획득해 attachment epoch를 증가시키고 해당 epoch의 미선형화 flush attempt를 무효화할 수 있다. controller Future 완료 후 flush는 두 번째 짧은 임계구역에 재진입해 attempt가 아직 current이고 owner/epoch/context가 일치하며 pin의 controller mutation version이 현재 pin version과 같은지 검증하고 snapshot lease를 원자 발급한다. 지연 callback은 version이 pin version 이하이면 idempotent 관측으로 병합하고, pin version을 넘는 callback은 controller pin 계약 위반 typed failure다. 이 두 번째 임계구역의 lease 발급이 snapshot 선형화점이다. detach가 lease 발급 전에 먼저 epoch를 증가시키면 flush는 `releaseActivePin(detached)`를 호출하고 `WorkbookDraftDetached` typed failure로 반환한다. lease 발급 뒤 detach는 이미 반환할 flush 성공을 소급 실패로 바꾸지 않지만 아직 freeze되지 않은 lease를 무효화한다. detach는 항상 새 flush를 거부하고 old epoch callback을 stale로 폐기하며 `_latestWorkbook`, DB workbook 또는 마지막 callback으로 fallback하지 않는다. 저장 coordinator는 사용자 영향 확인이 끝난 뒤 DB command를 dispatch하기 직전에 같은 serializer의 `validateSnapshotLeaseAndFreezeCommand()`를 호출한다. 이 API는 owner token, attachment epoch, generation, customer/market/label-size context와 controller pin/version을 재검증하고 pin이 보호하던 immutable workbook observation을 같은 generation의 command-scoped `WorkbookSaveAuthorizationBarrier`로 원자 인계한 뒤 immutable command를 동기 freeze하고 pin을 release하며, 이 전체가 save authorization의 두 번째 선형화점이다. barrier가 활성인 동안 해당 controller/generation의 새 workbook mutation은 대기시키지 않고 `WorkbookSaveAuthorized` typed reject한다. pre-commit 확정 실패는 barrier를 해제하고, commit 성공/미확정/committed-invalid는 resource별 reload·reconciliation·수동 수용이 terminal 상태에 도달할 때까지 barrier를 유지한다. detach/dispose가 먼저 이기면 typed validation conflict로 DB dispatch를 차단하고, freeze가 먼저 이기면 이후 UI detach는 이미 승인된 in-flight command를 취소하거나 snapshot을 바꾸지 않는다. pin 획득/검증·snapshot decode/복사 실패 또는 context/generation 변경도 저장을 차단한다. 사용자 영향 확인 취소와 모든 failure path는 pin을 정확히 한 번 release한다. command freeze 뒤에는 lease를 다시 열거나 최신 snapshot으로 자동 교체하지 않는다. rename은 변경 전 keyword, delete는 삭제 keyword 집합을 입력으로 하며 셀 표시 문자열/수식/RTF text와 이미지·바코드·QR object ID를 `ReferenceTokenParserV1`으로 검사하고, 현재 session의 완전한 품목 snapshot과 모든 active 출력 context를 12.5의 실제 `LegacyOutputTokenReplacerV1`로 replay한 dependency trace와 합쳐 판정한다. 직접 token과 replacement-created token 중 하나라도 변경 컬럼에 의존하면 영향 대상과 손상 가능성을 표시하고 사용자의 명시적 최종 확인 뒤에만 저장한다. parser/trace 입력 추출 실패, 불완전 품목 snapshot, context 불일치 또는 replay 실패도 저장을 차단해 현재 workbook/session을 정상화·재로드하도록 안내한다. 이 검사는 workbook 저장 포맷을 변경하지 않는다.

앞 문단의 저장 전 영향 확인은 `pending editor commit과 snapshot pin → workbook/parser/exact-trace 영향 계산과 품목/raw content/active output-context observation digest 생성 → DB 품목 영향과 workbook 참조 영향을 합친 단일 최종 확인 → validateSnapshotLeaseAndFreezeCommand() → durable prepare → DB dispatch` 순서로만 실행한다. 확인 취소 전에는 command를 freeze하거나 durable operation을 prepare하지 않고, freeze 뒤에는 추가 사용자 확인을 열지 않는다. 통합 확인 취소와 freeze 전 모든 실패는 `releaseActivePin(reason)`을 통해 lease/pin을 정확히 한 번 release한다. command는 영향 계산에 사용한 완전한 품목 stable-key 집합과 각 active output source의 canonical raw observation digest를 포함하고, label-size save transaction은 application lock 뒤 컬럼 mutation 전에 같은 item/content/output-context projection을 다시 읽어 digest가 일치하는지 검증한다. 불일치하면 어떤 CRUD도 실행하지 않고 typed `OutputDependencyObservationConflict`로 rollback하며 기존 확인을 재사용하지 않는다. 사용자는 최신 session으로 `pin → 영향 재계산 → 통합 확인` 전체를 다시 수행해 새 operation ID command를 만들어야 한다. 이 순서가 앞 문단의 일반적인 “사용자 영향 확인 뒤 freeze” 표현보다 우선하는 normative contract다.

11.2 저장 결과

- `저장` 확인 후 12장의 단일 transaction을 실행한다.
- DB transaction 실패 또는 commit 결과 미확정이면 오류 상태를 구분해 표시한다. 일반적인 commit 전 확정 실패에서만 다이얼로그와 working copy를 편집 가능한 상태로 유지하고 같은 command 저장 재시도를 허용한다. `DbConcurrencyConflict`이면 working copy를 비교 입력으로 보존하되 동일 command와 자동 rebase를 금지하고, 최신 label-column snapshot 재조회 후 사용자가 수동 재적용·재확인해 새 fingerprint와 operation ID를 가진 command를 생성해야 한다. `DbCommitOutcomeUnknown`이면 canonical `commitOutcomeUnknown`으로 전환하고 UI에서만 resource별 reconciling 표시명으로 투영하며 동일 save command 재실행을 금지한다.
- decode 경계는 `native result drain → resultContractValidated(pre-commit) → commit → commitCompleted → resultFrameSendCompleted(worker) → resultFrameFullyReceived(parent) → wireEnvelopeDecoded(parent) → domainDtoDecoded(DAO)`로 고정한다. versioned result contract는 native worker 안에서 저장 count와 신규 ID mapping payload의 JSON/object schema, 기대 draft key 집합, key/ID 유일성·양수 조건을 검증한 뒤에만 commit을 허용한다. parent frame reader가 length/checksum과 operation/session/epoch를 모두 검증한 경우에만 `resultFrameFullyReceivedDurable` local event를 게시한다. `commitCompleted`와 완전한 result frame 수신이 확인된 뒤 isolate envelope/`DbExecutionResult` 복원에 실패하면 `wireEnvelopeDecodeFailedDurable`을 거쳐 `DbCommittedResultInvalid(stage: wireEnvelopeDecode, committedKnown: true)`, envelope는 유효하지만 DAO domain DTO 복원에 실패하면 `domainDtoDecodeFailedDurable`을 거쳐 `DbCommittedResultInvalid(stage: domainDtoDecode, committedKnown: true)`로 분류한다. 호출자는 resource별 committed-invalid로 전환해 동일 save command를 영구 금지하고, 오류를 commit 전 실패나 commit 결과 미확정으로 표시하지 않는다. payload 원문은 로그이나 recovery artifact에 남기지 않는다.
- `committedResultInvalid`는 read-only 복구 화면에서 `전체 재조회`만 제공한다. 같은 프로세스에 검증된 신규 draft key/DB ID mapping payload가 남아 있어도 working draft나 GS1 endpoint에 중간 적용하지 않고 폐기하며 별도 mapping 복구 상태·버튼을 만들지 않는다. 전체 재조회 성공은 DB의 현재 상태를 새 session으로 수용하는 것이며 save를 재실행하거나 commit 여부 reconciliation을 호출하지 않는다. 재조회도 실패하면 `다시 불러오기`와 `화면 닫기`를 제공하되, 화면을 닫아도 앱 루트의 지속 복구 배너와 해당 resource의 `force-reload-required` 차단을 유지한다. 재시작도 같은 resource별 전체 재조회 정책과 14장의 durable startup 판정을 사용한다.
- 공용 reconciliation engine은 resource별 adapter가 제공하는 application lock, 일관된 raw snapshot reader, mutation-closure manifest, original/desired projection, natural-key resolver만 사용한다. label-column adapter는 label-size resource를, customer-column adapter는 customer resource를 사용한다. 같은 application lock을 획득한 짧은 `DbClient.strictTransaction()` 안에서 manifest의 모든 base table 대상 key/range를 동일한 전역 순서와 `UPDLOCK, HOLDLOCK`으로 읽어 transaction 종료까지 key-range lock을 유지한 하나의 관측 snapshot을 만든다. 단일 batch/transaction이라는 사실만으로 일관성을 주장하지 않는다. mutation-closure rowset별 predicate와 필수 index의 key 순서/leading column/filter/enabled/collation 호환성을 schema capability에 고정한다. 이 결정적 계약이 없으면 편집, save와 reconciliation을 fail-closed로 차단하고, 실제 execution plan과 range-lock 확인은 승인 배포의 integration gate에서 검증한다. 필요하면 검증된 index hint/query template을 사용한다. 별도 승인 migration으로 index를 배포하거나 성능·교착 영향을 검증한 명시적 table-level lock 전략을 채택하기 전 조용히 광범위 lock으로 진행하지 않는다. current DB projection을 original/desired와 비교해 desired와만 일치하면 `desiredStateObserved`로 보고 reload-only 경로로 이동하고, original과만 일치하면 `originalStateObserved`로 표시한 뒤 DB에서 새 snapshot을 만들어 사용자가 새 command를 명시적으로 생성할 때만 재저장을 허용한다. 둘 다 일치하거나 둘 다 불일치, natural key 매칭 0/복수, context/generation 변경, lock 실패, 재조회 실패는 reason code가 있는 `indeterminate`로 두고 `force-reload-required`와 수동 확인을 요구한다. original과 desired가 같은 no-op command는 DB 실행 전에 제거한다. `DbCommitOutcomeUnknown`의 비교 결과를 해당 operation의 commit 여부로 로그/문구에서 단정하지 않는다. 프로세스 재시작 후에는 original/desired projection이 없으므로 이 알고리즘을 호출하지 않는다.
- commit 성공 즉시 dialog session을 `committedReloadPending`으로 전환하고 저장/편집/닫기를 차단한다. 이 상태에서는 동일 save command를 다시 실행하지 않는다.
- 앱 root의 `LabelSizeSessionStore`와 `LabelSizeReloadCoordinator`가 컬럼, 특수 컬럼, scoped column content, 품목 목록/raw snapshot, validation rule, 공용라벨 required keyword/image/barcode 정보와 출력 미리보기를 immutable `LabelSizeSessionData`로 만들고, controller/journal/listener처럼 lifecycle이 있는 객체는 별도 `LabelSizeSessionResources`가 소유한다. 둘을 generation과 함께 묶은 `LabelSizeSession` 단일 reference를 전역 상태와 분리해 완전히 생성·교체한다. `HomePageManager`는 root store/coordinator에 attach하는 UI consumer/renderer이며 session factory나 authoritative reference를 소유하지 않는다. 따라서 `HomePageManager`가 detach/dispose된 동안에도 root coordinator는 committed reload를 실행해 candidate를 준비·활성화할 수 있고, UI `renderReady`가 필요한 단계는 새 manager attach까지 durable pending으로 보존한다. session scope에는 customer/market/label-size immutable context, mapping/concurrency fingerprint와 validation/preview 입력도 포함한다. `TColumnType`처럼 연결 generation 동안 불변인 참조 데이터만 application cache로 분류할 수 있다. `TColumn.datas`, `TColumnContent.datas`, `TColumnSpecial.datas`, `ItemOfMarket.datas`, `_currentLabelSize`, `Market.instance`를 세션 동작 중 직접 조합하거나 개별 static cache를 순차 교체하는 방식은 atomic swap으로 간주하지 않는다. 모든 세션 화면/helper는 generation-bound session accessor를 주입받는다.
- candidate는 controller, journal metadata, storage 접근과 baseline 검증을 부작용 없는 `prepare` 단계까지 수행하고 기존 journal과 같은 draft key의 listener를 미리 시작하거나 이전 파일을 정리하지 않는다. journal은 `draftKey`, `generation`, `ownerToken`, generation별 `filePath`, `phase`, `previousOwner`, payload/manifest checksum을 하나의 durable manifest에 temp-write, file handle `FlushFileBuffers`, 원자 교체 순서로 저장한다. Windows 구현은 target이 있으면 `ReplaceFileW(target, temp, backup, 0, ...)`, target이 없으면 같은 디렉터리의 `MoveFileExW(temp, target, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`를 공용 native primitive로 사용하고 target을 먼저 `.bak`으로 이동해 target 부재 구간을 만들지 않는다. POSIX `fsync(directory)`와 같은 directory-entry 또는 전원 차단 durability를 보장한다고 표현하지 않으며, target/tmp/bak recovery scan으로 process-crash consistency를 제공한다. SharedPreferences는 manifest discovery hint 하나만 저장하며 소유권 source of truth로 사용하지 않는다. startup은 hint 존재 여부와 무관하게 전용 manifest 디렉터리의 target/tmp/bak를 스캔한다. checksum이 유효한 target의 publish 완료 phase를 우선하고, target이 없거나 무효일 때만 같은 generation의 완료된 tmp를 승격하며, 그마저 없을 때 유효한 bak로 복구한다. 같은 generation에 서로 다른 ownerToken의 유효 artifact가 둘 이상이거나 phase 전이가 불가능하면 임의 선택·삭제하지 않고 격리 후 `force-reload-required`로 전환한다. 선택 owner가 resume된 뒤에만 더 낮은 generation artifact를 정리한다. 각 prepare/suspend/activate/swap/render/dispose 직후 process crash와 native API 실패에 대해 선택·보존·격리·삭제 규칙을 recovery matrix와 child-process fault-injection fixture로 고정한다. `prepare`, `suspend(clearFile: false)`, `activate`, `resume`, `dispose`는 manifest lease를 검증하고 `clear/dispose`는 현재 owner token과 일치할 때만 파일을 삭제한다. 소유권/manifest 저장 실패를 background error로 삼키지 않는다.
- load generation과 immutable customer/market/labelSize context가 일치할 때 root `LabelSizeReloadCoordinator`만 기존 journal write queue drain/suspend, candidate activate, authoritative session reference swap과 old resource retirement를 수행한다. `HomePageManager`의 attach API는 새 generation key로 widget subtree/listener를 재결합하고 `renderReady | typed failure`만 반환하며 activate/swap/dispose나 lease recovery 결정을 수행하지 않는다. 첫 `renderReady` 전에는 기존 resources를 유지하고, 성공 후에만 root coordinator가 기존 controller/journal을 dispose한다. activate/swap/render가 실패하면 root coordinator가 durable manifest recovery matrix에 따라 기존 session resume, candidate active 유지, 또는 `force-reload-required` 중 하나로 결정한다. 오래된 generation 완료 결과는 handoff 전에 폐기한다.
- 위 old resource 유지·resume·dispose와 `expectedOldGeneration` compare-and-swap은 `LabelSizeActivationMode.warmHandoff`에만 적용한다. 프로세스 재시작의 `coldRecoveryActivation`은 durable recovery operation ID와 새로 발급한 generation/context를 transition guard로 사용하고 old session generation 또는 old resources를 요구·합성하지 않는다. cold candidate를 authoritative initial session으로 activate한 뒤 필수 consumer의 durable `consumerApplyCompleted`와 현재 process incarnation/attachment epoch에 귀속된 `liveRenderReady`가 모두 새 generation을 관측하고 해당 recovery operation의 resource barrier 재평가가 완료돼야 성공이다. 이전 process의 durable apply ACK는 idempotent state 적용 근거로 재사용할 수 있지만 현재 UI attach/render 완료 근거로 사용할 수 없다. cold activation 실패는 존재하지 않는 old session resume로 낮추지 않고 candidate 폐기 또는 `force-reload-required` 중 recovery matrix가 정한 결과로 전이한다.
- 현재 `_handleLabelSizeChanged(forceReload: true)`/`_reloadItemDraftFromDatabase()`처럼 render 성공 전에 기존 journal/controller를 닫고 static cache를 순차 교체하는 경로는 label-column post-commit reload에서 호출하거나 adapter로 감싸 재사용하지 않는다. root coordinator만 `prepareCandidate()`와 `commitCandidateSwap(expectedOldGeneration, candidate)` 또는 동등 API를 호출하고, `HomePageManager`에는 완성된 candidate를 받는 `attachCandidateAndAwaitRender(candidateGeneration)`만 노출한다. 구조 lint와 integration test는 post-commit call graph가 legacy force-reload symbol 및 `TColumn.datas` 등 static cache write를 참조하면 실패한다.
- swap 완료 후 render가 취소되거나 실패하면 상위 상태를 `force-reload-required`로 전환해 후속 편집을 차단한다. 이미 commit된 DB를 되돌리거나 save command를 재실행하지 않는다.
- reload 성공 후에만 다이얼로그를 자동으로 닫는다. reload 실패 시 `committedReloadFailed` read-only 오류 화면으로 유지하고 `다시 불러오기`와 명시적 `화면 닫기` 버튼을 제공한다. 제목 표시줄 닫기/Esc는 계속 소비한다. `화면 닫기`로 overlay를 닫아도 앱 루트 bootstrap service가 `HomePageManager` 위에 표시하는 지속 복구 배너와 해당 resource의 `force-reload-required` 차단을 유지하며, 배너는 `다시 불러오기`, 진단 보기와 상태가 요구할 때만 `현재 DB 상태 수용` action을 제공한다. 이 지속 진입점이 준비되지 않은 플랫폼에서는 오류 overlay의 `화면 닫기`를 노출하지 않는다.

12. DB 모델과 DAO

12.1 추가할 모델

구체 파일명은 기존 모델 구조에 맞추되 최소한 다음 역할을 분리한다.

- `LabelColumnDraft`: 아래 persisted field allow-list, 기존 columnId 또는 신규 `DraftMappingKeyV1`, new/modified 상태와 `initialApplyState: notRequired | requiredPending | completed`
- `LabelColumnEditSession`: original/working/deleted/selection/property 상태와 content 비교
- `ReorderSession`: 진입 시 `snapshotKeys`, mode-local `draftKeys`, nullable `selectedKey`를 소유하고 확인 전 임시 순서의 유일한 source of truth가 되는 상태
- `BlockedCloseSource`: `escapeKey | frameCloseButton | systemBack | appOwnedNavigatorPop | desktopWindowClose`의 폐쇄 enum. `BlockingOverlayStack`은 현재 top token과 이 source를 하나의 비동기 close command에 전달하고 stack이 비었을 때만 root app-exit lifecycle로 위임한다. 임의 framework `Navigator.pop()`을 관측 가능한 source로 가장하지 않는다.
- `FixedColumnType`: 고정 항목 분류 ID와 이름. 존재하지 않는 order 필드를 만들지 않는다.
- `FixedColumnCandidate`: fixedColumnId, 타입, 키워드, 항목명, 분류 ID
- `CustomerColumnCandidate`: custColumnId, customerId, 타입, 키워드, 항목명
- `CustomerColumnDraft`: 기존 `custColumnId` 또는 session-local `DraftMappingKeyV1 draftCustomerColumnKey` 중 정확히 하나, customerId, 타입, 키워드, 항목명과 grandfather policy/new/modified 상태
- `CustomerColumnEditSession`: 사용자 항목 original/working/deleted/selected stable key 상태
- `DraftMappingKeyV1`: label/customer 신규 행이 공통으로 사용하는 session-local 128-bit UUID의 lowercase ASCII canonical text(`8-4-4-4-12`, 36자). 생성·JSON decode 단계에서 exact grammar와 nil UUID 금지, ordinal case-sensitive 유일성을 검증하고 SQL staging은 `VARCHAR(36) COLLATE Latin1_General_100_BIN2` 또는 동등한 36-byte binary/ordinal 표현만 사용한다. 업무 DB collation, `NVARCHAR(100)` 임의 길이, 대소문자 fold, trim, 절단·변환 성공에 identity 비교를 맡기지 않는다.
- `LabelColumnSaveCommand`: labelSizeId, insert/update/delete 목록, 최종 순서, 저장 context, concurrency fingerprint와 observation projection
- `OutputDependencyObservationV1`: `dbRecheckableObservation`과 `frozenWorkbookObservation`을 분리한다. 전자는 저장 영향 계산에 사용한 완전한 item stable-key 집합과 DB-backed active QR/barcode/GS1 raw content의 canonical digest 및 transaction 안에서 재계산할 key/version metadata를 가진다. 후자는 pinned immutable workbook의 generation/controller mutation version/context digest를 가지며 DB에서 재계산하지 않고 `WorkbookSaveAuthorizationBarrier`가 command terminal 상태까지 같은 generation의 mutation을 차단해 보호한다. 어느 projection도 payload 원문을 포함하지 않는다.
- `WorkbookSaveAuthorizationBarrier`: freeze가 controller pin의 mutation exclusion을 원자 인계받는 command-scoped generation barrier. pre-commit terminal failure 또는 post-commit resource recovery terminal transition만 해제할 수 있고 UI detach만으로 해제하지 않는다.
- `CustomerColumnSaveCommand`: customerId, insert/update/delete 목록, original concurrency fingerprint, desired observation projection, immutable 로그인/DB identity context와 opaque operation ID. labelSizeId, GS1 관계와 label session generation은 포함하지 않는다.
- `DbExecutionResult`/동등 DTO: 각 결과셋의 독립 columns/logical types/rows와 전체 affected count를 보존하는 driver 반환 타입
- `DbLogicalType`/`DbColumnMetadata`: ODBC native type, DB-Lib `SYB*` 또는 Android/iOS driver native type을 직접 노출·비교하지 않고 `integer`, `decimal`, `string`, `dateTime`, `binary`, `boolean` 등 공용 logical type으로 정규화한다. nullability는 `noNulls | nullable | unknown`, 각 수치 metadata는 `known(value) | unknown | notApplicable`로 구분하고 character length/octet length/numeric precision/numeric scale/temporal fractional precision을 혼용하지 않는다.
- `DbWireScalar`: row value를 driver 구현 타입에 맡기지 않고 integer 범위 보존 값, decimal canonical 문자열, timezone/precision이 명시된 temporal 문자열, boolean, string, binary base64 descriptor와 DB null로 정규화하는 versioned wire 값. DB null, 빈 string, 빈 binary, 문자열 `"0"`, 숫자 0과 false는 서로 다른 kind/value로 보존한다.
- `DbResultContract`: marker column/type, result-set/row cardinality, count 기대값, resource별 mapping object schema와 command의 신규 draft key 집합을 commit 전에 검증하는 versioned wire descriptor. label/customer mapping kind를 서로 cross-decode하지 않는다.
- `DbValidatedResultPayloadV1`: native worker의 `DbResultContract`가 logical type/cardinality/count/mapping JSON object schema, `DraftMappingKeyV1` grammar와 command key 집합, key/ID 유일성·양수 조건, resource kind와 모든 DTO discriminant/enum/version까지 검증한 뒤에만 만드는 sealed wire payload. `kind`, `schemaVersion`, operation/session/epoch, resource mapping kind, marker/count와 typed mapping entries를 명시하고 payload 내부 draft key도 `DraftMappingKeyV1` canonical text로만 직렬화한다. 같은 schema version의 resource DTO mapper는 이 payload에 대해 total/infallible projection이어야 하며 count/key/ID/discriminant 의미 검증을 다시 수행해 commit 후 protocol 오류로 재분류하지 않는다. post-commit `domainDtoDecodeFailedDurable`은 정상 지원 상태가 아니라 주입된 mapper defect 또는 sealed payload invariant 위반의 폐쇄 internal reason code에만 허용하고 알려지지 않은 wire enum/version은 pre-commit contract 또는 parent wire decode에서 차단한다.
- `DbResultSetContract`: raw snapshot의 rowset kind/version/ordinal, column/type와 cardinality를 검증하는 versioned descriptor
- `DatabaseIdentity`/`stableDatabaseIdentityDigest`/`connectionEpoch`: 비밀정보를 제외한 검증된 server/database identity, recovery namespace용 안정 digest와 connect 성공마다 증가하는 cache/요청 소유 epoch. 연결 전 endpoint/DB name은 `connectionProfileHint`일 뿐 identity가 아니다. digest는 canonicalization version과 아래 versioned identity probe의 verified tuple을 사용하고 password, connection epoch, `family_guid`와 단순 DNS/IP 별칭을 포함하지 않는다. 사용자 결정에 따라 AG의 `group_id`/`group_database_id`가 일치하는 failover 또는 standalone의 같은 `database_guid`만 같은 identity로 보고 restore·clone은 새 namespace로 분리한다.
- `DbIdentityProbeResult`: `verifiedAvailabilityGroup | verifiedStandalone | notInAvailabilityGroup | unsupportedPlatform | permissionDenied | metadataHidden | malformed` kind, canonical database name, `SERVERPROPERTY('EngineEdition')`/product version, current DB의 `sys.database_recovery_status.database_guid`, AG일 때 `sys.availability_databases_cluster.group_id`/`group_database_id`, 필드별 provenance와 권한 진단을 보존한다. `family_guid`, server/machine/instance 표시명은 진단값일 뿐 digest source가 아니다.
- `DbConnectionBootstrap`: `connectAttemptId`, `expectedPreviousEpoch`, transport/identity/recovery readiness를 소유하고 connect 성공 시 발급된 epoch보다 오래된 attempt 응답을 폐기하는 연결 상태기계. 외부 상태는 `disconnected | transportConnecting | transportConnected | identityProbing | recoveryBinding | ready | degradedReady`로 구분한다.
- `DbNativeSessionToken`: native connection을 새로 열 때마다 driver 내부에서 발급하며 transaction의 모든 statement/commit/rollback/cleanup이 같은 ODBC HDBC 또는 DB-Lib DBPROCESS를 사용하는지 검증하는 비공개 token
- `DbTransactionIsolation`: 최소 `snapshot | readCommitted | serializable`을 wire에서 폐쇄 열거하는 transaction isolation descriptor. V1은 baseline raw DAO=`snapshot`, label/customer save와 reconciliation=`serializable`로 고정하며 manifest나 호출자가 더 약한 값으로 낮출 수 없다.
- `NativeDbTransactionSession`: driver가 발급한 하나의 `DbNativeSessionToken`과 native connection을 배타 소유하고 `begin(DbTransactionIsolation isolation)`, `executeAndDrain`, `commit`, `rollback`, `verifyTransactionClosed`, `discard`만 노출하는 transaction 전용 객체. transaction 제어 SQL을 일반 `writeData()`로 보내거나 command마다 native connection을 다시 선택하지 않는다. transaction 종료 시 connection isolation을 검증된 기본값으로 복원하거나 native session을 폐기해 다음 command로 isolation이 누출되지 않게 한다.
- `DbOperationAck`: worker가 관측한 `operationAccepted → commitDispatchObserved → commitCompleted → resultFrameSendCompleted`의 cumulative high-watermark와 operation/session/epoch ID를 보존하는 versioned ack. worker의 send 완료는 parent의 receive 완료를 뜻하지 않는다. `commitDispatchObserved`는 worker가 native commit 호출에 진입하기 직전 별도 control channel로 방출한 관측 증거이며 parent의 사전 `commitDispatchIntentDurable`을 대체하지 않는다. control/result channel 간 지연·재정렬이나 중간 ACK 유실이 있어도 더 높은 유효 ACK는 이전 worker 관측 단계를 함의하는 high-watermark로 수용한다. 낮은 단계의 후착 ACK는 같은 canonical payload이면 idempotent stale ACK로 무시하고 ID/payload가 다르면 typed reject한다. `resultContractValidated`는 commit 전 worker 내부 증거로 result frame/contract에 포함한다. `resultFrameFullyReceived`, `wireEnvelopeDecoded`와 `domainDtoDecoded`는 worker ACK가 아니라 각각 parent frame reader, parent wire decoder와 DAO mapper가 동일 operation/session/epoch를 검증한 뒤 `RecoveryTransitionTableV1`에 제출하는 local event다.

DB 연결 전 namespace-neutral 무결성 scan과 identity bind 뒤 unresolved evidence 재발견을 수행하며 P2 recovery consumer가 아직 bind되지 않은 상태에서 unresolved evidence가 있으면 해당 resource의 새 strict dispatch를 fail-closed한다. P2 journal/registry는 이 store를 교체하거나 별도 evidence source를 만들지 않고 workflow/resource barrier/tombstone projection을 확장한다.

- `LabelWorkbookSnapshot`: immutable workbook, controller mutation version, stable database/customer/market/label-size context와 session generation을 묶은 영향 검사 입력

- `WorkbookSnapshotLeaseState`: `activePinned | frozenReleased | invalidatedReleased | cancelledReleased`의 폐쇄 상태. port serializer 안의 `releaseActivePin(reason)` CAS만 실제 controller pin release를 수행하며 detach, confirmation cancel과 coordinator failure cleanup은 이 API만 호출하고 pin을 직접 release하지 않는다.

`TColumn`에 UI 임시 상태를 넣지 않는다. 저장 command는 widget 상태를 직접 참조하지 않는 immutable DTO로 만든다.

`LabelColumnDraft`의 persisted field allow-list는 다음과 같다. 실제 배포 DB capability에서 컬럼이 없는 경우 조용히 누락하지 말고 진입을 차단하거나 호환 SQL을 명시적으로 분기한다.

- identity/context: `RICH_COLUMN_ID`, `RICH_LABELSIZE_ID`, `RICH_COLUMN_ORDER`
- 공통: `RICH_COLUMN_NAME`, `RICH_KEYWORD`, `RICH_TYPE`, `RICH_TITLE`, `RICH_VISIBLE`
- 크기/바코드: `RICH_WIDTH`, `RICH_HEIGHT`, `RICH_BARCODE_TYPE`, `RICH_USE_BARCODE_CHECKDIGIT`, `RICH_SHOW_BARCODE_NUM`, `RICH_TIMEBARCODE_TYPE`, `RICH_USER_DEFINE_BARCODE_TEXT`, `RICH_BARCODE_LINE`, `RICH_BARCODE_LINE_SIZE`, `RICH_BARCODE_ROTATE`
- QR/기본 사용자 정의: `RICH_SHOW_QRCODE_TEXT`, `RICH_QRTEXT_ALIGNMENT`, `RICH_USE_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRTEXT`, `RICH_PIXELSIZE`, `RICH_QRCODE_CREATE_TYPE`, `RICH_NATRIUM_JOIN_STRING`, `RICH_QRTEXT_FONTSIZE`, `RICH_QRTEXT_FONTNAME`, `RICH_QRCODE_SCALE`
- 자동 증가/날짜 범위: `RICH_AUTO_INC`, `RICH_AUTO_INC_SIZE`, `RICH_AUTO_INC_RANGE`, `RICH_AUTO_INC_SAVE`, `RICH_AUTO_INC_ZERODEL`, `RICH_AUTO_INC_UPDATE`, `RICH_USE_DATERANGE`, `RICH_DATERANGE`. `RICH_SEARCH_PRINT`는 레거시 별도 검색출력 설정 writer의 소유이므로 이번 UI/dirty/updateRows 대상에서 제외하되 기존 행 raw 값을 snapshot/fingerprint/projection에 보존하고 신규 행은 레거시 후보 기본값 `0`으로 생성한다.
- 누락 검사: `BM_RICH_CHECK_COLUMNS.RICH_CHECK_YN`; main table의 `RICH_USE_MISSING_KEYWORD_CHECK`가 배포 DB에 존재하면 같은 값으로 동기화한다.
- GS1: `BM_GS1_COLUMN_INFO.COLUMN_GS1_CODE`, `COLUMN_GS1_FORMAT_OPTION`, `COLUMN_SHOW_GS1CODE`와 `BM_GS1_CONTAIN_COLUMN` 최종 관계

`checkMode`, `editableCellNum`, `newColumnQRCodeInfo`, `barFontSize`, `modify`, `change`는 화면/런타임 상태이므로 draft 저장, dirty 비교, SQL parameter에서 제외한다.

`RICH_USE_USER_DEFINE_QRDATA`는 레거시 출력/create-type mode 판정 필드가 아니라 preservation-only persisted scalar다. 기존 행은 raw 값을 fingerprint/projection과 save round-trip에 보존하되 UI에서 수정하거나 `RICH_QRCODE_CREATE_TYPE`으로 재계산하지 않고 editable dirty/update assignment 대상에서 제외한다. 신규 후보만 레거시 기본값 `0`으로 생성한다. 기본 타입의 `RICH_USER_DEFINE_QRTEXT`도 data가 변경되지 않은 save에서는 preservation-only이며 data가 실제 변경된 command에서만 명시적으로 `''` update 대상이 된다.

`LabelColumnDraft`는 enum으로 해석된 값뿐 아니라 DB에서 읽은 raw type code, QR alignment code, QR create type code, barcode type name을 보존한다. 지원하지 않는 raw 값은 기본값으로 치환해 저장하지 않고 해당 행을 read-only 오류 상태로 표시하며, capability/호환 규칙이 추가되기 전 전체 저장을 차단한다.

fingerprint 계약은 다음 두 projection으로 분리한다.

- `concurrencyFingerprint`: 기존 column/custColumn DB ID, raw persisted scalar, null/빈 문자열 구분, order와 save가 변경하는 전체 mutation closure를 canonical JSON으로 정렬해 동시 변경을 검출한다.
- `desiredObservationProjection`: 기존 행은 DB ID를 유지하고 신규 행은 대상 컬럼 자체의 SQL Server 비교식으로 유일 keyword를 매칭한다. 관측된 신규 ID를 관계 endpoint와 child row에 다시 투영한 뒤 canonical JSON을 비교한다. keyword 후보가 0개 또는 2개 이상이면 `indeterminate`다.

label-column mutation-closure manifest는 최소한 다음 rowset을 각각 독립 key/필드/기대 행 수/absence 조건으로 고정한다: persisted allow-list의 `BM_RICH_COLUMN`, `RICH_MIN_CHECK`를 포함한 `BM_RICH_COL_MIN` 일반 행과 정확히 1개인 `ELEMENT` sentinel, `BM_RICH_CHECK_COLUMNS`와 capability가 있는 main check flag, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN` 양방향 endpoint, 삭제 컬럼의 `BM_COLUMN_QRCODE_INFO` 양방향 orphan 부재, 현재 item ID별 `BM_RICH_COL_CONTENT` 존재/부재, capability에 따른 `BM_UPDATE_COL_CONTENT`, `BM_RICH_STATUS_DATA` 변경 상태. 저장 중 item 집합도 같은 lock/snapshot에서 관측한다. `GETDATE()` status처럼 operation ledger 없이 desired exact value를 만들 수 없는 side effect가 commit 결과 미확정 command에 포함되면 추정 비교하지 않고 `indeterminate`로 판정한다. customer-column adapter는 customer-scoped `BM_RICH_CUST_COLUMN` persisted row 전체를 별도 manifest로 정의한다.

두 projection은 필드 순서, row 정렬, 숫자/boolean 표현, null과 빈 문자열, raw enum/name, 관계 endpoint 변환과 content 존재 조건을 하나의 공용 canonicalization fixture로 고정한다. Dart와 SQL에서 서로 다른 임의 hash 직렬화를 만들지 말고, 동일 canonical row 집합을 비교하거나 검증된 byte serialization만 사용한다.

natural-key 후보 계산은 Dart의 대소문자 변환, `trim`/`RTRIM` 또는 별도 정규화로 SQL collation을 흉내 내지 않는다. `RICH_KEYWORD = CONVERT(<target SQL type>, @keyword)` 또는 cust-column 대상 컬럼의 동등 비교를 사용해 case/accent/kana와 trailing-space 동등성을 DB가 직접 판정한다. 저장 전 working keyword 중복도 같은 SQL 동등성 fixture로 검증하고, 절단/변환 후 DB에 실제 저장된 keyword를 재조회해 projection에 사용한다.

기본 타입의 사용자 정의 데이터는 별도 DB 필드를 만들지 않고 레거시와 같이 `RICH_QRCODE_CREATE_TYPE`, `RICH_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRTEXT`를 재사용한다. 제조/유통 날짜·시간의 종류는 `RICH_TYPE`이며 별도 날짜 형식 컬럼을 만들지 않는다. 컬럼별 날짜 부가 설정은 `RICH_USE_DATERANGE`, `RICH_DATERANGE`만 저장한다.

각 속성 editor 구현 전 `type code → editor → UI 입력 → LabelColumnDraft/raw 필드 → DB 테이블/컬럼 → SQL 타입/max byte/nullability → 최소·최대 → 타입 변경 시 유지/초기화` 매핑표를 코드 옆 문서 또는 테스트 fixture로 작성한다. type 0~12의 모든 source→target 전환에 대해 각 persisted scalar와 QR/GS1 child row에 `legacyObserved`, `newPolicy`, `intentionalDivergence`, 레거시 근거 symbol/line과 저장 후 expected projection을 기록한다. `TYPE_BASE → TYPE_QR_CODE`와 `TYPE_QR_CODE → TYPE_BASE`는 `CColumnSetupMainDlg::OnCbnSelchangeComboType()`과 같이 `RICH_QRCODE_CREATE_TYPE=QRCODE_TYPE_PLAIN_TEXT`, `RICH_USER_DEFINE_QRDATA=''`, `RICH_USER_DEFINE_QRTEXT=''`로 초기화하고 `intentionalDivergence=false`로 고정한다. 다른 전환은 일관된 일괄 초기화 규칙을 새로 만들지 않고, 레거시가 editor 기본값으로 덮는 필드, 기존 객체 값을 보존하는 필드, create type에 따라 조건부 setter를 호출하는 QR data/text와 별도 child lifecycle을 각각 재현한다. 단, 기본 editor hydration의 QRTEXT 보존은 위의 승인된 `intentionalDivergence=true`다. 레거시 근거가 없는 전환은 구현하지 않고 fixture 미확정으로 진입을 차단한다.

12.2 조회 DAO

- 현재 사용 항목: 편집기 전용 `RawLabelColumnRowDAO.selectByLabelSizeId`. 기존 `TColumnDAO.selectByLabelSizeId()`와 `TColumn.fromMap()` fallback 경로를 편집기 snapshot, dirty 비교, fingerprint, SQL serializer에서 호출하지 않는다. raw DAO는 `DbClient.queryResultSets(..., required DbResultSetContract contract, isolation: DbTransactionIsolation.snapshot) -> DbExecutionResult` 또는 이름이 같은 typed public API만 사용해 하나의 짧은 transaction에서 `BM_RICH_COLUMN`, `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN` base table과 capability child를 독립 rowset으로 조회한다. 사용자 결정에 따라 최초 baseline은 bootstrap capability가 `snapshot_isolation_state=ON`을 확인한 DB에서 명시적 `SNAPSHOT` isolation으로 모든 manifest rowset을 읽고 DAO 반환 전에 transaction을 종료한다. 최초 조회에 `UPDLOCK, HOLDLOCK`을 사용하지 않으며 snapshot isolation이 없거나 version-store 오류가 발생하면 일반 조회로 낮추지 않고 typed 진입 실패로 차단한다. save/reconciliation은 `DbClient.transaction(..., isolation: <manifest value>)`으로 isolation을 명시하고 application lock 뒤 동일 순서의 `UPDLOCK, HOLDLOCK`을 사용한다. SQL text의 `SET TRANSACTION ISOLATION LEVEL`로 pooled/native connection의 다음 command에 상태를 누출하지 않는다. 각 `SELECT`는 rowset kind/version을 반환하거나 contract의 고정 ordinal/schema에 정확히 일치해야 하며 누락·중복·순서/schema 불일치는 protocol error다. raw DAO에서 기존 `Object` 반환 `getData*()` compatibility API와 transaction 밖 복수 query 사용을 금지한다. main/child raw SQL에는 null을 기본값으로 바꾸는 `CASE`/`COALESCE`를 사용하지 않고, `VIEW_BM_GS1_CONTAIN_COLUMN` 같은 집계 view로 0/1/복수 관계를 평탄화하지 않는다. 각 rowset은 원래 DB null, 미지원 scalar, 중복 child와 양쪽 endpoint를 그대로 보존한 뒤 strict mapper가 지원 여부를 판정한다. 사용 항목 표시 순서는 `RICH_COLUMN_ORDER ASC, RICH_COLUMN_ID ASC`로 고정한다.
- 고정 항목 분류: `BM_RICH_FIX_COL_TYPE`, `RICH_FIX_COL_TYPE_ID ASC`로 정렬
- 고정 항목 후보: `BM_RICH_FIX_COLUMN`, 선택한 type ID 조건
- 사용자 항목 후보: `BM_RICH_CUST_COLUMN`, 현재 로그인 customer ID 조건
- 항목 종류: 기존 `TColumnType.datas`; 미초기화 상태면 DB 조회 후 dialog를 표시한다.

모든 조회 문자열은 현재 프로젝트 DAO 규칙에 맞춰 CP949 컬럼을 명시적으로 NVARCHAR로 변환한다. 저장 capability는 `sys.columns`에서 필드별 `typeName`, `maxLength`, `isUnicode`, `isMax`, `nullable`, `collation`을 수집하고 mutation-closure predicate별 필수 index의 정확한 key 순서/leading column/filter/enabled 상태와 collation·predicate 호환 여부도 포함한다. runtime gate는 이 결정적 schema 계약만 사용하고 통계, parameter sniffing, SET option과 plan cache에 따라 바뀌는 관측 실행 계획으로 기능을 켜거나 끄지 않는다. 필요한 경우 검증된 index hint/query template을 고정하며 실제 plan/range-lock 검사는 배포 integration gate로만 사용한다. 권한 부족, schema 부적합과 integration plan 불일치는 서로 다른 reason code다. `max_length=-1`은 MAX로, `NVARCHAR/NCHAR`의 양수 `max_length`는 UTF-16 byte 단위로, `VARCHAR/CHAR`는 대상 code page byte 단위로 해석해 하나의 문자 수 제한으로 혼용하지 않는다. capability와 `TColumnType` 같은 reference cache는 `(DatabaseIdentity, connectionEpoch)`에 귀속한다. connect 성공마다 epoch를 증가시키고 connect/disconnect/connection loss/isolate 재생성/DB identity 변경/schema migration 때 기존 cache를 폐기한다. `DB_ID()`만으로 다른 server를 구분하지 않는다.

index capability는 `IndexPredicateRequirementV1` checked-in manifest가 source of truth다. raw snapshot, concurrency fingerprint, reconciliation과 absence 검증에 사용하는 각 SQL statement/predicate마다 `queryId`, `table`, `equalityPrefix`, `rangeSuffix`, `requiredUnique`, `acceptedFilter`의 normalized expression, `requiredCollation`, `includeColumns`, `approvedIndexNames`, optional verified query/index hint와 table-lock 대안을 기록한다. 최소한 `BM_RICH_COLUMN`, `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN`의 양 endpoint, `BM_COLUMN_QRCODE_INFO`의 양 endpoint, `BM_RICH_ITEM`, `BM_RICH_COL_CONTENT`, capability에 따른 `BM_UPDATE_COL_CONTENT`와 `BM_RICH_STATUS_DATA`, customer-scoped `BM_RICH_CUST_COLUMN`의 실제 save/snapshot predicate를 모두 열거한다. `sys.indexes`, `sys.index_columns`, `sys.columns`와 권한 probe를 함께 읽고 disabled/hypothetical/filtered index, key/include 순서와 collation을 검증해 `compatible | missing | incompatible | permissionDenied`를 구분한다. prose의 "적절한 index"나 index 이름만으로 통과시키지 않으며 manifest에 없는 query는 편집/save/reconciliation을 fail-closed로 차단한다. 승인 DDL 또는 table-lock 대안은 해당 `queryId`에 직접 연결한다.

identity bootstrap은 일반 SQL 실행 API가 아니라 `probeDatabaseIdentityV1` privileged operation 하나로 고정한다. probe SQL은 현재 DB의 `DB_NAME()`, `SERVERPROPERTY('EngineEdition')`/`ProductVersion`, `sys.database_recovery_status.database_guid`를 읽고, SQL Server AG catalog가 지원되고 metadata가 보이면 `sys.availability_databases_cluster`의 current database `group_id`/`group_database_id`를 함께 읽는다. `HAS_PERMS_BY_NAME`과 catalog 접근 결과를 사용해 AG 미가입, 권한 부족, metadata hidden, 미지원 engine을 구분하며 0행/NULL을 standalone으로 추정하지 않는다. exact SQL text, 최소 권한과 SQL Server edition/version별 expected row fixture를 identity probe schema version에 포함한다. 연결 전 `connectionProfileHint`는 namespace-neutral artifact 탐색에만 사용한다. `verifiedAvailabilityGroup`은 `(groupId, groupDatabaseId, canonicalDatabaseName)`, `verifiedStandalone`/`notInAvailabilityGroup`은 `(databaseGuid, canonicalDatabaseName)`의 versioned serialization으로 digest를 계산한다. 지원하는 identity 이동 절차는 backup/restore, detach/attach, AG seed/failover, storage/VM snapshot을 폐쇄 열거하고 각 절차의 metadata 유지·변경 기대값과 허용 여부를 fixture로 고정한다. metadata만으로 원본과 clone의 incarnation 분리를 증명할 수 없는 절차는 production에서 금지하며 임의 endpoint/server 표시명을 digest 보강값으로 사용하지 않는다. 사용자 결정에 따라 `permissionDenied | metadataHidden | unsupportedPlatform | malformed`이면 endpoint 임시 digest나 새 authoritative namespace를 만들지 않고 `degradedReady`로 전환한다. 이 상태의 허용 업무는 `DbActionRequirementV1.allowedInDegradedReady=true`인 action만이며 authoritative identity cache, 모든 write, label/session load, 항목 편집, save/reconciliation과 recovery namespace bind는 fail-closed로 차단한다. schema capability는 매 connect마다 다시 probe해도 된다. 사용자/거래처 ID를 화면 표시값에서 추정하지 말고 로그인 세션의 명시적 customer ID를 전달한다.

JSON은 `raw object → raw scalar staging → validation → target conversion` 4단계로 처리한다. 먼저 배열 행을 분리한 뒤 각 object에 `OPENJSON(objectJson)`을 적용해 `key`, `value NVARCHAR(MAX)`, `type`을 staging table에 저장한다. 이 단계에서 필수 field 존재, 알 수 없는/중복 key, 명시적 null과 field 부재를 검증한다. 문자열은 nullability, target collation 변환 후 `DATALENGTH`, Unicode→대상 type→Unicode binary round-trip을 검사하고 숫자/날짜/bit는 `TRY_CONVERT`를 통과한 값만 최종 table variable의 명시적 SQL 타입으로 변환한다. `OPENJSON ... WITH VARCHAR(n)` 또는 숫자 타입으로 곧바로 투영해 검증 전 절단·변환·null 합성을 허용하지 않는다. Dart CP949 validator도 encode 성공만 보지 않고 encode→decode round-trip이 원문과 동일한지 확인한다.

Web과 Linux를 제외한 Windows/macOS/Android/iOS를 production 대상으로 한다. 제품 지원 선언은 Windows 10/11 x64, macOS 10.15+ x64와 macOS 11.0+ arm64, Android API 24+ arm64-v8a, iOS 13+ arm64다. 열린 `+` 범위 자체를 무한 실행 matrix로 해석하지 않는다. 각 release의 checked-in `RequiredTargetMatrixV1`이 정확한 OS version/build, architecture/ABI, 실제 기기/runner, SQL Server edition/version과 `productionExitRequired`를 유한 목록으로 고정하고, 지원 범위의 최소 버전·최신 승인 버전·직전 주요 버전 및 위험 기반 대표 조합 선택 근거를 기록한다. `GateManifestV1`의 `blocking=true`이면서 해당 target의 `productionExitRequired=true`인 gate만 production-exit 필수 판정식에 포함한다. Android x86_64 emulator는 production device 배포 ABI가 아니라 별도 필수 native integration test target이며 iOS simulator는 UI/contract test target으로 native DB production gate를 대체하지 않는다. release matrix coverage gate는 normative 지원 선언의 필수 대표 범주 누락을 거부하되 모든 미래 OS 조합 실행을 요구하지 않는다. Windows desktop은 ODBC worker process, macOS desktop은 검증된 DB-Lib worker process, Android는 ABI별 native DB driver를 소유하고 별도 `android:process`에서 실행되는 bound remote native service, iOS는 앱 process 내부 native driver와 독립 cancel thread/control 경계를 사용한다. Android gate는 PID/UID/Binder identity handshake, service process 단독 종료, 앱 process 생존과 clean reconnect를 검증한다. iOS는 별도 process 강제 종료를 보장한다고 주장하지 않으며, deadline 내 native cancel 완료와 native session discard/cleanup을 실제 fixture로 증명하지 못한 driver/OS 조합에서는 transaction 시작 전 라벨 항목 편집을 fail-closed한다. 플랫폼 이름만으로 driver를 선택하지 않고 `PlatformDbExecutionCapabilityV1`과 `DbWorkerArtifactManifestV1` 검증이 완료된 조합만 허용한다. strict action은 기존 `_createDriver`의 비Windows in-isolate `MssqlConnectionDriver` 또는 직접 FFI compatibility 경로를 사용할 수 없고, 실제 boundary kind/PID 또는 service identity/cancel channel을 앱 통합 gate에서 검증한다. JSON parameter는 값 추론에 맡기지 않고 `DbNvarcharMax` 또는 동등한 명시적 타입으로 항상 Unicode large value에 bind한다. ODBC/DB-Lib/각 native adapter는 Unicode JSON scalar parameter, 작은따옴표, 한글, 4,000자 초과 payload와 marker가 있는 최종 결과셋을 동일하게 처리해야 한다. DB-Lib `SYBNVARCHAR` parameter의 UTF-16 길이 계산을 먼저 검증하고, binding API가 요구하는 byte length와 UTF-16 code-unit length를 공용 helper 한 곳에서 구분해 사용하도록 수정한다. ODBC는 4,000자 초과 값을 `SQL_WLONGVARCHAR` 또는 검증된 동등 경로로 전달한다.

모든 production adapter의 collector는 첫 schema에 결과를 평탄화하지 않고 모든 결과셋을 `DbExecutionResult.resultSets`에 독립 schema/rows로 보존한다. ODBC type integer, DB-Lib `SYB*` type과 Android/iOS native type은 adapter별로 `DbLogicalType`/`DbColumnMetadata`로 정규화하고 result contract는 native code를 직접 비교하지 않는다. adapter가 제공하지 못하는 metadata는 `unknown`으로 보존하며 native metadata API를 추가하지 않은 채 nullable/precision을 추정하지 않는다. result contract는 logical type별 필수 비교 metadata와 참고 metadata를 구분한다. row value도 `DbWireScalar`로 정규화해 ODBC `num.tryParse`나 DB-Lib/native `DECIMAL/NUMERIC → double` 결과를 canonical projection에 직접 사용하지 않는다. raw decoder는 길이만으로 null을 판정하지 않고 null pointer/indicator와 type을 사용하며 non-null zero-length string/binary를 각각 빈 string/binary로 보존한다. decimal은 scale을 보존하는 문자열로 전달하고 binary/date/time/integer의 wire 표현도 모든 adapter에서 동일해야 한다. strict raw API와 legacy compatibility API는 반환 타입과 mapper를 분리해 compatibility `COALESCE`/fallback 값이 fingerprint/projection에 들어오지 못하게 한다. marker SQL은 각 column을 명시적으로 `CAST`해 logical type을 고정한다. `DbTransactionStatement`에는 optional `resultContract: DbResultContract`를 추가하고 kind/schemaVersion만 별도 전달하지 않는다. `DbClient.transaction()`은 driver의 `NativeDbTransactionSession` 하나를 생성해 `begin → executeAndDrain* → contract validate → commit → verifyTransactionClosed` 순서를 소유하고 일반 `writeData()`로 `BEGIN/COMMIT/ROLLBACK`을 보내지 않는다. session은 시작 시 `DbNativeSessionToken`을 캡처하고 모든 statement, commit, rollback과 cleanup 직전에 동일성을 검증한다. DB-Lib의 현재 `_ensureConnectedOrReconnect()` 같은 command-path 암묵 재연결을 strict transaction path에서 금지하고, native session 재생성은 bootstrap connection owner만 수행한다. parent는 native commit command 전에 `commitDispatchIntentDurable` publish를 완료하고 worker는 native commit 호출 진입 직전 `commitDispatchObserved` ACK를 방출한다. token 불일치는 commit intent 전이면 cleanup 증거에 따라 `DbConnectionDiscarded | preCommitCleanupPending`, intent 이후 `commitCompleted` 증거 전이면 `DbCommitOutcomeUnknown`으로 분류한다. 이미 시작한 native commit을 observed ACK의 parent durable publish 완료까지 중단할 수 있다고 가정하지 않는다. 모든 statement의 result stream이 `NO_MORE_RESULTS`까지 완전히 drain된 뒤 contract에 따라 marker 결과셋/행 cardinality, 정확한 column 이름과 logical type, count의 정수 변환·command 기대값, `MAPPING_JSON` 배열/object field type, command 신규 draft key 집합과 mapping key/양수 ID 유일성을 commit 전에 검증한다. contract 불일치는 rollback 가능한 pre-commit protocol error다. `commitCompleted`가 확인되고 result frame 전체 수신 뒤 `wireEnvelopeDecoded` 또는 `domainDtoDecoded` 단계만 실패한 경우에만 stage가 있는 `DbCommittedResultInvalid`다. 임의 Dart closure는 isolate 경계를 통과할 수 없으므로 validator는 versioned descriptor와 공용 구현으로 고정한다. 일반 조회는 result contract가 null일 때 기존 반환 shape를 유지하는 compatibility adapter를 두되 raw DAO/reconciliation에서는 사용하지 않는다.

`DbNvarcharMax`, `DbTransactionStatement`, `DbResultContract`, `DbResultSetContract`, `DbExecutionResult`, `DbValidatedResultPayloadV1`, `DbLogicalType`, `DbColumnMetadata`, `DbWireScalar`, result set과 typed DB 오류는 모두 isolate wire schema의 `kind`, `schemaVersion`, 필수/선택 field, null 규칙과 `toMap/fromMap` round-trip을 갖는다. connect는 아직 새 epoch가 없으므로 일반 request epoch 계약에서 제외한다. connect envelope는 `connectAttemptId`와 `expectedPreviousEpoch`를 사용하고 native connect 성공 직후 isolate가 새 epoch를 발급해 응답한다. 이후 bootstrap identity/capability probe와 모든 일반 DB request는 dispatch 당시 새 `connectionEpoch`를 포함하고 isolate dequeue와 driver 실행 직전에 현재 native session epoch와 일치하는지 검증한다. 오래된 attempt 응답, 알 수 없는 kind/version, decode 실패와 epoch 불일치는 SQL 실행 전 폐기 또는 protocol/`DbConnectionDiscarded` 오류로 분류한다. driver 오류는 SQL Server error number와 SQLSTATE를 가능한 범위에서 구조화하고 `db_isolate.dart`의 `errorCode/details`를 거쳐 `DbClient`가 같은 typed exception으로 복원한다. application-lock SQL은 예약된 전용 error number를 사용하며 Windows ODBC native code와 DB-Lib SQL error number를 동일 domain kind로 매핑한다. DB-Lib가 error number를 버리는 현재 `SQLException(message)` 계약은 문자열 파싱으로 우회하지 말고 number/state를 보존하도록 먼저 확장한다. payload 원문과 lock resource 원문은 오류 envelope에 넣지 않는다. 앞 collector 문단의 `DbClient.transaction()` 표기는 strict path를 설명하는 역사적 이름이며 public API/codegen 입력에서는 `DbClient.strictTransaction()`으로만 생성하고 compatibility alias로 strict operation을 실행할 수 없다. strict operation은 root recovery orchestrator가 durable prepare/dispatch/commit-intent publish와 commit authorization을 소유하고 platform worker transaction executor가 `NativeDbTransactionSession`과 실제 native commit을 소유한다. canonical protocol은 `prepare → executeAndDrain → resultContractValidated → commitDispatchIntentDurable → authorizeCommit → commitDispatchObserved → commit → commitCompleted` 단계와 독립 control ACK를 가지며, worker는 동일 operation/session/epoch의 유효한 authorization을 받기 전 native commit을 호출할 수 없다. parent와 worker 어느 쪽도 단일 request 내부의 암묵적 commit을 durable authorization으로 간주하지 않는다.

bootstrap API migration은 다음 폐쇄 목록으로 수행한다. `DbBootstrapClient`만 `connectTransport`, `probeDatabaseIdentityV1`, `probeSchemaCapabilityV1`, `bindRecoveryNamespaceV1` privileged action을 호출할 수 있고 일반 DAO에는 이 send port/API를 노출하지 않는다. `DbConnectionPhase`, `isTransportConnected`, `isReady`, `readyFuture`, `degradedReason`을 public 상태로 제공하고 기존 `DbClient.isConnected`는 즉시 deprecated 처리해 신규 코드에서 금지한다. dispatcher는 모든 request의 action ID를 `DbActionRequirementV1`에서 조회해 phase/identity/cache/write 요구를 실행 전 강제하고 manifest에 없는 action은 거부한다. 최소 로그인 인증 조회, notice, monitor ping, label/session load와 모든 write를 열거한다. `StartupDbHelper`는 `connect()` bool이 아니라 `ready | degradedReady | failed` bootstrap result를 기다리고, `DbConnectionService.status.up=true`는 manifest상 허용 action이 하나 이상인 `ready | degradedReady`에서만 게시한다. 별도 `identityAuthoritative`, `recoveryAvailable`, `labelColumnEditingAvailable`과 reason을 필수 게시한다. reconnect는 bootstrap 전체를 다시 수행하고 `DbConnectionMonitor` ping은 manifest가 허용한 phase에서만 실행한다. 로그인 직후 DAO, connection monitor/service, startup helper, schema/reference cache와 기존 `Object` DB API 전체 호출부를 owner/action/required phase/new API로 나열한 migration 표를 작성하고 구조 lint로 manifest 우회 호출을 금지한다.

parameter wrapper는 `logPolicy`를 wire schema에 포함한다. 저장 JSON, keyword/name, QR/나트륨/사용자 정의 문자열과 인증 정보는 `redacted`로 강제하고 `DbClient._debugPrintSql`, Windows ODBC formatter, DB-Lib/isolate logger 어느 계층에서도 literal 값, 부분 preview 또는 hash를 기록하지 않는다. wire envelope, transaction statement map, `statements[].params` 또는 임의 중첩 payload를 `toString`/JSON 전체 직렬화해 로그에 남기지 않는다. 재귀 key masking은 새 key를 놓칠 수 있으므로 로그 전용 metadata allow-list가 operation, statement count/index, parameter name, SQL type, null 여부, byte/code-unit length와 collection count만 새 객체로 구성한다. raw SQL text에 민감 literal을 넣는 것도 금지한다.

12.3 사용자 항목 저장 DAO

레거시의 행별 CRUD 의미는 유지하되 현재 프로젝트에서는 부분 저장을 허용하지 않는다. customer-column transaction 소유자는 `DbClient.strictTransaction()` 하나로 고정하고 기존 품목 저장의 compatibility transaction과 API·execution class를 공유하지 않는다.

- SQL은 `SET XACT_ABORT ON`, `SET NOCOUNT ON`과 validation `THROW`를 포함한 단일 parameterized batch로 작성하되 batch 내부에 `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK`을 넣지 않는다.
- strict `NativeDbTransactionSession`은 begin 전에 isolation과 변경 가능한 SQL session option baseline(`XACT_ABORT`, `NOCOUNT` 포함)을 capture하고 success/rollback/contract failure/cancel cleanup 뒤 모두 원래 값으로 복원·검증하거나 native session을 폐기한다. transaction 종료만으로 `SET` option이 초기화된다고 가정하지 않으며 복원 검증 실패 connection은 compatibility command에 재사용하지 않는다.
- DAO는 해당 batch를 `DbClient.strictTransaction(StrictDbOperation(..., statements: [DbTransactionStatement(..., returnsRows: true, resultContract: customerColumnSaveResultContractV1(command))], isolation: DbTransactionIsolation.serializable))` 한 문장으로 실행한다. 외부 transaction API와 SQL 내부 transaction을 중첩하지 않는다.
- transaction 첫 단계에서 공용 formatter가 만든 `label-manager:customer:{customerId}:cust-column` resource를 `sys.sp_getapplock @LockMode='Exclusive', @LockOwner='Transaction', @DbPrincipal='public', @LockTimeout=<공용값>`으로 획득한다. `EXEC @lockResult=sys.sp_getapplock`으로 받아 rowset을 만들지 않고 `-1` timeout, `-2` cancel, `-3` deadlock victim, `-999` parameter/권한 오류를 typed domain error로 구분한다. 현재 customer 원본 목록을 `UPDLOCK, HOLDLOCK`으로 재조회해 command concurrency fingerprint와 비교하고 불일치하면 전체 rollback한다.
- 같은 lock/transaction 안에서 최종 customer working set의 keyword를 대상 `RICH_KEYWORD` column collation과 trailing-space 의미로 다시 비교해 `(customerId, keyword)` 중복이 있으면 rollback한다. DB schema 변경이 허용되면 natural key unique index는 별도 배포 migration으로 추가하고, 추가하지 못하면 lock protocol에 참여하지 않는 레거시/외부 writer가 중복을 만들 수 있음을 운영 전제에 기록한다.
- 신규: `BM_RICH_CUST_COLUMN(RICH_CUSTOMER_ID, RICH_KEYWORD, RICH_COLUMN_NAME, RICH_TYPE)` insert
- 수정: 현재 customer ID와 custColumnId를 함께 조건으로 update
- 삭제: 현재 customer ID와 custColumnId를 함께 조건으로 delete
- 기대 affected row가 다르면 `THROW`하여 전체 rollback한다.
- SQL 문자열 보간을 사용하지 않는다. 현재 공용 DB API는 목록 parameter를 지원하지 않으므로 insert/update/delete DTO 목록을 명시적 Unicode large JSON parameter 하나 또는 소수로 전달하고 12.2의 raw scalar staging/validation을 적용한다. customer insert staging row는 command의 `DraftMappingKeyV1 draftCustomerColumnKey`와 결정적 `ROW_NO`를 함께 보존한다. SQL Server의 일반 `INSERT ... SELECT ... OUTPUT`에서 source alias를 참조할 수 있다고 가정하지 않고, 승인된 insert-only `MERGE target USING staged source ON 1=0 WHEN NOT MATCHED THEN INSERT ... OUTPUT source.ROW_NO, source.draftCustomerColumnKey, inserted.RICH_CUST_COLUMN_ID INTO @mapping` template 또는 source key 대응이 동일하게 증명된 set-based template만 사용한다. template은 target-only trigger/FK 동작, 중복 source, 실행 계획과 concurrency를 integration fixture로 검증하며 identity 연속성, 마지막 N개 행 재조회나 공통 `NEW_COLUMN` sentinel에 의존하지 않는다.
- 최종 `SELECT`는 항상 정확히 1행이며 `RESULT_KIND='customer-column-save/v1'`, `SCHEMA_VERSION=1`, insert/update/delete count와 `MAPPING_JSON` 배열을 포함한다. 저장 건수가 모두 0이어도 marker 1행과 `MAPPING_JSON=[]`를 반환한다. mapping object는 `ROW_NO`, `draftCustomerColumnKey`, 양수 `custColumnId`를 가지며 result contract가 marker/schema/cardinality, count 정수·command 기대값, 신규 draft key 집합과 ROW_NO/key/ID의 누락·초과·중복을 commit 전에 검증한다. 정상 commit/result decode 성공 경로에서만 이 mapping을 재조회 선택 복원 입력으로 사용한다. `commitCompleted`와 frame 수신 뒤 wire envelope 또는 customer-column domain DTO 복원이 실패하면 stage가 있는 `DbCommittedResultInvalid(committedKnown: true)`로 분류하고 동일 command를 재실행하지 않는다. 이 경우 mapping payload를 폐기하고 customer dictionary 전체 재조회 후 선택을 해제하며 label-size session reload나 mapping 복구를 수행하지 않는다.

12.4 사용 항목 저장 transaction

레거시의 저장 범위를 유지하면서 동시성과 실패 처리를 보완한다.

1. `DbClient.strictTransaction(..., isolation: DbTransactionIsolation.serializable)`이 외부 transaction 시작
2. 공용 formatter의 `label-manager:label-size:{labelSizeId}:schema-content` resource를 `sys.sp_getapplock @LockMode='Exclusive', @LockOwner='Transaction', @DbPrincipal='public', @LockTimeout=<공용값>`으로 획득하고 return code를 typed domain error로 검증
3. 현재 labelSizeId와 기존 column ID의 소유권 및 concurrency fingerprint 검증
4. 신규 입력 JSON을 `ROW_NO`, `DRAFT_COLUMN_KEY: DraftMappingKeyV1`을 가진 table variable로 정규화하고, 각 행 insert의 `OUTPUT INSERTED.RICH_COLUMN_ID INTO @CapturedColumns` 결과를 같은 row의 draft key와 결합. row-by-row insert를 사용하면 현재 source row의 key를 같은 iteration에서 함께 기록하고, set-based insert를 사용하면 customer 저장과 같은 승인 insert-only `MERGE ... OUTPUT source.ROW_NO, source.DRAFT_COLUMN_KEY, inserted.RICH_COLUMN_ID INTO @mapping` 또는 source-key 대응이 동등하게 증명된 template만 허용한다.
5. 신규/기존 `BM_RICH_COL_MIN` upsert
6. 신규/기존 `BM_RICH_CHECK_COLUMNS` upsert
7. `ContentCreationOwnershipV1`이 `daoOwned`인 경우에만 신규 컬럼마다 해당 label size의 기존 `BM_RICH_ITEM`에 `BM_RICH_COL_CONTENT` 빈 값 insert. `triggerOwned`이면 trigger 결과의 정확한 key 집합/빈 값만 검증하고 DAO가 중복 insert하지 않음
8. update-item은 현 제품 consumer 기준 `legacyOnly | future`로 분류해 handoff 필수 ACK에서 제외한다. 다만 해당 label size에 실제 `BM_UPDATE_ITEM` row가 있으면 데이터 호환을 위해 ownership이 `daoOwned`일 때 신규 컬럼별 `BM_UPDATE_COL_CONTENT` 빈 값을 필수 insert하고, `triggerOwned`이면 정확한 key 집합을 검증한다. 테이블 존재만으로 필수 current consumer를 만들거나 no-op ACK를 게시하지 않는다.
9. 기존 행 중 persisted projection 또는 최종 order가 original과 다른 `updateRows`만 `BM_RICH_COLUMN` update. SQL 대상 집합과 result contract의 `expectedUpdateCount`는 같은 command 집합을 사용하고 변경 없는 기존 행을 재기록하지 않음
10. `BM_GS1_COLUMN_INFO` upsert/delete
11. `BM_GS1_CONTAIN_COLUMN`을 최종 working copy 관계와 일치하도록 insert/delete
12. 삭제 대상의 status date 갱신 및 종속 데이터 정리 후 `BM_RICH_COLUMN` delete
13. 모든 affected row와 최종 order/keyword uniqueness 검증
14. batch marker가 있는 최종 `SELECT` 반환 및 root orchestrator의 commit authorization 후 `DbClient.strictTransaction()`의 worker가 commit

저장 command의 insert/update/delete/GS1 관계 목록은 명시적 Unicode large JSON scalar parameter로 전달하고 12.2의 raw scalar staging/validation을 통과한 값만 대상 SQL 타입으로 변환한다. JSON payload가 4,000자를 넘는 정상 대량 저장도 잘리지 않도록 Windows ODBC, macOS DB-Lib와 Android/iOS native adapter 경로를 각각 검증한다.

신규 ID는 레거시 `SelectLastNRecord()` 방식으로 찾지 않는다. trigger와 driver의 결과셋 처리에 안전하도록 direct `OUTPUT` resultset을 중간에 노출하지 않고, `ROW_NO` 순회 insert마다 현재 source의 `DraftMappingKeyV1`과 `OUTPUT INSERTED... INTO` ID를 같은 iteration에서 결합하거나 승인된 insert-only `MERGE ... OUTPUT source.ROW_NO, source.DRAFT_COLUMN_KEY, inserted.ID INTO @mapping` template을 사용한다. 두 방식 모두 입력/출력 key 결합을 실행계획의 행 순서, identity 연속성 또는 마지막 N개 재조회에 의존해서는 안 된다.

batch 외부의 최종 `SELECT`는 신규 0건/N건과 무관하게 항상 정확히 1행이며 `RESULT_KIND='label-column-save/v1'`, `SCHEMA_VERSION=1`, 저장 요약과 `MAPPING_JSON` 배열을 포함하고 `DbTransactionStatement.resultContract`에도 command의 count와 신규 draft key 집합을 전달한다. 신규가 없으면 `MAPPING_JSON=N'[]'`다. 모든 production adapter의 collector는 모든 결과셋을 끝까지 drain하고 각 결과셋의 고유 schema로 보존한다. transaction executor는 trigger/procedure의 중간 `SELECT`, rowcount-only 결과와 빈 결과를 건너뛰어 기대 marker/schema 결과셋과 marker row가 각각 정확히 하나인지 검사하고, `MAPPING_JSON` 구조/field type/key 집합/ID까지 commit 전에 검증한다. marker 중복/누락/0행/복수행/schema 또는 result contract 불일치는 rollback 가능한 pre-commit protocol error다. commit 정상 완료 후 Dart DAO는 이미 검증된 wire payload를 typed DTO로 복원하며 이 단계의 전송/decode 실패만 `DbCommittedResultInvalid(committedKnown: true)`다.

삭제 시 다음 테이블을 명시적으로 검토한다.

- `BM_RICH_COL_CONTENT`
- `BM_UPDATE_COL_CONTENT`
- `BM_RICH_COL_MIN`
- `BM_RICH_CHECK_COLUMNS`
- `BM_GS1_COLUMN_INFO`
- `BM_GS1_CONTAIN_COLUMN`의 `MAIN_COLUMN_ID`와 `CONTAIN_COLUMN_ID` 양쪽 관계
- `BM_COLUMN_QRCODE_INFO`의 `RICH_COLUMN_ID`와 `RICH_COLUMN_TARGET_ID` 양쪽 관계
- `BM_RICH_STATUS_DATA.RICH_COLID_CHANGE_DELETE_DATE`
- 최종 `BM_RICH_COLUMN`

transaction 실행 전 또는 capability cache 초기화 시 `sys.tables`, `sys.columns`, `sys.foreign_keys`, `sys.triggers`로 실제 배포 스키마를 확인한다. `BM_RICH_COL_CONTENT`와 update content는 trigger 활성 상태/정의 hash, statement-level `inserted` 전체 집합 처리, label-size별 order 비변경, DAO 생성 여부와 unique key를 함께 판정해 `ContentCreationOwnershipV1`의 단일 주체를 확정한다. 저장소의 레거시 `AFTER_INSERT_COLUMN`과 동등한 정의는 `triggerOwned`가 될 수 없으며, 해당 trigger가 활성 상태면 편집기 진입을 차단하고 승인 migration으로 비활성화/교체한 뒤 `daoOwned` 또는 검증된 새 trigger를 사용한다. trigger와 DAO가 동시에 생성하거나 trigger 정의/주체를 판정할 수 없으면 진입을 차단한다. FK cascade에 암묵적으로 의존하지 않는다. 실제 cascade가 확인되면 중복 delete를 피하되 DAO 테스트에 그 전제를 기록한다.

QR/기본 사용자 정의 참조의 source of truth는 create type별 active field 안의 구조화된 token이다. `QRCodeCreateTypeActiveReferenceFieldsV1` 폐쇄 matrix는 `QRCODE_TYPE_PLAIN_TEXT=없음`, `QRCODE_TYPE_USER_DEFINE=RICH_USER_DEFINE_QRDATA+RICH_USER_DEFINE_QRTEXT`, `QRCODE_TYPE_NATRIUM=RICH_NATRIUM_JOIN_STRING records`, `BARCODE_TEXT_LINK=RICH_USER_DEFINE_QRDATA`로 고정한다. 비활성 필드는 persisted raw 값을 그대로 보존하지만 참조 표시, rename/delete guard와 workbook 영향 판정의 token source에서 제외한다. 편집기, workbook 영향 검사와 실제 출력 `ItemCodeDataResolver`는 같은 공용 V1 parser/replacer와 동일 token stream을 사용한다. 기존 라벨 컬럼 keyword에는 신규 `[A-Z0-9]+` 제한을 소급하지 않고 DB field/CP949 validation을 통과한 원문을 전체 keyword 집합에 보존한다. 다만 V1 parser에 주입하는 `referenceableKnownKeywordsV1`은 Unicode whitespace 또는 `#`를 포함하거나 예약어 `품목`, `ITEMNAME`과 ordinal exact match하는 keyword를 제외한다. 제외된 기존 keyword는 raw 값, DB 관계와 다른 속성을 그대로 보존하고 존재 자체로 정상 저장이나 삭제를 차단하지 않지만 V1 컬럼 참조 선택/생성, rename target과 workbook/QR 참조 귀속에는 사용하지 않는다. 기존 active-field/workbook 문자열도 자동 rewrite하거나 제외 keyword 참조로 추정하지 않고 아래 V1 grammar로만 해석한다. 신규 생성 또는 rename으로 separator 포함/예약어 충돌 keyword를 만드는 것은 validation에서 차단한다. parser는 `#` 위치에서 예약 token을 먼저 검사한 뒤 `referenceableKnownKeywordsV1`의 `# + keyword` 후보를 길이 내림차순, ordinal case-sensitive로 검사한다. full known match 뒤가 `EOF`, Unicode whitespace, 다음 `#` 또는 Unicode punctuation/symbol이면 token으로 인정하고 boundary 문자는 token span에 포함하지 않는다. 단, boundary로 보이는 punctuation/symbol까지 포함한 더 긴 known keyword가 있으면 가장 긴 full known match를 우선한다. known match 뒤가 Unicode letter/number/combining mark/connector punctuation이면 identifier continuation으로 보고 짧은 known prefix를 치환하지 않으며, 다음 `EOF | whitespace | #` 전까지의 unknown candidate 전체를 literal로 보존한다. 따라서 known keyword가 `AB`뿐이면 `#AB,`, `(#AB)`, `#AB #AB`, `#AB#AB`는 token을 치환하지만 `#ABC`와 `#AB_1`은 전체 unknown candidate literal이고, `AB,`가 known이면 `#AB,`는 더 긴 keyword token으로 우선 판정한다. 동일 full candidate에 같은 keyword를 가진 서로 다른 column ID가 있거나 SQL collation상 중복 keyword가 있으면 capability/validation 오류로 저장과 출력을 차단한다. column 순서나 순차 `replaceAll`에 의존하지 않고 parser가 만든 non-overlapping token span을 한 번만 치환한다. 기존 포맷에는 grammar version/escape가 없으므로 literal token escape를 조용히 추가하지 않고 이 V1 boundary 규칙을 기존·신규 template 모두에 동일 적용한다.

나트륨 V1은 레거시와 같이 `/`로 구분된 정확히 6개 record와 record 내부 첫 `-` 구분을 사용한다. name/keyword에 `-`, `/`를 허용하지 않고, URL percent-encoding은 token grammar와 별도 fixture로 레거시 결과를 고정한다. 이번 기능에서는 참조 token 자동 rewrite를 구현하지 않고 참조 대상 키워드 변경/삭제를 먼저 차단한다.

`BARCODE_TEXT_LINK`의 기존 persisted token은 위 공용 parser로 모든 referenceable existing keyword를 해석·보존한다. 신규 token picker에는 레거시 `CColumnSetupBarcode::InitInputTextColumns()`와 같이 `TYPE_BASE | TYPE_FIX` 컬럼만 제공하며 다른 타입의 신규 token 삽입은 차단한다. parser/output은 picker 제한과 별개이므로 기존에 다른 타입을 참조하는 token을 자동 삭제하거나 literal로 바꾸지 않는다.

`BM_COLUMN_QRCODE_INFO`는 레거시 DAO가 존재하지만 활성 항목 편집 저장 경로에서 insert/update 사용이 확인되지 않았으므로 기본 계약에서는 authoritative 관계나 upsert 대상으로 간주하지 않는다. capability 및 실제 운영 데이터 조사로 사용 주체가 확인되기 전에는 삭제 컬럼의 orphan 방지 cleanup만 수행한다. 사용 중인 정식 관계로 확인되면 별도 조회/working relation/upsert 계약과 migration 테스트를 추가한 뒤 사용한다.

삭제는 status date를 먼저 갱신한 뒤 non-cascade child를 정리하고 `BM_RICH_COLUMN`을 마지막에 삭제한다. `BM_GS1_CONTAIN_COLUMN`은 삭제 컬럼이 source/main인 경우와 target/contain인 경우를 모두 정리하고, `BM_COLUMN_QRCODE_INFO`는 위 cleanup-only 정책에 따라 양쪽 orphan을 제거한다. `BM_UPDATE_ITEM`/`BM_UPDATE_COL_CONTENT`의 배포 DB 존재와 ownership을 capability로 확인한다. 신규 빈 content는 해당 label size에 실제 `BM_UPDATE_ITEM` 행이 존재할 때만 그 실제 row key 집합에 대해 생성하고, 삭제 정리는 삭제 컬럼을 참조하는 실제 `BM_UPDATE_COL_CONTENT` 행에만 수행한다. 테이블 존재만으로 content를 생성하지 않는다.

`BM_RICH_COL_MIN`은 일반 컬럼 행뿐 아니라 label size별 `ELEMENT` sentinel 행을 사용하는 레거시 경로가 있다. 레거시의 `RICH_COLUMN_ID=''`/`'0'` 혼용을 애플리케이션 변환에 맡기지 않고 실제 SQL 타입과 운영 분포 fixture로 canonical sentinel predicate를 확정한다. predicate는 labelSizeId, sentinel column-ID 표현과 `RICH_KEYWORD='ELEMENT'`를 함께 사용하고 일반 컬럼 keyword만으로 sentinel을 판정하지 않는다. `''`/`0` 혼재, 중복 또는 predicate 불명확 데이터는 자동 정리하지 않고 진입 차단 또는 승인 migration 대상으로 둔다. `RICH_MIN_CHECK`는 이번 라벨 항목 편집기 UI에 노출하거나 수정하지 않는다. 기존 일반 행과 기존 sentinel은 raw 원본 값을 보존하고 update SQL에서 이 column을 제외한다. 신규 일반 행과 sentinel이 없어서 새로 만드는 canonical sentinel만 `RICH_MIN_CHECK=0`으로 생성한다. 신규/수정/삭제 후 sentinel을 정확히 1개 유지하며, 일반 컬럼의 keyword/name/order만 최종 working copy와 동기화한다.

누락 키워드 검사의 source of truth는 `BM_RICH_CHECK_COLUMNS.RICH_CHECK_YN`으로 확정한다. main table에 legacy `RICH_USE_MISSING_KEYWORD_CHECK`가 있으면 같은 transaction에서 동일 값으로 동기화한다. 두 값이 불일치한 기존 행은 조회 시 check table 값을 우선하고, 저장 후 두 값이 일치하도록 보정한다.

문자열 SQL 직접 결합, 마지막 N개 행 재조회, transaction 밖 보조 테이블 저장, 실패를 삼키는 void API를 사용하지 않는다. DAO는 성공 결과 또는 예외를 호출자에게 반환해야 한다.

12.5 token 참조 판정과 실제 출력 정책

12.4의 장문 token 설명에 있는 “실제 출력도 같은 공용 parser/replacer와 token stream을 사용한다”, column-order-independent 치환과 순차 `replaceAll` 금지는 참조 판정에만 유효한 이전 표현이며 실제 출력 계약으로 사용하지 않는다. `ReferenceTokenParserV1`은 rename/delete guard, workbook 영향 검사와 신규 picker validation에서 예약 token 우선, longest full known match, punctuation boundary와 identifier continuation 규칙을 사용한다.

실제 QR data/text와 barcode link 출력의 `LegacyOutputTokenReplacerV1`은 레거시 `TableRowRTFMaker`처럼 출력 대상 session의 persisted `RICH_COLUMN_ORDER ASC` 순서로 각 `# + rawKeyword`를 ordinal case-sensitive 전역 순차 치환한다. QR/user-defined/barcode-link context는 예약 item token을 먼저 치환한 뒤 컬럼을 순회하며, 앞선 치환 결과에 뒤 keyword token이 새로 생겨도 후속 치환 대상으로 삼는다. GS1 context는 레거시 `GetGS1CodeData()`와 같이 예약 item 선행 pass 없이 컬럼 pass만 실행한다. longest-match, identifier continuation과 punctuation boundary를 출력에 적용하지 않는다. 기존 raw session 출력은 `RICH_COLUMN_ORDER`가 유일하면 gap/nonpositive 값을 포함해 숫자 오름차순으로 허용하고, duplicate order는 레거시 query 결과 순서를 결정할 수 없으므로 출력 전에 capability 오류로 차단한다. 신규 저장 결과는 별도 working-order invariant에 따라 양의 정수 1부터 연속이어야 한다. `RICH_COLUMN_ID ASC`는 표시/raw DAO의 재현성 보조 정렬일 뿐 actual legacy output pass의 tie-break가 아니며 duplicate order를 허용하지 않는다. duplicate keyword 또는 기존 ID가 없는 raw row처럼 결정적 순서를 증명할 수 없는 입력도 차단한다. 참조 parser와 출력 replacer는 API, fixture와 golden을 공유하지 않고 parser 결과를 출력 span으로 재사용하지 않는다. 기존 출력 호환을 위한 `intentionalDivergence=false` 정책이다.

같은 실제 replacer는 선택 가능한 부가 모드가 아니라 치환 pass의 각 occurrence마다 `(traceEventId, parentEventIds, passOrdinal, occurrenceOrdinal, outputContextId, itemStableKey, sourceField, source, rawKeyword, prePassInputSpan, postPassOutputSpan, replacementCreated)`를 수집하는 `LegacyOutputDependencyTraceV1`을 지원한다. 하나의 전역 replace pass에서 같은 token이 여러 번 나타나면 pass 시작 문자열의 좌→우 순서로 occurrence event를 각각 만들고 span 좌표계는 이름 그대로 pass 직전 input과 pass 직후 output으로 고정한다. `LegacyOutputTraceSourceV1`은 `column(columnId) | reservedItemName(tokenKind) | system(sourceKind)`의 폐쇄 union이고, QR/user-defined/barcode-link의 예약 `품목 | ITEMNAME` 선행 치환만 `reservedItemName` source를 사용하며 GS1 context에는 이 event가 존재하지 않는다. replacement-created 후속 token은 자신을 만든 occurrence event ID와 해당 event의 parent lineage를 `parentEventIds`에 결정적으로 보존해 최종 컬럼 dependency뿐 아니라 예약 품목명과 system contributor까지 추적한다. trace mode도 일반 출력과 동일한 코드 경로·순서·문자열 결과를 사용하고 별도 parser나 유사 치환 구현으로 dependency를 재구성하지 않는다. rename/delete guard는 dialog open generation의 완전한 현재 session 품목 snapshot 전체에 대해 `QRCodeCreateTypeActiveReferenceFieldsV1`의 active QR data/text, barcode link, `Gs1OutputPolicyV1.legacyPermissive`가 조립한 GS1 data 및 workbook의 실제 출력 가능 context를 replay하고, 최초 template의 직접 치환뿐 아니라 앞선 replacement가 만든 후속 token의 transitive source를 모두 보존한다. dependency는 `tokenTextDependency`와 `gs1EndpointDependency`로 분리한다. keyword rename은 parser와 token text trace만 차단 근거로 사용하고 GS1 contain ID 관계 또는 GS1 builder가 자기 endpoint keyword로 만든 token만으로 차단하지 않는다. delete/type-change/관계 제거는 GS1 endpoint dependency를 별도 영향 확인에 사용한다. 출력 context 목록, 품목 snapshot completeness, stable key, generation/context 또는 trace 실행 중 하나라도 검증할 수 없으면 참조 없음으로 낮추지 않고 mutation을 fail-closed한다. 완전한 snapshot이 정상적으로 0개 품목임은 입력 누락과 구분해 empty trace로 허용한다.

`BARCODE_TEXT_LINK`의 기존 persisted token은 출력에서 모든 raw existing keyword를 위 순서대로 치환한다. 신규 picker는 레거시와 같이 `TYPE_BASE | TYPE_FIX`만 제공한다. 참조 판정에서 제외된 whitespace/`#` 포함 또는 예약어 충돌 keyword도 기존 출력 raw 치환 대상에서는 자동 제외하거나 rewrite하지 않으며, 해당 운영 데이터의 결정적 순서와 충돌 여부를 capability fixture로 검증한다.

GS1 barcode 실제 데이터는 사용자 결정에 따라 `Gs1OutputPolicyV1.legacyPermissive`로 고정한다. base table `BM_GS1_CONTAIN_COLUMN`에는 관계 순서 컬럼이 없으므로 “persisted 관계 순서”를 추정하지 않는다. 운영 capability fixture가 레거시 `VIEW_BM_GS1_CONTAIN_COLUMN.CONTAIN_COLUMNS_ID`의 정규화 definition과 집계 순서 근거를 고정하고 동일 관계 집합에서 결정적 순서를 증명한 경우에만 그 순서를 사용한다. view 정의/권한/순서 근거가 없거나 동일 집합이 둘 이상의 순서를 만들 수 있으면 편집·출력을 차단하고 승인된 relation-order 컬럼 migration 뒤에만 진행한다. 승인 순서대로 각 GS1 AI raw code와 `# + rawKeyword`를 조립하고 variable-length AI 사이에 code unit `0x1D`를 삽입하되 마지막 segment 뒤에는 넣지 않는다. 이후 출력 session의 위 검증된 persisted column order로 예약 item 선행 pass 없는 컬럼 전역 순차 치환을 적용한다. 관계 endpoint 누락, 지원하지 않는 raw AI 설정, contain 순서 중복·불명확처럼 문자열 자체를 결정할 수 없는 구조 오류는 출력 전에 차단하지만, 품목 cell 값이 AI definition의 길이·숫자·날짜 형식 validation에 실패한다는 이유만으로 결과를 빈 문자열로 바꾸거나 다른 barcode format으로 fallback하지 않는다. format option lookup은 레거시처럼 raw AI code의 마지막 한 글자만 제외하되 출력에는 full raw AI code를 사용하고, `TYPE_VALIDDATE` 값은 레거시 `DATE_FORMAT_NONE` 변환 결과를 치환한다. 이는 현 `ItemCodeDataResolver._resolveGs1()`의 value-level fail-closed를 레거시 출력과 맞추는 `intentionalDivergence=false` 정책이며, 편집 시 신규/수정 GS1 AI 설정 validation과 출력 시 기존 품목 value 처리 정책은 별도 계약이다. 미리보기, 라벨 시트 object 갱신, 일반 인쇄와 직접 출력은 모두 이 공용 GS1 data builder가 barcode encoder 직전에 제공하는 동일 code-unit/byte 및 FNC1 결과를 사용한다.

13. 공용 테이블 확장 원칙

현재 `SwipeActionTable`에 필요한 API가 없으면 라벨 항목 다이얼로그 안에서 gesture/table을 다시 구현하지 말고 공용 위젯을 최소 확장한다.

다음 공용 확장은 구현 필수 계약이다. 이름은 기존 API 스타일에 맞게 조정할 수 있지만 같은 타입 안전성과 lifecycle을 제공해야 한다.

- 행/열 헤더 교차 영역을 구성하는 `cornerBuilder`
- index 대신 안정 identity를 반환하는 `rowKeyBuilder`
- controlled stable selection용 nullable `selectedRowKey`와 `onStableSelectionChanged(StableSelectionChange<K> change)` 폐쇄 typed callback. change는 `userSelected(K key) | missingKeyInvalidated(K missingKey)`를 가지며 stable-key mode에서는 내부 `selectedIndex`를 source of truth로 사용하거나 별도 선택/invalidation callback을 병행하지 않는다. rows reconciliation에서 supplied key가 삭제되거나 현재 rows에 없으면 table은 effective selection을 먼저 `null`로 만들고 임의 이웃 행을 선택하지 않은 채 `missingKeyInvalidated(missingKey)`를 owner에게 정확히 한 번 통지한다. owner가 `selectedRowKey=null`/다른 유효 key를 공급하거나 해당 key가 다시 유효해질 때까지 같은 missing key event를 재진입·rebuild로 반복하지 않으며, callback 중 index 기반 내부 선택을 변경하지 않는다.
- `LabelColumnDragPayload`처럼 source table, stable row key, item kind를 담는 typed external drag payload builder
- typed payload를 받는 external drop target와 drag enter/leave/drop lifecycle callback
- row drag 시작/종료 callback. 삭제 hover/취소/성공 시 시각 상태를 모두 정리한다.
- 기존 index 기반 reorder callback은 호환용으로 유지하되 새 편집기는 `onRowReorderByKey(movingKey, targetKey, dropEdge)` 또는 동등한 stable-key callback만 사용한다. key→현재 index 변환은 async guard/확인 완료 후 command 실행 직전에 table owner가 수행한다.
- 편집 mode의 타입별 cell builder/dropdown cell
- table enabled 상태에서도 선택 표시를 유지하는 read-only mode

내부 reorder payload와 외부 add/delete payload를 `int` index 하나로 공유하지 않는다. `normal`에서는 외부 add/delete drag만, `reorder`에서는 같은 사용 항목 테이블 내부 reorder만 활성화한다. `userItemEdit`의 사용자 후보는 persisted order 필드가 없고 `RICH_CUST_COLUMN_ID ASC`가 표시 순서이므로 add/delete gesture만 허용하고 reorder gesture는 제공하지 않는다. disabled 영역은 drop을 수락하지 않으며 drag payload의 labelSize/customer/session identity가 현재 dialog와 다르면 거부한다.

기존 라벨 설정, 브랜드 설정, 품목 순서 변경 동작을 깨지 않도록 새 옵션 기본값은 현재 동작을 유지해야 한다. 공용 위젯 변경에는 기존 `test/swipe_action_table_test.dart` 회귀 테스트를 반드시 추가한다.

14. 오류, 동시성, 재진입 처리

- `RecoveryTransitionTableV1`의 label-column post-commit closed state에는 `committedReloadPending | committedReloadFailed`를 모두 포함하고, customer-column에는 `customerDictionaryReloadPending | customerDictionaryReloadFailed`를 모두 포함한다. reload failure event는 resourceKind에 맞는 failed state로만 전이하며 각 failed state의 retry는 save가 아니라 해당 resource reload action만 허용한다.
- checked-in `RecoveryTransitionTableV1` descriptor의 `evidenceSet`, `workflowStateSet`, `uiProjectionSet`이 각각 해당 계층 enum의 유일한 source of truth이고 단일 통합 `stateSet`은 존재하지 않는다. label-column의 normative post-commit UI projection은 `committedResultInvalid | committedReloadPending | committedReloadFailed`, customer-column은 `customerCommittedResultInvalid | customerDictionaryReloadPending | customerDictionaryReloadFailed`로 고정한다. committed-invalid는 commit 완료 뒤 wire/domain decode 실패에서 resource별 reload pending을 거치지 않고 직접 진입하고, reload-failed는 해당 resource의 reload pending에서 reload failure가 발생할 때만 진입한다. mapping 복구 상태는 V1에 존재하지 않는다. `committedReloadFailed`를 열거 누락 상태나 확장 문자열로 처리할 수 없고 Cartesian fixture에 정식 workflow transition과 UI projection, `reload failure → failed`, `retry → reload start` 행을 포함한다.
- dialog open 중 동일 버튼을 다시 눌러 중복 overlay를 만들지 않는다.
- 조회 중에는 loading 상태와 닫기 정책을 명확히 하고 빈 목록을 정상 조회 실패로 오인하지 않는다.
- DB 연결 실패는 진행 표시를 닫은 뒤 경고 dialog로 알리고 사용자의 working copy를 유지한다.
- 저장 command는 generation 또는 in-flight Future로 중복 실행을 막는다.
- 저장 중 dialog close, mode 전환, drag/drop, 행 선택을 막는다.
- 저장 성공 후 상위 widget이 dispose됐으면 setState하지 않되 DAO transaction 결과는 유실하지 않는다.
- 저장 시작 전 coordinator가 opaque random operation ID와 durable operation phase를 기록한다. dialog/HomePageManager dispose는 UI만 detach하며 in-flight Future를 취소하거나 commit 결과를 폐기하지 않는다. `LabelColumnSaveRecoveryRegistry`가 success/unknown/committed-invalid와 reload 필요 상태를 인수한 뒤 coordinator를 정리한다. registry record에는 raw save JSON/QR/사용자 문자열, original/desired projection과 content-derived command fingerprint/hash를 저장하지 않고 operation ID, `stableDatabaseIdentityDigest`, 비민감 resource key/context, phase와 recovery reason만 저장한다. 같은 프로세스 reconciliation에 필요한 fingerprint/projection은 coordinator memory에만 둔다.
- recovery registry는 journal과 같은 공용 crash-safe record primitive를 사용해 schema version, checksum, owner token, phase, lease와 완료 tombstone을 target/tmp/bak에 기록한다. Windows named mutex, macOS의 승인 advisory/process lock, Android/iOS의 app-container 단일 writer primitive를 `PlatformDbExecutionCapabilityV1`과 gate에서 고정하고 stale lease 인수 규칙, 원자 교체, startup directory scan, artifact 선택·격리 규칙을 플랫폼별 fault-recovery matrix로 검증한다. SharedPreferences hint와 메모리 map은 source of truth가 아니다.
- `RecoveryTransitionTableV1` descriptor의 `evidenceSet`, `workflowStateSet`, `uiProjectionSet`이 각각 durable evidence code, transition `from/to` code와 resource별 UI 표시 code generation/Cartesian fixture가 읽는 유일한 canonical 목록이다. `uiProjectionSet`의 label-column reload 상태에는 `committedReloadPending`, `committedReloadFailed`, `committedResultInvalid`만, customer-column reload 상태에는 `customerDictionaryReloadPending`, `customerDictionaryReloadFailed`, `customerCommittedResultInvalid`만 포함한다. 폐기된 mapping 복구 code는 어떤 set, transition, fixture와 UI mapping에도 존재할 수 없으며 descriptor schema validation이 이를 거부한다. worker/parent/DAO의 단조 증거를 workflow state로 생성하거나 UI projection을 durable evidence로 생성하지 않는다. 아래 장문 설명은 각 집합의 event/guard 동작을 설명하는 비생성 prose이고 state token 추출 입력으로 사용할 수 없다.
- durable phase는 코드와 테스트가 공유하는 `RecoveryTransitionTableV1` checked-in descriptor를 source of truth로 삼는다. V1 state/event/reject reason은 확장 가능한 문자열이 아니라 versioned closed enum이다. state는 최소 `preparedDurable`, `dispatchIntentDurable`, `operationAcceptedDurable`, `commitDispatchIntentDurable`, `commitDispatchObservedDurable`, `commitCompletedDurable`, `resultFrameSendCompletedDurable`, `resultFrameFullyReceivedDurable`, `wireEnvelopeDecoded`, `wireEnvelopeDecodeFailedDurable`, `domainDtoDecoded`, `domainDtoDecodeFailedDurable`, `preCommitFailedTerminal`, `preCommitCleanupPending`, `commitOutcomeUnknown`, `desiredObservedReloadPending`, `originalObservedAcknowledgementPending`, `indeterminateAcknowledgementPending`, `committedReloadPending`, `committedReloadFailed`, `committedResultInvalid`, `customerDictionaryReloadPending`, `customerDictionaryReloadFailed`, `customerCommittedResultInvalid`, `restartManualAcceptanceRequired`, `userAcknowledged`, `reloadVerifiedAutoClose`, `tombstonePending`, `tombstoned`, `quarantined`를 폐쇄 열거한다. event는 prepare/publish dispatch intent 성공·실패, cumulative worker ACK 수신, stale/duplicate/invalid ack, parent frame 완전 수신, IPC partial-send/decode 실패, commit dispatch intent publish, wire envelope decode 성공·실패, domain DTO decode 성공·실패, pre-commit cleanup verified/unknown, connection lost/worker exit/native timeout, lease lost, identity mismatch, startup artifact selected/corrupt/quarantined, reconnect/shutdown, desired/original/indeterminate observation, reload start/success/failure/retry, user accept/cancel, tombstone publish 성공·실패를 폐쇄 열거한다. 각 행은 `(resourceKind, from, event, payloadSchema, orderedGuards, to, durablePublish, resourceBlocked, allowedActions)`를 가지며 `resourceKind=labelColumn | customerColumn`과 모든 nonterminal state/event 조합은 정확히 한 transition 또는 typed reject를 반환한다. guard는 descriptor 순서대로 평가하고 reject는 side effect가 없다. worker high-watermark와 parent/DAO local evidence는 서로 독립된 monotonic evidence로 durable 저장하고 전이 상태는 그 결합으로 계산한다. prerequisite보다 먼저 온 유효 future-stage local event는 destructive reject하지 않고 pending evidence로 보존해 prerequisite ACK/event 수용 후 재평가한다. cumulative worker ACK는 더 높은 유효 high-watermark를 수용하고 낮은 후착 ACK를 canonical payload에 따라 idempotent stale 또는 typed reject로 분류하며, parent barrier인 `commitDispatchIntentDurable`을 함의하지 않는다. header만 수신했거나 payload가 짧은 EOF/partial frame은 `resultFrameFullyReceivedDurable`로 전이하지 않는다. `dispatchIntentDurable`은 최초 DB request 전 barrier이고 `commitDispatchIntentDurable`은 native commit command 전 barrier다. 이미 시작한 native 경계를 parent durable publish 완료까지 되돌리거나 정지할 수 있다고 가정하지 않는다. ACK/local-event publish 실패는 마지막 성공 durable evidence와 resource block을 유지한다. `preCommitFailedTerminal`은 commit intent가 없고 result drain/cancel, rollback과 같은 session의 `@@TRANCOUNT=0`이 모두 확인된 경우에만 허용한다. 하나라도 불명확하면 `preCommitCleanupPending`으로 resource를 계속 차단한다. descriptor에서 resourceKind별 V1 Cartesian matrix와 ACK/local-event 양방향 재정렬 기대 결과 fixture를 생성하고 각 상태의 terminal publish 완료 후에만 coordinator를 dispose한다.
- 위 장문 설명의 `state`는 생성 schema에서 단일 enum이 아니다. `preparedDurable`부터 decode evidence까지는 `evidenceSet`, `preCommitFailedTerminal`부터 recovery/tombstone 상태는 `workflowStateSet`, committed resource 표시명은 `uiProjectionSet`에 배치한다. transition row의 authoritative schema는 `(recoveryResourceKind, fromWorkflowState, evidenceSnapshot, event, payloadSchema, orderedGuards, toWorkflowState, durablePublish, resourceBlocked, allowedActions)`다. `RecoveryResourceKind=labelColumn | customerColumn`은 lock manifest의 `LockResourceKind=customer | brand | labelSize | form`과 별도 타입이며, strict writer manifest가 action별 두 kind의 폐쇄 매핑을 제공한다.
- startup은 DB 연결 전 namespace-neutral root의 전체 artifact 무결성과 digest directory 형식만 스캔하는 `storageReady`와 검증된 현재 `DatabaseIdentity` namespace를 bind하는 `identityReady`를 분리한다. registry owner는 `HomePage`/로그인 subtree가 아니라 `main.dart`에서 `MaterialApp`보다 먼저 생성되는 단일 `LabelManagerAppBootstrapService`로 고정하고 `storageReady → databaseIdentity bind → login context attach → logout detach → app shutdown` lifecycle을 가진다. coordinator는 DB dispatch 전에 이 root service에 등록되어 처음부터 registry 소유이며 `HomePageManager.dispose()`의 비동기 인수에 의존하지 않는다. main/startup DB helper/login 성공/logout/reconnect/app shutdown 호출부 migration 표를 P2 entry artifact로 고정한다. logout은 operation을 삭제하지 않고 identity/resource barrier를 유지하며 다음 identity나 로그인 context에 record를 재사용하지 않는다. `connectionProfileHint`는 후보 탐색만 돕고 authoritative barrier가 아니다. directory, target/tmp/bak record key, mutex와 resource barrier는 연결 후 계산한 `stableDatabaseIdentityDigest/resourceKind/resourceId/operationId`로 namespace한다. identity가 다른 record는 현재 DB를 차단하거나 tombstone하지 않고 해당 unresolved namespace에 보존한다. 각 operation 안에서는 checksum, owner token과 durable publish sequence로 authoritative target/tmp/bak artifact 하나를 결정한다. 동일 identity/resourceKind/resourceId에 unresolved operation이 복수면 wall-clock이나 file mtime으로 하나를 고르지 않고 모두 보존하며 resource barrier는 모든 unresolved operation의 합집합으로 계산한다. commit 확정/committed-invalid operation은 낮은 phase operation보다 우선해 차단하고, 서로 모순되는 operation은 격리하되 resource 차단을 유지한다. DB 연결 상태는 `disconnected → transportConnecting → transportConnected(epoch) → identityProbing → recoveryBinding → ready` 또는 identity 검증 실패의 `degradedReady`로 고정한다. 일반 DB action 허용은 `DbActionRequirementV1`으로만 판정한다. 현재 identity의 `identityReady` 전에는 항목 편집 진입과 save service를 차단한다. 미완료 record가 있으면 해당 customer/label-size resource만 `recovery-blocked`로 유지하고 다른 resource는 허용한다.
- startup recovery는 각 unresolved operation에서 prerequisite가 닫힌 가장 높은 유효 durable evidence와 `resourceKind`를 평가하고 resource barrier는 그 결과를 합성한다. decode local event를 canonical artifact에 publish할 때는 같은 operation/session/epoch의 prerequisite durable sequence/digest를 immutable `evidenceSnapshot`에 함께 원자 교체한다. `wireEnvelopeDecodeFailedDurable`의 closure는 `commitCompletedDurable + resultFrameFullyReceivedDurable`, `domainDtoDecodeFailedDurable`의 closure는 여기에 `wireEnvelopeDecoded`를 추가하며 operation/session/epoch와 frame identity도 모두 일치해야 한다. prerequisite보다 먼저 도착했거나 closure가 불완전한 decode event는 pending evidence로만 보존하고 committed-invalid, `committedKnown: true` 또는 resource reload 권한을 만들지 않는다. identity/sequence가 모순되면 artifact를 quarantine하되 commit 성공으로 추정하지 않는다. startup은 closure가 검증된 decode-failure evidence만 해당 stage의 authoritative failure로 사용해 파생 `committedResultInvalid | customerCommittedResultInvalid` publish 전 crash라도 stage/resourceKind의 committed recovery UI로 복원한다. closure가 닫히지 않은 future-stage evidence는 제외하고 남은 낮은 authoritative evidence로 판정한다. 따라서 `commitCompletedDurable`이 있으면 명시적 decode stage를 추정하지 않는 commit 확정 resource별 reload-only, commit intent 이후 완료 증거가 없으면 `commitOutcomeUnknown`, 그 전 cleanup이 불명확하면 `preCommitCleanupPending`이다. `preparedDurable`에서 DB dispatch intent가 없으면 미실행 확정으로 tombstone하고, `preCommitFailedTerminal`은 실패 확정으로 종료한다. `dispatchIntentDurable`부터 `operationAcceptedDurable`까지 commit intent가 없으면 fresh connection의 cleanup/reload 증거가 전이표를 만족할 때만 실패 확정하며 그렇지 않으면 `preCommitCleanupPending`으로 차단한다. `commitDispatchIntentDurable` 또는 `commitDispatchObservedDurable` 이후 `commitCompletedDurable` 전 종료만 `commitOutcomeUnknown`으로 분류한다. `wireEnvelopeDecoded | domainDtoDecoded` 뒤 파생 reload 상태 publish 전 crash이거나, `commitCompletedDurable | resultFrameSendCompletedDurable | resultFrameFullyReceivedDurable`만 있고 closure가 닫힌 명시적 decode-failure evidence가 없으면 stage를 추정하지 않고 commit 확정 resource별 reload-only로 이동한다. label-column은 전체 label-size DB reload와 candidate session handoff를 수행하고, customer-column은 customer dictionary 전체 재조회만 수행하며 label-size session reload와 candidate generation swap을 typed reject한다. recovery artifact에 result payload를 저장하지 않으므로 재시작 후 decode를 반복하지 않는다. 같은 프로세스에서 original/desired projection을 보유한 resource coordinator만 `commitOutcomeUnknown` reconciliation을 수행할 수 있으며 신규 ID mapping payload는 어떤 post-commit state에서도 working state 복구 입력으로 사용하지 않는다. 재시작 후 `commitOutcomeUnknown`, 손상/알 수 없는 artifact처럼 durable 증거만으로 결과를 확정할 수 없는 상태만 `restartManualAcceptanceRequired`로 전환하며, resource별 현재 DB 상태를 reload한 뒤 UI가 `이 작업의 반영 여부를 판정할 수 없으며 현재 DB 상태를 수용하면 차단을 해제합니다.`라고 명시하고 사용자가 수용한 경우에만 tombstone한다. 수동 수용은 성공/실패 판정이나 mapping 복구로 기록하지 않는다. 다른/unresolved identity artifact는 기본 무기한 보존하고 자동 삭제하지 않으며 관리자 진단 목록과 명시적 archive/delete 절차로만 정리한다.
- `LabelColumnSaveCommand`는 dialog open 시점의 기존 컬럼, `BM_RICH_COL_MIN` 일반/sentinel 행, `BM_RICH_CHECK_COLUMNS`, GS1 정보/포함 관계 및 저장 batch가 변경하는 child 상태의 `concurrencyFingerprint`와 목표 `desiredObservationProjection`을 필수로 가진다.
- application lock 참여 writer는 prose의 최소 목록이 아니라 `DbWriterManifestV1`을 source of truth로 폐쇄 관리한다. P1의 `existingWriter`에는 `ItemManagerSaveDAO`, `ItemDAO.updateOrders`, `ItemDAO.updateElementSheetByItemId`, `ItemDAO.autoMigrateElementSheetByItemId`, label-size delete뿐 아니라 같은 session의 form/name/size/preview 입력을 변경하는 모든 기존 `LabelSizeDAO` writer와 `BrandDAO.deleteByBrandId` 같은 상위 aggregate/cascade writer를 실제 call site, SQL target 및 FK/trigger/cascade mutation closure 기준으로 열거한다. 아직 존재하지 않는 `LabelColumnSaveDAO`/`CustomerColumnSaveDAO`는 P1에서 action ID, 예상 SQL target/lock/execution class만 가진 `reservedFutureWriter`로 등록하고 실제 call site를 요구하지 않는다. P3 entry에서 command/DAO owner가 생기면 예약 항목의 계약 일치를 검증하고 P3 development-complete 전에 `existingWriter`로 승격한다. 승격은 canonical `DbWriterManifestV1` digest를 변경하며 이전 digest에 바인딩된 P1 lock/range/deadlock gate artifact를 즉시 만료시킨다. P3 production-exit 전에 승격된 writer/call site/SQL target을 포함한 새 digest로 관련 P1 production gate를 재실행해야 한다. 각 writer는 resource kind/ID resolver, customer→brand→label-size→form의 전역 lock 순서, required session invalidation과 허용 transaction API를 가진다. AST/SQL 구조 lint는 manifest에 없는 direct 또는 cascade column/item/content/label-size/form writer를 production build에서 거부한다. 공용 `LabelSizeLockedTransaction.run(labelSizeId, statements)`와 `MultiLabelSizeLockedTransaction.run(scope, labelSizeIds, statements)` 또는 동등 API는 같은 transaction의 첫 statement에 lock 획득을 삽입하고 이후 statement만 실행한다. label-column/customer-column save는 strict native transaction/result/ACK/recovery 경계를 사용한다. P1 기존 writer는 business mutation, 반환값과 오류의 compatibility semantics를 유지하되 transaction 형태에 따라 세 범주로 고정한다: 이미 명시적 transaction을 소유한 writer는 기존 owner를 유지하고 그 transaction의 첫 DB mutation 전에 lock statement를 삽입한다. autocommit `writeDataWithParams()` 단일 writer는 `LockOwner='Transaction'` lock이 statement 종료 전에 해제되지 않도록 compatibility `LabelSizeLockedTransaction`이 새 transaction owner가 되며 lock 뒤 기존 SQL을 실행한다. 여러 label-size/상위 aggregate에 영향을 주는 writer는 `MultiLabelSizeLockedTransaction`이 transaction을 소유하고 상위 scope와 영향 ID 집합을 lock 안에서 확정한다. 이 transaction wrapping은 strict result/ACK/recovery 이관으로 간주하지 않고 기존 writer가 label/customer recovery state를 재사용하지 않는다. 품목 ID만 받는 API는 labelSizeId를 immutable parameter로 받도록 signature를 변경하고 lock 내부에서 item 소유권도 재검증한다.
- 모든 참여 writer는 어떤 대상 row/range lock보다 먼저 공용 formatter, DB principal, timeout을 사용해 application lock을 획득한다. 여러 resource가 필요하면 customer→brand→label-size→form의 전역 순서를 고정한다. 같은 종류의 label-size가 여럿이면 상위 brand/customer scope lock을 먼저 획득하고 영향 ID 집합을 lock 안에서 조회·고정한 뒤 numeric ID 오름차순으로 잠그고 소유권을 재검증한다. 컬럼 구조 save는 lock 획득 후 대상 label size의 기존 행과 mutation-closure 관계를 `UPDLOCK, HOLDLOCK`으로 다시 읽어 concurrency fingerprint를 계산하며, 원본과 다르면 어떤 update/delete도 실행하지 않고 conflict로 rollback한다. `sp_getapplock`의 `-1/-2/-3/-999` 및 SQL `THROW` error number는 driver/isolate/client wire schema를 통과해 timeout/cancel/deadlock/configuration typed 오류로 복원한다.
- application lock은 이 protocol을 사용하는 writer 사이에서만 유효하다. 레거시 앱, trigger, 외부 stored procedure처럼 lock을 사용하지 않는 writer가 운영 중이면 실제 item/content/column range에 필요한 `UPDLOCK, HOLDLOCK`과 FK/trigger 동작을 함께 검증하고, 공통 protocol 적용 또는 운영상 배타 조건 없이는 동시성 완료로 판정하지 않는다. row version 컬럼이 실제 스키마에 있으면 fingerprint 대신 또는 함께 사용할 수 있다.
- typed query/transaction은 `execute → 모든 result set complete drain → result contract validate → commit` 순서를 지킨다. 같은 Dart isolate에서 동기 FFI를 실행하는 동안 cancel 메시지를 처리할 수 있다고 가정하지 않는다. desktop worker와 Android service/process는 native DB state를 실행 경계 내부에만 소유하고 앱/parent는 opaque `sessionId`/`operationId`만 관리한다. iOS는 native driver와 cancel control thread를 분리하고 transaction capability gate가 확인한 session discard만 허용한다. ODBC에는 검증된 `SQLCancelHandle`/`SQLCancel`, DB-Lib에는 검증된 `dbcancel`과 필요한 `dbcanquery`/`dbfreebuf`를 binding한다. hard-kill을 지원하는 경계가 deadline 내 응답하지 않으면 해당 worker/service process를 종료해 강제 폐기하고, hard-kill이 없는 iOS는 deadline cancel/session discard fixture를 통과하지 못하면 기능을 시작하지 않는다. process/service command와 cancel/control channel은 분리하고 header magic/schemaVersion/messageKind/sessionId/operationId/payloadLength를 가진 length-prefix frame을 사용한다. protocol 상수는 command `maxFrameBytes=67108864`, control `maxFrameBytes=65536`, 세션당 `maxInFlightSqlOperations=1`로 고정한다. byte order, field width, header length, allocation 전 payload length 검사, sequence/duplicate 규칙과 부분 frame/EOF/crash/timeout 결과를 byte-level fixture로 고정한다. credential은 OS별 제한 채널로 한 번만 전달한다. desktop은 명시적으로 상속한 anonymous pipe 또는 제한 ACL named pipe, Android는 app UID와 binder identity가 검증된 bootstrap call, iOS는 앱 credential provider에서 native adapter로 process 내부 전달하며 command line, 환경변수, stdout/stderr, disk와 로그를 금지한다. spawn nonce/process 또는 service identity handshake와 bootstrap ack 뒤 credential channel 폐쇄를 필수로 한다. native mutable buffer는 사용 후 zeroize하되 immutable Dart `String`의 완전한 zeroization을 보장한다고 주장하지 않는다. Windows는 Job Object kill-on-close, macOS는 동등한 parent-death/orphan 방지, Android는 service/process death 관측을 gate로 검증한다. drain/contract/statement 실패 시 `cancel → remaining results drain/free → rollback → @@TRANCOUNT=0 확인` 결과를 구조화한다. cancel/session cleanup 증거가 없으면 먼저 `acceptingCommands=false`로 바꾸고 native session/execution boundary를 tainted 폐기한다. 같은 epoch request를 실행하거나 tainted session에서 후속 SQL을 실행하지 않는다.
- 로그는 operation/trace, labelSizeId, customerId, insert/update/delete 개수, mode 전환, 성공/실패와 redacted parameter의 type/length/count만 기록한다. 키워드 본문, 사용자 정의 QR 데이터, 비밀번호 등 실제 payload와 부분 preview/hash는 `DbClient`, isolate, ODBC, DB-Lib 어느 계층에서도 기록하지 않는다.
- 로그는 상태 관찰용이며 저장 여부나 분기를 결정하는 비즈니스 로직으로 사용하지 않는다.

15. 권한과 진입 조건

- 선택된 label size가 없으면 `항목 편집` 버튼을 비활성화한다.
- 공용라벨관리 탭 접근 권한과 컬럼 구조 변경 권한을 의미상 구분한다. `canManageCommonLabelColumns`의 초기 등급 matrix는 `SYSTEM_ADMIN_USER=true`, `COOP_ADMIN_USER=true`, `MANAGER_USER=true`, `CLIENT_USER=false`로 확정한다. 현재 `canManageItemStructure`와 결과가 같더라도 별도 getter와 테스트로 업무 권한 의미를 고정한다.
- 버튼 표시와 callback 진입은 `canManageCommonLabelColumns`를 사용하고, save service는 dialog open 때 캡처한 immutable user/customer/market context와 저장 직전 현재 로그인 context를 비교한다. DAO 자체의 전역 `User.instance` 확인을 보안 경계로 사용하지 않는다. SQL은 customer/label-size 소유권과 affected row를 강제하며, 더 강한 보안 경계가 필요하면 DB 권한 또는 stored procedure를 별도 배포한다.
- 품목관리 draft dirty/command busy/force-reload-required, 강제 reload, 공용라벨 저장 등 충돌 가능한 상위 상태에서는 진입을 차단하고 이유를 안내한다. DB bootstrap이 `ready`가 아니거나 현재 DB identity에 대한 `LabelColumnSaveRecoveryRegistry.identityReady` 전이거나 현재 customer/label-size resource에 미완료 recovery record가 있으면 편집 진입과 save service를 모두 차단한다. transport 연결만으로 `status.up`을 게시하지 않으며 recovery record가 있으면 강제 reload·사용자 확인 경로만 제공한다.
- dialog를 열 때 labelSizeId, customerId, marketId, 현재 column cache generation을 immutable input으로 전달한다. 열린 뒤 상단 dropdown 값에 다시 의존하지 않는다.
- open 직전 선택 context와 현재 로드된 label-size 세션의 customer/market/labelSize가 모두 일치하는지 확인한다. 저장 직전에도 권한과 context generation을 재검증하며 불일치하면 DB를 쓰지 않는다.

15.1 저장 후 session consumer 계약

- 레거시 `CLabelEditModel`, `CScalePrintModel`, `CUpdateItemModel`, `CLabelPrintModel`의 `OnCommonLabelColumnChange()` 구현을 `LabelSizeSessionConsumerManifestV1`의 근거로 사용한다. 단순 observer callback 호출 자체를 복제하지 않고 각 소비 효과가 새 generation에 귀속되도록 한다.
- 품목 편집 소비자는 DB 컬럼/콘텐츠로 동적 column을 재구성하고 기존 stable item ID 기준 선택을 복원하며 현재 행의 RTF가 비어 있거나 column schema가 바뀌었으면 새 session 입력으로 재생성한다.
- update-item 소비자는 현 프로젝트에 활성 call site가 없으므로 `legacyOnly | future`로 분류하고 handoff 필수 ACK에서 제외한다. 향후 화면/consumer를 활성화할 때 update column/content를 새 generation으로 재조회해 table column을 재구성하는 별도 scope와 gate를 추가한다. scale 소비자도 현 프로젝트의 저울출력 탭이 placeholder인 동안 `future`로 분류하고 handoff 필수 ACK와 no-op ACK 게시에서 제외한다. 실제 저울출력 화면/consumer를 활성화할 때만 `currentRequired`로 승격하고 레거시 `CScalePrintModel::OnCommonLabelColumnChange()`의 table rebinding을 새 generation에서 수행한 뒤 `renderReady`를 반환하는 별도 gate를 추가한다. 이때도 레거시 근거가 없는 preview clear/recompute를 자동 추가하지 않는다. 공용라벨/현 프로젝트 preview·validation 소비자는 현재 static cache 의존을 session accessor로 옮기는 데 필요한 invalidate/recompute를 별도 manifest 항목으로 명시한다. 레거시 `CLabelPrintModel` no-op consumer에는 근거 없이 부작용을 추가하지 않는다.
- warm handoff의 각 consumer 호출은 crash/ACK 유실 복구를 위해 at-least-once일 수 있다. consumer는 `(consumerId, expectedOldGeneration, newGeneration, context)`를 검증하고 `(stableDatabaseIdentityDigest, customerId, marketId, labelSizeId, consumerId, newGeneration)` 기준으로 재호출해도 같은 최종 상태를 만드는 idempotent apply를 수행한 뒤 `renderReady` 또는 typed failure를 반환한다. `expectedOldGeneration`은 warm transition guard이며 멱등 identity에는 넣지 않는다. 완료 acknowledgement는 같은 composite key로 durable manifest에 기록하고 duplicate ACK는 canonical payload가 같을 때만 허용하며 context가 다르면 typed reject한다. exactly-once 보장은 함수 호출 횟수가 아니라 새 generation에 귀속된 최종 관측 상태와 warm old resource의 단 한 번 dispose에 적용한다. warm handoff는 manifest의 필수 consumer acknowledgement가 모두 새 generation을 관측한 뒤에만 성공하며 그 전에는 old resources를 dispose하지 않는다.
- consumer transition guard는 activation mode별로 분리한다. warm handoff는 `(expectedOldGeneration, newGeneration)`, cold recovery는 `(recoveryOperationId, newGeneration)`을 검증한다. cold durable `consumerApplyCompleted`는 같은 멱등 composite key에 recovery operation ID를 추가해 다른 startup operation과 cross-ack하지 않는다. 별도 `liveRenderReady`는 `(processIncarnationId, attachmentEpoch, consumerId, newGeneration)`에 바인딩하고 startup마다 현재 process에서 다시 요구하며 recovery artifact의 과거 process render ACK로 충족하지 않는다. cold 경로는 old resource dispose acknowledgement를 생성하거나 요구하지 않는다. warm/cold mode를 cross-decode하거나 cold 경로에 임의 `expectedOldGeneration=0|null` sentinel을 넣으면 typed protocol error다.

16. 테스트 요구사항

16.1 순수 모델 테스트

- original/working/property dirty 구분
- 속성 적용과 취소
- 신규 pending 특수 행의 속성 취소 시 행 제거
- `requiresInitialPropertyApply={3,4,9,11,12}`만 `initialApplyState=requiredPending`으로 생성되고 날짜/기본 타입은 `notRequired`로 즉시 추가됨. 값 변경이 없어 `propertyDirty=false`여도 pending 행의 `적용`은 활성화되고 성공 시 `completed`가 되며, 그 전에는 선택 이탈·후보 추가·reorder/userItemEdit 진입·메인 저장이 모두 차단됨
- 현재 pending 행 자체의 삭제 request는 원자 행 제거 뒤 `requestConsumedByPendingRowRemoval`로 완료되어 삭제 continuation을 실행하지 않고, 다른 행 선택/후보 추가/모드 진입 request만 `proceedAfterPendingRowRemoved`로 원래 command를 정확히 한 번 실행함. pending 속성 `취소`는 확인 승인 시 행 제거, 거부 시 draft/focus 유지이며 baseline reset만으로 pending 행을 남기지 않음
- 같은 pending key에 버튼/drop/programmatic resolver 요청이 겹치면 single-flight confirmation 하나만 열리고 captured revision/key가 달라진 후착 결과는 `superseded`로 상태 변경·continuation 없이 종료됨
- 기존/신규 삭제 ID 처리
- 안정 key 기반 선택 유지
- duplicate keyword/빈 필드/type별 validation
- 제목 CP949 20바이트 경계: 한글, 영문, 혼합, CP949 변환 불가 문자
- 모든 DB 문자열의 field별 CP949 byte 경계, nullability, 변환 불가 문자 거부
- CP949 encode→decode round-trip, VARCHAR/NVARCHAR/MAX capability 단위, raw key/value/type staging 후 target 변환 검증
- raw JSON staging의 필드 부재/명시적 null/중복·알 수 없는 key/`TRY_CONVERT` 실패 구분
- `DraftMappingKeyV1`이 lowercase ASCII UUID 36자만 허용하고 uppercase, nil UUID, trim 전후 공백, 길이 초과·미달, 유효하지 않은 hyphen 위치와 ordinal 중복을 JSON decode/command 생성에서 거부함
- persisted field allow-list가 runtime-only `TColumn` 필드를 제외함
- `RawLabelColumnRow`와 strict mapper가 null, 숫자 문자열, 범위 밖 정수, unknown barcode name을 구분해 raw enum을 보존하고 저장을 차단함
- `RawLabelColumnMinRow`가 기존 일반/sentinel `RICH_MIN_CHECK`를 보존하고 신규 일반/sentinel만 0으로 생성함
- type code 13 제외, 0~12 editor 매핑, 미지원 raw enum 보존과 저장 차단
- 타입 dropdown은 DB reference row와 지원 code 0~12의 교집합이며 기존 행이 쓰는 reference 누락은 capability 오류, 미사용 reference 누락은 신규 목록 제외로 분류됨
- 제조일자/유통기한만 날짜 editor를 사용하고 제조시각/유통시각은 레거시 fallback 기본 editor를 사용하며 별도 시각 형식 필드를 만들지 않음
- 후보 추가 기본값 fixture가 실제 labelSize 생성 경로의 `barcodeType=0`, `lineSize=0`, GS1 AI `01`, QR scale `100`, QR text font size `10`과 나머지 persisted scalar를 재현하고 다른 생성자의 `lineSize=1`을 사용하지 않음
- 사용자 항목 신규/수정 dropdown은 editable type 0~12만 제공하고, 기존 0~12 외 raw type 행은 DB 표시명 보존 read-only로 표시되어 삭제만 가능하며 수정·복사·신규 저장이 차단됨
- 기존 `[A-Z0-9]+` 비준수 사용자 keyword는 raw 보존 read-only·삭제 가능이고 신규/실제 수정 행만 새 규칙과 `ITEMNAME` 예약어 금지를 적용함. 기존 예약어 충돌 행은 keyword/다른 속성을 보존하고 keyword 불변 저장·삭제를 허용하되 V1 컬럼 참조 선택·복사를 차단함. 비준수/충돌 행 존재가 다른 정상 행 저장이나 해당 행 삭제를 차단하지 않고 자동 정규화하지 않음
- QR 수치 범위 및 타입 변경 초기화 매핑. `TYPE_BASE ↔ TYPE_QR_CODE` 양방향은 create type plain text와 data/text 빈 문자열 projection을 검증함
- QR pixel size/scale 직접 입력 0은 출력 불가 경고 확인 후 적용 가능하고, 권장 범위 밖의 다른 값은 validation error이며 신규 pixel size 0이 첫 적용 전 보존됨
- 기본 타입은 data만 편집하고 data 실제 변경 시 text를 `''`로 초기화하며 다른 속성만 저장하면 기존 text를 보존함. `RICH_USE_USER_DEFINE_QRDATA` 기존 raw는 UI/create type에서 재계산하지 않고 round-trip 보존하며 신규만 0으로 생성함
- 누락 검사 check table/main legacy flag 충돌 시 source of truth와 동기화
- `QRCodeCreateTypeActiveReferenceFieldsV1`이 plain text=없음, user define=data+text, natrium=natrium records, barcode text link=data를 반환하고 비활성 stale field는 raw 보존하되 참조 판정에서 제외함
- 전체 keyword 집합은 기존 원문을 보존하되 `referenceableKnownKeywordsV1`이 whitespace/`#` 포함 및 `품목`/`ITEMNAME` 충돌 keyword를 제외하고 신규 생성·rename을 차단함. 제외 기존 행과 persisted active-field/workbook 원문은 자동 rewrite/참조 추정 없이 보존됨을 검증함. `ReferenceTokenParserV1`은 예약 token 우선, referenceable known-keyword 길이 내림차순 ordinal match, `EOF | whitespace | 다음 # | Unicode punctuation/symbol` boundary와 letter/number/combining mark/connector continuation 및 non-overlapping token span을 검증함. 별도 `LegacyOutputTokenReplacerV1`은 유일한 persisted column order 숫자 오름차순의 레거시 전역 순차 치환과 치환 결과 재치환을 golden으로 검증하고 parser의 longest-match 결과를 실제 출력에 사용하지 않음. duplicate order는 traversal 전에 typed capability error이며 `RICH_COLUMN_ID`를 출력 tie-break로 사용하지 않음. 동일 replacer trace는 `#ABC`의 known-prefix 부분 치환과 replacement-created 후속 token의 transitive source를 실제 출력과 같은 결과로 기록하며, 품목명이 `#OLD`를 생성하는 fixture에서 `reservedItemName` source와 parent event lineage를 보존하고 임의 column ID sentinel을 만들지 않음
- `BARCODE_TEXT_LINK` 기존 token은 모든 raw existing keyword를 유일한 persisted order의 숫자 오름차순으로 출력하고 exact dependency trace에도 포함하되 duplicate order는 출력 전 typed capability error로 차단함. 신규 picker는 `TYPE_BASE | TYPE_FIX`만 제공하고 다른 타입의 기존 token을 자동 변경하지 않음. whitespace/`#` 포함 또는 예약어 충돌로 parser/picker에서 제외된 기존 keyword도 출력·trace에는 포함되고 자동 rewrite되지 않는 fixture를 검증함
- `LegacyOutputTokenReplacerV1`은 기존 raw output session의 order가 유일하면 gap/nonpositive를 포함해 숫자 오름차순으로 레거시 출력하고 duplicate order만 ID tie-break 없이 차단함. 신규 저장 projection은 별도로 양의 정수 1부터 연속임을 검증함. 한 pass에 같은 token이 여러 번 있는 입력과 길이가 다른 replacement에서 occurrence별 `prePassInputSpan/postPassOutputSpan`, 좌→우 ordinal 및 각 replacement-created lineage가 결정적임
- `Gs1OutputPolicyV1.legacyPermissive`는 승인된 legacy view 순서 fixture의 raw AI/token/FNC1 조립 뒤 예약 item 선행 pass 없이 persisted column order의 column pass만 수행해 레거시 golden과 byte-for-byte로 재현함. `ITEMNAME/품목` 충돌 keyword는 item name이 아니라 해당 column ID/value trace를 만듦. view 정의/순서 근거 부재·다의성은 차단하고, 품목 값의 길이·숫자·날짜 validation 실패는 빈 문자열이나 format fallback으로 바꾸지 않음. variable AI 중간 `0x1D`와 마지막 segment trailing 없음, format-option lookup/full raw AI 출력, `TYPE_VALIDDATE/DATE_FORMAT_NONE`을 encoder 직전 code-unit/byte fixture로 검증함. 기존 `item_code_data_resolver_test.dart`의 형식 불일치 오류 기대는 이 legacy-permissive golden으로 교체함. GS1 관계만 있는 keyword rename은 허용되고 출력 값은 동일하며 delete/type-change/관계 제거만 endpoint dependency 확인을 요구함
- QR data/QR 하단 text/나트륨/GS1 참조 관계 계산, active create type field만 사용하는 예약 token 충돌과 unknown candidate의 known-prefix 비치환 처리

- 사용자 항목 customer-scoped lock/fingerprint 일치 저장과 동시 변경 conflict rollback

- strict save의 success/rollback/contract failure/cancel 각 경로가 `XACT_ABORT`/`NOCOUNT`와 isolation baseline을 복원·검증하거나 native session을 폐기하고, 다음 compatibility command가 이전 strict batch의 SET option을 관측하지 않음
- Windows ODBC, macOS DB-Lib와 Android/iOS native adapter 각각에서 `DbNvarcharMax`/동등 타입, raw scalar staging과 명시적 target 타입 변환, 한글, 작은따옴표, 4,000자 초과 batch 전달

- typed `queryResultSets`가 단일 batch/transaction의 모든 결과셋을 고유 schema로 drain하고 rowset kind/version 또는 고정 ordinal contract로 raw snapshot을 반환하며 기존 `Object` compatibility API를 사용하지 않음
- ODBC, DB-Lib와 Android/iOS native type이 동일 `DbLogicalType`/column metadata로 정규화되고 nullable/수치 metadata의 `unknown`/`notApplicable`이 실제 null/0과 구분되며 marker의 명시적 `CAST`와 result contract가 driver native code나 미지원 metadata 추정에 의존하지 않음
- 모든 production adapter의 integer 경계, 고정 scale decimal, datetime precision/timezone, binary와 DB null이 같은 `DbWireScalar` round-trip 및 canonical projection을 만들고 decimal이 `double`로 변환되지 않음
- 모든 production adapter가 모든 결과셋을 고유 schema로 drain하고 기대 `RESULT_KIND`/`SCHEMA_VERSION` marker 결과셋 하나만 반환
- trigger 중간 `SELECT`, rowcount-only/빈/marker 중복·누락 결과가 최종 결과로 오인되지 않음
- marker/schema 누락·중복과 count 불일치, malformed mapping JSON, mapping field type 오류, draft key 누락/초과, ROW_NO/key/ID 중복·0/음수 ID와 label/customer mapping kind cross-decode는 result contract의 commit 전 protocol error로 rollback됨
- label/customer SQL staging과 mapping은 `DraftMappingKeyV1`을 `VARCHAR(36) ... BIN2` 또는 승인 ordinal binary 표현으로 왕복하고 업무 collation의 case folding, `NVARCHAR(100)` 절단, trim 또는 identity 순서 추정에 의존하지 않음. row-by-row와 승인 insert-only MERGE template 모두 source key/ROW_NO/inserted ID를 같은 mapping row에 결합함
- `DbResultContract` 통과 뒤 `DbValidatedResultPayloadV1`의 resource DTO mapper는 동일 schema version에서 total projection이며 count/key/ID/discriminant 의미를 다시 검증하지 않음. pre-commit에서 검증 가능한 malformed mapping과 unknown DTO enum/version은 모두 rollback 또는 parent wire decode failure가 되고, post-commit domain decode failure는 주입한 internal mapper defect reason만 허용됨
- `DbValidatedResultPayloadV1`의 kind/schemaVersion/operation/session/epoch/resource mapping kind/marker/count/typed mapping entry와 내부 `DraftMappingKeyV1`이 isolate round-trip하고 unknown version, 필수 field 누락과 label/customer cross-decode를 거부함
- `NativeDbTransactionSession`이 하나의 native connection에서 begin/executeAndDrain/commit/rollback/verify/discard를 수행하고 일반 `writeData()`로 transaction 제어 SQL을 보내지 않음
- operation accepted/commit dispatch intent/commit dispatch observed/commit completed/result frame send 완료/parent frame receive 완료/wire envelope decode/domain DTO decode 각 경계의 crash·EOF·partial frame이 단일 오류 상태로 분류되고 `commitCompleted` 증거 없는 오류는 `DbCommittedResultInvalid`가 되지 않음. worker send 완료만으로 parent receive 완료를 게시하지 않으며 length/checksum/ID 검증 뒤에만 `resultFrameFullyReceivedDurable`이 됨. control/result channel 재정렬과 중간 ACK 유실에서 높은 cumulative ACK를 수용하고 낮은 후착 ACK는 idempotent stale/typed reject로 결정적으로 분류함. ACK보다 먼저 온 local decode evidence는 pending 보존 후 재평가되고, 같은 operation/session/epoch의 prerequisite sequence/digest closure를 가진 원자적 `evidenceSnapshot`으로 승격된 경우만 committed-invalid 권한을 가짐
- label/customer marker 결과셋과 marker row가 각각 정확히 1개이고 신규 0건은 `MAPPING_JSON=[]`, N건은 resource별 schema의 같은 1행 배열로 전달됨. customer 정상 result decode 성공에서만 mapping을 선택 복원에 사용하고 committed-invalid payload는 폐기함
- `DbNvarcharMax`/statement/result contract/result-set contract/result/logical metadata/wire scalar/typed lock·discard error의 isolate `toMap/fromMap` version round-trip, 알 수 없는 version 실행 전 차단, 모든 production adapter의 native error number/state 보존
- connect/reconnect/disconnect/connection loss/isolate 재생성/DB identity 변경에서 capability와 `TColumnType` cache가 올바른 epoch로 폐기·재조회됨
- connect envelope는 아직 생성되지 않은 새 epoch를 요구하지 않고 `connectAttemptId`/`expectedPreviousEpoch`를 검증하며, 성공 응답부터 발급된 epoch를 bootstrap/일반 request가 사용함. 겹친 connect의 오래된 응답은 SQL readiness와 cache owner를 덮지 않음
- `disconnected → transportConnected(epoch) → identityProbing → recoveryBinding → ready | degradedReady` 전이에서 폐쇄 목록의 bootstrap request만 특권 실행되고 `DbActionRequirementV1`이 각 일반 action의 phase/authoritative identity/cache/write 요구를 강제함. degradedReady는 manifest allow-list 외 action과 모든 write/label-session load/항목 편집/recovery bind를 차단함
- bootstrap 이후 모든 일반 DB request의 connection epoch가 dequeue/driver 실행 전 검증되고 taint 당시 epoch로 queue된 request는 SQL 실행 없이 `DbConnectionDiscarded`로 실패하며 새 native connection 성공 후에만 새 epoch 요청이 허용됨
- `DbClient.isConnected` 신규 사용 금지와 startup/connection service/monitor/로그인 초기 DAO/cache 호출부 migration 표가 구조 lint를 통과하고 privileged bootstrap send port가 일반 DAO에 노출되지 않음
- redacted save parameter와 임의 깊이 `statements[].params`가 `DbClient`, isolate, ODBC, DB-Lib 로그에 값/preview/hash 또는 중첩 payload 직렬화 없이 metadata allow-list의 name/type/length/count로만 기록됨
- label `ROW_NO/draftColumnKey/columnId`와 customer `ROW_NO/draftCustomerColumnKey/custColumnId` mapping의 resource별 key/ID 유일성 검증
- `ContentCreationOwnershipV1`이 trigger-owned/DAO-owned 생성 주체를 정확히 하나 선택하고 각 주체가 신규 column의 기존 item/update-item content를 중복 없이 정확히 한 번 생성함. 혼합·미승인 trigger hash·불명확 주체는 진입 차단됨
- 레거시 `AFTER_INSERT_COLUMN` 동등 trigger는 definition hash가 알려져 있어도 statement-level `inserted` 전체 집합을 처리하지 않고 전역 order를 변경하므로 `unsupported`이며 활성 상태에서 편집 진입이 차단됨. 검증된 set-based trigger 또는 DAO 단일 주체만 허용됨
- `updateRows`는 persisted projection 또는 최종 order가 달라진 기존 행만 포함하고 SQL affected count/result contract `expectedUpdateCount`가 같은 집합과 일치하며 변경 없는 행을 재기록하지 않음
- `RICH_SEARCH_PRINT`는 UI/dirty/updateRows에서 제외되고 기존 raw 값은 저장 전후 동일하며 신규 행만 0으로 생성됨
- delete가 content/check/min/GS1/QR 관계/status/main row를 순서대로 정리
- GS1 contain 관계의 양쪽 참조 정리
- QR target 관계의 source/target 양쪽 참조 정리
- 운영 SQL 타입/분포로 확정한 canonical `BM_RICH_COL_MIN` sentinel predicate가 `''`/`0` 혼재·중복·일반 `ELEMENT` keyword를 오분류하지 않고 insert/update/delete 뒤 sentinel을 정확히 1개 유지함
- 기존 일반/sentinel `RICH_MIN_CHECK`는 저장 전후 동일하고 신규 행만 0임
- `IndexPredicateRequirementV1`이 모든 save/snapshot/reconciliation `queryId`를 열거하고 key/include/filter/enabled/hypothetical/collation과 권한을 판정함. manifest 누락·schema 부적합은 runtime fail-closed, 권한 부족은 별도 reason이고 실행 계획 변화만으로 runtime 허용 상태가 바뀌지 않음
- concurrency fingerprint 일치 저장과 동시 변경 conflict rollback
- 컬럼 구조/품목 저장/품목 순서/element update·migration/라벨 크기 및 브랜드 cascade 삭제가 공용 locked transaction API만 사용하고 direct/FK/trigger/cascade mutation closure를 manifest에 포함함. 단일/복수 label-size application lock을 row lock보다 먼저 같은 connection/transaction에서 획득하며 복수 ID는 상위 scope lock 뒤 오름차순으로 획득함
- strict label/customer writer에는 SQL 내부 transaction 또는 단독 `writeDataWithParams()` 사용이 없고, P1 lock-only compatibility writer는 manifest 분류대로 기존 명시적 transaction owner 유지, autocommit 단일 writer의 compatibility locked transaction owner 이관, 복수 resource writer의 multi-resource owner 이관 중 정확히 하나를 사용함. 모든 범주에서 공용 lock이 같은 transaction의 첫 DB mutation 전에 실행되고 item 기반 writer가 전달받은 labelSizeId 소유권을 lock 내부에서 검증하며 strict ACK/recovery state를 게시하지 않음
- `sp_getapplock` timeout/cancel/deadlock/configuration return code가 모든 production adapter와 isolate/service 경계를 지나 typed error로 구분됨
- 중간 단계 실패 전체 rollback
- affected row 0 또는 identity 소유권 불일치 시 rollback
- 일반 commit 전 저장 실패는 UI working copy를 지우지 않고 같은 command 재시도를 허용하되 `DbConcurrencyConflict`는 최신 snapshot 수동 재적용 전까지 동일 command 재시도를 차단함
- `DbCommitOutcomeUnknown`이 save 재실행을 차단하고 desired/original/indeterminate 3상태로 reconciliation하며 실제 commit 여부를 단정하지 않음
- `DbCommittedResultInvalid(committedKnown: true)`은 commit 여부 reconciliation이나 save 재실행으로 이동하지 않고 같은 프로세스에서도 신규 ID mapping payload를 working state에 적용하지 않으며 resource별 전체 reload만 수행함. 재시작 뒤 `commitCompletedDurable` 이상은 commit 확정 reload-only, durable 증거가 불충분한 상태만 수동 수용으로 이동함
- label-column/customer-column reconciliation adapter가 각각 다른 resource/projection을 사용하고, mutation-closure 전체 base-table key/range를 같은 application lock과 `UPDLOCK, HOLDLOCK`의 단일 transaction에서 읽음
- 최초 raw snapshot은 snapshot isolation capability가 확인된 짧은 `SNAPSHOT` transaction으로 일관된 rowset을 만들고 잠금 격리로 조용히 낮추지 않음. save/reconciliation만 application lock 뒤 모든 base-table key/range를 같은 순서의 `UPDLOCK, HOLDLOCK`으로 읽으며 동시 non-participant writer와 absence insert를 주입해도 혼합 세대 rowset을 만들지 않음
- 모든 production adapter의 DB null, 빈 string, 빈 binary가 `DbWireScalar`와 strict raw API에서 서로 구분되고 DB-Lib non-null `len == 0`이 null로 축약되지 않으며 compatibility DTO 기본값이 canonical projection에 유입되지 않음
- DB-Lib command path에서 암묵적 reconnect가 0건이고 transaction의 모든 statement/commit/rollback/cleanup이 같은 `DbNativeSessionToken`을 검증함. 연결 단절/token 불일치는 새 DBPROCESS에서 후속 statement를 실행하지 않고 commit dispatch 여부에 맞는 typed 오류로 종료됨
- `PlatformDbExecutionCapabilityV1`이 Windows/macOS desktop worker, Android `android:process` remote native service, iOS in-process native driver의 실제 cancel/session-discard/hard-kill 능력을 구분하고 미검증 조합은 transaction 시작 전에 차단함. strict action이 비Windows in-isolate `MssqlConnectionDriver`/직접 FFI compatibility 경로를 사용하면 구조·앱 통합 gate가 실패함
- desktop/Android execution boundary만 native DB 자원/transaction을 소유하고 앱/parent는 opaque ID만 사용함. iOS는 독립 cancel thread와 session discard를 검증함. 각 플랫폼 channel의 byte-level framing/duplicate ack/crash·timeout/credential identity가 결정적 결과를 만들고 credential이 command line/env/stdout/stderr/disk/log에 나타나지 않음
- result drain/contract/statement 실패의 cancel/free-results, rollback, `@@TRANCOUNT=0` 확인이 순서대로 구조화됨. commit dispatch 없음과 cleanup 전체 성공이 증명된 경우만 `preCommitFailedTerminal`이고 나머지는 `preCommitCleanupPending`으로 resource를 차단하며 connection을 재사용하지 않음
- SQL Server 대상 컬럼 비교로 case/accent/kana/trailing-space natural-key 후보와 저장 전 중복을 판정하고 0/복수 매칭·context 변경·정확히 투영할 수 없는 시간 side effect를 indeterminate reason으로 반환함
- parameter binding으로 작은따옴표가 있는 허용 문자열도 SQL 문법을 깨지 않음

16.4 통합 회귀

- warm handoff 저장 후 root `LabelSizeReloadCoordinator`의 force reload가 `expectedOldGeneration`보다 큰 `newGeneration`을 발급하고 immutable `LabelSizeSessionData`와 lifecycle `LabelSizeSessionResources`를 candidate 내부 같은 generation의 `LabelSizeSession`으로 재구성하며 `HomePageManager`는 render/typed failure ACK만 반환하고 모든 세션 화면/helper가 session accessor를 사용함
- commit durable evidence 뒤 process restart한 cold recovery는 old session/generation/resources 없이 `(recoveryOperationId, newGeneration)`으로 candidate initial activation과 필수 durable `consumerApplyCompleted`를 수행하고, 현재 `(processIncarnationId, attachmentEpoch)`의 `liveRenderReady`를 다시 받은 뒤 resource barrier를 재평가함. 이전 process render ACK는 현재 attach/render를 충족하지 않음. `expectedOldGeneration=0|null` 또는 빈 old resources 합성, old dispose ACK와 warm/cold cross-decode는 typed reject되며 cold activation 실패는 old resume가 아니라 candidate 폐기 또는 force-reload-required로 전이함
- 현재 session의 `LabelWorkbookDraftPort`만 workbench 변경 callback과 pending edit flush를 소유하고 snapshot의 generation/context/revision이 저장 command와 일치함. session handoff/detach 중 snapshot은 실패하며 이전 session이나 DB workbook으로 fallback하지 않음
- candidate prepare는 기존 journal 파일/listener를 변경하지 않고, suspend/activate/swap/render 실패 시 durable manifest recovery matrix에 따라 기존 session resume, candidate active 또는 force-reload-required로 복구됨
- journal handoff 각 phase 직후 프로세스 종료 주입에서 generation/owner token이 다른 파일을 삭제하지 않고 startup recovery가 단일 owner를 선택함
- 각 production 플랫폼의 process/service/native cancel 실패 주입과 durable file API 실패에서 startup이 platform hint에 의존하지 않고 checksum/generation/phase/ownerToken으로 단일 owner를 복구하며, hard-kill 미지원 iOS는 cancel/session discard capability 미충족 시 기능을 사전 차단함
- P0-only bootstrap에서 P2 recovery consumer 없이 prepare/dispatch/commit-intent/worker ACK 각 publish 직후 process 종료를 주입해 `NativeOperationEvidenceStoreV1`이 target/tmp/bak authoritative artifact를 재발견함. clean store만 strict dispatch를 허용하고 unresolved resource는 P2 consumer bind·판정 전 새 strict dispatch를 차단하며 store 교체나 메모리 fallback이 없음
- 저장 coordinator가 overlay/HomePageManager dispose 후에도 commit success/unknown/committed-invalid와 reload 필요 상태를 `LabelColumnSaveRecoveryRegistry`에 정확히 한 번 전달한다. 같은 프로세스에서 projection이 남아 있을 때만 reconciliation하고 startup/reconnect에서 save를 재실행하지 않음
- closed V1 state/event/reject Cartesian matrix가 모든 ordered guard, duplicate/stale ack와 durable publish-DB send 경계를 정확히 하나의 transition/reject로 매핑함. process/service 종료 또는 iOS native failure에서 단일 record를 선택하고 publish 완료 전 DB send가 0건이며 각 실패가 정의된 block/action만 노출함
- 동일 server의 검증된 AG failover fixture는 같은 `stableDatabaseIdentityDigest` namespace를 사용하고, 폐쇄 열거된 backup/restore·detach/attach·AG seed/failover·storage/VM snapshot 절차는 기대 identity 유지/변경 또는 production 금지를 재현함. permission denied/metadata hidden/unsupported fixture는 degraded action allow-list만 허용하고 다른 identity record를 reload/tombstone하지 않음
- durable registry artifact에 original/desired projection, 저장 문자열, result payload와 content-derived fingerprint/hash가 없음. 재시작 시 `preparedDurable` 미실행과 `preCommitFailedTerminal` 실패 확정은 수동 수용 없이 종료됨. decode-failed event만 있고 prerequisite closure가 없는 crash는 committed-invalid로 승격하지 않으며 낮은 authoritative evidence에 따라 pending/cleanup/unknown으로 판정함. 같은 operation/session/epoch의 commit/frame prerequisite closure가 원자적 `evidenceSnapshot`에 포함된 decode-failed crash만 stage별 committed-invalid로 복원됨. decode-success evidence만 게시됐거나 decode evidence 없이 `commitCompletedDurable`부터 `resultFrameFullyReceivedDurable`까지만 남으면 stage를 추정하지 않고 동일 command 금지·resource별 reload-only 후 종료됨. commit intent 이후 완료 증거가 없거나 artifact가 손상된 진짜 미확정 상태만 resource별 reload·사용자 수용·tombstone 뒤 차단을 해제함
- 같은 identity/resource에 복수 unresolved operation artifact가 있어도 wall-clock/file mtime으로 하나를 버리지 않고 operation별 authoritative artifact를 결정한 뒤 모든 barrier를 합성함. commit 확정/committed-invalid operation이 낮은 phase에 가려지지 않고 모순 operation 격리 중에도 resource 차단이 유지됨
- unresolved/다른 identity artifact가 자동 삭제되지 않고 관리자 진단 목록, 보존 기간과 명시적 archive/delete 절차로만 정리됨
- 새 session subtree의 listener 재결합과 첫 renderReady 전까지 old resources가 살아 있고, 성공 후 정확히 한 번 dispose됨
- 공용라벨/품목관리/미리보기 세션 경로에서 `TColumn.datas`, `TColumnContent.datas`, `TColumnSpecial.datas`, `ItemOfMarket.datas`, `_currentLabelSize`, `Market.instance`를 조합한 session-state 직접 read가 0건이고 customer/market/label-size context도 같은 generation accessor에서 읽음
- 겹친 reload에서 오래된 generation 결과가 최신 session을 덮지 않음
- force reload 실패 시 부분 cache가 노출되지 않고 force-reload-required 상태로 후속 편집 차단
- commit 성공 후 reload 실패 시 DB save 재실행 없이 candidate session reload만 재시도
- 저장 후 공용라벨 사용 항목과 품목관리 동적 컬럼은 재조회하고, 현 preview/validation은 manifest에 명시한 invalidate/recompute만 수행하며 레거시 LabelPrint no-op에 임의 부작용을 추가하지 않음. scale은 실제 화면 활성화 전 `future`라 실행하거나 ACK를 게시하지 않고, 활성화 시 별도 gate와 함께 `currentRequired`로 승격해 table rebinding만 수행함
- `LabelSizeSessionConsumerManifestV1`의 `currentRequired` 품목/preview/validation 소비자만 `(stableDatabaseIdentityDigest, customerId, marketId, labelSizeId, consumerId, newGeneration)` 기준 idempotent하게 새 generation의 동적 column, 선택, RTF와 파생 cache를 재구성하고 durable acknowledgement를 남긴 뒤에만 `renderReady`를 반환함. update-item은 `legacyOnly | future`, scale은 화면 활성화 전 `future`라 필수 ACK에 참여하거나 no-op ACK를 게시하지 않고, 실제 `BM_UPDATE_ITEM` row가 있을 때 DB content 호환만 검증한다. crash/ACK 유실 재호출은 같은 최종 상태를 만들고 context가 다른 ACK는 거부하며 old resource는 한 번만 dispose됨
- 기존 공용라벨 `필수등록` 표시는 편집기 저장 결과를 읽기만 하며 직접 mutate하지 않음
- 새 이미지/바코드/QR keyword가 라벨 시트 object/required keyword 처리에 반영
- 삭제/키워드 변경한 항목을 참조하는 라벨 workbook에 대해 영향 경고가 표시됨
- 기존 라벨 설정/브랜드 설정/품목 순서 변경 테이블 테스트 전체 통과
- `flutter analyze`, 관련 테스트, 전체 `flutter test`, `git diff --check` 통과

16.5 실행 환경별 완료 gate

- P0 구현 착수 전 외부 prerequisite로 승인 운영 DB에서 비민감 schema capability snapshot을 채취해 checked-in fixture로 고정한다. fixture는 SQL Server edition/version, `snapshot_isolation_state`, 대상 table/column type·max_length·nullable·collation, PK/unique/index key/include/filter/enabled, FK/cascade, trigger 이름/활성/정규화 definition hash와 statement-level inserted 처리 여부, `BM_RICH_COL_MIN` sentinel SQL 타입/`''`·`0`·중복 분포, `BM_RICH_COLUMN_TYPE` 실제 행, content/update-item/status table 존재를 포함한다. 원본 업무 데이터와 credential은 fixture에 넣지 않는다. 이 fixture가 없으면 capability 코드를 추정 구현하거나 production gate를 통과시킬 수 없다.
- 플랫폼 prerequisite로 Windows worker executable, macOS worker target, Android 별도 `android:process` bound remote service와 ABI별 native library, iOS native adapter/cancel control target의 planned source target, build/package destination과 protocol ownership을 설계 manifest로 먼저 승인한다. P0 entry에는 실제 binary/target 존재를 요구하지 않는다. 각 target의 담당자, CI 또는 수동 승인 lane, 결과 artifact 저장 위치·보존 기간·승인 주체와 Android production signing 및 Apple signing/notarization 전제를 `GateManifestV1` 옆 release matrix에 기록한다. P0 development-complete는 source target과 contract harness artifact 존재를, P0 production-exit은 설치·bundle·서명된 실제 artifact와 필수 matrix 실행 결과를 요구한다. 현재 Dart isolate나 로컬 FFI library 발견만으로 native execution boundary 완료를 주장하지 않는다.
- `GateManifestV1`을 모든 실행 gate의 source of truth로 사용한다. 각 gate는 ID/blocking 여부, OS/architecture, SQL Server edition/version, provisioning·권한 DDL, driver/worker/service artifact와 protocol version, 실행 명령/timeout, expected assertion, 결과 artifact schema와 유효기간을 가진다. manifest에 없거나 유효기간이 지난 결과는 production 완료 근거가 아니다.
- 순수 모델/widget/compatibility 회귀는 `flutter test`로 검증한다.
- `DbWriterManifestV1` 누락 writer, strict label/customer writer의 단독 `writeDataWithParams`/SQL 내부 transaction, raw DAO의 legacy `Object` API, manifest를 우회한 DB action과 session static 직접 read 0건은 custom analyzer/lint 또는 AST/SQL 기반 구조 검사로 검증한다. P1 lock-only compatibility writer는 별도 allow-list에서 기존 transaction owner와 공용 lock statement의 동일 transaction·선행 순서를 구조 검사하며 strict ACK/recovery 사용을 요구하지 않는다. 단순 문자열 검색만 완료 근거로 사용하지 않는다.
- DB integration은 manifest가 고정한 disposable SQL Server fixture에서 snapshot isolation, 실제 trigger/FK/collation/trailing-space, content 생성 단일 주체, schema capability와 result contract rollback을 실행한다.
- identity gate는 SQL Server edition/AG/standalone, 폐쇄 열거된 backup/restore·detach/attach·AG seed/failover·storage/VM snapshot과 최소 권한·권한 부족·metadata-hidden fixture에서 exact probe row, digest 유지/변경 또는 금지, degraded action allow-list를 검증한다.
- schema capability runtime gate는 `IndexPredicateRequirementV1` 전체 query coverage와 고정 schema metadata fixture로 검증하고, 실제 execution plan/range-lock/index hint/query template은 권한·통계·SET option을 고정한 배포 integration gate에서 별도로 검증한다.
- native gate는 release별 `RequiredTargetMatrixV1`의 `productionExitRequired=true`인 Windows ODBC worker, macOS DB-Lib worker, Android arm64-v8a remote service, iOS arm64 in-process driver target과 필수 x86_64 Android integration target을 각각 실행한다. Android는 PID/UID/Binder identity, service process 단독 종료, 앱 process 생존과 clean reconnect를 검증한다. 공통으로 장시간 query/lock wait의 cancel, session discard, native 무응답, framing/credential 비노출과 ack crash matrix를 검증한다. hard-kill 미지원 iOS는 deadline cancel/session cleanup 실패 fixture에서 transaction 시작 전 capability 차단을 검증한다. 유한 required target 또는 blocking gate manifest 누락은 gate 실패다.
- recovery gate는 P0 `NativeOperationEvidenceStoreV1`의 각 플랫폼 process/service/native fault-injection harness로 durable publish/DB dispatch 경계를 중단하고 P2 없이도 다음 startup의 artifact 선택, DB identity namespace와 unresolved strict resource 차단을 먼저 검증한다. 이어 P2가 같은 store에 bind한 closed V1 ack/transition phase, owner/lease와 resource barrier를 검증한다. `preparedDurable`, `preCommitFailedTerminal`, `commitDispatchIntentDurable`, `commitDispatchObservedDurable`, `commitCompletedDurable`, `resultFrameSendCompletedDurable`, `resultFrameFullyReceivedDurable`, decode 성공/실패 evidence와 손상 artifact fixture가 각각 미실행 종료, 실패 확정, 결과 미확정 수동 수용, commit 확정 resource별 reload-only, stage별 committed-invalid 또는 격리로 전이되는지 검증한다. decode-failed fixture는 prerequisite 전 pending, operation/session/epoch 또는 sequence/digest 불일치 격리, wire closure와 domain closure 완성 뒤 committed-invalid 승격을 각각 포함한다. ACK/local-event 양방향 재정렬, decode evidence snapshot 원자 교체와 파생 UI/reload 상태 publish 사이 crash, decode 미시도 종료와 동일 resource 복수 unresolved operation의 barrier 합성 fixture를 포함한다. 같은 durable state라도 label-column은 label-size reload/session handoff, customer-column은 dictionary-only reload를 수행하고 금지된 교차 action을 typed reject한다.
- durable file primitive는 Windows `FlushFileBuffers`/`ReplaceFileW`/`MoveFileExW`, macOS/Android/iOS의 승인된 동등 primitive와 artifact 복구를 플랫폼별 native integration test로 검증한다. 실제 전원 차단 durability는 자동 완료 조건으로 주장하지 않는다.
- `DbWorkerArtifactManifestV1`의 build/package/install/bundle/hash/version 검증은 플랫폼별 release lane에서 수행한다. 한 환경의 mock/unit 통과를 다른 driver/OS/architecture gate 통과로 대체하지 않는다.

17. 구현 권장 순서

완료 판정은 한 덩어리로 처리하지 않고 다음 milestone gate로 분리한다. 각 gate는 독립 검증 결과와 미완료 prerequisite를 기록한다.

- `P0 DB substrate`: identity/bootstrap/readiness, action/writer/gate manifest, driver wire/result/null/decimal, strict native transaction session/ack, 플랫폼별 process/service/native cancel primitive와 최소 crash-safe `NativeOperationEvidenceStoreV1` 및 `NativeOperationEvidenceDescriptorV1`
- `P1 locked writer migration`: 공용 customer/label-size lock API와 모든 참여 writer 전환, predicate별 index capability
- `P2 session/recovery handoff`: immutable `LabelSizeSession`, P0 evidence store를 교체하지 않고 확장하는 durable journal/registry와 그 evidence schema를 입력으로 쓰는 유일한 canonical 총함수 `RecoveryTransitionTableV1`
- `P3 label-column feature`: edit session, UI, validation, 사용자 항목과 사용 항목 DAO/save/reload

milestone은 `entry`, `development-complete`, `production-exit`을 분리한다.

- `P0 entry`: 16.5의 운영 DB capability fixture, normative platform support matrix, planned native source target/build·package destination와 release lane/책임자가 설계 manifest로 확정되어야 하며 실제 binary 존재는 요구하지 않는다. `P0 development-complete`는 `main.dart`에 프로세스당 하나의 최소 `LabelManagerAppBootstrapService`, 동일 root identity의 `StrictOperationCommitAuthority`와 `NativeOperationEvidenceStoreV1`이 설치되고, fake store fault harness에서 target/tmp/bak 원자 교체, monotonic publish, process restart scan, identity bind와 unresolved resource dispatch 차단이 통과한 상태다. source target과 fake/native contract harness artifact가 존재하며 strict session, wire/result/ACK 및 worker/parent/DAO 단조 evidence schema인 `NativeOperationEvidenceDescriptorV1`도 통과해야 한다. application recovery workflow/UI transition은 P2 산출물이므로 P0 완료 조건에 포함하지 않는다. `P0 production-exit`은 설치·bundle·서명된 실제 artifact, 각 필수 OS/architecture/ABI 및 SQL Server fixture gate와 해당 플랫폼 crash-safe evidence primitive fault gate가 통과한 상태다.
- `P1 entry`: `DbWriterManifestV1`에 기존 `existingWriter`의 실제 call site/SQL target/API 변경이 모두 열거되고 기존 writer의 lock-only compatibility 경계가 분류되어야 한다. P3 label/customer writer는 action/target/lock/execution class만 가진 `reservedFutureWriter`로 등록하며 실제 call site는 P3 development-complete 승격 조건이다. `P1 development-complete`는 fake lock/transaction 회귀와 기존 writer compatibility 테스트 통과, `P1 production-exit`은 실제 DB lock/range/deadlock integration gate 통과다.
- `P2 entry`: 현재 static session read/write와 journal lifecycle 호출부 inventory, P0에서 설치한 동일 root owner/evidence store의 session/recovery 확장 및 startup/login/logout/reconnect/shutdown migration 표가 확정되어야 한다. `P2 development-complete`는 P0 authority/store를 교체하지 않은 동일 root 인스턴스에서 P0 `NativeOperationEvidenceDescriptorV1`을 입력으로 하는 canonical `RecoveryTransitionTableV1`과 fake session/journal fault harness의 handoff/recovery/consumer ACK가 통과한 상태다. `P2 production-exit`은 P0에서 검증한 플랫폼별 evidence primitive를 journal/registry workflow로 확장한 handoff·resource barrier·process/service/native fault gate 통과다.
- `P3 entry`: P0~P2의 public contract와 fake harness가 고정되어 UI/model 개발을 시작할 수 있다. `P3 development-complete`는 fake harness 위의 model/widget/DAO command 계약과 vertical slice 통과 및 reserved future writer의 existing 승격까지 포함한다. `P3 production-exit`은 승격 후 `DbWriterManifestV1` digest에 바인딩된 P1 lock/range/deadlock gate 재실행, 실제 P0~P2 production-exit 및 P3 SQL/native/session 통합 gate가 모두 통과한 상태다.

따라서 P3 vertical slice는 P0~P2 fake/contract harness 위에서 병행 개발할 수 있지만 이를 P0~P2 production 완료로 기록하지 않는다. "항목 편집 기능 개발 완료"와 "production release 완료"를 구분하고, 19장의 전체 조건은 production release gate로 해석한다.

1. `probeDatabaseIdentityV1` exact SQL/권한/이동 절차 fixture, `connectionProfileHint`/검증된 `DatabaseIdentity`/`stableDatabaseIdentityDigest`, `connectAttemptId` bootstrap과 ready/degraded-ready 상태기계, `DbActionRequirementV1`, 호출부 migration 표, `connectionEpoch` cache·request 폐기 protocol 구현
2. `IndexPredicateRequirementV1`, `DbWriterManifestV1`, `ContentCreationOwnershipV1`, `GateManifestV1`과 snapshot isolation capability, DB schema/index/trigger capability와 배포 plan gate, 전체 mutation-closure manifest, sentinel/운영 `BM_RICH_COLUMN_TYPE` 및 레거시 type 0~12의 raw field/default/editor 관측 fixture 작성. `LabelColumnDraft`와 source→target 저장 projection을 요구하는 전환 정책 fixture는 P3 entry에서 이 P0 raw fixture를 입력으로 작성하고 P3 model development-complete에서 확정한다.
3. `DraftMappingKeyV1`, tri-state `DbLogicalType`/column metadata, null/빈 값이 분리된 canonical `DbWireScalar`, 독립 result-set DTO/generic contract engine, sealed `DbValidatedResultPayloadV1`과 versioned wire schema를 먼저 구현한다. 이 단계는 pure DTO/codec/generic fixture까지이며 label/customer resource-specific mapping validator나 typed raw DAO 완료를 주장하지 않는다.
4. P0 최소 root bootstrap container/단일 `StrictOperationCommitAuthority`와 `NativeOperationEvidenceStoreV1`, `NativeDbTransactionSession`/`DbOperationAck`, Windows ODBC desktop worker, macOS DB-Lib worker, Android remote native service, iOS in-process native driver의 `PlatformDbExecutionCapabilityV1`/`DbWorkerArtifactManifestV1`, 명시적 transaction isolation·session option 복원/Unicode large parameter, DB-Lib 암묵 reconnect 제거, 플랫폼별 cancel/credential/framing/orphan 방지, metadata-only redaction, complete-drain/tainted-discard/generic result contract/marker collector 구현과 통합 테스트. 모든 result set을 독립 schema/rows로 보존하는 collector와 typed `queryResultSets`를 이 단계에서 제공한 뒤 독립 raw rowset/`RawLabelColumnRow`/`RawLabelColumnMinRow` strict mapper, stable ID/결정적 정렬을 구현한다. 기존 `Object` 조회 API는 명시적 compatibility read adapter로만 유지하고 strict raw/save/reconciliation에서 사용하지 않는다. evidence store의 원자 교체, startup scan/identity bind, unresolved strict resource dispatch 차단을 P0 fake/native fault harness에서 검증한다. `strictTransactionV1`/`compatibilityTransactionV1` wire action·DTO·decoder·result/error를 분리하고 strict action에서 기존 `executeDriverTransaction()`을 구조적으로 차단한다. label-column/customer-column save만 strict native session/result/ACK/recovery를 필수 사용한다. P1 기존 writer는 기존 명시적 transaction owner 유지, autocommit 단일 writer의 compatibility locked transaction owner 이관, 복수 resource writer의 multi-resource owner 이관으로 분류해 공용 lock만 우선 적용하고 별도 승인 전 strict ACK/recovery 완료 범위에 포함하지 않는다. legacy transaction API는 이 lock-only 경계로 격리하고 호출 inventory와 제거 gate를 둔다.
5. 공용 customer/label-size locked transaction API와 참여 writer 전환, typed application-lock error 구현
6. raw key/value/type JSON staging, CP949 round-trip과 target conversion 검증
7. customer/market/label-size context, `expectedOldGeneration/newGeneration`과 `LabelSizeSessionConsumerManifestV1`을 포함한 `LabelSizeSessionData`/`LabelSizeSessionResources`/`LabelSizeSession`, 단일 accessor와 generation guard, root `prepareCandidate`/`commitCandidateSwap`, manager `attachCandidateAndAwaitRender`, FortuneSheet mutation version과 `CommitAndPinResult` snapshot pin 공용 API, constructor-injected revisioned `LabelWorkbookDraftPort`의 owner-token/attachment-epoch attach/detach, serializer 안 attempt capture/밖 controller await/안 lease 발급과 `validateSnapshotLeaseAndFreezeCommand()` 이중 선형화, pin exclusion을 command-scoped `WorkbookSaveAuthorizationBarrier`로 원자 인계·terminal 해제하는 API 구현
8. P0 `NativeOperationEvidenceStoreV1`의 플랫폼별 atomic replace primitive와 startup artifact discovery를 재사용해 journal/recovery registry durable manifest/lease, 검증된 DB identity namespace, workflow tombstone과 process/service/native fault recovery matrix로 확장
9. 앱 bootstrap service가 소유하는 `LabelColumnEditCoordinator`/`LabelColumnSaveRecoveryRegistry`, closed `RecoveryTransitionTableV1`/필수 ack barrier, decode prerequisite sequence/digest closure를 포함한 원자적 `evidenceSnapshot`, `storageReady`/`identityReady`/resource barrier, logout detach, unresolved artifact와 재시작 수동 수용 구현
10. label/customer save command DTO와 resource-specific `DbResultContract`/`DbValidatedResultPayloadV1` mapping validator, resource별 reconciliation adapter, SQL Server natural-key resolver와 original/desired projection canonicalization, DB transaction에서 재관측할 `OutputDependencyObservationV1.dbRecheckableObservation`과 barrier가 보호할 `frozenWorkbookObservation` 분리, `QRCodeCreateTypeActiveReferenceFieldsV1`, punctuation boundary/identifier continuation 기반 longest full known-match `ReferenceTokenParserV1`, persisted-order 레거시 순차 치환 및 동일 코드 경로 `LegacyOutputDependencyTraceV1`을 제공하는 `LegacyOutputTokenReplacerV1`, 이를 사용하는 `Gs1OutputPolicyV1.legacyPermissive` 공용 data builder를 별도 구현
11. 사용 항목 edit session 및 validation 순수 로직
12. 사용자 항목 edit session 및 customer-scoped lock/fingerprint transaction
13. `SwipeActionTable`의 교차 헤더 action/외부 drag/drop/nullable key·typed event 기반 stable-key controlled selection 최소 확장과 root `BlockingOverlayStack`, `BlockingModelessDialog`의 `BlockedCloseSource` 기반 top-token Esc/system back/app-owned `requestGuardedPop()`/window-close 비동기 latch, blocking call site의 direct `Navigator.pop()` 구조 lint

각 단계의 `development-complete`를 미검증 상태로 다음 단계의 완료 근거로 사용하지 않는다. 다만 명시된 fake/contract harness가 준비되면 다음 milestone 구현 착수는 허용한다. 저장 vertical slice 전에 DB identity cache, driver parameter/redaction/result contract/marker collector, canonical projection, journal fault phase와 candidate session retirement 테스트를 fake harness에서 먼저 통과시킨다. 첫 저장 vertical slice는 `기본 타입 후보 1개 추가 → 속성 적용 → strict transaction의 commit 전 marker/mapping contract 검증 → commit → candidate session reload/swap → durable consumerApplyCompleted → 현재 process/attachment의 liveRenderReady → old resource dispose → 재조회 표시`로 잡고, 이후 특수 타입/GS1/drag/drop을 확장한다.

18. 레거시 대비 누락 방지 목록

사용자가 명시한 UI 요구 외에도 아래 레거시 기능이 빠지면 기능 회귀다.

- 현재 사용 항목의 신규/키워드/항목명/종류/제목/표시 여부
- 제목 직접 변경과 CP949 20바이트 검증
- 표시 여부 변경
- 누락 키워드 검사 `BM_RICH_CHECK_COLUMNS`
- QR/기본 사용자 정의에서 참조 중인 항목 표시와 참조 해제 전 키워드 변경/삭제 차단
- 같은 키워드 중복 추가/저장 차단
- 빈 키워드/항목명 저장 차단
- 기존 품목 존재 시 데이터 영향 이중 확인 또는 동등한 강도의 명확한 최종 확인
- 바코드/이미지/QR/GS1/날짜 타입의 전체 속성 UI와 검증
- 체크디지트/타임바코드 변경 영향 경고
- GS1 AI 포함 관계의 추가/수정/삭제
- 신규 컬럼의 기존 품목 및 update 품목 빈 content 생성
- `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, GS1 보조 테이블 동기화
- 삭제 status date 갱신
- 저장 후 컬럼 변경 observer와 label-size 세션 전체 force reload
- 고객별 사용자 항목 사전의 추가/수정/삭제와 대문자/영숫자 키워드 규칙

다음 항목은 레거시 구현에 존재하지만 그대로 재현하지 않고 개선해야 한다.

- `SelectLastNRecord()` 신규 ID 추정: `OUTPUT INSERTED... INTO` 수집 후 marker가 있는 최종 결과셋의 정확한 매핑으로 대체
- 문자열 보간 SQL: 명시적 Unicode large JSON parameter와 raw key/value/type staging 기반 batch query로 대체
- SQL 내부 transaction과 public transaction API 중첩 가능성: label/customer 저장은 `DbClient.strictTransaction()` 하나, 기존 lock-only writer는 `compatibilityTransaction()` 또는 manifest가 지정한 locked wrapper 하나만 transaction owner로 사용
- 사용자 항목의 transaction 없는 행별 CRUD: 단일 transaction으로 대체
- 저장 실패를 삼킨 뒤 화면을 재조회하는 동작: commit 전 실패는 working copy 보존, commit 성공 후 reload 실패는 save 재실행 금지와 reload-only 복구로 대체
- 빈 `InsertColumnsToLogDB()`: 별도 감사 로그 요구/스키마가 확정되기 전 구현 대상에서 제외
- 제목 `20Byte` 문구와 실제 20자 판정 불일치: UI/검증을 CP949 20바이트로 통일하고 모든 DB 문자열에 field별 byte 검증 적용
- 상세 설정 `Apply()` 실패 결과를 무시하고 닫는 동작: validation 실패 시 속성 패널을 유지
- 알 수 없는 enum을 기본값으로 치환: raw 값을 보존하고 명시적 호환 규칙 전까지 저장 차단
- QR/기본 참조 키워드 변경·삭제 경고 후 손상 허용: QR data와 하단 text를 모두 처리하는 공용 exact-token parser와 참조 해제 전 변경·삭제 차단으로 대체
- 삭제 시 content/FK cascade 의존: 실제 FK를 확인하고 GS1/QR 양방향 관계를 포함해 transaction에서 명시적으로 정리

19. 완료 조건

- 공용라벨관리에서 선택한 라벨 크기의 `라벨 항목 편집` 다이얼로그를 열 수 있다.
- 두 테이블과 순서 변경 UX가 라벨 설정의 공용 테이블 패턴을 사용한다.
- 별도 상세 dialog 없이 선택 행 타입에 맞는 속성을 왼쪽 패널에서 수정, 취소, 적용할 수 있다.
- 미적용 속성 변경은 다른 이벤트 전에 반드시 취소 질의를 거친다.
- 아이콘과 drag/drop 양쪽으로 후보 추가 및 항목 삭제가 가능하고 동일 command 결과를 낸다.
- 순서 변경과 사용자 항목 설정이 상호 배타 전용 모드로 동작한다.
- 특수 신규 행의 `initialApplyState=requiredPending`은 property dirty와 독립적으로 값 변경 없는 최초 적용 또는 행 제거를 요구하고 그 전에는 선택 이탈, 전용 모드와 메인 저장을 차단한다.
- pending 신규 행 자체의 삭제 request는 행 제거로 command가 소비되어 삭제 continuation을 재실행하지 않고, 속성 `취소`도 pending 행 제거와 일반 draft reset을 구분한다. `BlockingOverlayStack`은 Esc/제목 닫기/모바일 system back/중앙 `requestGuardedPop()`의 app-owned route pop/desktop window close를 같은 top-token close command로 중재해 dirty·mode·busy·committed guard를 우회하지 않는다. blocking 중 app-owned direct `Navigator.pop()`은 구조 lint가 실패한다.
- 순서 변경 모드는 mode-local `ReorderSession.draftKeys`만 변경하며 전용 저장 시에만 working copy에 원자 적용되고 최종 메인 저장 전까지 DB를 변경하지 않는다. 전용 취소는 진입 전 working copy와 dirty를 바꾸지 않는다.
- 사용자 항목 신규 행은 session-local draft key로 식별되고 정상 customer commit/result decode의 검증된 draft-key→DB-ID mapping으로만 재조회 선택을 복원한다. committed-invalid/reload-only는 mapping을 폐기하고 선택을 해제한다.
- 사용 항목과 사용자 항목 저장은 `DbClient.strictTransaction()`이 단독 소유하는 각각의 원자적 transaction이며 commit 전 실패 시 편집 상태를 보존한다. 기존 writer의 `compatibilityTransaction()`과 operation/session을 공유하지 않는다. 단, concurrency conflict는 동일 command 재시도를 금지하고 최신 snapshot 수동 재적용·재확인 뒤 새 command만 허용한다.
- save command와 post-commit 상태는 dialog widget 밖 coordinator가 소유하고 UI/HomePageManager dispose 뒤에도 앱 bootstrap service의 `LabelColumnSaveRecoveryRegistry`가 결과와 reload 필요 상태를 이어받는다. P0 `NativeOperationEvidenceStoreV1`이 P2와 무관하게 strict evidence를 crash-safe 원자 저장·재발견하고 unresolved resource의 새 dispatch를 차단하며, P2 registry는 같은 store를 교체하지 않고 workflow를 확장한다. 같은 프로세스에서 projection이 남아 있을 때만 reconciliation한다. 재시작은 마지막 durable 상태의 증거를 보존해 미실행/실패 확정, commit 결과 미확정, commit 확정 reload-only를 구분하며 durable 증거가 불충분한 상태에서만 전체 reload와 명시적 수동 수용으로 차단을 해제한다. durable DB dispatch intent와 commit dispatch intent publish 전에 각각 최초 DB request와 native commit을 보내지 않고 startup/reconnect에서 save command를 재실행하지 않는다.
- 저장 후 개별 static cache를 순차 교체하지 않고 immutable data/lifecycle resources candidate를 durable journal lease 검증 후 단일 `LabelSizeSession` reference로 activate한다. warm handoff는 `expectedOldGeneration`보다 큰 `newGeneration`과 old resource 유지·단일 dispose를, 프로세스 재시작 cold recovery는 `(recoveryOperationId, newGeneration)`과 initial activation/resource barrier 재평가를 사용하며 old generation/resources를 합성하지 않는다. 두 mode 모두 `LabelSizeSessionConsumerManifestV1`의 필수 소비자가 같은 candidate generation의 durable `consumerApplyCompleted`와 현재 `(processIncarnationId, attachmentEpoch)`의 `liveRenderReady`를 각각 충족해야 완료되며 이전 process render ACK를 재사용하지 않는다. post-commit call graph는 기존 `_handleLabelSizeChanged(forceReload: true)`/`_reloadItemDraftFromDatabase()`와 static cache write를 참조하지 않고 root `prepareCandidate`/mode별 activate 경계 및 manager `attachCandidateAndAwaitRender`만 사용한다.
- commit 성공 후 reload 실패는 같은 save command를 재실행하지 않고 force-reload-required 상태에서 reload만 재시도한다.
- commit 결과 미확정은 desired/original/indeterminate 3상태로 reconciliation하며 operation ledger 없이 실제 commit 여부를 단정하거나 자동 재실행하지 않는다.
- `DbCommittedResultInvalid(committedKnown: true)`은 commit 결과 미확정과 분리한다. 같은 프로세스에서도 신규 ID mapping payload를 working state에 적용하지 않고 resource별 전체 DB reload만 수행한다. 재시작 뒤 `commitCompletedDurable` 이상은 commit 확정 reload-only, 증거가 불충분한 상태만 수동 수용으로 이동한다.
- marker/schema/cardinality/count/mapping command 일치 오류는 canonical `DbWireScalar`와 driver-neutral `DbLogicalType` 기반 result contract가 complete drain 뒤 commit 전에 rollback한다. `NativeDbTransactionSession`과 필수 `DbOperationAck`가 같은 native connection 및 commit 경계를 보장하고, `commitDispatchIntentDurable` 뒤 worker의 `commitDispatchObserved`와 `commitCompleted`를 구분한다. `commitCompleted` 증거와 완전한 result frame 수신 뒤 wire envelope 또는 domain DTO decode만 실패한 경우에만 stage가 있는 `DbCommittedResultInvalid`다. `PlatformDbExecutionCapabilityV1`이 허용한 process/service/native cancel 경계가 실행 중단 또는 session discard를 보장하며 cleanup 전체 성공 증거가 없는 실패는 terminal로 오인하지 않는다.
- label/customer 신규 행 mapping key는 공통 `DraftMappingKeyV1` canonical UUID/ordinal SQL 표현을 사용하고 source key/ROW_NO/inserted ID를 같은 mapping row에 결합한다. `DbResultContract`가 만들고 seal한 `DbValidatedResultPayloadV1` 이후 DTO mapper는 total projection이며 pre-commit에서 검증 가능한 count/key/ID 의미 오류를 commit 후 domain decode 실패로 옮기지 않는다.
- `strictTransactionV1`/`compatibilityTransactionV1`은 wire action, DTO/decoder, result와 outcome-unknown 오류 타입이 분리되고 cross-decode fixture를 모두 거부한다. strict action은 기존 `executeDriverTransaction()` call graph에 도달하지 않으며 compatibility outcome은 `RecoveryTransitionTableV1` evidence/state를 게시하지 않는다.
- 모든 DB 문자열, type code와 enum, 숫자 범위가 명시적 매핑표와 validation을 가지며 미지원 raw 값은 조용히 변환되지 않는다.
- 모든 현 프로젝트 column/item/content writer가 공용 locked transaction API로 같은 connection/transaction의 label-size lock에 참여한다. P1 기존 writer는 manifest에서 기존 명시적 transaction, autocommit compatibility wrapper, 복수 resource wrapper 중 정확히 하나의 transaction owner를 가지며 lock-only 범위에서 strict ACK/recovery state를 게시하지 않는다. 사용자 항목 customer lock, typed 오류의 versioned isolate wire schema, resource별 mutation-closure reconciliation adapter가 테스트로 고정된다.
- raw DAO는 최초 baseline을 검증된 짧은 `SNAPSHOT` transaction으로 읽고 DB null/빈 값과 중복 관계를 보존한다. save/reconciliation은 `IndexPredicateRequirementV1`이 확인한 query key/range를 application lock 뒤 `UPDLOCK, HOLDLOCK`으로 관측한다. manifest/query/capability가 없으면 fail-closed다. 플랫폼별 durable manifest와 closed recovery 전이표는 검증된 DB identity별 원자 교체와 hint 비의존 startup recovery를 제공한다.
- P0 entry 전에 승인 운영 DB의 비민감 schema/snapshot-isolation/index/FK/trigger/sentinel/type fixture, normative platform support matrix, 플랫폼별 planned native source target/build·package destination, release lane·artifact 보관·승인 책임이 설계 manifest로 확정된다. 실제 target/binary는 development-complete/production-exit에서 단계별로 요구한다. 추정 schema, 현재 Dart isolate 또는 개발 PC의 우연한 native library 발견은 production 완료 근거가 아니다.
- `RICH_MIN_CHECK` 기존 값 보존, 레거시 혼합 동작 근거를 가진 type 0~12 전체 전환 matrix, 기존 미지원 사용자 타입의 읽기·삭제 전용 정책, 고정/사용 항목 stable ID·결정적 정렬, connect attempt/ready·degraded-ready 상태기계와 DB identity/connection epoch cache·request 폐기, failover/restore/clone namespace 정책 및 모든 DB 계층의 중첩 payload 비직렬화 metadata-only sensitive parameter redaction이 테스트로 고정된다.
- 권한 등급 matrix, 전용 모드와 committed 상태 Esc/닫기, QR V1 active-field matrix, 참조 판정용 punctuation boundary/identifier continuation longest full-match와 실제 출력용 persisted-order 레거시 순차 치환, `column | reservedItemName | system` trace source 및 parent lineage, 나트륨 문법과 concurrency fingerprint/desired observation projection이 각각 분리된 테스트로 고정된다. 기존 label keyword 원문에는 신규 ASCII 제한을 소급하지 않고 CP949/DB field validation만 적용하되 whitespace/`#` 포함 및 예약어 충돌 keyword는 V1 참조 가능 집합에서 제외하고 신규 생성·rename을 차단한다. QR 직접 입력 0 경고 허용, BASE↔QR data/text 초기화, 기본 data 실제 변경 시 text 초기화와 hydration 시 보존, preservation-only `RICH_USE_USER_DEFINE_QRDATA`와 바코드 picker의 `TYPE_BASE | TYPE_FIX` 제한도 fixture로 고정한다.
- 실제 기존 raw 출력 session의 column order는 gap/nonpositive라도 유일하면 숫자 오름차순으로 허용하고 duplicate order만 ID tie-break 없이 차단하며, 신규 저장 projection은 양의 정수 1부터 연속이어야 한다. `Gs1OutputPolicyV1.legacyPermissive`는 승인된 legacy view 순서의 raw AI/token/FNC1 조립과 GS1 전용 column-only persisted-order 순차 치환을 수행하고 품목 값 형식 실패로 출력을 비우거나 format fallback하지 않는다. view 순서·endpoint·AI 구조 오류는 차단한다. keyword rename은 token text dependency만, delete/type-change/관계 제거는 GS1 endpoint dependency를 사용하며 occurrence별 exact trace와 encoder 직전 `0x1D` bytes가 fixture로 고정된다.
- 삭제·키워드 변경의 workbook 영향 검사는 FortuneSheet controller가 모든 mutation 적용점에서 증가시킨 version과 immutable workbook/mutation pin을 원자 반환하고, constructor로 주입·attach된 `LabelWorkbookDraftPort`가 이를 owner token/attachment epoch/generation/context snapshot lease로 결합해 사용한다. `ReferenceTokenParserV1` 결과와 현재 session 전 품목 active output context의 실제 `LegacyOutputTokenReplacerV1` exact dependency trace를 합쳐 known-prefix 부분 치환 및 replacement-created token까지 판정한다. attach owner mismatch, detach/dispose·pin/flush/snapshot/parser/trace 입력 실패, 불완전 품목 snapshot과 context/generation 불일치는 저장을 차단하며 DB 저장본/마지막 callback으로 낮추지 않는다. callback revision은 저장 권한 근거가 아니며 pin 동안 새 mutation은 typed reject된다. `validateSnapshotLeaseAndFreezeCommand()`가 controller pin을 유지한 채 detach와 save authorization의 승자를 원자적으로 정하고, freeze 성공 시 `frozenWorkbookObservation`을 지키는 command-scoped `WorkbookSaveAuthorizationBarrier`로 mutation exclusion을 틈 없이 인계한다. DB transaction은 `dbRecheckableObservation`만 재관측한다. 모든 취소/failure는 pin을 정확히 한 번 release하며 barrier는 pre-commit terminal failure 또는 post-commit resource recovery terminal에서만 해제된다. committed-invalid는 신규 ID mapping을 working state에 중간 적용하지 않고 resource별 전체 재조회만 수행한다. scale consumer는 실제 화면 활성화 전 `future`와 필수 ACK 비참여이며 활성화 시 별도 table rebinding/renderReady gate와 함께 `currentRequired`로 승격한다.
- P0~P3 milestone의 독립 검증 결과와 prerequisite가 기록되고 production 진입 capability는 대상 플랫폼/architecture별 P0~P2 실제 gate와 P3 기능 gate가 모두 통과한 경우에만 true다. `RequiredGatePolicyV1`의 immutable digest와 필수 gate ID가 `GateManifestV1` 및 결과 artifact에 일치하고, unit/widget/구조 lint, SQL Server identity/trigger/snapshot, Windows/macOS/Android/iOS driver·cancel·fault, durable file와 release artifact gate 및 전체 정적 분석이 각각 통과한다. 필수 gate의 `blocking=false`, 누락, 만료 또는 digest 불일치는 production-exit을 거부한다.
