공용라벨관리 라벨 항목 편집기 구현 작업지시서
작성일: 2026-07-12

1. 목적

공용라벨관리의 `사용 항목 > 항목 편집`에서 현재 라벨 크기에 사용할 항목을 추가, 수정, 삭제, 정렬하고 DB에 저장할 수 있는 `라벨 항목 편집` 다이얼로그를 구현한다.

기능과 데이터 의미는 레거시 `CColumnEditDlg`, `CColumnEditModel`, `CColumnSetupMainDlg`, `CUserColumnEditDlg`, `CCommonLabelModel::SaveColumns`, `CColumnDAO`를 기준으로 한다. UI는 레거시 화면을 그대로 복제하지 않고 현 프로젝트의 라벨 설정 다이얼로그와 공용 테이블 패턴에 맞춘다.

핵심 원칙은 다음과 같다.

- 현재 라벨 크기의 실제 사용 항목과 고객별 사용자 항목 사전을 서로 다른 편집 단위로 관리한다.
- 다이얼로그의 두 테이블은 라벨 설정에서 사용하는 `SwipeActionTable` 계열 공용 위젯을 재사용한다.
- 사용 항목의 상세 속성은 별도 모달을 열지 않고 왼쪽 속성 패널에서 편집한다.
- 속성 편집, 순서 변경, 사용자 항목 설정은 동시에 열리지 않는 상호 배타 상태로 관리한다.
- 사용 항목 DB 저장은 신규, 수정, 삭제, 순서, 보조 테이블 및 기존 품목의 빈 컬럼 콘텐츠를 하나의 SQL Server 트랜잭션으로 반영한다.
- 사용 항목(label-column) DB transaction commit 전에는 working copy를 확정하지 않는다. commit 성공 후에는 같은 저장 command를 다시 실행할 수 없는 `committedReloadPending` 상태로 전환하고 `HomePageManager`가 현재 라벨 크기의 candidate `LabelSizeSession`에 기존 `expectedOldGeneration`보다 큰 단조 증가 `newGeneration`을 발급해 강제 재로드한다. 같은 generation이어야 하는 범위는 candidate 내부 data/resources/context뿐이며 기존 session generation을 재사용하지 않는다. reload가 실패해도 DB 저장 실패로 취급하거나 저장 command를 재시도하지 않고, 부분 cache를 노출하지 않은 채 reload만 다시 실행한다. 고객별 사용자 항목 사전 저장은 label-size session을 교체하지 않는 별도 post-commit 경로를 사용한다.
- `DbClient.transaction()`은 versioned result contract가 marker/schema/cardinality뿐 아니라 count와 신규 ID mapping의 결정적 구조·command 일치까지 검증한 뒤에만 commit한다. 정상 반환한 순간 이 pre-commit 검증과 DB commit은 완료된 것으로 취급한다. 그 이후 isolate 응답/wire decode처럼 commit 전에 검출할 수 없었던 payload 손상이 발견되면 일반 저장 실패가 아니라 `DbCommittedResultInvalid(committedKnown: true)`로 분류하고 동일 command 재실행을 금지한다.
- commit 응답이 유실된 `DbCommitOutcomeUnknown`은 재조회만으로 해당 operation의 실제 commit 여부를 단정하지 않는다. 기존 DB identity를 포함하는 `concurrencyFingerprint`와 신규 identity에 독립적인 `desiredObservationProjection`을 분리해 `desiredStateObserved`, `originalStateObserved`, `indeterminate` 3상태로 reconciliation하고, 정확한 operation 귀속이나 자동 멱등 재시도가 필요하면 별도 operation ID ledger 또는 저장 stored procedure를 선행한다.

2. 현재 프로젝트 기준점

2.1 현재 UI

- 공용라벨관리 오른쪽 `사용 항목` 영역의 `항목 편집` 버튼은 `lib/page_home/common_label_manage.dart`에 있으나 callback은 비어 있다.
- 현재 공용라벨의 사용 항목 목록은 `TColumn.datas`를 읽어 표시한다.
- 현재 목록용 `_CommonLabelTable`은 `FortuneTable` 기반이다. 기존 공용라벨 화면의 읽기 전용 목록은 그대로 유지하고, 새 편집 다이얼로그 안의 두 테이블만 라벨 설정과 같은 `SwipeActionTable` 계열로 구현한다.
- 현재 `_CommonLabelTable`의 `필수등록` 체크박스는 `TColumnBase.useMissingKeywordCheck`만 직접 변경하고 DB에 저장하지 않는다. 새 편집기 구현 시 이 체크박스를 읽기 전용 표시로 바꾸고 `필수등록` 변경과 DB 저장은 라벨 항목 편집기의 속성 패널만 소유한다. 별도 즉시 저장 UX를 유지해야 한다면 같은 원자적 DAO와 세션 재로드를 연결하는 별도 작업으로 분리한다.
- 라벨 설정 다이얼로그는 `BlockingModelessDialog`, `BlockingModelessDialogFrame`, `EditableSwipeNameTable`, `rowReorderEnabled`, 우측 위/아래 이동 rail, 전용 footer를 사용한다.

2.2 현재 모델/DAO

- `lib/models/column.dart`의 `TColumn`은 레거시 컬럼 속성 대부분을 이미 보유하고 있다.
- `TColumnDAO.selectByLabelSizeId()`는 `BM_RICH_COLUMN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `VIEW_BM_GS1_CONTAIN_COLUMN`을 조회한다.
- 현재 `TColumnDAO`에는 라벨 항목 편집용 insert/update/delete transaction API가 없다.
- 고정 항목 분류, 고정 항목, 고객별 사용자 항목에 대응하는 현 프로젝트 모델/DAO가 없다면 새로 추가해야 한다.
- `TColumn`과 `TColumnBase`는 대부분 불변 필드지만 편집용 `copyWith`와 안정적인 draft identity가 없다. DB 조회 모델을 직접 mutate하지 말고 편집 전용 draft를 사용한다.

3. 구현 범위

3.1 포함 범위

- 공용라벨관리 `사용 항목 > 항목 편집` 진입 연결
- `라벨 항목 편집` blocking modeless 다이얼로그
- 사용 항목 속성 패널과 사용 항목 테이블
- 고정 항목/사용자 항목 전환 및 후보 테이블
- 후보 항목 추가 버튼과 drag/drop 추가
- 사용 항목 삭제 버튼과 drag/drop 삭제
- 사용 항목 순서 변경 모드
- 고객별 사용자 항목 설정 모드
- 속성별 입력 UI와 검증
- 사용 항목 및 사용자 항목 모델/DAO/transaction
- 컬럼/품목/content를 쓰는 현 프로젝트의 모든 writer와 라벨 크기 삭제가 공유하는 label-size 단위 DB lock protocol
- Windows ODBC, macOS DB-Lib와 Android/iOS native adapter의 marker 기반 다중 결과셋 collector와 명시적 Unicode parameter type
- Web과 Linux를 제외한 Windows/macOS/Android/iOS의 플랫폼별 DB execution boundary와 cancel/session-discard capability gate
- 저장 후 `HomePageManager` 소유 label-size 세션 전체 강제 재로드
- widget/model/DAO/transaction 회귀 테스트

3.2 제외 범위

- 공용라벨 시트 workbook 자체의 셀/서식 저장 포맷 변경
- 품목관리의 기존 품목 값 편집 기능 변경. 단, 컬럼 구조 저장과의 동시 쓰기를 막기 위해 `ItemManagerSaveDAO`, 품목 순서 저장, element sheet update/migration과 라벨 크기 삭제가 같은 label-size DB lock protocol에 참여하고 필요한 context를 전달받는 최소 변경은 포함한다.
- 레거시 SpreadSheet OCX UI 복제
- 레거시의 비어 있는 `InsertColumnsToLogDB()`를 근거 없이 새 로그 테이블로 구현하는 작업
- DB 스키마를 임의 변경하는 작업. 스키마 변경이 필요하면 별도 SQL과 배포 절차를 먼저 합의한다.

4. 다이얼로그 공통 구조

4.1 표시 방식

- 기존 Label Manager 모달리스 규칙에 따라 `BlockingModelessDialog(child: BlockingModelessDialogFrame(...))`를 사용한다.
- 다이얼로그 `OverlayEntry`와 중복 open guard는 브랜드/라벨 설정과 같이 `HomePageManager`가 소유한다. `CommonLabelManage`는 open callback만 호출하고 overlay lifecycle이나 전역 cache를 직접 소유하지 않는다.
- `LabelColumnEditCoordinator`는 overlay widget보다 긴 lifecycle로 edit session, immutable save command, in-flight transaction Future, commit outcome, reconciliation/reload와 overlay attach 상태를 소유한다. dialog widget은 coordinator state를 표시하고 사용자 event를 전달하는 view로 제한한다. 앱 루트 수명의 `LabelColumnSaveRecoveryRegistry`는 UI detach 시 coordinator와 durable operation record를 인수하고 success/unknown/committed-invalid 후속 처리와 reload 필요 상태를 보존한다. `HomePageManager`가 dispose되어도 coordinator는 DB 결과와 동일 command 금지 상태를 registry에 넘긴 뒤에만 dispose한다. 같은 앱 프로세스에서 coordinator 또는 registry가 original/desired projection을 메모리에 보유한 동안에만 commit 결과 미확정 reconciliation을 허용한다. 프로세스 재시작 후에는 민감 projection을 durable storage에서 복원하지 않고 미완료 operation의 resource를 차단한 채 강제 DB reload와 사용자 확인으로만 해제한다. 앱 시작/DB reconnect 어느 경로에서도 save command를 자동 재실행하지 않는다.
- 다이얼로그 제목은 `라벨 항목 편집`으로 한다.
- 가용 너비가 960 logical px 이상이면 속성 패널, 두 테이블, 중앙 command rail, footer가 겹치지 않는 4영역 가로 배치를 사용한다. dialog 기본 크기는 화면 너비의 85~90%, 화면 높이의 80~90%로 하되 viewport 안에 제한한다.
- 가용 너비가 960 logical px 미만인 Android/iOS 및 축소 window에서는 사용자 결정에 따라 전체 가로 스크롤이나 진입 차단 대신 적응형 탭/단계 UI를 사용한다. `속성`, `사용 항목`, `후보` 세 view를 명시적으로 전환하고 추가/삭제 command와 현재 전용 모드 footer는 화면 하단 safe area 위에 고정한다. pending property dirty guard, 선택 stable key와 drag 대체 버튼은 view 전환에도 유지한다. drag/drop은 pointer가 있는 환경의 보조 UX이며 touch 환경에서 모든 기능을 아이콘/명령 버튼으로 수행할 수 있어야 한다.
- layout gate viewport는 desktop `1280×720`, desktop compact `960×600`, mobile portrait `360×640`, mobile landscape `640×360` logical px와 text scale `1.0`, `1.3`, `2.0`을 고정한다. safe area/keyboard가 있는 모바일에서는 현재 입력과 footer가 가려지지 않도록 해당 view 내부 세로 스크롤과 inset을 적용하며 960 미만에서 4영역을 억지로 축소하지 않는다.
- 확인, 경고, 실패 알림은 다이얼로그보다 위에 나타나는 공용 blocking overlay dialog API를 사용한다.
- 다이얼로그가 열린 동안 공용라벨의 시트, 브랜드/라벨 선택, 탭 전환 등 바깥 화면 입력을 차단한다.

4.2 기본 배치

왼쪽부터 다음 순서로 배치한다.

1. 사용 항목 속성 패널
2. 사용 항목 테이블
3. 중앙 command rail
4. 후보 영역

후보 영역 상단에는 `고정 항목`/`사용자 항목` segmented control 또는 radio를 둔다. 고정 항목일 때는 고정 항목 분류 dropdown을 표시하고, 사용자 항목일 때는 고객별 사용자 항목 테이블을 표시한다.

중앙 command rail에는 다음 아이콘 버튼을 세로로 둔다.

- 휴지통: 위쪽에 독립적으로 배치하고 아래 추가 버튼과 시각적 간격을 둔다.
- 왼쪽 화살표: 선택한 고정/사용자 후보를 사용 항목으로 추가한다.

아이콘은 현 프로젝트의 Material/Lucide 정책에 맞는 익숙한 아이콘을 사용하고 tooltip을 제공한다. 텍스트가 있는 둥근 사각형으로 아이콘 기능을 대신하지 않는다.

4.3 메인 footer

- 다이얼로그 하단 오른쪽에 `취소`, `저장` 버튼을 둔다.
- `저장`은 `workingDirty=true`, `propertyDirty=false`, busy=false일 때만 활성화한다. 속성 변경만 있고 아직 `적용`하지 않은 동안에는 비활성화하고 `먼저 속성 변경을 적용하거나 취소해 주세요.` 안내를 제공한다.
- `취소`는 다이얼로그 전체의 미저장 변경을 버리고 닫는 기능이다.
- 미저장 변경이 있으면 `변경 내용을 취소하고 닫으시겠습니까?`를 질의한다. 확인한 경우에만 원본 snapshot으로 복원하고 닫는다.
- 창 닫기 아이콘과 Esc도 메인 `취소`와 같은 guard를 거친다.
- 현재 `BlockingModelessDialog`는 wrapper가 primary focus일 때만 key를 소비하고 Esc 취소 callback이 없다. 공용 위젯에 optional `onEscape` callback을 추가하고 TextField/dropdown 등 child가 focus를 가진 상태에서도 Esc를 바깥 shortcut으로 전달하지 않고 callback을 정확히 한 번 호출하도록 key 처리 경계를 수정한다. callback 기본값은 기존 동작을 유지한다.
- `reorder` 또는 `userItemEdit` 모드에서 창 닫기/Esc를 누르면 메인 취소를 바로 실행하지 않는다. 먼저 현재 전용 모드의 취소 guard를 실행해 `normal`로 돌아가며, 사용자가 다시 닫기를 요청했을 때만 메인 close guard를 실행한다. DB busy, `commitOutcomeReconciling`, `committedResultInvalid`, `committedReloadPending`에서는 Esc와 제목 표시줄 닫기를 소비만 하고 상태를 변경하지 않는다.
- commit 후 reload 실패 상태는 `committedReloadFailed`로 분리한다. 이 상태에서도 Esc와 제목 표시줄 닫기는 소비하고, read-only 오류 화면의 명시적 `화면 닫기` 버튼만 overlay를 닫을 수 있다. 이 버튼은 상위 `force-reload-required`를 해제하지 않으며 저장 command도 실행하지 않는다.
- `normal` 이외의 전용 모드 또는 DB command 실행 중에는 메인 footer의 `취소`와 `저장`을 비활성화한다.

5. 편집 상태 모델

5.1 상호 배타 모드

다이얼로그 상태는 최소한 다음 enum으로 관리한다.

- `normal`: 사용 항목 선택, 속성 편집, 후보 추가/삭제, 메인 저장 가능
- `reorder`: 사용 항목 순서 변경 전용
- `userItemEdit`: 고객별 사용자 항목 사전 편집 전용

`reorder`와 `userItemEdit`는 동시에 true가 될 수 없다. 여러 boolean 조합으로 유효하지 않은 상태가 생기지 않도록 단일 mode를 source of truth로 사용한다.

DB 조회/저장 중에는 coordinator의 별도 busy state로 중복 command, 다중 route, 중복 저장을 막는다. label-column post-commit 상태는 최소 `commitOutcomeReconciling`, `committedResultInvalid`, `mappingRecoveryReloadPending`, `committedReloadPending`, `committedReloadFailed`로 구분한다. customer-column 저장은 별도 `customerDictionaryReloadPending`, `customerCommitOutcomeReconciling`, `customerCommittedResultInvalid` 상태를 사용하며 label-size session reload 상태로 합치지 않는다. post-commit 상태를 `normal`/busy boolean 조합이나 dialog-local State만으로 표현하지 않는다.

5.2 사용 항목 working copy

다이얼로그를 열 때 DB 조회 결과로 다음 상태를 만든다.

- `originalColumns`: 다이얼로그를 연 시점의 immutable snapshot
- `workingColumns`: 화면에서 추가/수정/삭제/정렬되는 목록
- `deletedColumnIds`: DB에 존재했던 행 중 working copy에서 삭제된 ID
- `selectedColumnKey`: index가 아닌 안정적인 행 identity
- `propertyBaseline`: 현재 선택 행에서 속성 패널을 연 시점의 값
- `propertyDraft`: 속성 패널 입력값
- `propertyDirty`: baseline과 draft의 실제 내용 비교 결과

기존 행 identity는 `columnId`, 신규 행 identity는 dialog session에서 생성한 `draftColumnKey`를 사용한다. 선택, drag/drop, reorder, 삭제 후 선택 복원은 list index를 identity로 사용하지 않는다.

5.3 dirty 구분

- `propertyDirty`: 속성 패널의 아직 적용하지 않은 변경
- `workingDirty`: 적용된 속성 변경, 항목 추가/삭제, 순서 변경으로 working copy가 original snapshot과 달라진 상태
- `userItemDirty`: 사용자 항목 설정 모드 안의 별도 working copy가 해당 모드 진입 snapshot과 달라진 상태
- `orderDirty`: 순서 변경 모드 진입 snapshot과 현재 순서가 다른 상태

속성 패널의 `적용`은 `propertyDraft`를 `workingColumns`에 반영하여 `workingDirty`를 만들지만 DB에는 쓰지 않는다. 사용 항목 DB transaction은 메인 `저장`에서만 실행한다. 순서 변경 모드의 `저장`은 순서를 working copy에 적용하는 의미이며 DB에 쓰지 않는다.

6. 사용 항목 테이블

6.1 테이블 구성

- `SwipeActionTable<LabelColumnDraft>` 또는 이를 일반화한 공용 wrapper를 사용한다.
- 컬럼은 레거시와 동일한 의미를 유지한다.
  - 신규 상태
  - 키워드
  - 항목명
  - 종류
  - 제목
  - 표시 여부
- 행 번호 영역과 컬럼 헤더의 좌상단 교차 영역에는 순서 변경 아이콘을 둔다.
- 현재 QR/기본 사용자 정의 token에서 참조 중인 행은 레거시의 `IsQRCodeUseThis()` 효과를 유지하고, GS1 포함 관계에서 참조 중인 행은 신규 UX로 별도 상태 표시를 제공한다. QR token 참조와 GS1 ID 관계를 하나의 `referenced` boolean으로 합치지 않고 서로 다른 아이콘/tooltip과 command guard를 사용한다. 색만으로 의미를 전달하지 않는다.
- 신규 행은 `신규` 상태를 표시한다.
- 행 클릭은 해당 행을 선택하고 속성 패널을 갱신한다. 더블클릭으로 별도 속성 다이얼로그를 열지 않는다.

6.2 선택과 속성 dirty guard

`propertyDirty=true`인 상태에서 다음 이벤트를 요청하면 먼저 `적용하지 않은 속성 변경을 취소하시겠습니까?`를 질의한다.

- 다른 사용 항목 행 선택
- 고정/사용자 후보 선택 또는 추가
- 사용 항목 삭제
- 사용 항목 순서 변경 모드 진입
- 고정/사용자 후보 모드 전환
- 사용자 항목 설정 모드 진입
- 메인 취소, 창 닫기

사용자가 `변경 취소`를 확인하면 property draft를 baseline으로 되돌린 뒤 원래 요청한 이벤트를 정확히 한 번 이어서 실행한다. 확인하지 않으면 현재 행과 입력 focus를 유지하고 요청 이벤트를 실행하지 않는다.

guard callback 안에서 이벤트별 로직을 복제하지 말고 `Future<bool> resolvePendingPropertyEdit()` 같은 공용 경계를 둔다. route가 닫히기 전에 다음 command가 실행되지 않도록 확인 dialog Future 완료 뒤 처리한다.

6.3 항목 삭제

- 사용 항목 선택이 없으면 중앙 휴지통 버튼을 비활성화한다.
- 휴지통 버튼을 누르면 선택 행을 working copy에서 삭제한다.
- DB 기존 행은 `deletedColumnIds`에 추가하고 신규 행은 working copy에서만 제거한다.
- QR/기본 사용자 정의 문자열에서 참조 중인 행은 삭제하지 못한다. 사용자가 참조하는 QR/기본 항목의 token을 먼저 제거하거나 다른 항목으로 바꿔 적용하도록 안내한다. GS1 관계에서 참조 중인 행은 제거될 관계를 명시한 영향 확인 후에만 삭제한다.
- 삭제 시 GS1 바코드 draft의 포함 항목 목록에서도 해당 기존 ID 또는 신규 draft key를 제거한다.
- 삭제 후 가능한 경우 다음 행, 마지막 행 삭제였으면 이전 행을 선택한다. 행이 없으면 선택과 속성 패널을 비운다.

사용 항목 행을 drag하여 휴지통 drop target에 올릴 수 있어야 한다.

- drag payload에는 안정적인 행 key와 source 종류를 넣고 index만 전달하지 않는다.
- drag hover 중 휴지통을 강조한다.
- 허용된 행을 drop하면 참조 경고/확인을 먼저 처리한다.
- 삭제가 확정된 경우에만 휴지통이 항목을 받아들이는 짧은 scale/fade 애니메이션을 실행하고 행을 제거한다.
- 확인을 취소하거나 유효하지 않은 payload이면 애니메이션과 삭제를 실행하지 않는다.
- 아이콘 버튼 삭제와 drag/drop 삭제는 같은 command handler를 사용한다.

7. 사용 항목 속성 패널

7.1 공통 동작

- 선택 행이 없으면 빈 상태를 표시하고 모든 입력을 비활성화한다.
- 행 선택 시 해당 타입에 맞는 속성 UI를 구성한다.
- 패널 하단에는 항상 `취소`, `적용` 버튼을 둔다.
- `적용`은 property draft가 baseline과 다르고 현재 입력이 유효할 때만 활성화한다.
- `취소`는 property draft를 baseline으로 복원한다. DB 또는 working copy의 적용 완료 값은 바꾸지 않는다.
- `적용` 성공 후 현재 값이 새 baseline이 되고 `propertyDirty=false`가 된다.
- 신규 특수 타입 행은 사용 항목 테이블에 pending 신규 행으로 표시하고 즉시 선택한다. 해당 행의 첫 속성 적용 전 `취소`하면 레거시 상세 설정 dialog 취소와 동일하게 신규 행 자체를 제거한다.
- 일반 타입처럼 별도 설정 없이 추가 가능한 항목은 레거시 기본값으로 즉시 working copy에 추가한다.

7.2 공통 속성

최소한 다음 속성을 제공한다.

- 키워드
- 항목명
- 항목 종류
- 제목
- 표시 여부
- 누락 키워드 검사 사용 여부

검증 규칙은 다음과 같다.

- 키워드와 항목명은 필수다.
- 키워드는 현재 사용 항목 안에서 중복될 수 없다.
- 제목은 실제 DB `RICH_TITLE VARCHAR(20)` 제약에 맞춰 CP949 인코딩 기준 최대 20바이트로 제한한다. UI에는 `한글은 최대 10자, 영문·숫자는 최대 20자이며 혼합 입력은 20바이트 이내`라고 안내하고 혼합 문자열도 실제 CP949 byte length로 검증한다.
- 제목뿐 아니라 키워드, 항목명, 사용자 정의 QR 데이터/텍스트, 나트륨 문자열, 폰트명, 사용자 정의 바코드 텍스트, 날짜 범위와 사용자 항목 사전 문자열도 실제 대상 DB 컬럼의 `max_length`, nullable, CP949 collation에 맞춰 저장 전에 검증한다. CP949로 표현할 수 없는 문자는 `?`로 대체하지 않고 해당 필드 validation error로 거부한다.
- 종류 dropdown은 `TColumnType.datas` 중 type code 0~12만 제공하고 `TYPE_END_OF_CULUMN(13)` sentinel은 표시·추가·저장하지 않는다. DB에서 0~12 밖의 알 수 없는 raw type code를 조회하면 fallback 타입으로 바꾸지 않고 원본 code를 보존한 채 해당 행 편집과 전체 저장을 차단한다.
- 키워드 변경 대상이 QR/기본 사용자 정의 문자열에서 참조 중이면 적용하지 않는다. 참조 token을 먼저 제거/교체하도록 안내한다. GS1 포함 관계는 기존 column ID 또는 신규 draft key로 연결되므로 키워드만 변경할 때 관계를 제거하거나 영향 경고를 표시하지 않는다. GS1 AI의 타입 변경·삭제 또는 GS1 barcode 포함 목록 변경처럼 endpoint 자체가 사라지는 경우에만 제거될 ID 관계를 명시한 영향 확인을 수행한다.
- 종류 변경 시 기존 타입 전용 값이 초기화될 수 있음을 확인한다.
- GS1 AI를 다른 타입으로 바꿀 때 GS1 바코드 포함 관계에서 제거되는 영향을 확인한다.

7.3 타입별 속성

레거시 `CColumnSetupMainDlg`와 각 하위 설정 화면에 있는 속성을 누락 없이 제공한다. 현재 `TColumn` 필드와 DB 컬럼을 source of truth로 사용한다.

단, `TColumn`에는 DB 저장값과 화면 런타임 상태가 함께 있으므로 클래스의 모든 필드를 저장 대상으로 간주하지 않는다. 12.1의 persisted field allow-list에 포함된 값만 속성 draft와 dirty 비교, SQL 저장에 사용한다.

- 기본/문자: 일반 텍스트 또는 사용자 정의 데이터, 자동 증가 사용/자리수/범위/저장/0 제거/업데이트, 검색 출력, 사용자 정의 텍스트
- 제조일자/유통기한: 레거시 `CColumnSetupDate`에 대응하는 날짜 editor, 자동 증가 속성, 날짜 범위 사용 및 전/후 범위
- 제조시각/유통시각: 사용자 결정에 따라 레거시 `CColumnSetupMainDlg` fallback과 같은 기본 editor를 사용한다. 날짜 editor나 별도 시각 형식 필드를 추가하지 않는다.
- 바코드: 바코드 종류, 폭, 높이, 체크디지트, 번호 표시, 텍스트 연동, 타임바코드 타입, 자동 증가 속성, 사용자 정의 바코드 텍스트, line check/size, 회전
- 이미지: 폭, 높이
- QR/2D 코드: 2D 종류, 생성 방식(일반/사용자 정의/나트륨), 사용자 정의 데이터와 하단 문자열, pixel size, scale, 하단 문자열 표시, 정렬, 폰트/크기, 자동 증가 속성
- GS1 AI: AI 코드, format option, GS1 코드 표시 여부
- GS1 바코드: 종류, 폭, 높이, 포함할 GS1 AI 항목 목록
- 고정(`TYPE_FIX`), 영양성분(`TYPE_NUT`), 매수(`TYPE_PRINTCOUNT`) 및 그 밖의 0~12 타입은 레거시 `ColumnSetupMainDlg`의 fallback과 같이 기본 editor를 사용하되 타입별 기본값과 변경 초기화 규칙을 매핑표에 명시한다.

레거시 검증과 경고도 유지한다.

- 바코드/이미지/GS1 바코드의 폭 또는 높이가 0이면 출력되지 않을 수 있음을 경고한다.
- QR pixel size 또는 scale이 0이면 출력되지 않을 수 있음을 경고한다.
- GS1 AI 코드는 필수다.
- 체크디지트 또는 타임바코드 변경이 기존 품목 바코드 값에 영향을 주면 경고한다.
- 사용자 정의 QR 데이터가 비어 있거나 나트륨 구성에 초기화되지 않은 값이 있으면 적용하지 않는다.
- 레거시 수치 범위를 최소 계약으로 유지한다. QRCode pixel size는 1~20, QR 하단 문자열 font size는 3~50, QR scale은 10~100, barcode text font size 의미를 사용하는 입력은 1~100이다. 폭/높이, 자동 증가, line size, 날짜 범위 등 나머지 숫자는 실제 DB 타입과 레거시 control range를 매핑표에서 확정하며 범위 미확정 상태로 editor를 구현하지 않는다. `RICH_BARCODE_LINE_SIZE`는 레거시 header의 `int` 선언과 implementation의 `BOOL` 반환 불일치를 범위 근거로 사용하지 않고 운영 스키마/데이터 분포 fixture로 정수 보존 또는 0/1 규격화를 먼저 확정한다.

속성 패널은 하나의 거대한 build 함수로 만들지 않는다. 공통 입력과 타입별 editor widget을 분리하되, 각 editor는 `LabelColumnPropertyDraft`를 입력받아 변경 callback만 반환하고 DB를 직접 호출하지 않는다.

8. 고정 항목 후보

8.1 조회와 표시

- `고정 항목` 선택 시 고정 항목 분류 dropdown을 활성화한다.
- 분류는 레거시 `BM_RICH_FIX_COL_TYPE`의 ID와 이름을 조회한다. 배포 스키마에 별도 순서 컬럼이 없으므로 `RICH_FIX_COL_TYPE_ID ASC`를 결정적 표시 순서로 사용한다. 향후 별도 사용자 정렬이 필요하면 이번 기능과 분리된 DB 스키마 변경으로 처리한다.
- 선택 분류의 후보는 `BM_RICH_FIX_COLUMN`에서 `RICH_FIX_COLUMN_ID`, 키워드, 항목명, 종류를 조회하고 stable identity와 표시값을 분리한다. 배포 capability에서 레거시 primary key `RICH_FIX_COLUMN_ID`가 확인되어야 편집기 진입을 허용하고 `RICH_FIX_COLUMN_ID ASC`로 정렬한다. ID가 없는 스키마에서 정규화 문자열이나 row index를 임시 identity로 만들지 말고 명시적 호환/migration 계약을 먼저 추가한다.
- 분류를 바꾸면 후보 선택을 해제하고 해당 분류 목록을 다시 표시한다.

8.2 사용 항목으로 추가

- 고정 항목 행 선택이 없거나 같은 키워드가 이미 사용 중이면 왼쪽 화살표를 비활성화한다.
- 행 선택 후 왼쪽 화살표를 누르면 후보 추가 전용 persisted-field 기본값 fixture로 신규 사용 항목 draft를 만든다. 생성자 이름이나 Dart model fallback을 기본값 source of truth로 사용하지 않는다. fixture는 실제 레거시 후보 추가 경로인 `CColumn(int labelSizeId, const CColumnBase&, int order)`를 기준으로 최소 `barcodeType=0`, `lineSize=0`, `GS1 AI='01'`, `QR scale=100`, `QR text font size=10`, visible/check digit/show barcode number와 각 persisted scalar를 타입별로 고정한다. 다른 레거시 생성자의 `lineSize=1` 같은 값은 후보 추가 기본값으로 사용하지 않는다.
- 고정 항목 행을 drag하여 사용 항목 테이블에 drop해도 같은 add command를 실행한다.
- 버튼과 drag/drop은 중복 검사, 초기값 생성, 특수 타입 pending 속성 편집, 선택 이동까지 동일한 handler를 사용한다.
- 같은 drag gesture가 중복 callback으로 전달되어 두 행이 추가되지 않도록 command generation 또는 in-flight guard를 둔다.

9. 사용자 항목 후보와 사용자 항목 설정

9.1 일반 후보 상태

- `사용자 항목` 선택 시 현재 로그인 고객 ID의 `BM_RICH_CUST_COLUMN`을 조회한다.
- 키워드, 항목명, 종류를 표시한다.
- 후보는 `RICH_CUST_COLUMN_ID ASC`로 결정적으로 정렬하고 재조회 뒤에도 stable ID로 선택을 복원한다.
- 선택 행을 왼쪽 화살표 또는 사용 항목 테이블 drop으로 추가한다.
- 추가 시 고객별 사전 row를 직접 연결하지 않고 레거시처럼 현재 라벨 크기의 신규 `TColumn` draft로 복사한다. 이후 사용자 항목 사전을 수정해도 이미 추가된 사용 항목은 자동 변경하지 않는다.
- 사용자 항목 테이블의 좌상단 헤더 교차 영역에는 `항목 편집` 아이콘과 tooltip을 둔다.

9.2 사용자 항목 설정 모드 진입

- `항목 편집` 아이콘을 누르면 `userItemEdit` 모드로 전환한다.
- 진입 전 pending property edit을 공용 guard로 해소한다.
- 모드 진입 시 고객별 사용자 항목 원본 snapshot과 별도 working copy를 만든다.
- 사용자 항목 영역 이외의 속성 패널, 사용 항목 테이블, 고정/사용자 전환, 분류 dropdown, 왼쪽 화살표, 메인 footer를 비활성화한다.
- 사용자 항목 테이블 좌상단의 편집 아이콘은 숨기고 `항목 추가` 아이콘으로 교체한다.
- 테이블 아래에는 라벨 설정 순서 변경 footer와 같은 형식으로 왼쪽 제목 `사용자 항목 설정`, 오른쪽 `취소`, `저장`을 둔다.

9.3 사용자 항목 inline 편집

- `항목 추가` 아이콘을 누르면 마지막에 신규 빈 행을 추가하고 첫 입력 셀에 focus한다.
- 키워드와 항목명은 직접 입력한다.
- 키워드 입력은 레거시처럼 즉시 대문자로 정규화한다.
- 신규 행과 사용자가 실제로 키워드를 수정한 기존 행은 `[A-Z0-9]+`만 허용한다. 한글, 공백, 기호가 들어오면 저장하지 않고 해당 셀에 오류를 표시한다. 레거시 `IsAlphabet()` 범위 때문에 이미 저장된 `_`, `[`, `\\`, `]`, `^`, `` ` `` 등을 포함한 비준수 키워드는 raw 값을 보존한 read-only 행으로 표시해 삭제만 허용하고 수정·복사·신규 생성은 차단한다. 비준수 기존 행이 존재한다는 이유만으로 다른 정상 행의 저장과 해당 행 삭제를 차단하지 않으며 자동 정규화하지 않는다.
- 종류 컬럼의 모든 셀을 dropdown으로 바꾼다.
- 종류 목록은 DB `BM_RICH_COLUMN_TYPE`을 `RICH_COLUMN_TYPE_ORDER`, `RICH_COLUMN_TYPE_CODE` 순서로 조회하되 공통 `editableColumnTypes` 정책으로 신규/수정 가능한 type code 0~12만 제공한다. `TYPE_END_OF_CULUMN(13)` sentinel과 미지원 raw type을 신규 dropdown에 제공하거나 새 값으로 저장하지 않으며 임의의 축약 목록을 별도로 하드코딩하지 않는다. 다만 운영 DB에 이미 존재하는 0~12 외 사용자 항목은 raw type code/DB 표시명을 보존한 read-only 행으로 표시하고 삭제만 허용한다. 해당 행의 키워드·항목명·종류 수정, 사용 항목으로 복사와 신규 생성은 차단한다. 실제 배포 `BM_RICH_COLUMN_TYPE` fixture에서 각 외부 type의 `legacyVisible`, `newReadOnly`, `deleteAllowed`, `copyBlocked`, `intentionalDivergence`를 고정한다.
- 신규/수정 행의 키워드와 항목명은 필수이며 고객별 사용자 항목 목록 안에서 키워드 중복을 허용하지 않는다. read-only 비준수 기존 행도 원본 keyword 그대로 중복 비교 집합에 포함하되, 삭제 command에는 신규 validation을 요구하지 않는다.
- 셀 값이 바뀔 때마다 원본 snapshot과 content 비교로 `userItemDirty`를 계산한다.

9.4 사용자 항목 삭제

- `userItemEdit` 모드에서는 중앙 휴지통의 대상이 사용자 항목 테이블로 전환된다.
- 선택 행이 없으면 휴지통을 비활성화한다.
- 기존 행 삭제는 delete ID에 기록하고 신규 행은 working copy에서만 제거한다.
- 사용자 항목 행을 휴지통에 drop하면 사용 항목 삭제와 같은 hover 및 수용 애니메이션 후 삭제한다.
- 사용자 항목 사전 삭제는 이미 현재 사용 항목으로 복사된 컬럼을 삭제하지 않는다. 이 동작을 확인 dialog 문구에서 명확히 알린다.

9.5 사용자 항목 설정 저장/취소

- `저장`은 `userItemDirty=true`, 모든 신규·수정 가능 행의 validation 성공, 변경되지 않은 grandfathered read-only 행의 raw 보존 검증 성공, busy=false일 때만 활성화한다. 기존 비준수 keyword나 미지원 raw type 자체는 validation error가 아니며 해당 행의 수정·복사만 거부한다. 삭제 command에는 신규 값 validation을 적용하지 않는다.
- 클릭하면 `사용자 항목 설정 변경을 저장하시겠습니까?`를 질의한다.
- 확인 시 신규/수정/삭제를 하나의 DB transaction으로 저장한다.
- 저장 command는 진입 시 customer-scoped 원본 목록의 정규화 original fingerprint와 working copy의 desired fingerprint를 필수로 가진다. transaction에서 같은 customer 범위를 공통 customer-column DB lock과 `UPDLOCK, HOLDLOCK`으로 다시 읽고 fingerprint가 다르면 어떤 CRUD도 실행하지 않은 채 conflict로 rollback한다.
- commit 성공하면 `customerDictionaryReloadPending`으로 전환해 동일 command 재실행과 편집을 차단하고 DB에서 사용자 항목 후보 전체를 다시 조회한다. 재조회 성공 후에만 새 customer-column baseline을 만들고 `normal` 모드로 돌아간다. 이 저장은 이미 사용 항목으로 복사된 label-column이나 현재 `LabelSizeSession`을 변경하지 않으므로 label-size session reload를 실행하지 않는다. 후보 재조회가 실패하면 read-only 복구 화면에서 후보 재조회만 다시 시도하며 customer-column save를 재실행하지 않는다.
- commit 전 실패는 모드를 유지하고 working copy를 보존해 재시도를 허용한다. `DbCommitOutcomeUnknown`은 11.2의 공용 desired/original/indeterminate 판정 알고리즘에 customer-column 전용 adapter를 주입해 수행하고 동일 command 자동 재실행을 금지한다. 이 adapter는 customer application lock resource, cust-column raw snapshot/projection, `(customerId, keyword)` natural-key resolver를 소유하며 label-size lock이나 label-column projection을 재사용하지 않는다.
- `취소`는 변경이 있으면 `사용자 항목 설정 변경을 취소하시겠습니까?`를 질의하고, 확인 시 snapshot으로 되돌린 뒤 `normal`로 돌아간다.
- 모드 종료 시 좌상단 `항목 추가` 아이콘을 다시 `항목 편집` 아이콘으로 바꾼다.

10. 사용 항목 순서 변경

10.1 진입과 UI

- 사용 항목 테이블 좌상단의 순서 변경 아이콘을 누르면 `reorder` 모드로 전환한다.
- 진입 전에 pending property edit을 공용 guard로 해소한다.
- 사용 항목 목록의 현재 순서를 별도 snapshot으로 보관한다.
- 사용 항목 테이블의 컬럼 구성과 행 내용은 그대로 유지한다.
- 테이블 오른쪽에 라벨 설정과 같은 폭/간격/버튼 크기의 위/아래 이동 rail을 표시한다.
- `rowReorderEnabled=true`로 전환하여 행 또는 행 번호 drag reorder를 지원한다.
- 선택 행 기준으로 위/아래 버튼 활성 상태를 계산한다.
- 속성 패널을 포함한 사용 항목 테이블 이외의 위젯은 비활성화한다.
- 속성 패널은 값을 표시해도 입력과 `취소`/`적용`은 비활성화한다.
- 메인 footer `취소`/`저장`도 비활성화한다.
- 사용 항목 테이블 아래에는 왼쪽 제목 `순서 변경`, 오른쪽 `취소`, `저장`을 둔다.

10.2 이동 규칙

- drag와 위/아래 버튼은 같은 reorder function을 사용한다.
- 인접 이동과 비인접 이동의 insert index 계산은 현재 `SwipeActionTable` 라벨 설정 테스트 계약을 따른다.
- 이동 후 선택은 이동한 행의 안정 key를 유지한다.
- 한 행뿐이거나 실제 순서가 바뀌지 않으면 `orderDirty=false`다.

10.3 저장과 취소

- `취소`는 reorder snapshot 순서로 복원하고 `normal` 모드로 돌아간다.
- `저장`은 `orderDirty=true`일 때만 활성화한다.
- 클릭하면 `변경한 사용 항목 순서를 적용하시겠습니까?`를 질의한다.
- 확인 시 현재 순서를 `workingColumns`에 적용하고 각 행의 order를 1부터 연속 값으로 다시 부여한 뒤 `workingDirty=true`로 만들고 `normal` 모드로 돌아간다. DB transaction은 실행하지 않는다.
- 확인을 취소하면 `reorder` 모드와 현재 임시 순서를 유지한다.
- 최종 DB 저장은 메인 footer의 `저장`에서 신규/수정/삭제/순서를 하나의 transaction으로 처리한다. 따라서 순서 변경 적용 후에도 메인 `취소`로 다이얼로그 전체 변경을 버릴 수 있다.

11. 메인 저장

11.1 저장 전 검증

- `propertyDirty=true`이면 메인 저장을 실행하지 않고 사용자가 속성 `적용` 또는 `취소`를 먼저 완료하도록 안내한다.
- 모든 행의 키워드와 항목명 필수
- 전체 키워드 중복 금지
- order를 1부터 연속 값으로 정규화
- 타입별 필수 속성과 범위 검증
- GS1 포함 대상이 현재 working copy에 존재하는지 검증
- 삭제 대상과 신규/수정 대상의 identity 중복 금지
- 현재 labelSizeId와 모든 기존 column의 labelSizeId 일치 확인

해당 라벨 크기에 `BM_RICH_ITEM`이 하나라도 있으면 레거시와 같이 기존 편집 데이터 영향 경고와 최종 확인을 제공한다. 문구는 실제 transaction이 신규 컬럼 콘텐츠 생성, 컬럼 삭제 및 타입 속성 변경을 수행한다는 사실을 명확히 설명한다.

11.2 저장 결과

- `저장` 확인 후 12장의 단일 transaction을 실행한다.
- DB transaction 실패 또는 commit 결과 미확정이면 오류 상태를 구분해 표시한다. commit 전에 확실히 실패한 경우에만 다이얼로그와 working copy를 편집 가능한 상태로 유지하고 저장 재시도를 허용한다. `DbCommitOutcomeUnknown`이면 `commitOutcomeReconciling`으로 전환하고 동일 save command 재실행을 금지한다.
- decode 경계는 `native result drain → resultContractValidated(pre-commit) → commit → commitCompleted → resultFrameSendCompleted(worker) → resultFrameFullyReceived(parent) → wireEnvelopeDecoded(parent) → domainDtoDecoded(DAO)`로 고정한다. versioned result contract는 native worker 안에서 저장 count와 신규 ID mapping payload의 JSON/object schema, 기대 draft key 집합, key/ID 유일성·양수 조건을 검증한 뒤에만 commit을 허용한다. parent frame reader가 length/checksum과 operation/session/epoch를 모두 검증한 경우에만 `resultFrameFullyReceivedDurable` local event를 게시한다. `commitCompleted`와 완전한 result frame 수신이 확인된 뒤 isolate envelope/`DbExecutionResult` 복원에 실패하면 `wireEnvelopeDecodeFailedDurable`을 거쳐 `DbCommittedResultInvalid(stage: wireEnvelopeDecode, committedKnown: true)`, envelope는 유효하지만 DAO domain DTO 복원에 실패하면 `domainDtoDecodeFailedDurable`을 거쳐 `DbCommittedResultInvalid(stage: domainDtoDecode, committedKnown: true)`로 분류한다. 호출자는 resource별 committed-invalid로 전환해 동일 save command를 영구 금지하고, 오류를 commit 전 실패나 commit 결과 미확정으로 표시하지 않는다. payload 원문은 로그이나 recovery artifact에 남기지 않는다.
- `committedResultInvalid`는 read-only 복구 화면을 가진다. 같은 프로세스에서 검증된 mapping payload가 남아 있으면 `mapping 복구 후 전체 재조회`, mapping이 없거나 복구가 실패하면 `전체 재조회`만 제공한다. 전체 재조회 성공은 DB의 현재 상태를 새 session으로 수용하는 것이며 save를 재실행하거나 commit 여부 reconciliation을 호출하지 않는다. 재조회도 실패하면 `다시 불러오기`와 `화면 닫기`를 제공하되, 화면을 닫아도 앱 루트의 지속 복구 배너와 해당 resource의 `force-reload-required` 차단을 유지한다. 재시작 뒤에는 mapping 복구 버튼을 제공하지 않고 14장의 상태별 startup 정책을 따른다.
- 공용 reconciliation engine은 resource별 adapter가 제공하는 application lock, 일관된 raw snapshot reader, mutation-closure manifest, original/desired projection, natural-key resolver만 사용한다. label-column adapter는 label-size resource를, customer-column adapter는 customer resource를 사용한다. 같은 application lock을 획득한 짧은 `DbClient.transaction()` 안에서 manifest의 모든 base table 대상 key/range를 동일한 전역 순서와 `UPDLOCK, HOLDLOCK`으로 읽어 transaction 종료까지 key-range lock을 유지한 하나의 관측 snapshot을 만든다. 단일 batch/transaction이라는 사실만으로 일관성을 주장하지 않는다. mutation-closure rowset별 predicate와 필수 index의 key 순서/leading column/filter/enabled/collation 호환성을 schema capability에 고정한다. 이 결정적 계약이 없으면 편집, save와 reconciliation을 fail-closed로 차단하고, 실제 execution plan과 range-lock 확인은 승인 배포의 integration gate에서 검증한다. 필요하면 검증된 index hint/query template을 사용한다. 별도 승인 migration으로 index를 배포하거나 성능·교착 영향을 검증한 명시적 table-level lock 전략을 채택하기 전 조용히 광범위 lock으로 진행하지 않는다. current DB projection을 original/desired와 비교해 desired와만 일치하면 `desiredStateObserved`로 보고 reload-only 경로로 이동하고, original과만 일치하면 `originalStateObserved`로 표시한 뒤 DB에서 새 snapshot을 만들어 사용자가 새 command를 명시적으로 생성할 때만 재저장을 허용한다. 둘 다 일치하거나 둘 다 불일치, natural key 매칭 0/복수, context/generation 변경, lock 실패, 재조회 실패는 reason code가 있는 `indeterminate`로 두고 `force-reload-required`와 수동 확인을 요구한다. original과 desired가 같은 no-op command는 DB 실행 전에 제거한다. `DbCommitOutcomeUnknown`의 비교 결과를 해당 operation의 commit 여부로 로그/문구에서 단정하지 않는다. 프로세스 재시작 후에는 original/desired projection이 없으므로 이 알고리즘을 호출하지 않는다.
- commit 성공 즉시 dialog session을 `committedReloadPending`으로 전환하고 저장/편집/닫기를 차단한다. 이 상태에서는 동일 save command를 다시 실행하지 않는다.
- `HomePageManager`는 컬럼, 특수 컬럼, scoped column content, 품목 목록/raw snapshot, validation rule, 공용라벨 required keyword/image/barcode 정보와 출력 미리보기를 immutable `LabelSizeSessionData`로 만들고, controller/journal/listener처럼 lifecycle이 있는 객체는 별도 `LabelSizeSessionResources`가 소유한다. 둘을 generation과 함께 묶은 `LabelSizeSession` 단일 reference를 전역 상태와 분리해 완전히 생성한다. session scope에는 customer/market/label-size immutable context, mapping/concurrency fingerprint와 validation/preview 입력도 포함한다. `TColumnType`처럼 연결 generation 동안 불변인 참조 데이터만 application cache로 분류할 수 있다. `TColumn.datas`, `TColumnContent.datas`, `TColumnSpecial.datas`, `ItemOfMarket.datas`, `_currentLabelSize`, `Market.instance`를 세션 동작 중 직접 조합하거나 개별 static cache를 순차 교체하는 방식은 atomic swap으로 간주하지 않는다. 모든 세션 화면/helper는 generation-bound session accessor를 주입받는다.
- candidate는 controller, journal metadata, storage 접근과 baseline 검증을 부작용 없는 `prepare` 단계까지 수행하고 기존 journal과 같은 draft key의 listener를 미리 시작하거나 이전 파일을 정리하지 않는다. journal은 `draftKey`, `generation`, `ownerToken`, generation별 `filePath`, `phase`, `previousOwner`, payload/manifest checksum을 하나의 durable manifest에 temp-write, file handle `FlushFileBuffers`, 원자 교체 순서로 저장한다. Windows 구현은 target이 있으면 `ReplaceFileW(target, temp, backup, 0, ...)`, target이 없으면 같은 디렉터리의 `MoveFileExW(temp, target, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`를 공용 native primitive로 사용하고 target을 먼저 `.bak`으로 이동해 target 부재 구간을 만들지 않는다. POSIX `fsync(directory)`와 같은 directory-entry 또는 전원 차단 durability를 보장한다고 표현하지 않으며, target/tmp/bak recovery scan으로 process-crash consistency를 제공한다. SharedPreferences는 manifest discovery hint 하나만 저장하며 소유권 source of truth로 사용하지 않는다. startup은 hint 존재 여부와 무관하게 전용 manifest 디렉터리의 target/tmp/bak를 스캔한다. checksum이 유효한 target의 publish 완료 phase를 우선하고, target이 없거나 무효일 때만 같은 generation의 완료된 tmp를 승격하며, 그마저 없을 때 유효한 bak로 복구한다. 같은 generation에 서로 다른 ownerToken의 유효 artifact가 둘 이상이거나 phase 전이가 불가능하면 임의 선택·삭제하지 않고 격리 후 `force-reload-required`로 전환한다. 선택 owner가 resume된 뒤에만 더 낮은 generation artifact를 정리한다. 각 prepare/suspend/activate/swap/render/dispose 직후 process crash와 native API 실패에 대해 선택·보존·격리·삭제 규칙을 recovery matrix와 child-process fault-injection fixture로 고정한다. `prepare`, `suspend(clearFile: false)`, `activate`, `resume`, `dispose`는 manifest lease를 검증하고 `clear/dispose`는 현재 owner token과 일치할 때만 파일을 삭제한다. 소유권/manifest 저장 실패를 background error로 삼키지 않는다.
- load generation과 immutable customer/market/labelSize context가 일치할 때 `HomePageManager`의 단일 handoff API가 기존 journal write queue drain 및 suspend, candidate activate, session reference swap, 새 generation key로 widget subtree/listener 재결합을 수행한다. 첫 `renderReady` 전에는 기존 resources를 유지하고, 성공 후에만 기존 controller/journal을 dispose한다. activate/swap/render가 실패하면 durable manifest recovery matrix에 따라 기존 session resume, candidate active 유지, 또는 `force-reload-required` 중 하나로 결정한다. 오래된 generation 완료 결과는 handoff 전에 폐기한다.
- swap 완료 후 render가 취소되거나 실패하면 상위 상태를 `force-reload-required`로 전환해 후속 편집을 차단한다. 이미 commit된 DB를 되돌리거나 save command를 재실행하지 않는다.
- reload 성공 후에만 다이얼로그를 자동으로 닫는다. reload 실패 시 `committedReloadFailed` read-only 오류 화면으로 유지하고 `다시 불러오기`와 명시적 `화면 닫기` 버튼을 제공한다. 제목 표시줄 닫기/Esc는 계속 소비한다. `화면 닫기`로 overlay를 닫아도 앱 루트 bootstrap service가 `HomePageManager` 위에 표시하는 지속 복구 배너와 해당 resource의 `force-reload-required` 차단을 유지하며, 배너는 `다시 불러오기`, 진단 보기와 상태가 요구할 때만 `현재 DB 상태 수용` action을 제공한다. 이 지속 진입점이 준비되지 않은 플랫폼에서는 오류 overlay의 `화면 닫기`를 노출하지 않는다.

12. DB 모델과 DAO

12.1 추가할 모델

구체 파일명은 기존 모델 구조에 맞추되 최소한 다음 역할을 분리한다.

- `LabelColumnDraft`: 아래 persisted field allow-list, 기존 columnId 또는 신규 draft key, new/modified 상태
- `LabelColumnEditSession`: original/working/deleted/selection/property 상태와 content 비교
- `FixedColumnType`: 고정 항목 분류 ID와 이름. 존재하지 않는 order 필드를 만들지 않는다.
- `FixedColumnCandidate`: fixedColumnId, 타입, 키워드, 항목명, 분류 ID
- `CustomerColumnCandidate`: custColumnId, customerId, 타입, 키워드, 항목명
- `CustomerColumnEditSession`: 사용자 항목 original/working/deleted 상태
- `LabelColumnSaveCommand`: labelSizeId, insert/update/delete 목록, 최종 순서, 저장 context, concurrency fingerprint와 observation projection
- `DbExecutionResult`/동등 DTO: 각 결과셋의 독립 columns/logical types/rows와 전체 affected count를 보존하는 driver 반환 타입
- `DbLogicalType`/`DbColumnMetadata`: ODBC native type, DB-Lib `SYB*` 또는 Android/iOS driver native type을 직접 노출·비교하지 않고 `integer`, `decimal`, `string`, `dateTime`, `binary`, `boolean` 등 공용 logical type으로 정규화한다. nullability는 `noNulls | nullable | unknown`, 각 수치 metadata는 `known(value) | unknown | notApplicable`로 구분하고 character length/octet length/numeric precision/numeric scale/temporal fractional precision을 혼용하지 않는다.
- `DbWireScalar`: row value를 driver 구현 타입에 맡기지 않고 integer 범위 보존 값, decimal canonical 문자열, timezone/precision이 명시된 temporal 문자열, boolean, string, binary base64 descriptor와 DB null로 정규화하는 versioned wire 값. DB null, 빈 string, 빈 binary, 문자열 `"0"`, 숫자 0과 false는 서로 다른 kind/value로 보존한다.
- `DbResultContract`: marker column/type, result-set/row cardinality, count 기대값, mapping object schema와 command의 신규 draft key 집합을 commit 전에 검증하는 versioned wire descriptor
- `DbResultSetContract`: raw snapshot의 rowset kind/version/ordinal, column/type와 cardinality를 검증하는 versioned descriptor
- `DatabaseIdentity`/`stableDatabaseIdentityDigest`/`connectionEpoch`: 비밀정보를 제외한 검증된 server/database identity, recovery namespace용 안정 digest와 connect 성공마다 증가하는 cache/요청 소유 epoch. 연결 전 endpoint/DB name은 `connectionProfileHint`일 뿐 identity가 아니다. digest는 canonicalization version과 아래 versioned identity probe의 verified tuple을 사용하고 password, connection epoch, `family_guid`와 단순 DNS/IP 별칭을 포함하지 않는다. 사용자 결정에 따라 AG의 `group_id`/`group_database_id`가 일치하는 failover 또는 standalone의 같은 `database_guid`만 같은 identity로 보고 restore·clone은 새 namespace로 분리한다.
- `DbIdentityProbeResult`: `verifiedAvailabilityGroup | verifiedStandalone | notInAvailabilityGroup | unsupportedPlatform | permissionDenied | metadataHidden | malformed` kind, canonical database name, `SERVERPROPERTY('EngineEdition')`/product version, current DB의 `sys.database_recovery_status.database_guid`, AG일 때 `sys.availability_databases_cluster.group_id`/`group_database_id`, 필드별 provenance와 권한 진단을 보존한다. `family_guid`, server/machine/instance 표시명은 진단값일 뿐 digest source가 아니다.
- `DbConnectionBootstrap`: `connectAttemptId`, `expectedPreviousEpoch`, transport/identity/recovery readiness를 소유하고 connect 성공 시 발급된 epoch보다 오래된 attempt 응답을 폐기하는 연결 상태기계. 외부 상태는 `disconnected | transportConnecting | transportConnected | identityProbing | recoveryBinding | ready | degradedReady`로 구분한다.
- `DbNativeSessionToken`: native connection을 새로 열 때마다 driver 내부에서 발급하며 transaction의 모든 statement/commit/rollback/cleanup이 같은 ODBC HDBC 또는 DB-Lib DBPROCESS를 사용하는지 검증하는 비공개 token
- `NativeDbTransactionSession`: driver가 발급한 하나의 `DbNativeSessionToken`과 native connection을 배타 소유하고 `begin`, `executeAndDrain`, `commit`, `rollback`, `verifyTransactionClosed`, `discard`만 노출하는 transaction 전용 객체. transaction 제어 SQL을 일반 `writeData()`로 보내거나 command마다 native connection을 다시 선택하지 않는다.
- `DbOperationAck`: worker가 관측한 `operationAccepted → commitDispatchObserved → commitCompleted → resultFrameSendCompleted`의 cumulative high-watermark와 operation/session/epoch ID를 보존하는 versioned ack. worker의 send 완료는 parent의 receive 완료를 뜻하지 않는다. `commitDispatchObserved`는 worker가 native commit 호출에 진입하기 직전 별도 control channel로 방출한 관측 증거이며 parent의 사전 `commitDispatchIntentDurable`을 대체하지 않는다. control/result channel 간 지연·재정렬이나 중간 ACK 유실이 있어도 더 높은 유효 ACK는 이전 worker 관측 단계를 함의하는 high-watermark로 수용한다. 낮은 단계의 후착 ACK는 같은 canonical payload이면 idempotent stale ACK로 무시하고 ID/payload가 다르면 typed reject한다. `resultContractValidated`는 commit 전 worker 내부 증거로 result frame/contract에 포함한다. `resultFrameFullyReceived`, `wireEnvelopeDecoded`와 `domainDtoDecoded`는 worker ACK가 아니라 각각 parent frame reader, parent wire decoder와 DAO mapper가 동일 operation/session/epoch를 검증한 뒤 `RecoveryTransitionTableV1`에 제출하는 local event다.
- `DbActionRequirementV1`: 모든 bootstrap/일반 DB action ID별 `requiredPhase`, `requiresAuthoritativeIdentity`, `allowedInDegradedReady`, `cacheScope`, `isWrite`를 폐쇄 열거하는 checked-in manifest
- `ContentCreationOwnershipV1`: `BM_RICH_COL_CONTENT`와 capability에 따른 `BM_UPDATE_COL_CONTENT`별 `triggerOwned | daoOwned | unsupported` 생성 주체, trigger 이름/활성 상태/정의 hash, statement-level inserted 집합 처리 여부, label-size별 order 부작용, unique key와 검증 query를 보존하는 배포 capability. 레거시 `AFTER_INSERT_COLUMN`은 `inserted` 집합 대신 전역 마지막 row와 전역 `MAX(RICH_COLUMN_ORDER)+1`을 사용하므로 승인 hash 여부와 무관하게 `unsupported`다.
- `GateManifestV1`: gate ID, blocking 여부, 대상 OS/architecture/SQL Server edition·version, provisioning/권한 DDL, 실행 명령, timeout, expected assertion과 결과 artifact schema/유효기간을 고정하는 checked-in 완료 gate
- `PlatformDbExecutionCapabilityV1`: `windowsDesktopWorker | macosDesktopWorker | androidNativeService | iosInProcessNative` kind, driver/ABI, cancel primitive, independent control 경계, hard-kill 지원 여부, session discard/cleanup 증거, credential transport와 transaction 허용 여부를 보존하는 플랫폼 capability. Flutter Web과 Linux는 제품 범위에서 제외한다.
- `DbWorkerArtifactManifestV1`: 플랫폼/architecture별 worker 또는 native service 산출물 이름, source target, build 명령, 설치·bundle 위치, protocol version, binary hash/signature 검증과 parent/app 호환 범위를 고정하는 checked-in manifest
- `DbWriterManifestV1`: 실제 SQL target별 writer action ID, resource kind/ID resolver, application lock 순서, transaction API와 commit 후 session invalidation을 폐쇄 열거하는 checked-in manifest
- `DbConnectionDiscarded`: taint된 native session과 같은 epoch에 귀속된 대기 요청이 SQL 실행 없이 실패했음을 나타내는 typed 오류
- `DbApplicationLockException`: timeout/cancel/deadlock/configuration을 구분하고 lock resource 종류와 비민감 ID만 보존하는 typed 오류
- `DbWireEnvelope`: `DbNvarcharMax`, parameter log policy, transaction statement/result/contract, typed DB 오류를 isolate 경계에서 전달하는 명시적 kind/schemaVersion/payload 계약
- `RawLabelColumnRow`: DB scalar와 null을 변형하지 않고 보존하는 편집기 전용 조회 DTO
- `RawLabelColumnMinRow`: 일반/sentinel identity, keyword/name/order와 UI 비노출 `RICH_MIN_CHECK` 원본 값을 보존하는 DTO
- `StrictLabelColumnValue<T>`: `supported(raw, value)` 또는 `unsupported(raw, reason)`로 해석 결과와 raw 값을 함께 보존하는 타입
- `ReconciliationAdapter`: resource lock, raw snapshot reader, mutation-closure manifest/projection과 natural-key resolver를 제공하는 label-column/customer-column별 adapter
- `LabelSizeSessionData`: 같은 generation의 컬럼/콘텐츠/품목/validation/미리보기 입력을 소유하는 immutable snapshot
- `LabelSizeSessionResources`: controller/journal/listener와 dispose 상태를 소유하는 lifecycle 객체
- `LabelSizeSession`: data/resources/context/generation을 묶어 단일 reference로 교체하는 상위 세션
- `LabelColumnEditCoordinator`: dialog 밖에서 edit/save/post-commit 상태와 in-flight Future를 소유하고 UI detach와 application recovery handoff를 처리하는 coordinator
- `LabelColumnSaveRecoveryRegistry`: 앱 루트 수명으로 detached coordinator와 opaque random operation ID, DB identity별 resource key/context/phase를 소유한다. 같은 프로세스에서는 projection을 가진 coordinator의 reconciliation/reload-only를 이어받고, 프로세스 재시작 후에는 startup scan과 identity-bound resource 차단, 강제 reload·사용자 확인 해제만 담당하는 recovery service
- `LabelSizeSessionConsumerManifestV1`: 레거시 `OnCommonLabelColumnChange()` 효과를 현 소비자별로 매핑해 새 generation에서 수행할 column reset, item/update-item row 재구성, 현재 선택 복원, RTF/validation/preview invalidate·recompute와 `renderReady` acknowledgement를 폐쇄 열거하는 manifest

`TColumn`에 UI 임시 상태를 넣지 않는다. 저장 command는 widget 상태를 직접 참조하지 않는 immutable DTO로 만든다.

`LabelColumnDraft`의 persisted field allow-list는 다음과 같다. 실제 배포 DB capability에서 컬럼이 없는 경우 조용히 누락하지 말고 진입을 차단하거나 호환 SQL을 명시적으로 분기한다.

- identity/context: `RICH_COLUMN_ID`, `RICH_LABELSIZE_ID`, `RICH_COLUMN_ORDER`
- 공통: `RICH_COLUMN_NAME`, `RICH_KEYWORD`, `RICH_TYPE`, `RICH_TITLE`, `RICH_VISIBLE`
- 크기/바코드: `RICH_WIDTH`, `RICH_HEIGHT`, `RICH_BARCODE_TYPE`, `RICH_USE_BARCODE_CHECKDIGIT`, `RICH_SHOW_BARCODE_NUM`, `RICH_TIMEBARCODE_TYPE`, `RICH_USER_DEFINE_BARCODE_TEXT`, `RICH_BARCODE_LINE`, `RICH_BARCODE_LINE_SIZE`, `RICH_BARCODE_ROTATE`
- QR/기본 사용자 정의: `RICH_SHOW_QRCODE_TEXT`, `RICH_QRTEXT_ALIGNMENT`, `RICH_USE_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRTEXT`, `RICH_PIXELSIZE`, `RICH_QRCODE_CREATE_TYPE`, `RICH_NATRIUM_JOIN_STRING`, `RICH_QRTEXT_FONTSIZE`, `RICH_QRTEXT_FONTNAME`, `RICH_QRCODE_SCALE`
- 자동 증가/출력/날짜 범위: `RICH_AUTO_INC`, `RICH_AUTO_INC_SIZE`, `RICH_AUTO_INC_RANGE`, `RICH_AUTO_INC_SAVE`, `RICH_AUTO_INC_ZERODEL`, `RICH_AUTO_INC_UPDATE`, `RICH_SEARCH_PRINT`, `RICH_USE_DATERANGE`, `RICH_DATERANGE`
- 누락 검사: `BM_RICH_CHECK_COLUMNS.RICH_CHECK_YN`; main table의 `RICH_USE_MISSING_KEYWORD_CHECK`가 배포 DB에 존재하면 같은 값으로 동기화한다.
- GS1: `BM_GS1_COLUMN_INFO.COLUMN_GS1_CODE`, `COLUMN_GS1_FORMAT_OPTION`, `COLUMN_SHOW_GS1CODE`와 `BM_GS1_CONTAIN_COLUMN` 최종 관계

`checkMode`, `editableCellNum`, `newColumnQRCodeInfo`, `barFontSize`, `modify`, `change`는 화면/런타임 상태이므로 draft 저장, dirty 비교, SQL parameter에서 제외한다.

`LabelColumnDraft`는 enum으로 해석된 값뿐 아니라 DB에서 읽은 raw type code, QR alignment code, QR create type code, barcode type name을 보존한다. 지원하지 않는 raw 값은 기본값으로 치환해 저장하지 않고 해당 행을 read-only 오류 상태로 표시하며, capability/호환 규칙이 추가되기 전 전체 저장을 차단한다.

fingerprint 계약은 다음 두 projection으로 분리한다.

- `concurrencyFingerprint`: 기존 column/custColumn DB ID, raw persisted scalar, null/빈 문자열 구분, order와 save가 변경하는 전체 mutation closure를 canonical JSON으로 정렬해 동시 변경을 검출한다.
- `desiredObservationProjection`: 기존 행은 DB ID를 유지하고 신규 행은 대상 컬럼 자체의 SQL Server 비교식으로 유일 keyword를 매칭한다. 관측된 신규 ID를 관계 endpoint와 child row에 다시 투영한 뒤 canonical JSON을 비교한다. keyword 후보가 0개 또는 2개 이상이면 `indeterminate`다.

label-column mutation-closure manifest는 최소한 다음 rowset을 각각 독립 key/필드/기대 행 수/absence 조건으로 고정한다: persisted allow-list의 `BM_RICH_COLUMN`, `RICH_MIN_CHECK`를 포함한 `BM_RICH_COL_MIN` 일반 행과 정확히 1개인 `ELEMENT` sentinel, `BM_RICH_CHECK_COLUMNS`와 capability가 있는 main check flag, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN` 양방향 endpoint, 삭제 컬럼의 `BM_COLUMN_QRCODE_INFO` 양방향 orphan 부재, 현재 item ID별 `BM_RICH_COL_CONTENT` 존재/부재, capability에 따른 `BM_UPDATE_COL_CONTENT`, `BM_RICH_STATUS_DATA` 변경 상태. 저장 중 item 집합도 같은 lock/snapshot에서 관측한다. `GETDATE()` status처럼 operation ledger 없이 desired exact value를 만들 수 없는 side effect가 commit 결과 미확정 command에 포함되면 추정 비교하지 않고 `indeterminate`로 판정한다. customer-column adapter는 customer-scoped `BM_RICH_CUST_COLUMN` persisted row 전체를 별도 manifest로 정의한다.

두 projection은 필드 순서, row 정렬, 숫자/boolean 표현, null과 빈 문자열, raw enum/name, 관계 endpoint 변환과 content 존재 조건을 하나의 공용 canonicalization fixture로 고정한다. Dart와 SQL에서 서로 다른 임의 hash 직렬화를 만들지 말고, 동일 canonical row 집합을 비교하거나 검증된 byte serialization만 사용한다.

natural-key 후보 계산은 Dart의 대소문자 변환, `trim`/`RTRIM` 또는 별도 정규화로 SQL collation을 흉내 내지 않는다. `RICH_KEYWORD = CONVERT(<target SQL type>, @keyword)` 또는 cust-column 대상 컬럼의 동등 비교를 사용해 case/accent/kana와 trailing-space 동등성을 DB가 직접 판정한다. 저장 전 working keyword 중복도 같은 SQL 동등성 fixture로 검증하고, 절단/변환 후 DB에 실제 저장된 keyword를 재조회해 projection에 사용한다.

기본 타입의 사용자 정의 데이터는 별도 DB 필드를 만들지 않고 레거시와 같이 `RICH_QRCODE_CREATE_TYPE`, `RICH_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRTEXT`를 재사용한다. 제조/유통 날짜·시간의 종류는 `RICH_TYPE`이며 별도 날짜 형식 컬럼을 만들지 않는다. 컬럼별 날짜 부가 설정은 `RICH_USE_DATERANGE`, `RICH_DATERANGE`만 저장한다.

각 속성 editor 구현 전 `type code → editor → UI 입력 → LabelColumnDraft/raw 필드 → DB 테이블/컬럼 → SQL 타입/max byte/nullability → 최소·최대 → 타입 변경 시 유지/초기화` 매핑표를 코드 옆 문서 또는 테스트 fixture로 작성한다. type 0~12의 모든 source→target 전환에 대해 각 persisted scalar와 QR/GS1 child row에 `legacyObserved`, `newPolicy`, `intentionalDivergence`, 레거시 근거 symbol/line과 저장 후 expected projection을 기록한다. 사용자 결정에 따라 일관된 일괄 초기화 규칙을 새로 만들지 않고, 레거시가 editor 기본값으로 덮는 필드, 기존 객체 값을 보존하는 필드, create type에 따라 조건부 setter를 호출하는 QR data/text와 별도 child lifecycle을 각각 재현한다. 레거시 근거가 없는 전환은 구현하지 않고 fixture 미확정으로 진입을 차단한다.

12.2 조회 DAO

- 현재 사용 항목: 편집기 전용 `RawLabelColumnRowDAO.selectByLabelSizeId`. 기존 `TColumnDAO.selectByLabelSizeId()`와 `TColumn.fromMap()` fallback 경로를 편집기 snapshot, dirty 비교, fingerprint, SQL serializer에서 호출하지 않는다. raw DAO는 `DbClient.queryResultSets(..., required DbResultSetContract contract) -> DbExecutionResult` 또는 이름이 같은 typed public API만 사용해 하나의 짧은 transaction에서 `BM_RICH_COLUMN`, `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN` base table과 capability child를 독립 rowset으로 조회한다. 사용자 결정에 따라 최초 baseline은 bootstrap capability가 `snapshot_isolation_state=ON`을 확인한 DB에서 명시적 `SNAPSHOT` isolation으로 모든 manifest rowset을 읽고 DAO 반환 전에 transaction을 종료한다. 최초 조회에 `UPDLOCK, HOLDLOCK`을 사용하지 않으며 snapshot isolation이 없거나 version-store 오류가 발생하면 일반 조회로 낮추지 않고 typed 진입 실패로 차단한다. save/reconciliation에서만 application lock 뒤 동일 순서의 `UPDLOCK, HOLDLOCK`을 사용한다. 각 `SELECT`는 rowset kind/version을 반환하거나 contract의 고정 ordinal/schema에 정확히 일치해야 하며 누락·중복·순서/schema 불일치는 protocol error다. raw DAO에서 기존 `Object` 반환 `getData*()` compatibility API와 transaction 밖 복수 query 사용을 금지한다. main/child raw SQL에는 null을 기본값으로 바꾸는 `CASE`/`COALESCE`를 사용하지 않고, `VIEW_BM_GS1_CONTAIN_COLUMN` 같은 집계 view로 0/1/복수 관계를 평탄화하지 않는다. 각 rowset은 원래 DB null, 미지원 scalar, 중복 child와 양쪽 endpoint를 그대로 보존한 뒤 strict mapper가 지원 여부를 판정한다. 사용 항목 표시 순서는 `RICH_COLUMN_ORDER ASC, RICH_COLUMN_ID ASC`로 고정한다.
- 고정 항목 분류: `BM_RICH_FIX_COL_TYPE`, `RICH_FIX_COL_TYPE_ID ASC`로 정렬
- 고정 항목 후보: `BM_RICH_FIX_COLUMN`, 선택한 type ID 조건
- 사용자 항목 후보: `BM_RICH_CUST_COLUMN`, 현재 로그인 customer ID 조건
- 항목 종류: 기존 `TColumnType.datas`; 미초기화 상태면 DB 조회 후 dialog를 표시한다.

모든 조회 문자열은 현재 프로젝트 DAO 규칙에 맞춰 CP949 컬럼을 명시적으로 NVARCHAR로 변환한다. 저장 capability는 `sys.columns`에서 필드별 `typeName`, `maxLength`, `isUnicode`, `isMax`, `nullable`, `collation`을 수집하고 mutation-closure predicate별 필수 index의 정확한 key 순서/leading column/filter/enabled 상태와 collation·predicate 호환 여부도 포함한다. runtime gate는 이 결정적 schema 계약만 사용하고 통계, parameter sniffing, SET option과 plan cache에 따라 바뀌는 관측 실행 계획으로 기능을 켜거나 끄지 않는다. 필요한 경우 검증된 index hint/query template을 고정하며 실제 plan/range-lock 검사는 배포 integration gate로만 사용한다. 권한 부족, schema 부적합과 integration plan 불일치는 서로 다른 reason code다. `max_length=-1`은 MAX로, `NVARCHAR/NCHAR`의 양수 `max_length`는 UTF-16 byte 단위로, `VARCHAR/CHAR`는 대상 code page byte 단위로 해석해 하나의 문자 수 제한으로 혼용하지 않는다. capability와 `TColumnType` 같은 reference cache는 `(DatabaseIdentity, connectionEpoch)`에 귀속한다. connect 성공마다 epoch를 증가시키고 connect/disconnect/connection loss/isolate 재생성/DB identity 변경/schema migration 때 기존 cache를 폐기한다. `DB_ID()`만으로 다른 server를 구분하지 않는다.

index capability는 `IndexPredicateRequirementV1` checked-in manifest가 source of truth다. raw snapshot, concurrency fingerprint, reconciliation과 absence 검증에 사용하는 각 SQL statement/predicate마다 `queryId`, `table`, `equalityPrefix`, `rangeSuffix`, `requiredUnique`, `acceptedFilter`의 normalized expression, `requiredCollation`, `includeColumns`, `approvedIndexNames`, optional verified query/index hint와 table-lock 대안을 기록한다. 최소한 `BM_RICH_COLUMN`, `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, `BM_GS1_COLUMN_INFO`, `BM_GS1_CONTAIN_COLUMN`의 양 endpoint, `BM_COLUMN_QRCODE_INFO`의 양 endpoint, `BM_RICH_ITEM`, `BM_RICH_COL_CONTENT`, capability에 따른 `BM_UPDATE_COL_CONTENT`와 `BM_RICH_STATUS_DATA`, customer-scoped `BM_RICH_CUST_COLUMN`의 실제 save/snapshot predicate를 모두 열거한다. `sys.indexes`, `sys.index_columns`, `sys.columns`와 권한 probe를 함께 읽고 disabled/hypothetical/filtered index, key/include 순서와 collation을 검증해 `compatible | missing | incompatible | permissionDenied`를 구분한다. prose의 "적절한 index"나 index 이름만으로 통과시키지 않으며 manifest에 없는 query는 편집/save/reconciliation을 fail-closed로 차단한다. 승인 DDL 또는 table-lock 대안은 해당 `queryId`에 직접 연결한다.

identity bootstrap은 일반 SQL 실행 API가 아니라 `probeDatabaseIdentityV1` privileged operation 하나로 고정한다. probe SQL은 현재 DB의 `DB_NAME()`, `SERVERPROPERTY('EngineEdition')`/`ProductVersion`, `sys.database_recovery_status.database_guid`를 읽고, SQL Server AG catalog가 지원되고 metadata가 보이면 `sys.availability_databases_cluster`의 current database `group_id`/`group_database_id`를 함께 읽는다. `HAS_PERMS_BY_NAME`과 catalog 접근 결과를 사용해 AG 미가입, 권한 부족, metadata hidden, 미지원 engine을 구분하며 0행/NULL을 standalone으로 추정하지 않는다. exact SQL text, 최소 권한과 SQL Server edition/version별 expected row fixture를 identity probe schema version에 포함한다. 연결 전 `connectionProfileHint`는 namespace-neutral artifact 탐색에만 사용한다. `verifiedAvailabilityGroup`은 `(groupId, groupDatabaseId, canonicalDatabaseName)`, `verifiedStandalone`/`notInAvailabilityGroup`은 `(databaseGuid, canonicalDatabaseName)`의 versioned serialization으로 digest를 계산한다. 지원하는 identity 이동 절차는 backup/restore, detach/attach, AG seed/failover, storage/VM snapshot을 폐쇄 열거하고 각 절차의 metadata 유지·변경 기대값과 허용 여부를 fixture로 고정한다. metadata만으로 원본과 clone의 incarnation 분리를 증명할 수 없는 절차는 production에서 금지하며 임의 endpoint/server 표시명을 digest 보강값으로 사용하지 않는다. 사용자 결정에 따라 `permissionDenied | metadataHidden | unsupportedPlatform | malformed`이면 endpoint 임시 digest나 새 authoritative namespace를 만들지 않고 `degradedReady`로 전환한다. 이 상태의 허용 업무는 `DbActionRequirementV1.allowedInDegradedReady=true`인 action만이며 authoritative identity cache, 모든 write, label/session load, 항목 편집, save/reconciliation과 recovery namespace bind는 fail-closed로 차단한다. schema capability는 매 connect마다 다시 probe해도 된다. 사용자/거래처 ID를 화면 표시값에서 추정하지 말고 로그인 세션의 명시적 customer ID를 전달한다.

JSON은 `raw object → raw scalar staging → validation → target conversion` 4단계로 처리한다. 먼저 배열 행을 분리한 뒤 각 object에 `OPENJSON(objectJson)`을 적용해 `key`, `value NVARCHAR(MAX)`, `type`을 staging table에 저장한다. 이 단계에서 필수 field 존재, 알 수 없는/중복 key, 명시적 null과 field 부재를 검증한다. 문자열은 nullability, target collation 변환 후 `DATALENGTH`, Unicode→대상 type→Unicode binary round-trip을 검사하고 숫자/날짜/bit는 `TRY_CONVERT`를 통과한 값만 최종 table variable의 명시적 SQL 타입으로 변환한다. `OPENJSON ... WITH VARCHAR(n)` 또는 숫자 타입으로 곧바로 투영해 검증 전 절단·변환·null 합성을 허용하지 않는다. Dart CP949 validator도 encode 성공만 보지 않고 encode→decode round-trip이 원문과 동일한지 확인한다.

Web과 Linux를 제외한 Windows/macOS/Android/iOS를 production 대상으로 한다. 최소 제품 지원 matrix는 Windows 10/11 x64, macOS 10.15+ x64/arm64, Android API 24+의 arm64-v8a 실제 기기와 x86_64 emulator/test lane, iOS 13+ arm64 실제 기기다. Android x86_64는 production device 배포 ABI가 아니라 자동/수동 native integration test ABI다. iOS simulator와 그 architecture는 UI/contract test에 사용할 수 있지만 native DB production gate를 대체하지 않는다. 이 normative matrix의 모든 필수 조합이 manifest에 존재하는지를 별도 coverage gate로 검증하며 manifest 작성자가 임의로 지원 조합을 줄일 수 없다. Windows desktop은 ODBC worker process, macOS desktop은 검증된 DB-Lib worker process, Android는 ABI별 native DB driver를 소유한 bound native service 또는 isolated process, iOS는 앱 process 내부 native driver와 독립 cancel thread/control 경계를 사용한다. iOS는 별도 process 강제 종료를 보장한다고 주장하지 않으며, deadline 내 native cancel 완료와 native session discard/cleanup을 실제 fixture로 증명하지 못한 driver/OS 조합에서는 transaction 시작 전 라벨 항목 편집을 fail-closed한다. 플랫폼 이름만으로 driver를 선택하지 않고 `PlatformDbExecutionCapabilityV1`과 `DbWorkerArtifactManifestV1` 검증이 완료된 조합만 허용한다. JSON parameter는 값 추론에 맡기지 않고 `DbNvarcharMax` 또는 동등한 명시적 타입으로 항상 Unicode large value에 bind한다. ODBC/DB-Lib/각 native adapter는 Unicode JSON scalar parameter, 작은따옴표, 한글, 4,000자 초과 payload와 marker가 있는 최종 결과셋을 동일하게 처리해야 한다. DB-Lib `SYBNVARCHAR` parameter의 UTF-16 길이 계산을 먼저 검증하고, binding API가 요구하는 byte length와 UTF-16 code-unit length를 공용 helper 한 곳에서 구분해 사용하도록 수정한다. ODBC는 4,000자 초과 값을 `SQL_WLONGVARCHAR` 또는 검증된 동등 경로로 전달한다.

모든 production adapter의 collector는 첫 schema에 결과를 평탄화하지 않고 모든 결과셋을 `DbExecutionResult.resultSets`에 독립 schema/rows로 보존한다. ODBC type integer, DB-Lib `SYB*` type과 Android/iOS native type은 adapter별로 `DbLogicalType`/`DbColumnMetadata`로 정규화하고 result contract는 native code를 직접 비교하지 않는다. adapter가 제공하지 못하는 metadata는 `unknown`으로 보존하며 native metadata API를 추가하지 않은 채 nullable/precision을 추정하지 않는다. result contract는 logical type별 필수 비교 metadata와 참고 metadata를 구분한다. row value도 `DbWireScalar`로 정규화해 ODBC `num.tryParse`나 DB-Lib/native `DECIMAL/NUMERIC → double` 결과를 canonical projection에 직접 사용하지 않는다. raw decoder는 길이만으로 null을 판정하지 않고 null pointer/indicator와 type을 사용하며 non-null zero-length string/binary를 각각 빈 string/binary로 보존한다. decimal은 scale을 보존하는 문자열로 전달하고 binary/date/time/integer의 wire 표현도 모든 adapter에서 동일해야 한다. strict raw API와 legacy compatibility API는 반환 타입과 mapper를 분리해 compatibility `COALESCE`/fallback 값이 fingerprint/projection에 들어오지 못하게 한다. marker SQL은 각 column을 명시적으로 `CAST`해 logical type을 고정한다. `DbTransactionStatement`에는 optional `resultContract: DbResultContract`를 추가하고 kind/schemaVersion만 별도 전달하지 않는다. `DbClient.transaction()`은 driver의 `NativeDbTransactionSession` 하나를 생성해 `begin → executeAndDrain* → contract validate → commit → verifyTransactionClosed` 순서를 소유하고 일반 `writeData()`로 `BEGIN/COMMIT/ROLLBACK`을 보내지 않는다. session은 시작 시 `DbNativeSessionToken`을 캡처하고 모든 statement, commit, rollback과 cleanup 직전에 동일성을 검증한다. DB-Lib의 현재 `_ensureConnectedOrReconnect()` 같은 command-path 암묵 재연결을 strict transaction path에서 금지하고, native session 재생성은 bootstrap connection owner만 수행한다. parent는 native commit command 전에 `commitDispatchIntentDurable` publish를 완료하고 worker는 native commit 호출 진입 직전 `commitDispatchObserved` ACK를 방출한다. token 불일치는 commit intent 전이면 cleanup 증거에 따라 `DbConnectionDiscarded | preCommitCleanupPending`, intent 이후 `commitCompleted` 증거 전이면 `DbCommitOutcomeUnknown`으로 분류한다. 이미 시작한 native commit을 observed ACK의 parent durable publish 완료까지 중단할 수 있다고 가정하지 않는다. 모든 statement의 result stream이 `NO_MORE_RESULTS`까지 완전히 drain된 뒤 contract에 따라 marker 결과셋/행 cardinality, 정확한 column 이름과 logical type, count의 정수 변환·command 기대값, `MAPPING_JSON` 배열/object field type, command 신규 draft key 집합과 mapping key/양수 ID 유일성을 commit 전에 검증한다. contract 불일치는 rollback 가능한 pre-commit protocol error다. `commitCompleted`가 확인되고 result frame 전체 수신 뒤 `wireEnvelopeDecoded` 또는 `domainDtoDecoded` 단계만 실패한 경우에만 stage가 있는 `DbCommittedResultInvalid`다. 임의 Dart closure는 isolate 경계를 통과할 수 없으므로 validator는 versioned descriptor와 공용 구현으로 고정한다. 일반 조회는 result contract가 null일 때 기존 반환 shape를 유지하는 compatibility adapter를 두되 raw DAO/reconciliation에서는 사용하지 않는다.

`DbNvarcharMax`, `DbTransactionStatement`, `DbResultContract`, `DbResultSetContract`, `DbExecutionResult`, `DbLogicalType`, `DbColumnMetadata`, `DbWireScalar`, result set과 typed DB 오류는 모두 isolate wire schema의 `kind`, `schemaVersion`, 필수/선택 field, null 규칙과 `toMap/fromMap` round-trip을 갖는다. connect는 아직 새 epoch가 없으므로 일반 request epoch 계약에서 제외한다. connect envelope는 `connectAttemptId`와 `expectedPreviousEpoch`를 사용하고 native connect 성공 직후 isolate가 새 epoch를 발급해 응답한다. 이후 bootstrap identity/capability probe와 모든 일반 DB request는 dispatch 당시 새 `connectionEpoch`를 포함하고 isolate dequeue와 driver 실행 직전에 현재 native session epoch와 일치하는지 검증한다. 오래된 attempt 응답, 알 수 없는 kind/version, decode 실패와 epoch 불일치는 SQL 실행 전 폐기 또는 protocol/`DbConnectionDiscarded` 오류로 분류한다. driver 오류는 SQL Server error number와 SQLSTATE를 가능한 범위에서 구조화하고 `db_isolate.dart`의 `errorCode/details`를 거쳐 `DbClient`가 같은 typed exception으로 복원한다. application-lock SQL은 예약된 전용 error number를 사용하며 Windows ODBC native code와 DB-Lib SQL error number를 동일 domain kind로 매핑한다. DB-Lib가 error number를 버리는 현재 `SQLException(message)` 계약은 문자열 파싱으로 우회하지 말고 number/state를 보존하도록 먼저 확장한다. payload 원문과 lock resource 원문은 오류 envelope에 넣지 않는다.

bootstrap API migration은 다음 폐쇄 목록으로 수행한다. `DbBootstrapClient`만 `connectTransport`, `probeDatabaseIdentityV1`, `probeSchemaCapabilityV1`, `bindRecoveryNamespaceV1` privileged action을 호출할 수 있고 일반 DAO에는 이 send port/API를 노출하지 않는다. `DbConnectionPhase`, `isTransportConnected`, `isReady`, `readyFuture`, `degradedReason`을 public 상태로 제공하고 기존 `DbClient.isConnected`는 즉시 deprecated 처리해 신규 코드에서 금지한다. dispatcher는 모든 request의 action ID를 `DbActionRequirementV1`에서 조회해 phase/identity/cache/write 요구를 실행 전 강제하고 manifest에 없는 action은 거부한다. 최소 로그인 인증 조회, notice, monitor ping, label/session load와 모든 write를 열거한다. `StartupDbHelper`는 `connect()` bool이 아니라 `ready | degradedReady | failed` bootstrap result를 기다리고, `DbConnectionService.status.up=true`는 manifest상 허용 action이 하나 이상인 `ready | degradedReady`에서만 게시한다. 별도 `identityAuthoritative`, `recoveryAvailable`, `labelColumnEditingAvailable`과 reason을 필수 게시한다. reconnect는 bootstrap 전체를 다시 수행하고 `DbConnectionMonitor` ping은 manifest가 허용한 phase에서만 실행한다. 로그인 직후 DAO, connection monitor/service, startup helper, schema/reference cache와 기존 `Object` DB API 전체 호출부를 owner/action/required phase/new API로 나열한 migration 표를 작성하고 구조 lint로 manifest 우회 호출을 금지한다.

parameter wrapper는 `logPolicy`를 wire schema에 포함한다. 저장 JSON, keyword/name, QR/나트륨/사용자 정의 문자열과 인증 정보는 `redacted`로 강제하고 `DbClient._debugPrintSql`, Windows ODBC formatter, DB-Lib/isolate logger 어느 계층에서도 literal 값, 부분 preview 또는 hash를 기록하지 않는다. wire envelope, transaction statement map, `statements[].params` 또는 임의 중첩 payload를 `toString`/JSON 전체 직렬화해 로그에 남기지 않는다. 재귀 key masking은 새 key를 놓칠 수 있으므로 로그 전용 metadata allow-list가 operation, statement count/index, parameter name, SQL type, null 여부, byte/code-unit length와 collection count만 새 객체로 구성한다. raw SQL text에 민감 literal을 넣는 것도 금지한다.

12.3 사용자 항목 저장 DAO

레거시의 행별 CRUD 의미는 유지하되 현재 프로젝트에서는 부분 저장을 허용하지 않는다. transaction 소유자는 기존 품목 저장과 동일하게 `DbClient.transaction()` 하나로 고정한다.

- SQL은 `SET XACT_ABORT ON`, `SET NOCOUNT ON`과 validation `THROW`를 포함한 단일 parameterized batch로 작성하되 batch 내부에 `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK`을 넣지 않는다.
- DAO는 해당 batch를 `DbClient.transaction([DbTransactionStatement(..., returnsRows: true, resultContract: customerColumnSaveResultContractV1(command))])` 한 문장으로 실행한다. 외부 transaction API와 SQL 내부 transaction을 중첩하지 않는다.
- transaction 첫 단계에서 공용 formatter가 만든 `label-manager:customer:{customerId}:cust-column` resource를 `sys.sp_getapplock @LockMode='Exclusive', @LockOwner='Transaction', @DbPrincipal='public', @LockTimeout=<공용값>`으로 획득한다. `EXEC @lockResult=sys.sp_getapplock`으로 받아 rowset을 만들지 않고 `-1` timeout, `-2` cancel, `-3` deadlock victim, `-999` parameter/권한 오류를 typed domain error로 구분한다. 현재 customer 원본 목록을 `UPDLOCK, HOLDLOCK`으로 재조회해 command concurrency fingerprint와 비교하고 불일치하면 전체 rollback한다.
- 같은 lock/transaction 안에서 최종 customer working set의 keyword를 대상 `RICH_KEYWORD` column collation과 trailing-space 의미로 다시 비교해 `(customerId, keyword)` 중복이 있으면 rollback한다. DB schema 변경이 허용되면 natural key unique index는 별도 배포 migration으로 추가하고, 추가하지 못하면 lock protocol에 참여하지 않는 레거시/외부 writer가 중복을 만들 수 있음을 운영 전제에 기록한다.
- 신규: `BM_RICH_CUST_COLUMN(RICH_CUSTOMER_ID, RICH_KEYWORD, RICH_COLUMN_NAME, RICH_TYPE)` insert
- 수정: 현재 customer ID와 custColumnId를 함께 조건으로 update
- 삭제: 현재 customer ID와 custColumnId를 함께 조건으로 delete
- 기대 affected row가 다르면 `THROW`하여 전체 rollback한다.
- SQL 문자열 보간을 사용하지 않는다. 현재 공용 DB API는 목록 parameter를 지원하지 않으므로 insert/update/delete DTO 목록을 명시적 Unicode large JSON parameter 하나 또는 소수로 전달하고 12.2의 raw scalar staging/validation을 적용한다.
- 최종 `SELECT`는 항상 정확히 1행이며 `RESULT_KIND='customer-column-save/v1'`, `SCHEMA_VERSION=1`, insert/update/delete count를 포함한다. 저장 건수가 모두 0이어도 marker 1행을 반환한다. result contract가 marker/schema/cardinality와 count 정수·command 기대값을 commit 전에 검증한다. `commitCompleted`와 frame 수신 뒤 wire envelope 또는 customer-column domain DTO 복원이 실패하면 stage가 있는 `DbCommittedResultInvalid(committedKnown: true)`로 분류하고 동일 command를 재실행하지 않는다. 이 경우 customer dictionary 전체 재조회만 허용하고 label-size session reload나 mapping 복구를 수행하지 않는다.

12.4 사용 항목 저장 transaction

레거시의 저장 범위를 유지하면서 동시성과 실패 처리를 보완한다.

1. `DbClient.transaction()`이 외부 transaction 시작
2. 공용 formatter의 `label-manager:label-size:{labelSizeId}:schema-content` resource를 `sys.sp_getapplock @LockMode='Exclusive', @LockOwner='Transaction', @DbPrincipal='public', @LockTimeout=<공용값>`으로 획득하고 return code를 typed domain error로 검증
3. 현재 labelSizeId와 기존 column ID의 소유권 및 concurrency fingerprint 검증
4. 신규 입력 JSON을 `ROW_NO`, `DRAFT_COLUMN_KEY`를 가진 table variable로 정규화하고, 각 행 insert의 `OUTPUT INSERTED.RICH_COLUMN_ID INTO @CapturedColumns` 결과를 같은 row의 draft key와 결합
5. 신규/기존 `BM_RICH_COL_MIN` upsert
6. 신규/기존 `BM_RICH_CHECK_COLUMNS` upsert
7. `ContentCreationOwnershipV1`이 `daoOwned`인 경우에만 신규 컬럼마다 해당 label size의 기존 `BM_RICH_ITEM`에 `BM_RICH_COL_CONTENT` 빈 값 insert. `triggerOwned`이면 trigger 결과의 정확한 key 집합/빈 값만 검증하고 DAO가 중복 insert하지 않음
8. 레거시 update 품목 테이블을 현 DB가 실제 사용하고 해당 ownership이 `daoOwned`이면 `BM_UPDATE_COL_CONTENT` 빈 값 insert. `triggerOwned`이면 검증만 수행하고 테이블/기능이 사용되지 않는다고 확인되면 근거를 문서화하고 제외
9. 기존 `BM_RICH_COLUMN` 전체 속성 및 최종 order update
10. `BM_GS1_COLUMN_INFO` upsert/delete
11. `BM_GS1_CONTAIN_COLUMN`을 최종 working copy 관계와 일치하도록 insert/delete
12. 삭제 대상의 status date 갱신 및 종속 데이터 정리 후 `BM_RICH_COLUMN` delete
13. 모든 affected row와 최종 order/keyword uniqueness 검증
14. batch marker가 있는 최종 `SELECT` 반환 후 `DbClient.transaction()`이 commit

저장 command의 insert/update/delete/GS1 관계 목록은 명시적 Unicode large JSON scalar parameter로 전달하고 12.2의 raw scalar staging/validation을 통과한 값만 대상 SQL 타입으로 변환한다. JSON payload가 4,000자를 넘는 정상 대량 저장도 잘리지 않도록 Windows ODBC, macOS DB-Lib와 Android/iOS native adapter 경로를 각각 검증한다.

신규 ID는 레거시 `SelectLastNRecord()` 방식으로 찾지 않는다. trigger와 driver의 결과셋 처리에 안전하도록 direct `OUTPUT` resultset을 중간에 노출하지 않고, 기존 품목 저장처럼 `ROW_NO` 순회 insert마다 `OUTPUT INSERTED... INTO`로 ID를 수집한 뒤 해당 `DRAFT_COLUMN_KEY`와 결합한다. 검증된 SQL Server `MERGE ... OUTPUT source.DRAFT_COLUMN_KEY, inserted.ID` 대안을 사용할 수 있지만 입력/출력 key 결합을 실행계획의 행 순서에 의존해서는 안 된다.

batch 외부의 최종 `SELECT`는 신규 0건/N건과 무관하게 항상 정확히 1행이며 `RESULT_KIND='label-column-save/v1'`, `SCHEMA_VERSION=1`, 저장 요약과 `MAPPING_JSON` 배열을 포함하고 `DbTransactionStatement.resultContract`에도 command의 count와 신규 draft key 집합을 전달한다. 신규가 없으면 `MAPPING_JSON=N'[]'`다. 모든 production adapter의 collector는 모든 결과셋을 끝까지 drain하고 각 결과셋의 고유 schema로 보존한다. transaction executor는 trigger/procedure의 중간 `SELECT`, rowcount-only 결과와 빈 결과를 건너뛰어 기대 marker/schema 결과셋과 marker row가 각각 정확히 하나인지 검사하고, `MAPPING_JSON` 구조/field type/key 집합/ID까지 commit 전에 검증한다. marker 중복/누락/0행/복수행/schema 또는 result contract 불일치는 rollback 가능한 pre-commit protocol error다. commit 정상 완료 후 Dart DAO는 이미 검증된 wire payload를 typed DTO로 복원하며 이 단계의 전송/decode 실패만 `DbCommittedResultInvalid(committedKnown: true)`다.

삭제 시 다음 테이블을 명시적으로 검토한다.

- `BM_RICH_COL_CONTENT`
- `BM_UPDATE_COL_CONTENT`
- `BM_RICH_COL_MIN`
- `BM_RICH_CHECK_COLUMNS`
- `BM_GS1_COLUMN_INFO`
- `BM_GS1_CONTAIN_COLUMN`의 `MAIN_COLUMN_ID`와 `CONTAIN_COLUMN_ID` 양쪽 관계
- `BM_COLUMN_QRCODE_INFO`의 `RICH_COLUMN_ID`와 `RICH_COLUMN_TARGET_ID` 양쪽 관계
- `BM_RICH_STATUS_DATA.RICH_COLID_CHANGE_DELETE_DATE`
- 최종 `BM_RICH_COLUMN`

transaction 실행 전 또는 capability cache 초기화 시 `sys.tables`, `sys.columns`, `sys.foreign_keys`, `sys.triggers`로 실제 배포 스키마를 확인한다. `BM_RICH_COL_CONTENT`와 update content는 trigger 활성 상태/정의 hash, statement-level `inserted` 전체 집합 처리, label-size별 order 비변경, DAO 생성 여부와 unique key를 함께 판정해 `ContentCreationOwnershipV1`의 단일 주체를 확정한다. 저장소의 레거시 `AFTER_INSERT_COLUMN`과 동등한 정의는 `triggerOwned`가 될 수 없으며, 해당 trigger가 활성 상태면 편집기 진입을 차단하고 승인 migration으로 비활성화/교체한 뒤 `daoOwned` 또는 검증된 새 trigger를 사용한다. trigger와 DAO가 동시에 생성하거나 trigger 정의/주체를 판정할 수 없으면 진입을 차단한다. FK cascade에 암묵적으로 의존하지 않는다. 실제 cascade가 확인되면 중복 delete를 피하되 DAO 테스트에 그 전제를 기록한다.

QR/기본 사용자 정의 참조의 source of truth는 `RICH_NATRIUM_JOIN_STRING`, `RICH_USER_DEFINE_QRDATA`, `RICH_USER_DEFINE_QRTEXT` 안의 구조화된 token이다. 편집기와 실제 출력 `ItemCodeDataResolver`가 같은 공용 V1 parser/replacer를 사용한다. V1 token은 `#`와 저장 keyword의 ordinal case-sensitive exact 조합이며 identifier boundary를 요구한다. `#품목`, `#ITEMNAME`은 예약 token으로 먼저 판정하고 동일 keyword 생성을 금지한다. token을 길이 우선 순차 `replaceAll`로 처리하지 않으며 `#ABC`는 `#ABCD`와 일치하지 않는다. 기존 포맷에는 grammar version/escape가 없으므로 literal token escape를 조용히 추가하지 않고 V1 제한으로 명시한다.

나트륨 V1은 레거시와 같이 `/`로 구분된 정확히 6개 record와 record 내부 첫 `-` 구분을 사용한다. name/keyword에 `-`, `/`를 허용하지 않고, URL percent-encoding은 token grammar와 별도 fixture로 레거시 결과를 고정한다. 이번 기능에서는 참조 token 자동 rewrite를 구현하지 않고 참조 대상 키워드 변경/삭제를 먼저 차단한다.

`BM_COLUMN_QRCODE_INFO`는 레거시 DAO가 존재하지만 활성 항목 편집 저장 경로에서 insert/update 사용이 확인되지 않았으므로 기본 계약에서는 authoritative 관계나 upsert 대상으로 간주하지 않는다. capability 및 실제 운영 데이터 조사로 사용 주체가 확인되기 전에는 삭제 컬럼의 orphan 방지 cleanup만 수행한다. 사용 중인 정식 관계로 확인되면 별도 조회/working relation/upsert 계약과 migration 테스트를 추가한 뒤 사용한다.

삭제는 status date를 먼저 갱신한 뒤 non-cascade child를 정리하고 `BM_RICH_COLUMN`을 마지막에 삭제한다. `BM_GS1_CONTAIN_COLUMN`은 삭제 컬럼이 source/main인 경우와 target/contain인 경우를 모두 정리하고, `BM_COLUMN_QRCODE_INFO`는 위 cleanup-only 정책에 따라 양쪽 orphan을 제거한다. `BM_UPDATE_ITEM`/`BM_UPDATE_COL_CONTENT`가 배포 DB와 현 프로젝트에서 사용되는지 capability로 확인하고, 존재하면 신규 빈 content 생성과 삭제 정리를 필수 transaction 단계로 수행한다.

`BM_RICH_COL_MIN`은 일반 컬럼 행뿐 아니라 label size별 `ELEMENT` sentinel 행을 사용하는 레거시 경로가 있다. 레거시의 `RICH_COLUMN_ID=''`/`'0'` 혼용을 애플리케이션 변환에 맡기지 않고 실제 SQL 타입과 운영 분포 fixture로 canonical sentinel predicate를 확정한다. predicate는 labelSizeId, sentinel column-ID 표현과 `RICH_KEYWORD='ELEMENT'`를 함께 사용하고 일반 컬럼 keyword만으로 sentinel을 판정하지 않는다. `''`/`0` 혼재, 중복 또는 predicate 불명확 데이터는 자동 정리하지 않고 진입 차단 또는 승인 migration 대상으로 둔다. `RICH_MIN_CHECK`는 이번 라벨 항목 편집기 UI에 노출하거나 수정하지 않는다. 기존 일반 행과 기존 sentinel은 raw 원본 값을 보존하고 update SQL에서 이 column을 제외한다. 신규 일반 행과 sentinel이 없어서 새로 만드는 canonical sentinel만 `RICH_MIN_CHECK=0`으로 생성한다. 신규/수정/삭제 후 sentinel을 정확히 1개 유지하며, 일반 컬럼의 keyword/name/order만 최종 working copy와 동기화한다.

누락 키워드 검사의 source of truth는 `BM_RICH_CHECK_COLUMNS.RICH_CHECK_YN`으로 확정한다. main table에 legacy `RICH_USE_MISSING_KEYWORD_CHECK`가 있으면 같은 transaction에서 동일 값으로 동기화한다. 두 값이 불일치한 기존 행은 조회 시 check table 값을 우선하고, 저장 후 두 값이 일치하도록 보정한다.

문자열 SQL 직접 결합, 마지막 N개 행 재조회, transaction 밖 보조 테이블 저장, 실패를 삼키는 void API를 사용하지 않는다. DAO는 성공 결과 또는 예외를 호출자에게 반환해야 한다.

13. 공용 테이블 확장 원칙

현재 `SwipeActionTable`에 필요한 API가 없으면 라벨 항목 다이얼로그 안에서 gesture/table을 다시 구현하지 말고 공용 위젯을 최소 확장한다.

다음 공용 확장은 구현 필수 계약이다. 이름은 기존 API 스타일에 맞게 조정할 수 있지만 같은 타입 안전성과 lifecycle을 제공해야 한다.

- 행/열 헤더 교차 영역을 구성하는 `cornerBuilder`
- index 대신 안정 identity를 반환하는 `rowKeyBuilder`
- `LabelColumnDragPayload`처럼 source table, stable row key, item kind를 담는 typed external drag payload builder
- typed payload를 받는 external drop target와 drag enter/leave/drop lifecycle callback
- row drag 시작/종료 callback. 삭제 hover/취소/성공 시 시각 상태를 모두 정리한다.
- 편집 mode의 타입별 cell builder/dropdown cell
- table enabled 상태에서도 선택 표시를 유지하는 read-only mode

내부 reorder payload와 외부 add/delete payload를 `int` index 하나로 공유하지 않는다. `normal`에서는 외부 add/delete drag만, `reorder`에서는 같은 테이블 내부 reorder만 활성화하고, `userItemEdit`에서는 사용자 후보 전용 add/delete/reorder gesture만 활성화한다. disabled 영역은 drop을 수락하지 않으며 drag payload의 labelSize/customer/session identity가 현재 dialog와 다르면 거부한다.

기존 라벨 설정, 브랜드 설정, 품목 순서 변경 동작을 깨지 않도록 새 옵션 기본값은 현재 동작을 유지해야 한다. 공용 위젯 변경에는 기존 `test/swipe_action_table_test.dart` 회귀 테스트를 반드시 추가한다.

14. 오류, 동시성, 재진입 처리

- dialog open 중 동일 버튼을 다시 눌러 중복 overlay를 만들지 않는다.
- 조회 중에는 loading 상태와 닫기 정책을 명확히 하고 빈 목록을 정상 조회 실패로 오인하지 않는다.
- DB 연결 실패는 진행 표시를 닫은 뒤 경고 dialog로 알리고 사용자의 working copy를 유지한다.
- 저장 command는 generation 또는 in-flight Future로 중복 실행을 막는다.
- 저장 중 dialog close, mode 전환, drag/drop, 행 선택을 막는다.
- 저장 성공 후 상위 widget이 dispose됐으면 setState하지 않되 DAO transaction 결과는 유실하지 않는다.
- 저장 시작 전 coordinator가 opaque random operation ID와 durable operation phase를 기록한다. dialog/HomePageManager dispose는 UI만 detach하며 in-flight Future를 취소하거나 commit 결과를 폐기하지 않는다. `LabelColumnSaveRecoveryRegistry`가 success/unknown/committed-invalid와 reload 필요 상태를 인수한 뒤 coordinator를 정리한다. registry record에는 raw save JSON/QR/사용자 문자열, original/desired projection과 content-derived command fingerprint/hash를 저장하지 않고 operation ID, `stableDatabaseIdentityDigest`, 비민감 resource key/context, phase와 recovery reason만 저장한다. 같은 프로세스 reconciliation에 필요한 fingerprint/projection은 coordinator memory에만 둔다.
- recovery registry는 journal과 같은 공용 crash-safe record primitive를 사용해 schema version, checksum, owner token, phase, lease와 완료 tombstone을 target/tmp/bak에 기록한다. Windows named mutex, macOS의 승인 advisory/process lock, Android/iOS의 app-container 단일 writer primitive를 `PlatformDbExecutionCapabilityV1`과 gate에서 고정하고 stale lease 인수 규칙, 원자 교체, startup directory scan, artifact 선택·격리 규칙을 플랫폼별 fault-recovery matrix로 검증한다. SharedPreferences hint와 메모리 map은 source of truth가 아니다.
- durable phase는 코드와 테스트가 공유하는 `RecoveryTransitionTableV1` checked-in descriptor를 source of truth로 삼는다. V1 state/event/reject reason은 확장 가능한 문자열이 아니라 versioned closed enum이다. state는 최소 `preparedDurable`, `dispatchIntentDurable`, `operationAcceptedDurable`, `commitDispatchIntentDurable`, `commitDispatchObservedDurable`, `commitCompletedDurable`, `resultFrameSendCompletedDurable`, `resultFrameFullyReceivedDurable`, `wireEnvelopeDecoded`, `wireEnvelopeDecodeFailedDurable`, `domainDtoDecoded`, `domainDtoDecodeFailedDurable`, `preCommitFailedTerminal`, `preCommitCleanupPending`, `commitOutcomeUnknown`, `desiredObservedReloadPending`, `originalObservedAcknowledgementPending`, `indeterminateAcknowledgementPending`, `committedReloadPending`, `committedResultInvalid`, `mappingRecoveryReloadPending`, `customerDictionaryReloadPending`, `customerDictionaryReloadFailed`, `customerCommittedResultInvalid`, `restartManualAcceptanceRequired`, `userAcknowledged`, `reloadVerifiedAutoClose`, `tombstonePending`, `tombstoned`, `quarantined`를 폐쇄 열거한다. event는 prepare/publish dispatch intent 성공·실패, cumulative worker ACK 수신, stale/duplicate/invalid ack, parent frame 완전 수신, IPC partial-send/decode 실패, commit dispatch intent publish, wire envelope decode 성공·실패, domain DTO decode 성공·실패, pre-commit cleanup verified/unknown, connection lost/worker exit/native timeout, lease lost, identity mismatch, startup artifact selected/corrupt/quarantined, reconnect/shutdown, desired/original/indeterminate observation, reload start/success/failure/retry, user accept/cancel, tombstone publish 성공·실패를 폐쇄 열거한다. 각 행은 `(resourceKind, from, event, payloadSchema, orderedGuards, to, durablePublish, resourceBlocked, allowedActions)`를 가지며 `resourceKind=labelColumn | customerColumn`과 모든 nonterminal state/event 조합은 정확히 한 transition 또는 typed reject를 반환한다. guard는 descriptor 순서대로 평가하고 reject는 side effect가 없다. worker high-watermark와 parent/DAO local evidence는 서로 독립된 monotonic evidence로 durable 저장하고 전이 상태는 그 결합으로 계산한다. prerequisite보다 먼저 온 유효 future-stage local event는 destructive reject하지 않고 pending evidence로 보존해 prerequisite ACK/event 수용 후 재평가한다. cumulative worker ACK는 더 높은 유효 high-watermark를 수용하고 낮은 후착 ACK를 canonical payload에 따라 idempotent stale 또는 typed reject로 분류하며, parent barrier인 `commitDispatchIntentDurable`을 함의하지 않는다. header만 수신했거나 payload가 짧은 EOF/partial frame은 `resultFrameFullyReceivedDurable`로 전이하지 않는다. `dispatchIntentDurable`은 최초 DB request 전 barrier이고 `commitDispatchIntentDurable`은 native commit command 전 barrier다. 이미 시작한 native 경계를 parent durable publish 완료까지 되돌리거나 정지할 수 있다고 가정하지 않는다. ACK/local-event publish 실패는 마지막 성공 durable evidence와 resource block을 유지한다. `preCommitFailedTerminal`은 commit intent가 없고 result drain/cancel, rollback과 같은 session의 `@@TRANCOUNT=0`이 모두 확인된 경우에만 허용한다. 하나라도 불명확하면 `preCommitCleanupPending`으로 resource를 계속 차단한다. descriptor에서 resourceKind별 V1 Cartesian matrix와 ACK/local-event 양방향 재정렬 기대 결과 fixture를 생성하고 각 상태의 terminal publish 완료 후에만 coordinator를 dispose한다.
- startup은 DB 연결 전 namespace-neutral root의 전체 artifact 무결성과 digest directory 형식만 스캔하는 `storageReady`와 검증된 현재 `DatabaseIdentity` namespace를 bind하는 `identityReady`를 분리한다. registry owner는 `HomePage`/로그인 subtree가 아니라 `MaterialApp` 위 앱 bootstrap service로 고정하고 `storageReady → databaseIdentity bind → login context attach → logout detach` lifecycle을 가진다. logout은 operation을 삭제하지 않고 identity/resource barrier를 유지하며 다음 identity나 로그인 context에 record를 재사용하지 않는다. `connectionProfileHint`는 후보 탐색만 돕고 authoritative barrier가 아니다. directory, target/tmp/bak record key, mutex와 resource barrier는 연결 후 계산한 `stableDatabaseIdentityDigest/resourceKind/resourceId/operationId`로 namespace한다. identity가 다른 record는 현재 DB를 차단하거나 tombstone하지 않고 해당 unresolved namespace에 보존한다. 각 operation 안에서는 checksum, owner token과 durable publish sequence로 authoritative target/tmp/bak artifact 하나를 결정한다. 동일 identity/resourceKind/resourceId에 unresolved operation이 복수면 wall-clock이나 file mtime으로 하나를 고르지 않고 모두 보존하며 resource barrier는 모든 unresolved operation의 합집합으로 계산한다. commit 확정/committed-invalid operation은 낮은 phase operation보다 우선해 차단하고, 서로 모순되는 operation은 격리하되 resource 차단을 유지한다. DB 연결 상태는 `disconnected → transportConnecting → transportConnected(epoch) → identityProbing → recoveryBinding → ready` 또는 identity 검증 실패의 `degradedReady`로 고정한다. 일반 DB action 허용은 `DbActionRequirementV1`으로만 판정한다. 현재 identity의 `identityReady` 전에는 항목 편집 진입과 save service를 차단한다. 미완료 record가 있으면 해당 customer/label-size resource만 `recovery-blocked`로 유지하고 다른 resource는 허용한다.
- startup recovery는 각 unresolved operation의 가장 높은 유효 durable evidence와 `resourceKind`를 평가하고 resource barrier는 그 결과를 합성한다. `preparedDurable`에서 DB dispatch intent가 없으면 미실행 확정으로 tombstone하고, `preCommitFailedTerminal`은 실패 확정으로 종료한다. `dispatchIntentDurable`부터 `operationAcceptedDurable`까지 commit intent가 없으면 fresh connection의 cleanup/reload 증거가 전이표를 만족할 때만 실패 확정하며 그렇지 않으면 `preCommitCleanupPending`으로 차단한다. `commitDispatchIntentDurable` 또는 `commitDispatchObservedDurable` 이후 `commitCompletedDurable` 전 종료만 `commitOutcomeUnknown`으로 분류한다. `wireEnvelopeDecodeFailedDurable | domainDtoDecodeFailedDurable` 자체를 해당 stage의 authoritative failure evidence로 사용해 파생 `committedResultInvalid | customerCommittedResultInvalid` publish 전 crash라도 stage/resourceKind의 committed recovery UI로 복원한다. `wireEnvelopeDecoded | domainDtoDecoded` 뒤 파생 reload 상태 publish 전 crash이거나, `commitCompletedDurable | resultFrameSendCompletedDurable | resultFrameFullyReceivedDurable`만 있고 명시적 decode evidence가 없으면 stage를 추정하지 않고 commit 확정 resource별 reload-only로 이동한다. label-column은 전체 label-size DB reload와 candidate session handoff를 수행하고, customer-column은 customer dictionary 전체 재조회만 수행하며 label-size session reload, mapping 복구와 candidate generation swap을 typed reject한다. recovery artifact에 result payload를 저장하지 않으므로 재시작 후 decode를 반복하지 않는다. 같은 프로세스에서 original/desired projection과 mapping payload를 보유한 label-column coordinator만 reconciliation 또는 mapping 복구를 수행한다. 재시작 후 `commitOutcomeUnknown`, 손상/알 수 없는 artifact처럼 durable 증거만으로 결과를 확정할 수 없는 상태만 `restartManualAcceptanceRequired`로 전환하며, resource별 현재 DB 상태를 reload한 뒤 UI가 `이 작업의 반영 여부를 판정할 수 없으며 현재 DB 상태를 수용하면 차단을 해제합니다.`라고 명시하고 사용자가 수용한 경우에만 tombstone한다. 수동 수용은 성공/실패 판정이나 mapping 복구로 기록하지 않는다. 다른/unresolved identity artifact는 기본 무기한 보존하고 자동 삭제하지 않으며 관리자 진단 목록과 명시적 archive/delete 절차로만 정리한다.
- `LabelColumnSaveCommand`는 dialog open 시점의 기존 컬럼, `BM_RICH_COL_MIN` 일반/sentinel 행, `BM_RICH_CHECK_COLUMNS`, GS1 정보/포함 관계 및 저장 batch가 변경하는 child 상태의 `concurrencyFingerprint`와 목표 `desiredObservationProjection`을 필수로 가진다.
- application lock 참여 writer는 prose의 최소 목록이 아니라 `DbWriterManifestV1`을 source of truth로 폐쇄 관리한다. 초기 manifest에는 `LabelColumnSaveDAO`, `ItemManagerSaveDAO`, `ItemDAO.updateOrders`, `ItemDAO.updateElementSheetByItemId`, `ItemDAO.autoMigrateElementSheetByItemId`, label-size delete뿐 아니라 같은 session의 form/name/size/preview 입력을 변경하는 모든 `LabelSizeDAO` writer를 실제 SQL target 기준으로 열거한다. 각 writer는 resource kind/ID resolver, customer→label-size→form의 전역 lock 순서, required session invalidation과 허용 transaction API를 가진다. AST/SQL 구조 lint는 manifest에 없는 column/item/content/label-size/form writer를 production build에서 거부한다. 공용 `LabelSizeLockedTransaction.run(labelSizeId, statements)` 또는 동등 API는 `DbClient.transaction()`과 같은 native session/transaction의 첫 statement에 lock 획득을 삽입하고 이후 statement만 실행한다. 참여 writer는 이 API만 사용하며 SQL 내부 `BEGIN/COMMIT/ROLLBACK TRANSACTION`과 단독 `writeDataWithParams()`를 사용하지 않는다. 품목 ID만 받는 API는 labelSizeId를 immutable parameter로 받도록 signature를 변경하고 lock 내부에서 item 소유권도 재검증한다.
- 모든 참여 writer는 어떤 대상 row/range lock보다 먼저 공용 formatter, DB principal, timeout을 사용해 application lock을 획득한다. 여러 resource가 필요하면 customer→label-size의 전역 순서를 고정한다. 컬럼 구조 save는 lock 획득 후 대상 label size의 기존 행과 mutation-closure 관계를 `UPDLOCK, HOLDLOCK`으로 다시 읽어 concurrency fingerprint를 계산하며, 원본과 다르면 어떤 update/delete도 실행하지 않고 conflict로 rollback한다. `sp_getapplock`의 `-1/-2/-3/-999` 및 SQL `THROW` error number는 driver/isolate/client wire schema를 통과해 timeout/cancel/deadlock/configuration typed 오류로 복원한다.
- application lock은 이 protocol을 사용하는 writer 사이에서만 유효하다. 레거시 앱, trigger, 외부 stored procedure처럼 lock을 사용하지 않는 writer가 운영 중이면 실제 item/content/column range에 필요한 `UPDLOCK, HOLDLOCK`과 FK/trigger 동작을 함께 검증하고, 공통 protocol 적용 또는 운영상 배타 조건 없이는 동시성 완료로 판정하지 않는다. row version 컬럼이 실제 스키마에 있으면 fingerprint 대신 또는 함께 사용할 수 있다.
- typed query/transaction은 `execute → 모든 result set complete drain → result contract validate → commit` 순서를 지킨다. 같은 Dart isolate에서 동기 FFI를 실행하는 동안 cancel 메시지를 처리할 수 있다고 가정하지 않는다. desktop worker와 Android service/process는 native DB state를 실행 경계 내부에만 소유하고 앱/parent는 opaque `sessionId`/`operationId`만 관리한다. iOS는 native driver와 cancel control thread를 분리하고 transaction capability gate가 확인한 session discard만 허용한다. ODBC에는 검증된 `SQLCancelHandle`/`SQLCancel`, DB-Lib에는 검증된 `dbcancel`과 필요한 `dbcanquery`/`dbfreebuf`를 binding한다. hard-kill을 지원하는 경계가 deadline 내 응답하지 않으면 해당 worker/service process를 종료해 강제 폐기하고, hard-kill이 없는 iOS는 deadline cancel/session discard fixture를 통과하지 못하면 기능을 시작하지 않는다. process/service command와 cancel/control channel은 분리하고 header magic/schemaVersion/messageKind/sessionId/operationId/payloadLength를 가진 length-prefix frame을 사용한다. protocol 상수는 command `maxFrameBytes=67108864`, control `maxFrameBytes=65536`, 세션당 `maxInFlightSqlOperations=1`로 고정한다. byte order, field width, header length, allocation 전 payload length 검사, sequence/duplicate 규칙과 부분 frame/EOF/crash/timeout 결과를 byte-level fixture로 고정한다. credential은 OS별 제한 채널로 한 번만 전달한다. desktop은 명시적으로 상속한 anonymous pipe 또는 제한 ACL named pipe, Android는 app UID와 binder identity가 검증된 bootstrap call, iOS는 앱 credential provider에서 native adapter로 process 내부 전달하며 command line, 환경변수, stdout/stderr, disk와 로그를 금지한다. spawn nonce/process 또는 service identity handshake와 bootstrap ack 뒤 credential channel 폐쇄를 필수로 한다. native mutable buffer는 사용 후 zeroize하되 immutable Dart `String`의 완전한 zeroization을 보장한다고 주장하지 않는다. Windows는 Job Object kill-on-close, macOS는 동등한 parent-death/orphan 방지, Android는 service/process death 관측을 gate로 검증한다. drain/contract/statement 실패 시 `cancel → remaining results drain/free → rollback → @@TRANCOUNT=0 확인` 결과를 구조화한다. cancel/session cleanup 증거가 없으면 먼저 `acceptingCommands=false`로 바꾸고 native session/execution boundary를 tainted 폐기한다. 같은 epoch request를 실행하거나 tainted session에서 후속 SQL을 실행하지 않는다.
- 로그는 operation/trace, labelSizeId, customerId, insert/update/delete 개수, mode 전환, 성공/실패와 redacted parameter의 type/length/count만 기록한다. 키워드 본문, 사용자 정의 QR 데이터, 비밀번호 등 실제 payload와 부분 preview/hash는 `DbClient`, isolate, ODBC, DB-Lib 어느 계층에서도 기록하지 않는다.
- 로그는 상태 관찰용이며 저장 여부나 분기를 결정하는 비즈니스 로직으로 사용하지 않는다.

15. 권한과 진입 조건

- 선택된 label size가 없으면 `항목 편집` 버튼을 비활성화한다.
- 공용라벨관리 탭 접근 권한과 컬럼 구조 변경 권한을 의미상 구분한다. `canManageCommonLabelColumns`의 초기 등급 matrix는 `SYSTEM_ADMIN_USER=true`, `COOP_ADMIN_USER=true`, `MANAGER_USER=true`, `CLIENT_USER=false`로 확정한다. 현재 `canManageItemStructure`와 결과가 같더라도 별도 getter와 테스트로 업무 권한 의미를 고정한다.
- 버튼 표시와 callback 진입은 `canManageCommonLabelColumns`를 사용하고, save service는 dialog open 때 캡처한 immutable user/customer/market context와 저장 직전 현재 로그인 context를 비교한다. DAO 자체의 전역 `User.instance` 확인을 보안 경계로 사용하지 않는다. SQL은 customer/label-size 소유권과 affected row를 강제하며, 더 강한 보안 경계가 필요하면 DB 권한 또는 stored procedure를 별도 배포한다.
- 품목관리 draft dirty/command busy/force-reload-required, 강제 reload, 공용라벨 저장 등 충돌 가능한 상위 상태에서는 진입을 차단하고 이유를 안내한다. DB bootstrap이 `ready`가 아니거나 현재 DB identity에 대한 `LabelColumnSaveRecoveryRegistry.identityReady` 전이거나 현재 customer/label-size resource에 미완료 recovery record가 있으면 편집 진입과 save service를 모두 차단한다. transport 연결만으로 `status.up`을 게시하지 않으며 recovery record가 있으면 강제 reload·사용자 확인 경로만 제공한다.
- dialog를 열 때 labelSizeId, customerId, marketId, 현재 column cache generation을 immutable input으로 전달한다. 열린 뒤 상단 dropdown 값에 다시 의존하지 않는다.
- open 직전 선택 context와 현재 로드된 label-size 세션의 customer/market/labelSize가 모두 일치하는지 확인한다. 저장 직전에도 권한과 context generation을 재검증하며 불일치하면 DB를 쓰지 않는다.

15.1 저장 후 session consumer 계약

- 레거시 `CLabelEditModel`, `CScalePrintModel`, `CUpdateItemModel`, `CLabelPrintModel`의 `OnCommonLabelColumnChange()` 구현을 `LabelSizeSessionConsumerManifestV1`의 근거로 사용한다. 단순 observer callback 호출 자체를 복제하지 않고 각 소비 효과가 새 generation에 귀속되도록 한다.
- 품목 편집 소비자는 DB 컬럼/콘텐츠로 동적 column을 재구성하고 기존 stable item ID 기준 선택을 복원하며 현재 행의 RTF가 비어 있거나 column schema가 바뀌었으면 새 session 입력으로 재생성한다.
- update-item 소비자는 update column/content를 새 generation으로 재조회해 table column을 재구성한다. scale 소비자는 레거시 `CScalePrintModel`의 table rebinding 효과만 기본 계약으로 삼고 preview clear/recompute를 자동 추가하지 않는다. 공용라벨/현 프로젝트 preview·validation 소비자는 현재 static cache 의존을 session accessor로 옮기는 데 필요한 invalidate/recompute를 별도 manifest 항목으로 명시한다. 레거시 `CLabelPrintModel` no-op consumer에는 근거 없이 부작용을 추가하지 않는다.
- 각 consumer 호출은 crash/ACK 유실 복구를 위해 at-least-once일 수 있다. consumer는 `(consumerId, expectedOldGeneration, newGeneration, context)`를 검증하고 `(stableDatabaseIdentityDigest, customerId, marketId, labelSizeId, consumerId, newGeneration)` 기준으로 재호출해도 같은 최종 상태를 만드는 idempotent apply를 수행한 뒤 `renderReady` 또는 typed failure를 반환한다. `expectedOldGeneration`은 transition guard이며 멱등 identity에는 넣지 않는다. 완료 acknowledgement는 같은 composite key로 durable manifest에 기록하고 duplicate ACK는 canonical payload가 같을 때만 허용하며 context가 다르면 typed reject한다. exactly-once 보장은 함수 호출 횟수가 아니라 새 generation에 귀속된 최종 관측 상태와 old resource의 단 한 번 dispose에 적용한다. handoff는 manifest의 필수 consumer acknowledgement가 모두 새 generation을 관측한 뒤에만 성공하며 그 전에는 old resources를 dispose하지 않는다.

16.3 DAO/transaction 테스트

- 고정 분류/후보 및 customer scoped 사용자 후보 조회
- 고정 후보가 필수 `RICH_FIX_COLUMN_ID` stable key와 ID 순서를 사용하고, 사용 항목이 `RICH_COLUMN_ORDER, RICH_COLUMN_ID` 순서로 재현됨
- 사용자 항목 insert/update/delete가 한 transaction으로 commit
- 사용자 항목 중간 실패 전체 rollback
- 사용자 항목 customer-scoped lock/fingerprint 일치 저장과 동시 변경 conflict rollback
- 신규 column ID가 source draft key에 정확히 매핑
- `DbClient.transaction()` 단독 transaction 소유와 SQL 내부 transaction 문구 부재
- Windows ODBC, macOS DB-Lib와 Android/iOS native adapter 각각에서 `DbNvarcharMax`/동등 타입, raw scalar staging과 명시적 target 타입 변환, 한글, 작은따옴표, 4,000자 초과 batch 전달
- DB-Lib `SYBNVARCHAR` binding의 byte/code-unit 길이와 ODBC Unicode 길이 회귀 테스트
- typed `queryResultSets`가 단일 batch/transaction의 모든 결과셋을 고유 schema로 drain하고 rowset kind/version 또는 고정 ordinal contract로 raw snapshot을 반환하며 기존 `Object` compatibility API를 사용하지 않음
- ODBC, DB-Lib와 Android/iOS native type이 동일 `DbLogicalType`/column metadata로 정규화되고 nullable/수치 metadata의 `unknown`/`notApplicable`이 실제 null/0과 구분되며 marker의 명시적 `CAST`와 result contract가 driver native code나 미지원 metadata 추정에 의존하지 않음
- 모든 production adapter의 integer 경계, 고정 scale decimal, datetime precision/timezone, binary와 DB null이 같은 `DbWireScalar` round-trip 및 canonical projection을 만들고 decimal이 `double`로 변환되지 않음
- 모든 production adapter가 모든 결과셋을 고유 schema로 drain하고 기대 `RESULT_KIND`/`SCHEMA_VERSION` marker 결과셋 하나만 반환
- trigger 중간 `SELECT`, rowcount-only/빈/marker 중복·누락 결과가 최종 결과로 오인되지 않음
- marker/schema 누락·중복과 count 불일치, malformed mapping JSON, mapping field type 오류, draft key 누락/초과, key/ID 중복·0/음수 ID는 result contract의 commit 전 protocol error로 rollback됨
- `NativeDbTransactionSession`이 하나의 native connection에서 begin/executeAndDrain/commit/rollback/verify/discard를 수행하고 일반 `writeData()`로 transaction 제어 SQL을 보내지 않음
- operation accepted/commit dispatch intent/commit dispatch observed/commit completed/result frame send 완료/parent frame receive 완료/wire envelope decode/domain DTO decode 각 경계의 crash·EOF·partial frame이 단일 오류 상태로 분류되고 `commitCompleted` 증거 없는 오류는 `DbCommittedResultInvalid`가 되지 않음. worker send 완료만으로 parent receive 완료를 게시하지 않으며 length/checksum/ID 검증 뒤에만 `resultFrameFullyReceivedDurable`이 됨. control/result channel 재정렬과 중간 ACK 유실에서 높은 cumulative ACK를 수용하고 낮은 후착 ACK는 idempotent stale/typed reject로 결정적으로 분류하며, ACK보다 먼저 온 local decode evidence는 pending 보존 후 재평가됨
- marker 결과셋과 marker row가 각각 정확히 1개이고 신규 0건은 `MAPPING_JSON=[]`, N건은 같은 1행의 배열로 전달됨
- `DbNvarcharMax`/statement/result contract/result-set contract/result/logical metadata/wire scalar/typed lock·discard error의 isolate `toMap/fromMap` version round-trip, 알 수 없는 version 실행 전 차단, 모든 production adapter의 native error number/state 보존
- connect/reconnect/disconnect/connection loss/isolate 재생성/DB identity 변경에서 capability와 `TColumnType` cache가 올바른 epoch로 폐기·재조회됨
- connect envelope는 아직 생성되지 않은 새 epoch를 요구하지 않고 `connectAttemptId`/`expectedPreviousEpoch`를 검증하며, 성공 응답부터 발급된 epoch를 bootstrap/일반 request가 사용함. 겹친 connect의 오래된 응답은 SQL readiness와 cache owner를 덮지 않음
- `disconnected → transportConnected(epoch) → identityProbing → recoveryBinding → ready | degradedReady` 전이에서 폐쇄 목록의 bootstrap request만 특권 실행되고 `DbActionRequirementV1`이 각 일반 action의 phase/authoritative identity/cache/write 요구를 강제함. degradedReady는 manifest allow-list 외 action과 모든 write/label-session load/항목 편집/recovery bind를 차단함
- bootstrap 이후 모든 일반 DB request의 connection epoch가 dequeue/driver 실행 전 검증되고 taint 당시 epoch로 queue된 request는 SQL 실행 없이 `DbConnectionDiscarded`로 실패하며 새 native connection 성공 후에만 새 epoch 요청이 허용됨
- `DbClient.isConnected` 신규 사용 금지와 startup/connection service/monitor/로그인 초기 DAO/cache 호출부 migration 표가 구조 lint를 통과하고 privileged bootstrap send port가 일반 DAO에 노출되지 않음
- redacted save parameter와 임의 깊이 `statements[].params`가 `DbClient`, isolate, ODBC, DB-Lib 로그에 값/preview/hash 또는 중첩 payload 직렬화 없이 metadata allow-list의 name/type/length/count로만 기록됨
- ROW_NO/draft key 기반 mapping과 mapping key/ID 유일성 검증
- `ContentCreationOwnershipV1`이 trigger-owned/DAO-owned 생성 주체를 정확히 하나 선택하고 각 주체가 신규 column의 기존 item/update-item content를 중복 없이 정확히 한 번 생성함. 혼합·미승인 trigger hash·불명확 주체는 진입 차단됨
- 레거시 `AFTER_INSERT_COLUMN` 동등 trigger는 definition hash가 알려져 있어도 statement-level `inserted` 전체 집합을 처리하지 않고 전역 order를 변경하므로 `unsupported`이며 활성 상태에서 편집 진입이 차단됨. 검증된 set-based trigger 또는 DAO 단일 주체만 허용됨
- update가 전체 속성과 order 및 보조 테이블 반영
- delete가 content/check/min/GS1/QR 관계/status/main row를 순서대로 정리
- GS1 contain 관계의 양쪽 참조 정리
- QR target 관계의 source/target 양쪽 참조 정리
- 운영 SQL 타입/분포로 확정한 canonical `BM_RICH_COL_MIN` sentinel predicate가 `''`/`0` 혼재·중복·일반 `ELEMENT` keyword를 오분류하지 않고 insert/update/delete 뒤 sentinel을 정확히 1개 유지함
- 기존 일반/sentinel `RICH_MIN_CHECK`는 저장 전후 동일하고 신규 행만 0임
- `IndexPredicateRequirementV1`이 모든 save/snapshot/reconciliation `queryId`를 열거하고 key/include/filter/enabled/hypothetical/collation과 권한을 판정함. manifest 누락·schema 부적합은 runtime fail-closed, 권한 부족은 별도 reason이고 실행 계획 변화만으로 runtime 허용 상태가 바뀌지 않음
- concurrency fingerprint 일치 저장과 동시 변경 conflict rollback
- 컬럼 구조/품목 저장/품목 순서/element update·migration/라벨 크기 삭제가 공용 locked transaction API만 사용하고 같은 label-size application lock을 row lock보다 먼저 같은 connection/transaction에서 획득함
- 참여 writer에 SQL 내부 transaction 또는 단독 `writeDataWithParams()` 사용이 없고 item 기반 writer가 전달받은 labelSizeId 소유권을 lock 내부에서 검증함
- `sp_getapplock` timeout/cancel/deadlock/configuration return code가 모든 production adapter와 isolate/service 경계를 지나 typed error로 구분됨
- 중간 단계 실패 전체 rollback
- affected row 0 또는 identity 소유권 불일치 시 rollback
- commit 전 저장 실패가 UI working copy를 지우지 않고 재시도를 허용함
- `DbCommitOutcomeUnknown`이 save 재실행을 차단하고 desired/original/indeterminate 3상태로 reconciliation하며 실제 commit 여부를 단정하지 않음
- `DbCommittedResultInvalid(committedKnown: true)`은 commit 여부 reconciliation이나 save 재실행으로 이동하지 않음. 같은 프로세스에서 mapping payload가 남아 있을 때만 mapping 복구를 먼저 시도하고 항상 전체 reload로 마무리함. 재시작 뒤 `commitCompletedDurable` 이상은 commit 확정 reload-only, durable 증거가 불충분한 상태만 수동 수용으로 이동함
- label-column/customer-column reconciliation adapter가 각각 다른 resource/projection을 사용하고, mutation-closure 전체 base-table key/range를 같은 application lock과 `UPDLOCK, HOLDLOCK`의 단일 transaction에서 읽음
- 최초 raw snapshot은 snapshot isolation capability가 확인된 짧은 `SNAPSHOT` transaction으로 일관된 rowset을 만들고 잠금 격리로 조용히 낮추지 않음. save/reconciliation만 application lock 뒤 모든 base-table key/range를 같은 순서의 `UPDLOCK, HOLDLOCK`으로 읽으며 동시 non-participant writer와 absence insert를 주입해도 혼합 세대 rowset을 만들지 않음
- 모든 production adapter의 DB null, 빈 string, 빈 binary가 `DbWireScalar`와 strict raw API에서 서로 구분되고 DB-Lib non-null `len == 0`이 null로 축약되지 않으며 compatibility DTO 기본값이 canonical projection에 유입되지 않음
- DB-Lib command path에서 암묵적 reconnect가 0건이고 transaction의 모든 statement/commit/rollback/cleanup이 같은 `DbNativeSessionToken`을 검증함. 연결 단절/token 불일치는 새 DBPROCESS에서 후속 statement를 실행하지 않고 commit dispatch 여부에 맞는 typed 오류로 종료됨
- `PlatformDbExecutionCapabilityV1`이 Windows/macOS desktop worker, Android native service/process, iOS in-process native driver의 실제 cancel/session-discard/hard-kill 능력을 구분하고 미검증 조합은 transaction 시작 전에 차단함
- desktop/Android execution boundary만 native DB 자원/transaction을 소유하고 앱/parent는 opaque ID만 사용함. iOS는 독립 cancel thread와 session discard를 검증함. 각 플랫폼 channel의 byte-level framing/duplicate ack/crash·timeout/credential identity가 결정적 결과를 만들고 credential이 command line/env/stdout/stderr/disk/log에 나타나지 않음
- result drain/contract/statement 실패의 cancel/free-results, rollback, `@@TRANCOUNT=0` 확인이 순서대로 구조화됨. commit dispatch 없음과 cleanup 전체 성공이 증명된 경우만 `preCommitFailedTerminal`이고 나머지는 `preCommitCleanupPending`으로 resource를 차단하며 connection을 재사용하지 않음
- SQL Server 대상 컬럼 비교로 case/accent/kana/trailing-space natural-key 후보와 저장 전 중복을 판정하고 0/복수 매칭·context 변경·정확히 투영할 수 없는 시간 side effect를 indeterminate reason으로 반환함
- parameter binding으로 작은따옴표가 있는 허용 문자열도 SQL 문법을 깨지 않음

16.4 통합 회귀

- 저장 후 `HomePageManager`의 force reload가 `expectedOldGeneration`보다 큰 `newGeneration`을 발급하고 immutable `LabelSizeSessionData`와 lifecycle `LabelSizeSessionResources`를 candidate 내부 같은 generation의 `LabelSizeSession`으로 재구성하며 모든 세션 화면/helper가 session accessor를 사용함
- candidate prepare는 기존 journal 파일/listener를 변경하지 않고, suspend/activate/swap/render 실패 시 durable manifest recovery matrix에 따라 기존 session resume, candidate active 또는 force-reload-required로 복구됨
- journal handoff 각 phase 직후 프로세스 종료 주입에서 generation/owner token이 다른 파일을 삭제하지 않고 startup recovery가 단일 owner를 선택함
- 각 production 플랫폼의 process/service/native cancel 실패 주입과 durable file API 실패에서 startup이 platform hint에 의존하지 않고 checksum/generation/phase/ownerToken으로 단일 owner를 복구하며, hard-kill 미지원 iOS는 cancel/session discard capability 미충족 시 기능을 사전 차단함
- 저장 coordinator가 overlay/HomePageManager dispose 후에도 commit success/unknown/committed-invalid와 reload 필요 상태를 `LabelColumnSaveRecoveryRegistry`에 정확히 한 번 전달한다. 같은 프로세스에서 projection이 남아 있을 때만 reconciliation하고 startup/reconnect에서 save를 재실행하지 않음
- closed V1 state/event/reject Cartesian matrix가 모든 ordered guard, duplicate/stale ack와 durable publish-DB send 경계를 정확히 하나의 transition/reject로 매핑함. process/service 종료 또는 iOS native failure에서 단일 record를 선택하고 publish 완료 전 DB send가 0건이며 각 실패가 정의된 block/action만 노출함
- 동일 server의 검증된 AG failover fixture는 같은 `stableDatabaseIdentityDigest` namespace를 사용하고, 폐쇄 열거된 backup/restore·detach/attach·AG seed/failover·storage/VM snapshot 절차는 기대 identity 유지/변경 또는 production 금지를 재현함. permission denied/metadata hidden/unsupported fixture는 degraded action allow-list만 허용하고 다른 identity record를 reload/tombstone하지 않음
- durable registry artifact에 original/desired projection, 저장 문자열, result payload와 content-derived fingerprint/hash가 없음. 재시작 시 `preparedDurable` 미실행과 `preCommitFailedTerminal` 실패 확정은 수동 수용 없이 종료되고, 명시적 decode-failed durable evidence만 게시된 crash도 stage별 committed-invalid로 복원됨. decode-success evidence만 게시됐거나 decode evidence 없이 `commitCompletedDurable`부터 `resultFrameFullyReceivedDurable`까지만 남으면 stage를 추정하지 않고 동일 command 금지·resource별 reload-only 후 종료됨. commit intent 이후 완료 증거가 없거나 artifact가 손상된 진짜 미확정 상태만 resource별 reload·사용자 수용·tombstone 뒤 차단을 해제함
- 같은 identity/resource에 복수 unresolved operation artifact가 있어도 wall-clock/file mtime으로 하나를 버리지 않고 operation별 authoritative artifact를 결정한 뒤 모든 barrier를 합성함. commit 확정/committed-invalid operation이 낮은 phase에 가려지지 않고 모순 operation 격리 중에도 resource 차단이 유지됨
- unresolved/다른 identity artifact가 자동 삭제되지 않고 관리자 진단 목록, 보존 기간과 명시적 archive/delete 절차로만 정리됨
- 새 session subtree의 listener 재결합과 첫 renderReady 전까지 old resources가 살아 있고, 성공 후 정확히 한 번 dispose됨
- 공용라벨/품목관리/미리보기 세션 경로에서 `TColumn.datas`, `TColumnContent.datas`, `TColumnSpecial.datas`, `ItemOfMarket.datas`, `_currentLabelSize`, `Market.instance`를 조합한 session-state 직접 read가 0건이고 customer/market/label-size context도 같은 generation accessor에서 읽음
- 겹친 reload에서 오래된 generation 결과가 최신 session을 덮지 않음
- force reload 실패 시 부분 cache가 노출되지 않고 force-reload-required 상태로 후속 편집 차단
- commit 성공 후 reload 실패 시 DB save 재실행 없이 candidate session reload만 재시도
- 저장 후 공용라벨 사용 항목, 품목관리 동적 컬럼 및 출력 미리보기 재조회/갱신
- `LabelSizeSessionConsumerManifestV1`의 품목/update-item/scale/preview/validation 소비자가 `(stableDatabaseIdentityDigest, customerId, marketId, labelSizeId, consumerId, newGeneration)` 기준 idempotent하게 새 generation의 동적 column, 선택, RTF와 파생 cache를 재구성하고 durable acknowledgement를 남긴 뒤에만 `renderReady`를 반환함. crash/ACK 유실 재호출은 같은 최종 상태를 만들고 context가 다른 ACK는 거부하며 old resource는 한 번만 dispose됨
- 기존 공용라벨 `필수등록` 표시는 편집기 저장 결과를 읽기만 하며 직접 mutate하지 않음
- 새 이미지/바코드/QR keyword가 라벨 시트 object/required keyword 처리에 반영
- 삭제/키워드 변경한 항목을 참조하는 라벨 workbook에 대해 영향 경고가 표시됨
- 기존 라벨 설정/브랜드 설정/품목 순서 변경 테이블 테스트 전체 통과
- `flutter analyze`, 관련 테스트, 전체 `flutter test`, `git diff --check` 통과

16.5 실행 환경별 완료 gate

- P0 구현 착수 전 외부 prerequisite로 승인 운영 DB에서 비민감 schema capability snapshot을 채취해 checked-in fixture로 고정한다. fixture는 SQL Server edition/version, `snapshot_isolation_state`, 대상 table/column type·max_length·nullable·collation, PK/unique/index key/include/filter/enabled, FK/cascade, trigger 이름/활성/정규화 definition hash와 statement-level inserted 처리 여부, `BM_RICH_COL_MIN` sentinel SQL 타입/`''`·`0`·중복 분포, `BM_RICH_COLUMN_TYPE` 실제 행, content/update-item/status table 존재를 포함한다. 원본 업무 데이터와 credential은 fixture에 넣지 않는다. 이 fixture가 없으면 capability 코드를 추정 구현하거나 production gate를 통과시킬 수 없다.
- 플랫폼 prerequisite로 Windows worker executable, macOS worker target, Android bound service/isolated process와 ABI별 native library, iOS native adapter/cancel control target의 planned source target, build/package destination과 protocol ownership을 설계 manifest로 먼저 승인한다. P0 entry에는 실제 binary/target 존재를 요구하지 않는다. 각 target의 담당자, CI 또는 수동 승인 lane, 결과 artifact 저장 위치·보존 기간·승인 주체와 Android production signing 및 Apple signing/notarization 전제를 `GateManifestV1` 옆 release matrix에 기록한다. P0 development-complete는 source target과 contract harness artifact 존재를, P0 production-exit은 설치·bundle·서명된 실제 artifact와 필수 matrix 실행 결과를 요구한다. 현재 Dart isolate나 로컬 FFI library 발견만으로 native execution boundary 완료를 주장하지 않는다.
- `GateManifestV1`을 모든 실행 gate의 source of truth로 사용한다. 각 gate는 ID/blocking 여부, OS/architecture, SQL Server edition/version, provisioning·권한 DDL, driver/worker/service artifact와 protocol version, 실행 명령/timeout, expected assertion, 결과 artifact schema와 유효기간을 가진다. manifest에 없거나 유효기간이 지난 결과는 production 완료 근거가 아니다.
- 순수 모델/widget/compatibility 회귀는 `flutter test`로 검증한다.
- `DbWriterManifestV1` 누락 writer, 참여 writer의 단독 `writeDataWithParams`/SQL 내부 transaction, raw DAO의 legacy `Object` API, manifest를 우회한 DB action과 session static 직접 read 0건은 custom analyzer/lint 또는 AST/SQL 기반 구조 검사로 검증한다. 단순 문자열 검색만 완료 근거로 사용하지 않는다.
- DB integration은 manifest가 고정한 disposable SQL Server fixture에서 snapshot isolation, 실제 trigger/FK/collation/trailing-space, content 생성 단일 주체, schema capability와 result contract rollback을 실행한다.
- identity gate는 SQL Server edition/AG/standalone, 폐쇄 열거된 backup/restore·detach/attach·AG seed/failover·storage/VM snapshot과 최소 권한·권한 부족·metadata-hidden fixture에서 exact probe row, digest 유지/변경 또는 금지, degraded action allow-list를 검증한다.
- schema capability runtime gate는 `IndexPredicateRequirementV1` 전체 query coverage와 고정 schema metadata fixture로 검증하고, 실제 execution plan/range-lock/index hint/query template은 권한·통계·SET option을 고정한 배포 integration gate에서 별도로 검증한다.
- native gate는 normative support matrix의 Windows 10/11 x64 ODBC desktop worker, macOS 10.15+ x64/arm64 DB-Lib worker, Android API 24+ arm64-v8a 기기와 x86_64 test lane의 native service/process, iOS 13+ arm64 기기의 in-process native driver를 각각 실행한다. 장시간 query/lock wait의 cancel, session discard, native 무응답, framing/credential 비노출, ack crash matrix와 clean reconnect를 검증한다. hard-kill 미지원 iOS는 deadline cancel/session cleanup 실패 fixture에서 transaction 시작 전 capability 차단을 검증한다. matrix 필수 조합의 manifest 누락은 gate 실패다.
- recovery gate는 각 플랫폼의 process/service/native fault-injection harness로 closed V1 ack/transition phase와 durable publish/DB dispatch 경계를 중단하고 다음 startup의 artifact 선택, DB identity namespace, owner/lease와 resource 차단을 검증한다. `preparedDurable`, `preCommitFailedTerminal`, `commitDispatchIntentDurable`, `commitDispatchObservedDurable`, `commitCompletedDurable`, `resultFrameSendCompletedDurable`, `resultFrameFullyReceivedDurable`, decode 성공/실패 evidence와 손상 artifact fixture가 각각 미실행 종료, 실패 확정, 결과 미확정 수동 수용, commit 확정 resource별 reload-only, stage별 committed-invalid 또는 격리로 전이되는지 검증한다. ACK/local-event 양방향 재정렬, decode evidence 게시와 파생 UI/reload 상태 publish 사이 crash, decode 미시도 종료와 동일 resource 복수 unresolved operation의 barrier 합성 fixture를 포함한다. 같은 durable state라도 label-column은 label-size reload/session handoff, customer-column은 dictionary-only reload를 수행하고 금지된 교차 action을 typed reject한다.
- durable file primitive는 Windows `FlushFileBuffers`/`ReplaceFileW`/`MoveFileExW`, macOS/Android/iOS의 승인된 동등 primitive와 artifact 복구를 플랫폼별 native integration test로 검증한다. 실제 전원 차단 durability는 자동 완료 조건으로 주장하지 않는다.
- `DbWorkerArtifactManifestV1`의 build/package/install/bundle/hash/version 검증은 플랫폼별 release lane에서 수행한다. 한 환경의 mock/unit 통과를 다른 driver/OS/architecture gate 통과로 대체하지 않는다.

17. 구현 권장 순서

완료 판정은 한 덩어리로 처리하지 않고 다음 milestone gate로 분리한다. 각 gate는 독립 검증 결과와 미완료 prerequisite를 기록한다.

- `P0 DB substrate`: identity/bootstrap/readiness, action/writer/gate manifest, driver wire/result/null/decimal, strict native transaction session/ack와 플랫폼별 process/service/native cancel/recovery primitive
- `P1 locked writer migration`: 공용 customer/label-size lock API와 모든 참여 writer 전환, predicate별 index capability
- `P2 session/recovery handoff`: immutable `LabelSizeSession`, durable journal/registry와 총함수 transition table
- `P3 label-column feature`: edit session, UI, validation, 사용자 항목과 사용 항목 DAO/save/reload

milestone은 `entry`, `development-complete`, `production-exit`을 분리한다.

- `P0 entry`: 16.5의 운영 DB capability fixture, normative platform support matrix, planned native source target/build·package destination와 release lane/책임자가 설계 manifest로 확정되어야 하며 실제 binary 존재는 요구하지 않는다. `P0 development-complete`는 source target과 fake/native contract harness artifact가 존재하고 strict session, wire/result/ACK/recovery descriptor가 통과한 상태다. `P0 production-exit`은 설치·bundle·서명된 실제 artifact와 각 필수 OS/architecture/ABI 및 SQL Server fixture gate가 통과한 상태다.
- `P1 entry`: `DbWriterManifestV1`에 실제 writer/call site/SQL target/API 변경이 모두 열거되어야 한다. `P1 development-complete`는 fake lock/transaction 회귀와 기존 writer compatibility 테스트 통과, `P1 production-exit`은 실제 DB lock/range/deadlock integration gate 통과다.
- `P2 entry`: 현재 static session read/write와 journal lifecycle 호출부 inventory가 확정되어야 한다. `P2 development-complete`는 fake session/journal fault harness에서 handoff/recovery/consumer ACK가 통과, `P2 production-exit`은 플랫폼별 durable primitive와 process/service/native fault gate 통과다.
- `P3 entry`: P0~P2의 public contract와 fake harness가 고정되어 UI/model 개발을 시작할 수 있다. `P3 development-complete`는 fake harness 위의 model/widget/DAO command 계약과 vertical slice 통과, `P3 production-exit`은 실제 P0~P2 production-exit 및 P3 SQL/native/session 통합 gate가 모두 통과한 상태다.

따라서 P3 vertical slice는 P0~P2 fake/contract harness 위에서 병행 개발할 수 있지만 이를 P0~P2 production 완료로 기록하지 않는다. "항목 편집 기능 개발 완료"와 "production release 완료"를 구분하고, 19장의 전체 조건은 production release gate로 해석한다.

1. `probeDatabaseIdentityV1` exact SQL/권한/이동 절차 fixture, `connectionProfileHint`/검증된 `DatabaseIdentity`/`stableDatabaseIdentityDigest`, `connectAttemptId` bootstrap과 ready/degraded-ready 상태기계, `DbActionRequirementV1`, 호출부 migration 표, `connectionEpoch` cache·request 폐기 protocol 구현
2. `IndexPredicateRequirementV1`, `DbWriterManifestV1`, `ContentCreationOwnershipV1`, `GateManifestV1`과 snapshot isolation capability, DB schema/index/trigger capability와 배포 plan gate, 전체 mutation-closure manifest와 모든 문자열/enum/type 매핑표, sentinel/운영 `BM_RICH_COLUMN_TYPE` 및 레거시 type 0~12 전환 fixture 작성
3. tri-state `DbLogicalType`/column metadata와 null/빈 값이 분리된 canonical `DbWireScalar`, typed `queryResultSets`, 독립 raw rowset/`RawLabelColumnRow`/`RawLabelColumnMinRow` strict mapper, stable ID/결정적 정렬 구현. 기존 `Object` 조회 API는 명시적 compatibility read adapter로만 유지하고 strict raw/save/reconciliation에서 사용하지 않는다.
4. `NativeDbTransactionSession`/`DbOperationAck`, Windows ODBC desktop worker, macOS DB-Lib worker, Android native service/process, iOS in-process native driver의 `PlatformDbExecutionCapabilityV1`/`DbWorkerArtifactManifestV1`, 명시적 Unicode large parameter, DB-Lib 암묵 reconnect 제거, 플랫폼별 cancel/credential/framing/orphan 방지, metadata-only redaction, versioned wire schema, complete-drain/tainted-discard/result contract/marker collector 구현과 통합 테스트. strict transaction과 기존 `executeDriverTransaction()`을 같은 operation/session에서 혼용하지 않으며 label-column/customer-column save와 P1 migrated writer는 strict API만 사용한다. legacy transaction API는 미이행 writer의 한시적 compatibility 경계로 격리하고 호출 inventory와 제거 gate를 둔다.
5. 공용 customer/label-size locked transaction API와 참여 writer 전환, typed application-lock error 구현
6. raw key/value/type JSON staging, CP949 round-trip과 target conversion 검증
7. customer/market/label-size context, `expectedOldGeneration/newGeneration`과 `LabelSizeSessionConsumerManifestV1`을 포함한 `LabelSizeSessionData`/`LabelSizeSessionResources`/`LabelSizeSession`, 단일 accessor와 generation guard 구현
8. 플랫폼별 atomic replace primitive, journal/recovery registry 공용 durable manifest/lease, 검증된 DB identity namespace, startup artifact discovery와 process/service/native fault recovery matrix 구현
9. 앱 bootstrap service가 소유하는 `LabelColumnEditCoordinator`/`LabelColumnSaveRecoveryRegistry`, closed `RecoveryTransitionTableV1`/필수 ack barrier, `storageReady`/`identityReady`/resource barrier, logout detach, unresolved artifact와 재시작 수동 수용 구현
10. save command DTO, resource별 reconciliation adapter, SQL Server natural-key resolver와 original/desired projection canonicalization
11. 사용 항목 edit session 및 validation 순수 로직
12. 사용자 항목 edit session 및 customer-scoped lock/fingerprint transaction
13. `SwipeActionTable`의 교차 헤더 action/외부 drag/drop 최소 확장과 `BlockingModelessDialog.onEscape`
14. 다이얼로그 기본 layout과 normal mode
15. 속성 패널 공통/타입별 editor
16. 후보 추가와 휴지통 삭제
17. reorder mode와 userItemEdit mode
18. 사용 항목 원자적 save, pre-commit result contract, post-commit wire 오류 분류, resource별 3상태 reconciliation/reload 연결
19. `GateManifestV1`의 unit/widget/구조 lint, SQL Server/identity/trigger/snapshot, 플랫폼별 driver·cancel·process/service/native fault, durable file와 release artifact gate 실행

각 단계의 `development-complete`를 미검증 상태로 다음 단계의 완료 근거로 사용하지 않는다. 다만 명시된 fake/contract harness가 준비되면 다음 milestone 구현 착수는 허용한다. 저장 vertical slice 전에 DB identity cache, driver parameter/redaction/result contract/marker collector, canonical projection, journal fault phase와 candidate session retirement 테스트를 fake harness에서 먼저 통과시킨다. 첫 저장 vertical slice는 `기본 타입 후보 1개 추가 → 속성 적용 → strict transaction의 commit 전 marker/mapping contract 검증 → commit → candidate session reload/swap → idempotent renderReady ACK → old resource dispose → 재조회 표시`로 잡고, 이후 특수 타입/GS1/drag/drop을 확장한다.

18. 레거시 대비 누락 방지 목록

사용자가 명시한 UI 요구 외에도 아래 레거시 기능이 빠지면 기능 회귀다.

- 현재 사용 항목의 신규/키워드/항목명/종류/제목/표시 여부
- 제목 직접 변경과 CP949 20바이트 검증
- 표시 여부 변경
- 누락 키워드 검사 `BM_RICH_CHECK_COLUMNS`
- QR/기본 사용자 정의에서 참조 중인 항목 표시와 참조 해제 전 키워드 변경/삭제 차단
- 같은 키워드 중복 추가/저장 차단
- 빈 키워드/항목명 저장 차단
- 기존 품목 존재 시 데이터 영향 이중 확인 또는 동등한 강도의 명확한 최종 확인
- 바코드/이미지/QR/GS1/날짜 타입의 전체 속성 UI와 검증
- 체크디지트/타임바코드 변경 영향 경고
- GS1 AI 포함 관계의 추가/수정/삭제
- 신규 컬럼의 기존 품목 및 update 품목 빈 content 생성
- `BM_RICH_COL_MIN`, `BM_RICH_CHECK_COLUMNS`, GS1 보조 테이블 동기화
- 삭제 status date 갱신
- 저장 후 컬럼 변경 observer와 label-size 세션 전체 force reload
- 고객별 사용자 항목 사전의 추가/수정/삭제와 대문자/영숫자 키워드 규칙

다음 항목은 레거시 구현에 존재하지만 그대로 재현하지 않고 개선해야 한다.

- `SelectLastNRecord()` 신규 ID 추정: `OUTPUT INSERTED... INTO` 수집 후 marker가 있는 최종 결과셋의 정확한 매핑으로 대체
- 문자열 보간 SQL: 명시적 Unicode large JSON parameter와 raw key/value/type staging 기반 batch query로 대체
- SQL 내부 transaction과 `DbClient.transaction()` 중첩 가능성: transaction 소유자를 `DbClient.transaction()` 하나로 고정
- 사용자 항목의 transaction 없는 행별 CRUD: 단일 transaction으로 대체
- 저장 실패를 삼킨 뒤 화면을 재조회하는 동작: commit 전 실패는 working copy 보존, commit 성공 후 reload 실패는 save 재실행 금지와 reload-only 복구로 대체
- 빈 `InsertColumnsToLogDB()`: 별도 감사 로그 요구/스키마가 확정되기 전 구현 대상에서 제외
- 제목 `20Byte` 문구와 실제 20자 판정 불일치: UI/검증을 CP949 20바이트로 통일하고 모든 DB 문자열에 field별 byte 검증 적용
- 상세 설정 `Apply()` 실패 결과를 무시하고 닫는 동작: validation 실패 시 속성 패널을 유지
- 알 수 없는 enum을 기본값으로 치환: raw 값을 보존하고 명시적 호환 규칙 전까지 저장 차단
- QR/기본 참조 키워드 변경·삭제 경고 후 손상 허용: QR data와 하단 text를 모두 처리하는 공용 exact-token parser와 참조 해제 전 변경·삭제 차단으로 대체
- 삭제 시 content/FK cascade 의존: 실제 FK를 확인하고 GS1/QR 양방향 관계를 포함해 transaction에서 명시적으로 정리

19. 완료 조건

- 공용라벨관리에서 선택한 라벨 크기의 `라벨 항목 편집` 다이얼로그를 열 수 있다.
- 두 테이블과 순서 변경 UX가 라벨 설정의 공용 테이블 패턴을 사용한다.
- 별도 상세 dialog 없이 선택 행 타입에 맞는 속성을 왼쪽 패널에서 수정, 취소, 적용할 수 있다.
- 미적용 속성 변경은 다른 이벤트 전에 반드시 취소 질의를 거친다.
- 아이콘과 drag/drop 양쪽으로 후보 추가 및 항목 삭제가 가능하고 동일 command 결과를 낸다.
- 순서 변경과 사용자 항목 설정이 상호 배타 전용 모드로 동작한다.
- 순서 변경 모드 저장은 working copy에만 적용되고 최종 메인 저장 전까지 DB를 변경하지 않는다.
- 사용 항목과 사용자 항목 저장은 `DbClient.transaction()`이 단독 소유하는 각각의 원자적 transaction이며 commit 전 실패 시 편집 상태를 보존한다.
- save command와 post-commit 상태는 dialog widget 밖 coordinator가 소유하고 UI/HomePageManager dispose 뒤에도 앱 bootstrap service의 `LabelColumnSaveRecoveryRegistry`가 결과와 reload 필요 상태를 이어받는다. 같은 프로세스에서 projection이 남아 있을 때만 reconciliation한다. 재시작은 마지막 durable 상태의 증거를 보존해 미실행/실패 확정, commit 결과 미확정, commit 확정 reload-only를 구분하며 durable 증거가 불충분한 상태에서만 전체 reload와 명시적 수동 수용으로 차단을 해제한다. durable DB dispatch intent와 commit dispatch intent publish 전에 각각 최초 DB request와 native commit을 보내지 않고 startup/reconnect에서 save command를 재실행하지 않는다.
- 저장 후 개별 static cache를 순차 교체하지 않고 `expectedOldGeneration`보다 큰 `newGeneration`의 immutable data/lifecycle resources candidate를 durable journal lease 검증 후 단일 `LabelSizeSession` reference로 swap한다. `LabelSizeSessionConsumerManifestV1`의 필수 소비자가 같은 candidate generation을 관측하고 render acknowledgement를 반환한 뒤에만 old resources를 폐기한다.
- commit 성공 후 reload 실패는 같은 save command를 재실행하지 않고 force-reload-required 상태에서 reload만 재시도한다.
- commit 결과 미확정은 desired/original/indeterminate 3상태로 reconciliation하며 operation ledger 없이 실제 commit 여부를 단정하거나 자동 재실행하지 않는다.
- `DbCommittedResultInvalid(committedKnown: true)`은 commit 결과 미확정과 분리한다. 같은 프로세스에서 보유 mapping payload가 있을 때만 mapping 복구를 먼저 시도하고 전체 DB reload로 마무리한다. 재시작 뒤 `commitCompletedDurable` 이상은 commit 확정 reload-only, 증거가 불충분한 상태만 수동 수용으로 이동한다.
- marker/schema/cardinality/count/mapping command 일치 오류는 canonical `DbWireScalar`와 driver-neutral `DbLogicalType` 기반 result contract가 complete drain 뒤 commit 전에 rollback한다. `NativeDbTransactionSession`과 필수 `DbOperationAck`가 같은 native connection 및 commit 경계를 보장하고, `commitDispatchIntentDurable` 뒤 worker의 `commitDispatchObserved`와 `commitCompleted`를 구분한다. `commitCompleted` 증거와 완전한 result frame 수신 뒤 wire envelope 또는 domain DTO decode만 실패한 경우에만 stage가 있는 `DbCommittedResultInvalid`다. `PlatformDbExecutionCapabilityV1`이 허용한 process/service/native cancel 경계가 실행 중단 또는 session discard를 보장하며 cleanup 전체 성공 증거가 없는 실패는 terminal로 오인하지 않는다.
- 모든 DB 문자열, type code와 enum, 숫자 범위가 명시적 매핑표와 validation을 가지며 미지원 raw 값은 조용히 변환되지 않는다.
- 모든 현 프로젝트 column/item/content writer가 공용 locked transaction API로 같은 connection/transaction의 label-size lock에 참여하고, 사용자 항목 customer lock, typed 오류의 versioned isolate wire schema, resource별 mutation-closure reconciliation adapter가 테스트로 고정된다.
- raw DAO는 최초 baseline을 검증된 짧은 `SNAPSHOT` transaction으로 읽고 DB null/빈 값과 중복 관계를 보존한다. save/reconciliation은 `IndexPredicateRequirementV1`이 확인한 query key/range를 application lock 뒤 `UPDLOCK, HOLDLOCK`으로 관측한다. manifest/query/capability가 없으면 fail-closed다. 플랫폼별 durable manifest와 closed recovery 전이표는 검증된 DB identity별 원자 교체와 hint 비의존 startup recovery를 제공한다.
- P0 entry 전에 승인 운영 DB의 비민감 schema/snapshot-isolation/index/FK/trigger/sentinel/type fixture, normative platform support matrix, 플랫폼별 planned native source target/build·package destination, release lane·artifact 보관·승인 책임이 설계 manifest로 확정된다. 실제 target/binary는 development-complete/production-exit에서 단계별로 요구한다. 추정 schema, 현재 Dart isolate 또는 개발 PC의 우연한 native library 발견은 production 완료 근거가 아니다.
- `RICH_MIN_CHECK` 기존 값 보존, 레거시 혼합 동작 근거를 가진 type 0~12 전체 전환 matrix, 기존 미지원 사용자 타입의 읽기·삭제 전용 정책, 고정/사용 항목 stable ID·결정적 정렬, connect attempt/ready·degraded-ready 상태기계와 DB identity/connection epoch cache·request 폐기, failover/restore/clone namespace 정책 및 모든 DB 계층의 중첩 payload 비직렬화 metadata-only sensitive parameter redaction이 테스트로 고정된다.
- 권한 등급 matrix, 전용 모드와 committed 상태 Esc/닫기, QR V1 token/나트륨 문법, concurrency fingerprint/desired observation projection이 테스트로 고정된다.
- P0~P3 milestone의 독립 검증 결과와 prerequisite가 기록되고 production 진입 capability는 대상 플랫폼/architecture별 P0~P2 실제 gate와 P3 기능 gate가 모두 통과한 경우에만 true다. `GateManifestV1`의 unit/widget/구조 lint, SQL Server identity/trigger/snapshot, Windows/macOS/Android/iOS driver·cancel·fault, durable file와 release artifact gate 및 전체 정적 분석이 각각 통과하고 유효한 결과 artifact가 기록된다. Flutter Web, Linux와 전원 차단 내구성은 이번 완료 조건에 포함하지 않는다.
